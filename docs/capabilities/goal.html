Goals in chat

A Goal keeps an objective active across ordinary turns of the current agent, with the conversation's tools, model, permissions and history. There is no nested working agent.

Start and plan

Enter /goal <objective>, use Abilities → Programs → Tools → planning → goal → Use, or ask the agent. In the Rich REPL /goal starts a canonical chat execution and prints its ID.

PartRule
Plantodo_create, todo_update, todo_list for multi-step work; a simple objective needs none. New items attach to the Goal and revision. Progress refreshes after each todo change and when a turn ends; a failed progress notice does not undo todos.
CandidateThe agent checks evidence against every requirement, then update_goal(status="complete"). This only submits. Unfinished associated todos prevent it. A fully completed plan also triggers verification, once per changed plan.
VerifyingAssesses the original objective and each todo requirement, with trusted built-in inspection tools under normal permissions. No shell, writes or Goal mutation; needed tests go back to the working agent as missing evidence.
AchievedNeeds a per-requirement assessment with evidence references. The runtime rechecks requirements, user controls, todos, unfinished executions, unknown effects and evidence. Pause, edit, cancellation, new instructions or changed evidence prevent stale success. A failed execution stays recoverable.

Semantic verification is an independent model judgment, not a guarantee. Completion describes the time of verification and starts no monitoring. Checking every todo does not prove the objective.

Goals have no round limit. The badge shows todo completion and omits it when there are no todos; status stays visible. Limits are optional and use cumulative usage. Automatic continuation does not expand tool permissions.

In the transcript and details
  • Verification turns are not rendered as replies. Starting, running, pausing and verifying add no transcript cards. An ended Goal leaves one compact card; clicking opens its saved result, progress and usage, read-only and still tied to that Goal after a new one starts.
  • Details keep objective, status, usage and progress across reloads, and show each limit next to its usage. They do not edit the budget.
  • Add instructions in the normal input, with its queue or steering mode. A queued message goes before the next automatic turn, which waits up to 15 seconds for it.
  • Details use the backend's current action eligibility. Disabled Resume or Verify explains the prerequisite. Refresh status retries a failed read without losing your draft. End always stops the Goal intent. Unresolved operations show identifiers, tool names, timestamps and status. Inspect execution opens that exact execution, with pending approvals and questions.
Restart and recovery
CaseBehaviour
Worker restartDoes not pause a chat Goal: compatible checkpoints resume under the automatic restart policy, and a turn completed during shutdown keeps a durable continuation notification
Automatic work prevented byUser pause, cancellation, exhausted budgets, explicit restart limits. Legacy recoverable pauses and Goals with no saved continuation provenance need explicit Resume. External-event wakeups remain a recovery limitation. A wait or unresolved execution is not evidence of completion.
Verify needsFinished work, completed associated todos, available budget and no unresolved relevant work. Goal-owned background processes running or of unknown outcome prevent it; unrelated resources do not. Pause, cancellation, changed versions and duplicate requests cannot bypass this.
Resume of an ordinary chat with no owner or active descendantsCan close its interrupted frame and start a restricted inspection turn, without replaying old tool calls. Unknown effects stay unknown; nothing claims an external operation was cancelled.
New admissionHas a durable identity, so a crash before saving the Goal cannot duplicate turns. Incompatible checkpoints use a new chat turn; temporary activation or credential errors do not authorize that. Provider-only interrupted background Jobs keep their input and resource admission. Child executions with unresolved effects need inspection.
Incomplete tool-call history in provider requestsRepaired without rewriting saved records: missing outputs get an unknown-outcome placeholder, real outputs win, duplicates collapse, interrupted text stays labelled, unpaired results are omitted from the request but stay saved. This does not prove failure or authorize a retry.
Ownerless interrupted execution, unknown outcomeThe next non-inspection tool result is prefixed with a notice, once per execution. Nothing is held back or replayed. Real built-in read, grep, glob and list get no notice; custom tools with those names do. Restarted chat turns included.
Metering
PartRule
Active timeKeeps observed work across restart and excludes offline time. After abrupt worker loss the last durable heartbeat is a lower bound and the final interval is shown as unknown. Late receipts do not restart a paused timer. An explicit active-time ceiling blocks work if that unknown prevents checking; removing it allows continuation. No default time or round ceiling exists.
Chat requestsCapture Goal identity, revision and price before dispatch. Receipts update that Goal even after pause or edit; replacing the Goal moves no charges. Duplicates do not add. A started request without a receipt is unknown, not free; details show known subtotals beside unknown request counts. Receipts rebuild from the ledger after restart without repeating the request.
Older totals and failuresCursor-based totals stay as a legacy subtotal on the next attributed request. Metering failures show unknown. Partial streaming counters are cumulative lower bounds; a final receipt replaces them.
Background JobsThose admitted by an active Goal inherit its identity, including descendants and cross-session calls; an unrelated Goal in the destination gets no charges. Jobs without saved attribution stay unassigned. Goal and Job reservations start and settle in one accounting transaction. Missing token or price information keeps the reserved exposure.
Token or cost limitsReserve conservative exposure before credentials or provider calls, count parallel requests, and recheck at dispatch. Token limits can reduce the output cap. An unsupported bound, unknown price or unpriced tier cannot bypass a hard limit: the Goal pauses or reports exhaustion. An expired reservation that never started cannot dispatch; a started request never becomes free by time. These bounds need audited provider adapters.

设计理念

传统 AgentAgentic Programming
流程LLM 规划，循环运行到它说完成Python 代码
决策LLM 判断每一步、工具和参数Python 决定是否调用 LLM
状态塞进上下文函数变量、返回值
测试提示词回归单元测试

把控制权交给概率黑盒，去做确定性代码本可以完成的工作，轨迹每次不同，历史不断膨胀。无法保证完成，出错也分不清是提示词、工具还是幻觉。

所以把任务拆成函数调用图，逐节点决定：用普通 Python，还是用调用 llm(...) 的 Agent 方法来做理解、生成或判断。LLM 成为你调用、约束和组合的东西。

三个基本元素

Agent 方法

from openprogram import Agent
from openprogram.runtime.agent import llm

class ExampleAgent(Agent):
    method_options = {'summarize': {'tool': True}}

    def summarize(self, text: str) -> str:
        """Summarize a text in one sentence, preserving the core point."""
        return llm([{"type": "text", "text": (
            f"Summarize in one sentence, preserving the core point:\n\n{text}"
        )}])

_example_agent = ExampleAgent()
summarize = _example_agent.summarize

docstring 作为描述性上下文随调用传递；llm(...) 在环境 Runtime 上发起一次模型调用。对调用者来说，summarize(article) 就是普通 Python 函数。

Runtime

打包对话历史，调用 Provider（Anthropic、OpenAI、Claude Code 等），把结果写回上下文。编排用 llm()；Runtime.exec() 是其下层的嵌入 API。

Context

规则行为
DAG每次 Agent 执行拥有一个。对话记录用户消息、模型请求和直接派发的工具；普通帮助函数不产生持久节点。
另一个 Agent独立 DAG；父级保存结果和 child_session_id 引用
归属权限、取消和文件检查点仍属于发起的执行
llm() 历史从 DAG 渲染，所以上下文是在函数上声明的属性
expose调用完成后向父级暴露什么。"io"（名称、输入、输出；工具默认），普通方法默认 "full"。
render_range函数自身的调用读取多少历史。{"callers": 0} 得到隔离的草稿上下文。

同一个 DAG 也是调试视图：可视化、Token 统计、回放失败路径。

衍生概念

概念含义
LLM 也写代码Agent 用普通文件编辑编写函数，不需要专门的 create() 或 fix()。通过 openprogram programs check 后，worker 无需重启即可从 ~/.openprogram/programs/ 加载。代码是数据，LLM 是编译器，函数是产物。
双模式既是可导入、手写的库，也是在 CLI 或 WebUI 里提需求的产品。得到的是可读的 Python，可以逐步理解。

How a call is decided

  1. Who is speaking. Anyone but the owner is limited, whatever the mode. Never fires for you.
  2. Your rules. Empty by default. Global, project and conversation rules merge; deny beats ask beats allow. Deny applies in every mode. Plan is checked after deny and before ask and allow.
  3. The mode.

A call that would ask with no one to answer (a schedule, a sub-agent, an always-on turn) is refused, and the refusal says how to allow it. That happens only under Manual, Plan, an Auto fallback or an ask rule.

Delivery, waiting and file freshness
  • An answer closes only after server confirmation; an unconfirmed one can retry the same decision. The card shows submitted answer, delivery progress and confirmation or retry. Confirmed receipts stay until reload; pending requests return on reconnect. A confirmed approval leaves the conversation and the tool row shows what happened.
  • Human approvals have no default time limit. Waiting saves progress and releases the active execution attempt; reopening the App restores the request.
  • Resuming uses the context saved for that turn, so later memory or date updates do not invalidate the approval. Tool, permission and working-directory checks still apply. If execution cannot resume, the conversation says the operation did not run. Cancelling the task withdraws its approval. Expired older requests are not reactivated.
  • edit, write and apply_patch record the target files' state at approval and check it before executing and again before writing. A deleted target is not recreated; a changed file must be read again first. Arbitrary shell commands do not declare their targets, so this does not cover their side effects.
  • Allow once and Deny answer only the current request and create no project rule.

Change permissions during a task

A change applies to the running task without stopping it; once the server confirms Bypass permissions, later tools in the same response no longer ask.

What a live change touches
  • The selection is sent at once when the interface knows the confirmed session version, and shown as effective only after confirmation. The change holds even while the model reasons, streams or generates arguments.
  • The new mode enters later model requests; text being generated is not rewritten. A tool already authorized keeps its authorization. Switching into Plan stops pending writes from being authorized.
  • An ordinary approval no longer required resolves through the execution's durable wait and the task continues. Explicit ask rules, questions, forms and Sandbox escalation are not answered by a mode change. Repeated answers, cancellation, timeout and recovery cannot run a completed call again.
  • Branch-specific. Other windows on that branch receive the confirmed mode; stale branch or version updates are rejected. A failed or disconnected update stays unconfirmed: reconnect, review the mode, then retry. An unsent draft stores its mode locally and sends it with the first message.

Project rules

History → Projects → project → Settings → Permission Rules holds Deny, Ask and Allow lists. Add ToolName or ToolName(pattern); remove to revoke; replace by removing and adding. An empty list does not rule out session or global rules.

Saving and timing
  • A submitted rule clears only after a project-specific server confirmation. Failed or unconfirmed saves keep the input and show a status. Success updates other open views of that project.
  • The next operation in an authenticated interactive owner session reads current rules, including changes made mid-turn. Authorized operations keep their authorization; approval waits still need an answer; admitted sub-agents keep their captured policy.
  • Removing a rule affects future authorization, not what already ran.
  • Windows paths: forward slashes avoid escaping ambiguity, as in read(C:/Users/me/project/**). Ordinary backslashes in drive paths are preserved. The syntax escapes its own characters with \\, \( and \). JSON configuration adds JSON's own backslash escaping.
  • A path rule matches however the same file is written: either slash, a short name, a link to the folder. Deny and Ask rules ignore letter case and also catch a relative path from the working directory; Allow rules compare the full path in the case stored on disk. A network share is written //server/share/**, or pasted with backslashes throughout.
  • When commands run in PowerShell, a command containing {, } or , matches an Allow rule only by its exact text, as Always allow saves it. Deny and Ask rules read it as usual.

Restrict commands to public network domains

macOS: set sandbox.network to true and sandbox.network_domains to a map.

{"example.com":"allow","*.example.org":"allow","blocked.example.org":"deny"}
  • Exact hosts and *.example.org (subdomains at any depth, excluding the root). Deny wins. An empty map blocks every destination; null keeps the existing network switch.
  • Private, local, multicast and reserved IPs stay blocked even when a hostname is allowed. All DNS answers are checked and the connection uses a checked address.
  • Each command gets an authenticated local proxy; the sandbox prevents direct connections, including clients ignoring proxy settings. HTTP on 80 and HTTPS CONNECT on 443; clients need ordinary HTTP proxy settings.
  • Rules authorize destinations, not encrypted HTTPS methods or contents. No TLS interception, SOCKS/UDP, arbitrary ports, local network or upstream proxy chaining. No chunked HTTP uploads or plain HTTP Upgrade; HTTPS tunnels carry HTTPS and WSS.
  • Proxy and connections close when the command ends or is cancelled.
  • Linux and Windows/WSL reject a configured domain policy rather than run unrestricted. A missing sandbox also rejects it, even with the unavailable policy at warn. Turning Sandbox off disables its restrictions.
  • Affects sandboxed commands, not the host's model-provider requests or other tool transports.

System access

macOS permissions are separate from modes: a mode cannot grant them. One registry covers screen recording, Accessibility, Automation, Calendar, Reminders, file read and write, microphone and camera. Settings, the CLI/TUI doctor, GUI preflight, durable system-access waits and the HTTP endpoint read it. Each row has status, identity checked, the operation needing it and whether the platform can request it.

macOS asks for access again after an update
  • App and named backend are signed applications that macOS can record separately. A similarly named entry (python3, node, a cached app) proves nothing: installed products check and request through the signed runtime bundle ai.openprogram.runtime; the outer App is not a second executor.
  • Automation is per target app, file access per selected path. Calendar, Reminders, microphone and camera can each need consent. Unselected apps or paths cannot be pre-authorized.
  • App refresh, local packages and conversational self-update reuse a private identity in ~/Library/Application Support/OpenProgram/local-signing. Keep it when cleaning: it holds the signing keychain. Missing or damaged state stops the build rather than creating a replacement.
  • The first move from an old ad hoc build may need consent again; an old toggle can look on while macOS rejects the new signature. Use Request authorization. Accessibility and previously denied permissions may need System Settings.
  • When a recorded grant belongs to an older verified identity, explicit setup renews that one capability once. Startup and ordinary checks never reset TCC records, accept dialogs or modify other applications.
  • Local signing is for this computer's development builds; public apps need Developer ID signing and notarization.

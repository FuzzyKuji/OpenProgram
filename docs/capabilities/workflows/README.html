Agentic workflows

An agentic workflow, called a harness or agentic program in code, is a git repository of Agent methods built with Agentic Programming. Releases bundle none. Installed ones appear in chat, on the Web UI Programs page, and in openprogram programs run.

Commands

CommandEffect
openprogram programs listEvery Program: tools, applications, your packages, harnesses. Each Workflow in ~/.openprogram/programs is a package row with entries and state: loaded, error, or pending (not callable yet: no commit has passed the check).
openprogram programs install <owner>/<repo>Any harness; a git URL or directory also works. Clones it, installs declared dependencies, records the approved source. Mutable environments only: a source checkout or CLI/server installation. The packaged desktop runtime refuses.
openprogram programs install <ref> --upgradeReinstall or upgrade
openprogram programs uninstall <name>Set a harness aside
openprogram programs run <name> -a key=valueRun directly. --provider (auto-detected by default) and --model override the model.

Workflows the agent writes

Worth it for a stable multi-stage structure, repeated use or reviewable history; not for a one-off. No special tools, just file tools and the command line:

  1. Create ~/.openprogram/programs/<name>/ as a Git repository with roles, functions, PROGRAM_ENTRIES, README.md and behavior tests.
  2. openprogram programs check ~/.openprogram/programs/<name> imports the package, runs tests in the OS sandbox, then on success commits and records that commit as checked.
  3. On failure, read the report, fix, check again.

The worker loads the checked commit within seconds; entries appear as tools in every chat and on the Programs page without restart. Editing works the same way. Earlier versions stay in Git.

Forms ask for task information, never execution settings. Text polishing infers style from the text. Browser backend and session handles stay internal. Page ranges and output destinations are optional requirements. Explicit Python callers keep supported overrides.

Body calls no modelRuns with none configured

Browser workflows

Keep an explicit initial URL when a backend is selected. Official MCP backends support guarded waits and propagate snapshot failures. Page recovery stays in the current window scope and does not replay the failed action. A verified result keeps its actual evidence and observed target.

Weekly reports

If weekly_report is in your catalog, give it the report text or the change: submit this week's report, update only next week's plan, inspect the record, or draft locally at a named path.

How it writes to Feishu
  • Reads the configured form and matches name and year/week before writing. A missing record is submitted once; an existing editable record is opened from history and saved. Partial updates keep untouched fields. Draft and read-only requests do not submit.
  • Unknown inspection results, login failures and ambiguous records stop. A submission cap alone does not rule out editing.
  • Success needs a fresh page confirmation and persisted values. Uncertain results are reported without retry. Ordinary browser authorization applies. Bounded browser steps, no goal() loop; never invents progress, metrics or paper titles.

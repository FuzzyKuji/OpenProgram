渠道要求与约束

结构和消息流：渠道子系统设计。

契约

@dataclass(frozen=True)
class MessageHandle:
    platform: str
    account_id: str
    target: str
    message_id: str

    @property
    def editable(self) -> bool: ...


class Channel(abc.ABC):
    platform_id: str = ""

    @abc.abstractmethod
    def run(self, stop: threading.Event) -> None: ...

    def send_text(self, target, text) -> Optional[MessageHandle]: ...
    def send_text_full(self, target, text, thread_id=None) -> SendResult: ...
    def send_file(self, target, path, caption="", thread_id=None) -> SendResult: ...
    def edit_text(self, handle, new_text) -> bool: ...
    def edit_text_full(self, handle, new_text) -> SendResult: ...
约束原因
run 是唯一抽象方法入站循环没有共同形状。出站有，所以发送和编辑在 _transport 上具体实现。只实现 run 的适配器就能完整收发和编辑；只有 SDK 带来额外能力（如提及解析、上传）才覆盖。强制 send/edit/react 会要求平台可能没有的能力。
MessageHandle 全是字符串可序列化：一个进程发送，另一个编辑
两个入口，一个实现outbound.send 在进程内没有适配器时也能用；adapter.send_text 保留 id 以便编辑。只有 _transport 负责 HTTP、凭据和分块，所以新操作是一份实现，而不是八份。
发送返回 SendResultbool 无法区分瞬态和永久失败。error_kind（auth、rate_limit、bad_target、network、not_supported、format、unknown）来自 _classify_http_status、_telegram_kind_from_description、_slack_kind_from_error。bool 形式保留。
编辑能力是句柄属性iLink 不能编辑。微信句柄 editable == False；edit_text_full 返回 SendResult.fail("not_supported", ...)，绝不用删除重发伪装。调用方不用针对平台名特判。
拒绝跨平台编辑handle.platform != self.platform_id 时返回 SendResult.fail("bad_target", ...)。跨适配器协调由调用方负责。
内置优先注册_BUILTIN_CHANNEL_CLASSES 优先于 _PLUGIN_CHANNEL_CLASSES。插件用 [project.entry-points."openprogram.channels"] 或 register_channel(name, cls)。CHANNEL_CLASSES 是两者之上的类字典代理。

中立入站消息

_message.py:ChannelMessage，frozen：text、chat_id、user_id、user_display、message_id、chat_type、ts、reply_to_id、quoted_text、thread_id、parent_chat_id、attachments（Attachment 元组）、mentioned、from_bot。

管线把 quoted_text 作为 > 块放在前面，下载 attachments，小图片作为视觉输入转发。thread_id 把占位、回复和文件发回原 thread，不参与会话路由。

入站分发

步骤动作
1. 路由session_aliases 和 bindings 决定 agent_id
2. 键按 agent.session_scope 计算 session_key
3. 重置daily_reset 或 idle_minutes
4. 存储_load_or_init_session 写入会话存储
5. 轮次构造 TurnRequest，调用 process_user_turn
6. 回复追加
7. 广播向 Web UI 发 channel_turn 信封

progress_stream=False 返回回复由适配器发送。True 时驱动 send_text/edit_text，工具事件在回合中到达用户；分发器本来就发这些事件，流式只是基于 MessageHandle 和 patch_message 的接线。路由、存储、广播拆到 _session_routing.py、_session_store.py、_broadcast.py。

无状态入口存在的原因

范式谁驱动入口
A：Agentic ProgrammingPython 控制流；Agent 方法创建 Context 节点；Runtime.exec 只在调用时请求 LLM程序员写的代码
B：Agent 循环（渠道、Web UI 聊天）LLM 选工具：process_user_turn → agent_loop → 工具流外部消息
部署形式适配器实例
openprogram worker 运行中在 worker 中
导入 Agent 方法的脚本；独立进程中的任务；notebook；pytest没有
  • 渠道挂在 B 上，但 A 也要发送。A 是库模式，不假定有 worker。OpenClaw 和 Hermes 只经适配器发送，适合它们的单守护进程，定时任务可通过注入拿到适配器。
  • 任何异步优先的基类都要保留同步的模块级封装，让 Agent 方法不用 asyncio 也能发送。
  • 流式编辑在 A 中仍可用：Agent 方法可以持有 MessageHandle 并编辑。

借鉴什么

主题取自 OpenClaw取自 Hermes
方法签名、生命周期、返回结构是，更完整是
流式三状态单次编辑
审批生命周期完整/approve 命令
健康探测是—
代码组织否：50+ 契约和每平台 70+ 文件过度是：一个基类文件，每平台一个
为什么不照搬 OpenClaw，以及暂缓的内容
  • 没有 Python 可抄：OpenClaw 全是 TypeScript，仅有的 .py 是 CI 和 skill 工具。复用意味着重新实现设计；TS 接口对应 Protocol/abc.ABC，dataclass 和插件 manifest 可以迁移。
  • 50+ 契约文件靠静态类型才划算。Python Protocol 运行时不强制，mypy 也不是默认开启。所以不值得每个接口一个文件，但接口形状值得学。
  • OpenClaw 和 Hermes 异步优先；这一层是同步加每适配器一线程。改异步要把 dispatch_inbound 变成异步生成器，并重接四个事件循环。
  • Hermes 的防抖合并、快捷命令绕过和附件缓存来自生产流量，等问题出现再加。

Channel requirements and invariants

Structure and message flow: Channel subsystem design.

The contract

@dataclass(frozen=True)
class MessageHandle:
    platform: str
    account_id: str
    target: str
    message_id: str

    @property
    def editable(self) -> bool: ...


class Channel(abc.ABC):
    platform_id: str = ""

    @abc.abstractmethod
    def run(self, stop: threading.Event) -> None: ...

    def send_text(self, target, text) -> Optional[MessageHandle]: ...
    def send_text_full(self, target, text, thread_id=None) -> SendResult: ...
    def send_file(self, target, path, caption="", thread_id=None) -> SendResult: ...
    def edit_text(self, handle, new_text) -> bool: ...
    def edit_text_full(self, handle, new_text) -> SendResult: ...
InvariantReason
run is the only abstract methodInbound loops have no common shape. Outbound does, so send and edit are concrete over _transport. An adapter implementing only run can fully send and edit; overrides exist only when an SDK adds something, such as mention parsing or upload. Mandating send/edit/react would force capabilities a platform may lack.
MessageHandle is all stringsSurvives serialization: one process sends, another edits
Two entry points, one implementationoutbound.send works with no adapter in the process; adapter.send_text keeps the id to edit. _transport alone owns HTTP, credentials and chunking, so a new operation is one implementation, not eight.
Sends return SendResultA bool cannot separate a transient failure from a permanent one. error_kind (auth, rate_limit, bad_target, network, not_supported, format, unknown) comes from _classify_http_status, _telegram_kind_from_description, _slack_kind_from_error. Bool forms remain.
Edit capability is a handle propertyiLink cannot edit. WeChat handles report editable == False; edit_text_full returns SendResult.fail("not_supported", ...), never faking it by deleting and reposting. No caller special-cases a platform name.
Cross-platform edits are refusedhandle.platform != self.platform_id returns SendResult.fail("bad_target", ...). Coordinating adapters is the caller's concern.
Built-ins win registration_BUILTIN_CHANNEL_CLASSES over _PLUGIN_CHANNEL_CLASSES. Plugins use [project.entry-points."openprogram.channels"] or register_channel(name, cls). CHANNEL_CLASSES is a dict-like proxy over both.

Neutral inbound message

_message.py:ChannelMessage, frozen: text, chat_id, user_id, user_display, message_id, chat_type, ts, reply_to_id, quoted_text, thread_id, parent_chat_id, attachments (tuple of Attachment), mentioned, from_bot.

The pipeline prepends quoted_text as a > block and downloads attachments, forwarding small images as vision input. thread_id sends placeholders, replies and files back to the thread; it does not join session routing.

  • Channels attach to B, but A still sends. A is library mode: no worker assumed. OpenClaw's and Hermes's adapter-only sends fit their single daemon, where a job can get adapters by injection.
  • Any async-first base must keep a synchronous module-level wrapper, so an Agent method can send without asyncio.
  • Streaming edit stays reachable from A: an Agent method can hold a MessageHandle and edit it.

Why OpenClaw is not copied, and what is deferred
  • No Python to copy: OpenClaw is entirely TypeScript; its only .py files are CI and skill tooling. Reuse means re-implementing the design; TS interfaces map to Protocol/abc.ABC, dataclasses and plugin manifests carry across.
  • Static typing is what makes 50+ contract files pay off. Python Protocols are not enforced at runtime, and mypy is not on by default. So one file per interface is not worth it; the interface shapes are.
  • OpenClaw and Hermes are async-first; this layer is synchronous with one thread per adapter. Going async means turning dispatch_inbound into an async generator and rewiring four event loops.
  • Hermes's debounce merging, quick-command bypass and attachment caching came from production traffic and are deferred until those problems appear.

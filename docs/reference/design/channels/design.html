One message, end to end

You send the Telegram bot "what Python files are here?"

StageWhat happens
telegram.py_handle_update receives the update and builds ChannelMessage{text, chat_id="123", user_id="456", chat_type="direct", attachments=()}. An @mention or reply to the bot sets mentioned=True; the mention is stripped.
handle_inboundA per-message daemon thread, so a turn paused on runtime.ask does not block polling. decide_inbound_sender, download_inbound, quoted block, then dispatch_inbound(channel="telegram", account_id="default", peer_kind="direct", peer_id="123", progress_stream=True, ...). Messages from one peer take a place in line on arrival and start turns in that order; commands skip the line.
dispatch_inboundBindings pick the agent. session_key = "default_direct_123". Takes the per-session lock: same-session turns queue, different sessions run in parallel; /answer and /decline are handled before the lock; /stop and /help never reach it. Loads the session. Posts ⏳ working..., keeping MessageHandle{message_id="9001"}. Runs process_user_turn.
Tool runstool_use edits the placeholder to ⚙ bash once more than 1 s has passed since the last edit; tool_result swaps it to ✓ bash.
ReplyA forced edit bypasses the throttle and turns message 9001 into the reply. Persists, broadcasts, returns None, so handle_inbound sends nothing.
Degraded pathPlaceholder failed, the platform cannot edit, or WeChat: dispatch_inbound returns the reply and handle_inbound sends it via Channel.send_text, chunked at MAX_CHARS.

peer_id is Channel.peer_id_for: chat_id on Telegram and WeChat, or {chat_id}_{user_id} in Telegram groups with group_sessions=per-user; {chat_id}_{user_id} on Discord and Slack.

Sending from code

from openprogram.interfaces.channels.outbound import send

send("telegram", "default", "1234", "Good morning")

Credentials, HTTPS POST, SendResult to True/False. No adapter, worker, session, agent call or broadcast.

Principles

Two entry points, one implementation

EntryPurposeStateCaller
outbound.sendOne-shot, no long-running processstatelessJobs, notebooks, Agent methods, Web UI reply
Channel.send_text + edit_textHolds message_id for editsstatefuldispatch_inbound progress

Both use _transport.post_message / patch_message: one copy of HTTP, credentials and chunking.

Traffic hub

_conversation.py holds only the flow: route, session key and reset policy, then under the per-session lock load the session, post a placeholder when streaming, run the agent, persist and broadcast. Routing, storage and broadcast live in their own modules.

Platform differences sealed low

LayerOwns
_transport.pyEvery outward HTTP call: editMessageText, PATCH /messages/{id}, chat.update, iLink, post_file per platform (sendPhoto/sendDocument, multipart, external-upload, iLink CDN). MAX_CHARS, chunking, HARD_CAPS re-split, rate-limit retry.
_format.pyMarkdown to Telegram HTML (everything escaped; the poster falls back to tag-stripped text if entities are rejected), Slack mrkdwn, Discord passthrough, WeChat plain text. Code is placeholder-protected.
AdaptersOnly the event loop and parsing into ChannelMessage. They do not send; everything after the parse lives in handle_inbound.
run_forever(stop)A raising run() reconnects: 5 s doubling, cap 300 s, reset after surviving 60 s. A clean return means permanently stopped, e.g. invalid WeChat token.

Structured errors

@dataclass(frozen=True)
class SendResult:
    ok: bool
    message_id: str = ""
    error_kind: str = ""     # auth, rate_limit, bad_target, network,
                             # not_supported, format, unknown
    error_detail: str = ""   # one human-readable line
    retryable: bool = False
    retry_after: float = 0.0 # platform-stated wait; 0 = unstated
    connect_failed: bool = False   # connection never opened; safe to resend

rate_limit retries inside _transport: Retry-After first, else 1 s then 3 s, sleep capped at 30 s, 3 attempts.

A connection that never opened (connect_failed) retries after 1, 2 and 4 s, 4 attempts; a failure after the request went out does not retry, since a resend could arrive twice.

outbound.send, send_text and edit_text return bool or a handle; _full variants return SendResult, as do both send_files.

Inbound access

AspectRule
FileOne access.json per (channel, account): allowlist by stable platform user id, at most three pending. Admission is always pairing; a legacy policy: "open" is ignored.
Code8 uppercase characters without 0O1I, valid 1 hour. Same sender not re-prompted in that hour; excess requests silently ignored.
GateRuns before routing; an unpaired sender never reaches dispatch_inbound.
Mutationapprove, approve_user, revoke only from the local CLI and loopback Web UI. The inbound path only reads and mints codes, so no channel message can approve anyone.

Adding a platform

# pyproject.toml, scanned at startup
[project.entry-points."openprogram.channels"]
whatsapp = "my_pkg.whatsapp:WhatsAppChannel"

# or, for notebooks and plugin hooks
from openprogram.interfaces.channels import register_channel
register_channel("whatsapp", WhatsAppChannel)

Built-ins take priority; a same-named plugin is ignored.

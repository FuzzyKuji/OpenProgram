一条消息的全过程

你给 Telegram 机器人发送“这里有哪些 Python 文件？”

阶段发生什么
telegram.py_handle_update 收到 update，构造 ChannelMessage{text, chat_id="123", user_id="456", chat_type="direct", attachments=()}。@ 机器人或回复机器人时 mentioned=True，并去掉提及。
handle_inbound每条消息一个守护线程，runtime.ask 暂停的回合不会阻塞轮询。decide_inbound_sender、download_inbound、引用块，然后 dispatch_inbound(channel="telegram", account_id="default", peer_kind="direct", peer_id="123", progress_stream=True, ...)。同一 peer 的消息到达时排队，按这个顺序开启轮次；命令不排队。
dispatch_inbound绑定决定 agent。session_key = "default_direct_123"。获取按会话的锁：同会话回合排队，不同会话并行；/answer 和 /decline 在锁之前处理；/stop 和 /help 不经过这里。加载会话。发送 ⏳ working...，保留 MessageHandle{message_id="9001"}。运行 process_user_turn。
工具运行tool_use 在距上次编辑超过 1 秒时把占位改成 ⚙ bash；tool_result 改成 ✓ bash。
回复强制编辑绕过节流，把消息 9001 改成回复。持久化、广播，返回 None，handle_inbound 不再发送。
降级路径占位发送失败、平台不能编辑或微信：dispatch_inbound 返回回复，handle_inbound 经 Channel.send_text 按 MAX_CHARS 分块发送。

peer_id 来自 Channel.peer_id_for：Telegram 和微信为 chat_id；Telegram 群组 group_sessions=per-user 时为 {chat_id}_{user_id}；Discord 和 Slack 为 {chat_id}_{user_id}。

从代码发送

from openprogram.interfaces.channels.outbound import send

send("telegram", "default", "1234", "Good morning")

取凭据、HTTPS POST、SendResult 转为 True/False。没有适配器、worker、会话、agent 调用或广播。

设计原则

两个入口，一个实现

入口用途状态调用方
outbound.send一次性，无需常驻进程无状态定时任务、notebook、Agent 方法、Web UI 回复
Channel.send_text + edit_text持有 message_id 用于编辑有状态dispatch_inbound 进度

两者都用 _transport.post_message / patch_message：HTTP、凭据和分块只有一份。

流量枢纽

_conversation.py 只保留流程：路由、会话 key 和重置策略，然后在按会话的锁内加载会话、流式时发占位、运行 agent、持久化和广播。路由、存储和广播各在自己的模块。

平台差异封在底层

层负责
_transport.py所有对外 HTTP：editMessageText、PATCH /messages/{id}、chat.update、iLink，各平台 post_file（sendPhoto/sendDocument、multipart、external-upload、iLink CDN）。MAX_CHARS、分块、HARD_CAPS 再拆分、限流重试。
_format.pyMarkdown 转 Telegram HTML（全部转义；实体被拒时回退为去标签文本）、Slack mrkdwn、Discord 直通、微信纯文本。代码用占位保护。
适配器只负责事件循环和解析成 ChannelMessage。它们不发送；解析之后的一切在 handle_inbound。
run_forever(stop)run() 抛异常时重连：5 秒起翻倍，上限 300 秒，存活 60 秒后重置。正常返回表示永久停止，如微信 token 失效。

结构化错误

@dataclass(frozen=True)
class SendResult:
    ok: bool
    message_id: str = ""
    error_kind: str = ""     # auth, rate_limit, bad_target, network,
                             # not_supported, format, unknown
    error_detail: str = ""   # one human-readable line
    retryable: bool = False
    retry_after: float = 0.0 # platform-stated wait; 0 = unstated
    connect_failed: bool = False   # connection never opened; safe to resend

rate_limit 在 _transport 内重试：优先 Retry-After，否则 1 秒、3 秒，等待上限 30 秒，共 3 次。

连接没建立（connect_failed）时隔 1、2、4 秒重试，共 4 次；请求发出后的失败不重试，重发可能送达两次。

outbound.send、send_text、edit_text 返回 bool 或句柄；_full 变体和两个 send_file 返回 SendResult。

入站访问控制

方面规则
文件每个（渠道、账号）一个 access.json：按稳定平台用户 id 的 allowlist，最多三个 pending。准入始终是配对；旧的 policy: "open" 被忽略。
配对码8 位大写字符，不含 0O1I，有效 1 小时。这一小时内不再提示同一发送者；超额请求静默忽略。
门禁在路由前运行；未配对发送者到不了 dispatch_inbound。
修改approve、approve_user、revoke 只能在本地 CLI 和回环 Web UI 中使用。入站路径只读取和生成配对码，渠道消息无法批准任何人。

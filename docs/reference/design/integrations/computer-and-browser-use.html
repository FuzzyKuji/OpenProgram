computer_use_agent

Shape

computer_use_agent(target, action?, args?, actions?, code?, timeout?)
ParameterMeaning
targetapp, browser or vm, as this host offers them when the turn starts; a target it cannot reach is not in the schema, and a call that still names one answers with how to set it up
action, argsone step and its arguments; omitted, the call opens the target
actionsup to 20 steps {action, args} on one target, stopping at the first error; the state comes back once
codePython run in the isolated interpreter (see Code); in the schema only where that sandbox runs (macOS)
timeoutseconds a code call may run, at most 120 (default 60); present with code
How the schema is built
  • The description and schema are built when each turn resolves its tools (tool.describe, through the describe hook of function() and current_tool), so they name only what the host has:
    • app where the platform backend loads
    • browser while the browser application is enabled
    • vm once computer_use.vm_url is set
    • The user's Chrome or Edge only where the Playwright Extension is installed (extension.installed, which looks for <profile>/Extensions/<id> in the browser's data directory and never touches the browser)
    • code only where the sandbox runs
  • Without the extension the browser line says that a page in the user's Chrome or Edge is operated as an application window.
  • The model therefore never learns of an absent target from a refusal.
  • With no target at all, check_fn hides the tool.

action, actions and code are exclusive. Arguments are validated by the target, and an error names the right spelling, since the schema does not list every action's arguments.

Guide delivery and the user's browser
Item
GuidesEach target has a guide (guides/<target>.md; the app guide has macOS, Linux and Windows variants): its actions, their arguments and how results look.
Deliverytool.py registers them as included tool guides: computer_use_agent.<target> arrives with the first result of a call that operates that target, and computer_use_agent.code arrives with the first result of a call that operates any target, on hosts where code runs, so the model has read how code works before it sends any.
No waitingNo call waits for a guide: a call that sends code before either guide was seen runs, and the guides come back with its result.
Known guidesWhether a guide is known is read from the request the agent loop last sent, so compaction, cleared tool results and a worker restart all lead to the guide being sent again; a guide inside a prompt that another agent wrote reaches the model inside the speaker's JSON envelope, so guides.known also matches the marker with its quotes escaped.
On requestaction: "guide" and help("computer_use_agent.<target>") return them on request.
Item
ActionsThe app actions are those of the application target, with the same arguments; the browser actions are the tab driver's (tabs, open, read, click, type …, see Browser target: the tab driver).
Browser firstAs in Codex, the browser is chosen first and the actions do not change with it.
Guide per deliveryThe browser guide is built per delivery from the same check: it names only the user's browsers that have the extension, and with none it points pages in them to the app target.
No extensionA call naming a browser without the extension is answered at once with that advice, asks no approval and starts no server.
ServerFor those that have it, targets/browser.py hands each step to extension.py of the browser application, which runs a pinned @playwright/mcp --extension --browser chrome|msedge through its own MCP client, one server per conversation and browser, kept between calls.
ConnectionThe server opens chrome-extension://<id>/connect.html in that browser with the address of its relay, and the Playwright Extension connects back and relays CDP for the tab the user shares; with computer_use.chrome_extension_token set, the server passes PLAYWRIGHT_MCP_EXTENSION_TOKEN and the extension connects without asking.
Action mappingtabs, read (with tab an index, which selects that tab), open, close, screenshot, upload, evaluate and the logs map to the server's tab, snapshot, screenshot, file, evaluate and log tools; every element and pointer action goes through OfficialMCPPageBackend._action_call, the same translation the playwright_mcp backend applies to App Pages.
RefsRefs are the server's snapshot refs.
Code modeIn code mode cu.browser reaches the user's browser when the code call names it in args.browser.

Code
Item
Interpretercode runs in the persistent sandboxed interpreter of computer_use_agent/sandbox/runner.py (seatbelt on macOS, no file, network or process access).
NamespaceThe namespace has cu.app, cu.browser and cu.vm; await cu.app.click(app="Numbers", element_index=3) is the structured step click with those arguments, dispatched by the host through the same target code and checks, one effect receipt per step (computer_use_agent/sandbox/broker.py).
DocstringsThe prelude gives each cu method the guide line of its action as its docstring, so dir(cu.app) and help(cu.app.click) work inside the interpreter.
Parameter textThe code parameter's own description shows one such call for each target present, so a model that no longer has the code guide in view still writes cu.browser.click(...) and not a bare click(...).
Item
ScreenA code call acts on the screen its call names: for app, args.app; for browser, the browser of args.browser (the built-in one when omitted).
GrantThe call's grant covers that screen, so code._validator refuses a step that names another application or another browser and lets everything else the target offers through, page scripts and opening sites included.
UploadRefused in code: an upload from the built-in browser sends a local file, so it is made as an action of its own.
Page scriptA page script does not run where nobody attends the turn, from code as from an action: code.run reads that from the turn's request when the call starts.
Item
LifetimeOne interpreter serves one execution attempt, so variables persist for the rest of the turn; it is replaced when it fails or times out.
Held byInterpreters are held per conversation and execution, and the app target's window states per conversation and job (tool.operator, from the job the call runs in).
Shared keyThe conversation's own turns share one key, so a turn acts on the window the turn before it read. An agent the conversation starts runs as its own job, whose reads and code never replace what the main turn or another agent is acting on.
Item
LimitsEach call may run 120 seconds and 100 steps.
Printed textPrinted text is kept up to 256 KB and the rest is dropped with a note in the result; what a step returns goes to the code and is not counted against that.
Not dispatchedA step that stops before input reaches the app (NotDispatched: an element that is gone, a hidden element, an app not found) returns action_dispatched: false, so the broker records it as not committed.
Failed after inputA step that fails after input may have been sent raises in the code with the target's message, and the steps before it stay made.
Timed outA call that outruns its time, or whose interpreter stops, comes back as an error result: the steps already made stay made, the step that was running may or may not have applied, and the next code call starts a new interpreter without this one's variables.
Open receiptsWhen a call returns, the broker closes the receipts of the steps whose outcome it never learned (GuiBroker.settle, receipt state unknown): the result is what tells the model, and no open receipt outlives the call.
PlatformCode mode needs the macOS sandbox; elsewhere a code call reports that the sandbox is unavailable.
Who operates
Item
CallerThe agent that calls the tool operates the screen and carries the task through. The tool takes no argument that passes the task to another agent, so a failed step is retried where it failed.
Long taskscode runs many steps in one call and returns only what it prints, which keeps intermediate screens out of the conversation.
Several screensWork on separate screens at once goes through the agent tool, which the base instructions allow only when the user or project instructions ask for sub-agents. Each agent keeps its own window states, element indices and code interpreter.
Time limitThe tool has no overall time limit: each action bounds itself and code stops at its own timeout.

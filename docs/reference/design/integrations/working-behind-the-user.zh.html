不打扰用户

Agent 操作某个应用、浏览器或页面时，用户在别处继续工作。用户的七样东西保持原样。

保持含义
前台应用用户所在的应用仍然是接收其按键的那个。
窗口前后顺序没有窗口移到用户留下位置的前面或后面。
正在看的标签页用户自己浏览器里和 App 里正在看的标签页不变。
鼠标指针真实指针不移动。
键盘焦点用户输入的内容仍然进入原来的位置。
剪贴板用户复制的内容还在。
桌面空间不切换桌面，窗口不换空间。

两层

层覆盖范围
投递时不占用任何东西每个目标发送输入时都不激活应用、不抬起窗口：应用走辅助功能和按进程投递的事件（macOS 投递），内置浏览器向隐藏页面发送可信输入（浏览器标签页驱动），用户的 Chrome 或 Edge 里用后台标签页。
被占用的还回去应用启动，或打开页面、文档、对话框时，可能自己激活自己，发送方没有选项能阻止。在 macOS 15 上实测：只要有标签页在前台打开，Chrome 就会到所有应用前面，无论标签页是命令行打开、open -g 打开还是 AppleScript 打开。openprogram/host/_platform/front.py 在一处处理所有这类情况。

把前台还回去

窗口服务器先换前台应用，之后才用事件通知各个应用。应用收到自己的事件，才把窗口带到前面、画出菜单栏，原来的应用才把标题栏变灰。这些事件被拦下，所以这次变化什么都不会画出来。

  1. 步骤开始：front.kept(operated) 记下前台应用和窗口顺序。所有正在运行的步骤共用一个事件拦截点。
  2. 通知用户的应用“失去前台”的事件，先到拦截点，后到应用。
  3. 被操作的应用在前台：在拦截点里就把前台还给用户的应用，并丢弃这个事件。
  4. 随后的事件也丢弃：被操作应用的“获得”和“失去”，用户应用的“获得”。两个应用都不知道发生过。
  5. 之后 0.5 s 内每 4 ms 读一次窗口顺序。应用仍然自己把窗口移到前面时，原先排在它上面的窗口从最深的开始重新抬起。
  6. 步骤立即返回；监视再持续 0.8 s，因为应用可能稍后才激活自己。

在 macOS 15 上对三种情况实测：计算器在前台启动、运行中的计算器被激活、Chrome 在前台打开标签页。每次读到的窗口顺序里最上面都是用户的窗口，标题栏一个像素都没变，事件到达后 1.4 到 2.8 ms 前台就已还回。同样的事件放行时，计算器的窗口到了最上面，标题栏变灰。

规则
变化算谁的operated(pid) 指明一个步骤操作哪些进程：args.app 指的应用（front.named），用户的 Chrome 或 Edge，或内置浏览器所在的 App（front.bundles）。其他应用到了前台，就是用户自己切过去的：留在那里，之后前台还给它。
用户本来就在步骤开始时用户就在被操作的应用里，则不监视。
有上限一个步骤反复抢前台时，还回去六次，之后不再处理。
拦下的事件在带标注的会话位置设一个主动拦截点，接收类型 19（失去前台）、20（获得前台）和子类型为 1 或 2 的类型 13（应用启动期间收到的那一对）。只有前台确实还回去之后才丢弃事件，所以不会让应用相信不属实的状态。
授权拦截点需要辅助功能授权；没有授权时不去申请，因为申请会在用户面前弹出提示。
没有拦截点时每 50 ms 读一次前台，还回去，再把窗口重新抬起；这时被操作应用的窗口会在屏幕上出现 15 到 43 ms。有拦截点时，这种读取只处理连续两次看到的占用。
读取前台GetFrontProcess，每次 0.6 ms。NSWorkspace 靠主运行循环更新结果，工作线程不转动它。
还回前台SetFrontProcessWithOptions，只带最前窗口的选项，2 ms。从工作线程调用 NSRunningApplication.activateWithOptions 要等一秒才生效。
窗口顺序按窗口服务器 id 找到每个窗口并执行 AXRaise；窗口在步骤开始时就查好，抬起只需一次调用。与被操作应用的窗口都不重叠的窗口不动。消息超时设为 0.25 s，不等待忙碌的应用。没有辅助功能授权时，前台应用照样还回去，顺序不恢复。
记录每一次都带应用名写入日志，并保存在该代码块的 Watch.taken 中。
入口使用者
kept(operated)targets/app.py 和 targets/browser.py 包住每一次调用，结构化步骤和代码模式都覆盖。
watch_for(operated, seconds)自更新切换，在桌面外壳重新启动的 30 s 内。
front.py <bundle path> <seconds>scripts/refresh-local-app.sh 和 scripts/install-dev-app.sh 单独运行这个文件；这时它只需要标准库，没有辅助功能授权时每 50 ms 读一次前台。

什么会占用屏幕，以及处理方式

来源处理
为某个步骤启动应用用 open -g 启动；仍然自己激活的，把前台还回去。
坐标点击让被点的窗口在其层级内上移原先叠在它上面的窗口重新抬起（macOS 投递）。
用户的浏览器打开扩展连接页前台还回去。连接页作为该浏览器的一个标签页留着。
扩展连上后聚焦浏览器窗口设置了 token 时，连接链接带上扩展自己的 background=true。
Playwright 在前台开标签页、把选中的标签页拉到前面playwright_background_tabs.cjs 让标签页以非活动方式打开，并去掉那次调用。
没有 token 时连接用户要在那个页面上同意连接，所以这一次调用里浏览器留在前台。
Agent 在内置页面里按 Cmd/Ctrl+F、L、K 或 P只有页面显示在聚焦窗口里并且持有键盘时，App 才把它们当作自己的快捷键；否则按键留在页面里。
页面要求确认离开没人在看的页面直接离开，不弹对话框。
网站请求摄像头、位置或通知来自没人在看的页面时：这一次拒绝，不记住，用户打开该页面时再问。
Agent 在用户自己的标签页里点击后弹出新页面新页面在旁边打开；正在看的标签页和路由不变。
App 被重新安装，或因更新重新启动只有关闭时用户正在用它，才回到前台。
工作进程自行连接 MCP 服务器时需要登录不打开浏览器；链接留在 /api/mcp/auth/pending，重新连接该服务器时再打开。

用户仍然会看到的

显示原因
Agent 光标和窗口标记不激活、可穿透点击的覆盖层，让用户知道 Agent 正在用哪个窗口（Computer use 界面）。
对话里的页面预览在 App 内，只对屏幕上的对话显示；用户隐藏后不再出现。
通知只在没有 App 窗口聚焦时出现；点击通知后 App 才到前面。
命令打开的东西Agent 为了展示而运行的 shell 命令（open report.html）按要求在前台打开。

Linux 和 Windows

这两个系统没有能拦下事件的位置，所以读取前台、还回去，再把窗口顺序放回。

WindowsLinux，X11
读取前台每 20 ms 调用 GetForegroundWindowxprop -spy 在活动窗口和堆叠顺序每次变化时报告
还回前台接入前台线程的输入队列后调用 SetForegroundWindowwindowactivate
窗口顺序不激活的 SetWindowPoswindowraise，窗口管理器可能不采纳
规则
变化算谁的应用按进程区分。后端把解析到的进程告诉保护（front.note）；启动应用期间（front.starting），步骤开始时没有窗口的进程就是新启动的那个。浏览器按可执行文件名区分（front.programs）。
有意上前这些系统只交给前台窗口的输入，会让窗口在该步骤上前（非 macOS 后端）；同意卡片上会说明。这时保护让开（front.forward），后端自己把前台窗口、指针和窗口在顺序里的位置放回去。
Wayland应用没有合成器发的令牌就拿不到焦点；不运行任何东西。

在带 Xvfb 和 Openbox 的 Debian 容器里实测：运行中的应用自己激活后 8.6 ms 失去前台，之后读到的堆叠顺序相同；有意上前的窗口没有被处理；用户自己的切换没有被处理。

Working behind the user

While an agent operates an application, a browser or a page, the user goes on working in something else. Seven things of theirs stay as they are.

KeptMeaning
Front applicationThe application the user is in stays the one that takes their keys.
Window orderNo window moves in front of, or behind, where the user left it.
Tab in viewThe tab they are looking at, in their own browser and in the App, stays the one shown.
PointerThe real pointer does not move.
Keyboard focusWhat they type goes where they were typing.
ClipboardWhat they copied is still there.
SpaceNo desktop switches, and no window changes Space.

Two layers

LayerWhat it covers
Delivery that takes nothingEach target sends its input so that nothing is activated or raised: Accessibility and per-process events for applications (macOS delivery), trusted input into hidden pages for the built-in browser (Browser tab driver), background tabs in the user's Chrome or Edge.
Giving back what is takenAn application that starts, or opens a page, a document or a dialog, may activate itself, and no option of the sender stops it. Measured on macOS 15: Chrome comes in front of every application whenever a tab opens in front, whether the tab was opened from the command line, by open -g or by AppleScript. openprogram/host/_platform/front.py answers all of these in one place.

Giving the front back

The window server changes the front application first and tells the applications afterwards, with events. An application brings its windows forward and draws its menu bar, and the one before it dims its title bars, only when its own event arrives. The events are held back, so nothing of the change is drawn.

  1. A step starts: front.kept(operated) records the front application and the window stack. One event tap serves every step that is running.
  2. The event telling the user's application that it lost the front reaches the tap before the application.
  3. An operated application is in front: inside the tap the front goes back to the user's application, and the event is dropped.
  4. The events that follow are dropped too: the operated application's "gained" and "lost", and the user's "gained". Neither application learns of it.
  5. For 0.5 s the window stack is read every 4 ms. An application that moved its own window forward anyway has the windows that stood over it raised again, deepest first.
  6. The step returns at once; the watch goes on for 0.8 s, since an application may activate itself a moment later.

Measured on macOS 15 against Calculator starting in front, Calculator activated while running, and Chrome opening a tab in front: the user's window was on top in every reading, its title bar did not change by one pixel, and the front was back within 2.8 ms of the event. With the events let through, Calculator's window stood on top and the title bar dimmed.

Rule
Whose change it isoperated(pid) names the processes a step operates: the application of args.app (front.named), the user's Chrome or Edge, or the App for the built-in browser (front.bundles). Any other application that comes to the front is one the user switched to: it is left there and becomes the one the front is given back to.
User already thereWhen the user is in the operated application as the step starts, nothing is watched.
BoundedA step that keeps taking the front is answered six times, then left.
Events held backAn active tap on the annotated session for event types 19 (lost the front), 20 (gained it) and 13 with subtype 1 or 2 (the pair an application gets while it starts). An event is dropped only after the front has really been given back, so no application is left believing something untrue.
GrantThe tap needs the Accessibility grant and is not asked for without it, since asking would put a prompt in front of the user.
Without the tapThe front is read every 50 ms, given back, and the windows raised again; the operated application's window is then on screen for 15 to 43 ms. With the tap, this reading acts only on a theft it sees twice.
Reading the frontGetFrontProcess, 0.6 ms a call. NSWorkspace keeps its answer current from the main run loop, which a worker thread does not turn.
Giving it backSetFrontProcessWithOptions with the front-window-only option, 2 ms. NSRunningApplication.activateWithOptions called from a worker thread waits one second before it takes effect.
Window orderAXRaise on each window, found by its window-server id; the windows are looked up as the step starts, so that raising is one call. Windows that touch none of the operated application's are left alone. A 0.25 s messaging timeout is set so that a busy application is not waited for. Without the Accessibility grant the front application is still given back and the order is left.
RecordEach time is logged with the application's name, and kept in the block's Watch.taken.

Linux and Windows

Neither system has a place where the events can be held, so the front is read, given back, and the windows put back in order.

WindowsLinux, X11
Reading the frontGetForegroundWindow every 20 msxprop -spy reports each change of the active window and the stacking order
Giving it backSetForegroundWindow from the foreground thread's input queuewindowactivate
Window orderSetWindowPos without activatingwindowraise, which a window manager may decline
Rule
Whose change it isApplications are told apart by process. A backend names the process it resolved (front.note); while it starts one (front.starting), a process that had no window as the step began is the new one. Browsers are told by executable (front.programs).
Forward on purposeInput those systems give only to the front window brings the window forward for the step (Linux and Windows backends); the approval card says so. The guard stands aside (front.forward), and the backend puts back the front window, the pointer and the window's place in the order.
WaylandAn application cannot take the focus without a token from the compositor; nothing runs.

Measured in a Debian container with Xvfb and Openbox: a running application that activated itself lost the front after 8.6 ms and the stacking order read the same afterwards; a window brought forward on purpose was left alone; a user's own switch was left alone.

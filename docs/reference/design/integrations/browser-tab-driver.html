Browser tab driver

  • tabs.py of the browser application drives the App's built-in tabs for the browser target.
  • It replaces, for that target, the web_use runtime's page context tokens, sessions, frames, leases and revision checks: none of them reach the model.
  • The web_use runtime stays for the programs and MCP clients that still call it directly; it is the only page entry the application registers.

Tabs

Item
IdentityA tab is (window_id, tab_id) as the renderer lists it (surface_context.capture_pages_for_listing, which carries each tab's CDP target_id).
IdThe driver names it t plus the first four base32 letters of the SHA-1 of window_id and tab_id (one letter more on a collision), so every process, the worker and a forked workflow subprocess alike, gives the same tab the same id in every turn, conversation and sub-agent, and listing again in any order does not rename.
Moved tabA tab that moved to another window keeps its id: a listed tab whose target_id belongs to a known tab takes that tab over.
Changed targetA tab whose target_id changed (the App restarted) forgets its refs, document baselines and screenshots.
BindingEach listing binds every page again, so the binding a tab had is released when a new one replaces it.
Default tabAn action without tab goes to the tab its agent used last (see below), else to the focused tab, else to the one visible tab.
open, close, screenshotopen asks the renderer for a background tab (surface_context.open_page) and makes it the current one; close and screenshot go through the tab's binding (request_close_tab, request_bound_screenshot), and a binding that expired is renewed by listing again.
OwnershipTabs belong to the conversation that opened them (browser_tabs_opened, kept across restarts). tabs lists those and the current one; tabs(all=true) adds the rest. The guide tells the model to reuse an open page and close its tabs when done. Archiving or deleting a conversation closes the tabs it opened; the user's own tabs stay.

Connection

Item
Owner threadPlaywright's sync API belongs to one thread, so one owner thread holds connect_over_cdp to the App (desktop_app_ws_url) and runs every page call; callers wait on it with their context variables.
Finding a pageA page is found by matching Target.getTargetInfo against the tab's target_id.
ReconnectA connection does not always learn of tabs the App opens after it, so a target that is not found makes the driver connect again and look once more; a dropped connection reconnects on the next call.
RecordingWhen a page listener is first attached, the driver records its console, page errors and requests (the last 300 of each), and counts its document navigations and in-flight fetch/XHR requests.

Several agents

Item
No leaseAgents of one conversation share its session id, and sub-agents run in parallel, so no tab is leased to one agent for longer than one action or one list of actions: a lease held across turns would make a conversation refuse its own turns.
LockEach Tab has a lock.
Lock spanAn action takes it before its first page call and keeps it through settling and its result, so another agent's input never lands between an action and the state it reports.
ListsA list of actions (targets/browser.run with several steps, inside tabs.batch()) keeps every lock it took until the list ends, so a form filled in one list is not interleaved.
WaitingWaiting for a lock polls with cancellation checks, and after TAB_WAIT_SECONDS (60 s) the action fails with tab_busy; two lists that each wait for the other's tab end that way rather than deadlock.
AgentThe agent a call acts for is <session>/<execution> (the _VIEWER context variable, carried into the owner thread).
Current tabEach agent remembers its own current tab; an agent without one starts from the tab its conversation used last.
SnapshotsSnapshots are tracked per agent (track = openprogram:<agent>, and each agent's document baseline), so an agent's changes cover everything since it last looked, including what other agents did.
Write logEach tab records its write actions with the agent that made them; a result adds a note when another agent acted on the tab since this agent's last result.
Owner threadOnly single page calls run on the owner thread.
Pollingwait and the settling after an action poll on the caller's thread with short owner calls (_shows, _activity, _loaded), so one agent's wait never holds up another agent's click on another tab.

Writes are sent once

Item
RetryOnly tab_gone, which _page raises before any input, makes the driver list the tabs again and try the action once more.
Failed actionAn action that failed after Playwright may have sent its input counts as a write, and its error says it may have taken effect when it timed out, with the page as it is; a tab that closed during the action is tab_closed.
After successOnce an action succeeded, any failure while settling or reading the page comes back as a successful result with a note, never as an error the caller would retry.
closeclose treats the renderer's response timeout as close_uncertain, an expired binding as tab_gone (nothing was sent), and other failures as close_failed.
evaluateevaluate counts as a write.

Tabs an action opens

The connection discovers targets (Target.setDiscoverTargets) and counts each new page target. When the count changed during an action, the driver lists the tabs and the result's opened names the new ones whose opener_tab_id is the acted-on tab or unknown. The agent's current tab stays where it was.

Coordinates

Item
RecordA screenshot records, per agent, the CSS-to-image ratio, the tab's last write, its URL, its scroll offset and the image.
ClickA click by x,y needs that agent's screenshot, and fails with screenshot_stale when the tab navigated or scrolled since.
Point checkWhen an agent wrote to the tab since, the driver captures the tab again and compares the 64 CSS px square around the point in both images (decoded with CoreGraphics; up to 6 % of its pixels may differ by more than 32 per channel, for a caret or anti-aliasing).
DecisionThe click goes ahead while the point still shows what the screenshot showed, so typing elsewhere or a key that did nothing costs no new screenshot. It is refused when it does not, or when the pixels cannot be compared.
RefusalA refusal carries a new screenshot, recorded as the agent's, so the next x,y need no extra call.

Preview follow

Item
Follow ruleThe conversation's page preview follows the operations the driver reports, as it does for the web_use runtime: the frontend follows only a live browser.resource event whose last_operation is new and dispatched or acknowledged, never a snapshot.
Write actionEvery write action (anything but read, console, network, wait, screenshot, tabs and close) first retains the tab's resource row for the current execution (publish_bound_page), then reports dispatched with follow (pages.report_browser_operation), which stores the operation and sets the resource's control state to active before the input is sent.
After the actionAfter the action it reports acknowledged, or failed with the reason code, under the same operation id; a failed one does not set the control state again.
OperatedThe page shows as operated only while the execution that set it is running: the resource projection turns active back into idle once that execution has ended, as for web_use.
Marker pointA click's outcome carries the marker point: before clicking, _aim scrolls the element into view and records the centre of its bounding box, or the CSS point a click by x,y maps to, with the viewport's innerWidth and innerHeight; sanitize_operation turns that into point with the viewport size as width and height, which browser-marker-geometry maps onto the screenshot.
ReadsReads (read, console, network, wait, screenshot) report an acknowledged operation without follow, so the preview follows them and the page is not marked operated, and open reports the same for the new tab after publishing it, which makes it the tab followed.
List stepsEach step of a list reports on its own.
ReportingReporting never fails an action: errors are logged at debug level.

Workflow subprocesses

Item
DriverA forked child drops the parent's driver (os.register_at_fork), because its owner thread and connection belong to the parent, and starts its own.
Renderer callsIts renderer calls (capture_pages_for_listing, open_page, request_close_tab, request_bound_screenshot) go through the parent's webtab bridge, which confines them to the originating window, authorizes only bindings it handed out and closes the tabs the child opened when the child ends.
Operation reportsThe child holds no App connection, so its operation reports go to the worker as well: pages.forward_operations_to_parent hands each one to the child's event queue as __op_browser_operation__, and the worker reports it with report_forwarded_operation, which keeps only the operation's own fields and falls back to the execution it launched.
LocksTab locks and the write log are per process, so a child and the worker on one tab interleave at single page calls.

Access and cancellation. When the turn's surface has agent access disabled (preview_status disabled), every built-in browser action is refused with page_access_disabled. Waiting for a tab, wait, settling and each step of a list check for cancellation.

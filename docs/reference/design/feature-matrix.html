Feature matrix

160 user-callable or configurable features, in OpenProgram and 12 reference columns, for scoping future work. Each cell records what the listed version confirms. Not an implementation specification, quality ranking or marketing. Framework comparison covers mechanisms (execution, state, context, permissions); the two counts do not add up.

Design-reference sequence

Six provisional batches for design discussion, not approved plans; recheck status and estimate each before work starts. Ordered by irreversible risk, dependencies, protocol stability and definable acceptance.

BatchCandidatesMinimum acceptance
1Irreversible operations and credentials: recoverable deletion on the remaining execution pathsCovered deletions reach recoverable storage; restore paths and distributed artifacts are tested; new paths keep sandbox fail-closed; secrets stay out of ordinary config and logs; external commands have argument constraints, timeouts and redaction.
2Deterministic loop tests: default redaction for recordingsRecordings redact by default; replay never touches the network; event-order and failure differences are traceable; recording formats are versioned.
3Git workflows: diff security review, default commit, push and PR entriesAll remote writes need explicit authorization by default; dry run; uncommitted changes preserved; GitHub and GitLab adaptations tested; findings trace to the specific diff.
4External control: inbound webhooks, OpenAI-compatible endpoints, remote-control SDKAuthentication on by default; explicit tool permission, cancellation, progress and error semantics; external-client end-to-end tests pass; SDK wraps only stable protocols.
5Session operations: temporary side sessionsFirst needs persistence, cancellation, recovery and cross-interface semantics, then design approval.
6Interfaces and diagnostics: keyboard and screen-reader use first, then shortcut remapping, Vim, code-aware /init, usage insightsMajor flows work by keyboard; screen readers get semantic labels; settings persist with clear scope. Each later item needs its own scope.
Why this order
BatchReason and foundation
1Irreversible local changes and secret exposure come first. Explicit deny already precedes bypass in runtime/permissions/approval.py.
2Protocol, session and permission changes need a regression baseline. The scripted provider and openprogram recordings exist, including real agent_loop result reinsertion.
3Few dependencies, close to existing coding workflows. Local capabilities do not authorize remote writes.
4Protocol and security boundaries first, so clients do not invent conflicting behaviour. openprogram acp reuses process_user_turn and existing approval.
5Temporary side sessions change history visibility. Existing SessionStore and branching do not imply an arbitrary /side entry point.
6Accessibility is a basic requirement. Keybinding work first needs a cross-interface configuration model.
Left out of the sequenceWhy
Inline completion and chat, CodeLens, status-bar actionsNeed long-term native IDE-plugin maintenance. openprogram acp covers an IDE that only invokes OpenProgram.
Enterprise policy, silent audit reporting, credit purchases, organization-wide configurationAssume multi-user governance or commercial billing, outside the single-user local scope. Reassess if users or deployment change.

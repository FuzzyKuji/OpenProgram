Persistence

  • Actual requests, effective parameters, stop reasons, available usage and retries are distinguishable. Unknown usage stays unknown.
  • Error paths keep metadata without requiring reasoning or sensitive partial text. Paused is distinct from actively retrying.
  • Durable execution and effect records own restart and side-effect reconciliation; there is no parallel scheduler.
  • Report stages keep resolved scope, supplied materials, retrieved evidence and validated drafts. A text-only resume_task is a restart request, not a durable continuation.

Browser tool contract and Desktop registration
  • Stages expose only computer_use_agent, and accept only its browser target in the built-in browser; prompts describe tabs, read, open and the four actions a stage may take. Missing tools, login and permission failures stay explicit and never authorize another transport or a write.
  • With an origin window and no bound Page, the tabs listing keeps that origin. With no authorized origin, inventory does not fall back to all desktop windows.
  • In a subprocess, inventory goes through the parent webtab bridge, which accepts only the originating window and bindings authorized for that execution. The child's own registry mints and consumes its Page tokens; tokens do not cross registries.
  • Opening a URL through computer_use_agent and page recovery creates a background Page through Resources, with no foreground chat route, mounted Browser pane or existing page needed. Window registration and native Page target availability are separate failure stages.
  • The direct MCP entry keeps a failed browser result as ToolReturn(is_error=True); HTTP dispatch success is not browser success.
  • The Desktop bridge registers its exact window identifier on startup and reconnection, before awaiting retained-view or resource restoration, and may repeat that idempotently afterward. Pending restoration does not block a first page. Registration never selects another window or broadens ownership.
  • desktop_unavailable: the worker cannot use a registered Desktop WebTab at that moment. It differs from a model imitating a tool call and from page network or content errors.
  • Report writes need a real observed save or submit and a matching post-action observation with positive success evidence. Explicit failure or missing confirmation is an unknown, non-retryable outcome.
  • Out of scope: a second scheduler, durable checkpoints inferred from strings, browser-permission bypass, a new durable report state machine.

Model routing and group reports

  • A subscription provider keeps an explicit model id in the request body and the routing header. The Grok proxy routes by x-grok-model-override; grok-build is only the fallback for an empty id, and an alias stays an alias.
  • Native function calls run only from provider function-call events, never parsed from prose.
  • The read tool treats a null offset or limit as omitted, because strict schemas make optional fields required and nullable. Text defaults: line 1, 2000 lines. PDF defaults: page 1, 20 pages. No global null removal.
  • Group-report parsing may use prompt-based schema validation when the provider cannot express the schema. Runtime errors are execution errors, not successful BLOCKED strings. Missing member attribution asks for clarification and never invents authors. A local draft authorizes no messaging or submission.

Goals and restart recovery

Resuming a session does not mean retrying its tools: an old turn may end interrupted while its operations stay outcome_unknown, and a new turn checks actual state first. Behaviour: Goals in chat.

  • Web, TUI, ACP, background Jobs and authorized subtasks share one chat execution layer.
  • No second engine, no general scheduler, no exactly-once promise for external operations.
Goal stepWhat happens
Save the objectiveOriginal objective, completion conditions, permission scope, explicit budget
Work through chatThe agent keeps a Todo and uses existing tools and approvals
Check at turn endSettle usage; continue, wait, pause or verify
AcceptIndependent read-only turn confirms every condition; otherwise back to work

No default round cap: round count is diagnostic. create_goal, get_goal and update_goal only read and write objectives.

Automatic recovery

Run intent and shutdown
  • Durable run_intent builds on existing admission, command and restart intent. Clients are acknowledged only after the request is saved.
  • run_intent records work_id, original input and unconsumed messages, desired_state (run, paused, cancelled, done), latest control version, permission scope, objective revision, execution host, parent and child links, last committed progress and recovery policy.
  • By default, authorized work still in run resumes without reopening the session. Ordinary requests continue only until they finish. Background work keeps its authorization and concurrency quota; restart authorizes no new subtasks.
  • Closing a window or reloading only disconnects. "Quit and stop all tasks" persists a stop intent.
  • App exit, upgrades, worker crashes and machine restarts are not Pause. Graceful shutdown stops admission and saves controls and checkpoints; forced shutdown recovers from the last commit.
  • Unacknowledged client drafts are not submitted requests.
  • execution.auto_resume_window_seconds: -1 by default (no expiry), 0 opts out; existing finite deadlines are not extended.
  • Continuation rechecks directory, host, model and tool availability, credentials, permissions and budget. Missing resources show a precise waiting reason and never switch project, account or model or widen permissions.
  • Old paused records with unknown reasons stay paused with an explanation.

  • Coordination belongs to execution control. The server and JobRunner may call the same idempotent entry but decide nothing independently. UI orphan cleanup repairs only derived projections. Goal.after_terminal submits continuation only for the current version.
  • A message in the client's send queue goes first: the client reports it and the continuation yields for up to 15 seconds, during which the user turn's admission supersedes it under the Goal lock.
  • Temporary faults use durable retry times and bounded backoff, not idle model calls. Persistent faults keep pending-recovery records and show the error with Retry, Pause and End.

Choosing a recovery mode
SituationMode
Owner aliveReconnect only
Death confirmed, verifiable checkpointNew attempt under the same execution
No reliable checkpointTake exclusive recovery ownership, fill missing outputs with a stable repair key, end the old turn interrupted, admit a new turn
  • Mutually exclusive, bound to one durable decision, control version and continuation key. Checkpoints must cover committed effects and satisfy permission, wait and safe-point contracts.
  • Old executors are confirmed by lease and generation: no repairs when the lease is uncertain or storage unreadable; a dropped connection does not prove death; later writes from the old generation are rejected. Trackable live processes are reconnected, waited for or explicitly cancelled.
  • Repairs are repeatable with no side effects. Real results take priority; no usage is fabricated. Late verifiable receipts append as reconciliation events that replace placeholders in later context.
  • Only permission, budget, resource or unknown-operation issues need a person; restart alone is no reason for manual Resume. Old unknowns do not block investigation or independent work; related writes keep their restrictions, and recovery turns related to unknown writes start with trusted reads only.
  • An old effect audit may stay unresolved while its turn ends interrupted. Ordinary chat and Goals share this entry.

Permission scope for uncertain effects
  • Conversation provenance scopes old executions and invoked Jobs, not every execution in an invoked session.
  • Only the actual built-in read, grep, glob and list functions count as read-only investigation; names, acceptEdits and plugin declarations do not.
  • Within scope, everything else needs one-time approval, which bypass, automatic classification and allow rules cannot waive. Approval binds to the new call and the unknown-effect set; a changed set needs fresh approval and erases nothing. Unreadable or corrupt recovery state fails closed.
  • A new interactive owner turn in Auto or bypass evaluates uncertain effects only in its own execution subtree.
  • A nested Runtime uses that boundary only when immutable admission proves an owner chat: stored actor is the interactive owner, the integrity-checked payload has the same source, and execution, session and principal match.
  • Executor-thread submission carries the ContextVars so scope capture checks the same execution. Runtime stays non-interactive and cannot grant approval.
  • Mismatched evidence keeps the restriction. Old receipts are never resolved or replayed by this filter. Explicit ask or deny, source constraints, plan mode and exact Page binding still apply.

Goal in the transcript

  • Only an explicitly activated Goal produces UI. Starting, running, pausing and verifying add no cards; the composer shows the current Goal only.
  • At termination one compact, clickable status row stays at the ending anchor and opens the read-only historical details. Each row carries its own snapshot; a later Goal cannot replace it. Saved with Goal state under optimistic concurrency.
  • Success: animated Lucide check and "Goal achieved in 9m 42s", from active elapsed time. Missing time is not zero; interrupted time keeps its lower-bound label. Other endings show their status. Nothing is inferred from assistant text or Todo counts.
  • Canonically identified verifier messages are internal; no assessment text, evidence id or raw report enters chat.

Restart failure matrix

Work is created through public chat, Goal, Job, approval and control entries, with real termination on isolated storage. Never terminate the user's current work.

Events
Frontend reload, App exit, graceful and forced worker stop, long downtime, crash during recovery. Host restart through process-identity change; an actual OS reboot is unverified.
Interruption points
Around input acceptance, provider requests, tool dispatch, result commit, parent-child delivery, all Todos done, completion commit, usage persistence
Concurrency
Several sessions recover together: fair queueing, shared quotas, one owner, no duplicates. Pause, End, permission changes and new input win.
Live and unknown
Live children only reconnect; unknown writes only get investigation. Approvals consumed once. Late results keep identity.
Faults
Unavailable databases, broken migrations, missing credentials or directories, changed tool versions, lost projection events: explicit states and recoverable actions

Nested-scope acceptance

An old interrupted effect followed by a new owner activation through permission_decision and real nested Runtime gates: Auto and bypass, exact current and descendant uncertainty, mismatched provenance, rules, real subprocess Page access.

Semantic evaluators alone guarantee no convergence. Reliable controllers need hard budgets, evidence-based stall detection, explicit blocked, impossible and waiting categories, and waits released only by events. A tool call proves action, not progress: compare new evidence, passed gates, unfinished items and external state. Waits consume no turns.

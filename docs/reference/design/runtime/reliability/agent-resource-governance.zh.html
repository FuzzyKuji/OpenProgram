Agent 资源治理

谁能创建 Job、能跑多少、能花多少、容量怎样收回。单用户、本机、一个常驻 worker。

资源状态独立于 Job 状态（pending、queued、running、completed、cancelled、errored）。Job 可以显示已取消而名额仍在 stopping，因此只改状态的 30 秒升级不会造成超配。

不在范围内：后台会话 UI、MCP server、购买或充值、组织计费、跨机器调度。这些以后可复用 DTO、reason code、预算 scope 和 reservation 协议。

为什么有这些限制
限制是否存在原因
max_live_global否OPENPROGRAM_JOB_WORKERS（默认 4）已决定进程级 ThreadPoolExecutor，再加一项可能冲突。界面只读展示。
max_live_per_session是防止一个会话占满 worker。只计正在运行或尚未确认停止的工作。
max_queued_per_session是限制持久队列长度。
max_jobs_per_session是限制会话生命周期内成功 admission 的数量。
token、成本、运行时长、空闲时长是强制条件各不相同，见预算。
实际用量复用usage_events 是唯一记录。admission 和未结算 reservation 是执行状态，不是第二本账。

限制

限制计什么达到上限
agent.max_spawn_depth执行上下文中的代数。只有创建分支的 agent(...) 加一。拒绝新分支（quota.spawn_depth）。已有分支仍可接收工作。
agent.max_messages按路径：spawn、agent(to=...) 和 send_message 把目标设为发送方加一。自动回送沿用已完成 Job 的计数。同一轮的并行调用不共享计数。拒绝新投递并隐藏 agent。不取消任何工作。
agent.max_spawn_fanout按调用方 (session_id, turn_id) 统计新分支（creates_agent=true）。拒绝本轮更多分支（quota.spawn_fanout）。子执行完成不返还。
max_jobs_per_session目标会话（parent_session_id）成功 admission 的累计数，含新分支和已有分支。调用方来源另行记录。quota.jobs_exhausted，不可重试。
max_queued_per_session目标会话处于 preparing 或 queued 的 admission。quota.queue_full，可重试。不创建 Job。
max_live_per_session、scheduler_capacity会话与全局处于 live 或 stopping 的 claim。Job 保持排队。等待不是失败。
取值含义
协作限制 0关闭检查，计数仍传播。
资源限制 null未设置、继承。继承后仍未设置则不启用；live 例外，默认取 scheduler_capacity。
资源限制 0无效。非空值必须为正。
  • Job 的 id 就是 canonical execution_id；job_output(job_id=...) 接收这个标识。
  • agent(to=...) 不建分支但建新执行：检查消息限制并申请目标会话 admission。
  • send_message 发给空闲目标时，通过 run_agent_turn_async 创建 creates_agent=false 的 Job，消耗目标会话 admission。
  • 消息限制只约束新投递。已归属执行的 job_output、list_jobs 和取消仍可用。
  • 已注册工具是 agent、list_jobs、job_output。没有 job_stop；取消走执行控制和内部的 JobRunner.cancel_execution。

操作与消息计数：Agent 协作设计 §5。

Admission

每次创建 Job 都调用 ResourceGovernor.admit_job：同步和异步 agent()、agent(to=...) 忙目标预创建、run_agent_turn_async、WebSocket 和 API spawn、模型工具，以及任何直接的 JobRunner.spawn_job。模型工具另有进程内 fan-out 预检查。

  1. 生成 job_id、admission_id 和请求指纹。校验参数、目标和权限，不做修改。
  2. 在 run table 事务中检查深度、fan-out、队列和累计数，写入预算 scope 和 preparing admission。所有并发检查都能看到它。
  3. 持久化 canonical 执行，再在会话锁和 openprogram.host._platform.locking.flock 下把 Job 写入该会话的 jobs.json。此时不广播。
  4. 第二个事务转为 queued。此后才创建分支和绑定 Job 的 inbox 条目，并广播接纳。
  5. 失败时删除 preparing 行及其 scope，关闭 canonical 行。事务不跨 Job 存储 I/O。
  • 拒绝返回 {accepted:false, job_id:null, reason_code, retryable, effective_limits, usage, capacity}，不创建 Job、分支、绑定 Job 的 inbox 条目或接纳广播。
  • 相同 job_id 和指纹的重试是幂等读取，不增加计数。内容不同返回 quota.admission_conflict。
  • 累计或父级预算耗尽不可重试，除非 owner 提高限制或新建会话。

普通 send_message 发给忙目标时，可在消息授权和 inbox 限制（50 条待处理）内先落一条回执。它不是 Job，也不代表已接纳。之后 admission 失败时，回执标记失败并把原因告知发送方。投递时它与接纳的 Job 关联。

队列与 live 容量

  • 调度器选取会话有 live 容量且 admitted_seq 最小的任务。暂不符合的会话被跳过，其队首不会阻塞他人。
  • queued 到 live 在一个事务里释放队列名额并取得 live 名额。
  • 只有持有 worker 锁的进程可以 claim。run table 就在该进程内，函数子进程和定时运行把 JobRunner 调用转发给它。多个执行 worker 需要单独的调度设计。

父子预算

  • Job 请求可带一个只含 token、成本、运行和空闲的 limits 对象，不能超过会话限制、父级限制或父 scope 的当前余额（quota.parent_budget_exhausted）。
  • 没有显式限制时，子任务加入父级共享 scope。不预先均分，也不用 fan-out 预测工作量。
  • 每次预占都检查 Job 上限、每个祖先 scope 和会话 scope；先完成持久预占的先得。
  • 显式子预算是更严的局部上限，不预先扣减。实际预占才消耗父级。
  • 界面把 shared_remaining 标为共享实时余额，不是配额。

预算

预算计量调用前调用中和调用后无法强制时
TokenProvider 输入加输出。缓存读写单列诊断。预占输入上界加 max_output_tokens，输出上限收紧到余额。最终 usage 结算并退回差额。未结预占计入。无 tokenizer 或安全上界：quota.accounting_unavailable。
成本已知的 Provider、模型、费率和实际 token；保留 cost_source。只在价格全部已知时预占 micro-USD 上界。按实际 token 和费率结算；聚合返回 cost_known 和 unknown_cost_events。有预算时，本次或 scope 内有未知价格：quota.cost_unavailable。无预算时可运行，显示未知，绝不显示 $0。后来的价格表不改写历史。
运行时长进入 live 起的单调时间，不含排队。操作超时取其上限与剩余时间的较小者。到期设置取消，级联到子任务。error.nonpreemptible_operation。
空闲时长距上次有效活动的单调时间。记录调用起点；等待子任务时关联其活动。Provider 数据、工具进度和子任务事件算活动。传输 keepalive 不算。既无进度也无有界超时的工具属于不可抢占。
  • 受治理的 Provider 调用在访问凭证或网络前经 BudgetedRequest 预占。生产路径用 reserve_provider_request，不用单独的 reserve_tokens、reserve_cost。
  • 耗尽在请求和工具边界强制；运行和空闲由每 0.25 秒轮询的预算循环触发取消。不把执行中的操作描述为立刻结束。
  • 最长不可抢占区间取声明超时、剩余运行时长和取消宽限的最小值。达不到的进程内同步操作改用可终止的子进程，或在严格预算下被拒绝。asyncio.wait_for 返回不代表 executor 线程已结束。
记账延迟与崩溃
  • 预占状态为 reserved、started、settled，或在 Provider I/O 前 reserved、released。
  • 启动前的凭证、配置或生成器创建失败会释放。成功启动后，取消、传输错误或缺少 usage 都保留保守敞口，等同一预占延迟结算。没有首个流事件不能证明 Provider 没收到请求。
  • 绝不虚构实际 token 或成本。
  • 调用前记账不可用时，有预算的 Job 失败关闭。结算失败时 Job 报错、停止后续调用并保留预占待对账。
  • 无预算的旧路径可保留尽力记录。

各结局返还什么

事件队列名额live 名额累计Job

preparing 回滚释放未占用不增加无，或恢复一致

重启与恢复

发现处理
preparing，有匹配 Job转为 queued。
preparing，无 Job删除行和 scope。
queued回到调度器，不占 live 容量。Job 缺失或已终态：释放。
live、stopping，owner 存活不动。
live、stopping，owner 消失提升 lease_generation 加以隔离，按孤儿策略把 Job 标为错误并记 error.worker_lost，然后释放。诊断保留在 Job 输出中。
待处理的 job_finalizations写入并比对终态字段；不一致记为冲突，不释放。
  • claim 需要 owner_instance_id 和 worker 锁，通过探测真实 advisory lock 确认。写入由 lease_generation 隔离。reconcile 循环每 5 秒运行。
  • lease 证明 worker 所有权，不代表外部副作用已回滚。
  • run table 是持有配置档的进程内的内存表。每个事务向会话日志追加一行，并由日志重建。budget_scopes 使用一份全局日志。唯一键使 admission 和预占幂等。
  • jobs.json 每会话一份，存于其日志中，在会话锁和 flock 下写入。
  • 没有集群共识或远程调度。多 worker 需要 leader 选举、时钟假设和外部运行时隔离。

用户看到什么

Web、TUI、CLI 和模型工具读取同一个 JobResourceView。措辞可以不同，字段和 reason code 不变。

界面展示交互兼容
WebJob 和资源状态、队列位置、会话 live/队列/累计、四类剩余预算、成本已知或未知、原因。沿用现有 Job 卡片和取消。没有后台会话 UI 或独立 Tasks 面板。job_status 增加可选资源字段。
TUI紧凑的会话容量、所选 Job 的剩余预算、停止原因。沿用列表、详情、停止。缺失字段按旧任务显示，不当作零。
CLI表格和稳定 JSON：有效限制、用量、预占、原因、retryable。沿用查询和取消命令。新字段只增不改；状态枚举不变。
模型工具list_jobs、job_output 和执行控制返回相同原因和简化预算。拒绝是结构化工具结果，不虚构 Job 记录。保留文本结果，增加机器可读字段。

Agent resource governance

Who may create a Job, how many run, what they may spend, and how capacity comes back. Single user, local machine, one persistent worker.

Resource state is separate from Job status (pending, queued, running, completed, cancelled, errored). A Job can show cancelled while its slot is still stopping, so a 30-second escalation that only changes status cannot overallocate.

Out of scope: background-session UI, MCP server, purchases or top-ups, organization billing, multi-machine scheduling. These may later reuse the DTO, reason codes, budget scopes and reservation protocol.

Admission

Every Job creation calls ResourceGovernor.admit_job: synchronous and asynchronous agent(), send_message busy-target precreation, run_agent_turn_async, WebSocket and API spawn, model tools, and any direct JobRunner.spawn_job. The model tool also keeps a process-local fan-out precheck.

  1. Create job_id, admission_id and request fingerprint. Validate arguments, target and permissions without changes.
  2. In a run-table transaction, check depth, fan-out, queue and cumulative count, then write the budget scope and a preparing admission. Every concurrent check sees it.
  3. Persist the canonical execution, then the Job in the session's jobs.json under the session lock and openprogram.host._platform.locking.flock. No broadcast yet.
  4. In a second transaction, move to queued. Only now create the branch and Job-bound inbox entry and broadcast acceptance.
  5. On failure, delete the preparing row and its scope and close the canonical row. No transaction spans Job-store I/O.
  • A refusal returns {accepted:false, job_id:null, reason_code, retryable, effective_limits, usage, capacity} and creates no Job, branch, Job-bound inbox entry or acceptance broadcast.
  • A retry with the same job_id and fingerprint is an idempotent read and adds no count. Different content is quota.admission_conflict.
  • Exhausted cumulative or parent budgets are not retryable until the owner raises limits or a new session starts.

An ordinary send_message to a busy target may persist a receipt first, under message authorization and inbox limits (50 pending). It is not a Job and claims no admission. If admission later fails, the receipt is marked failed and the sender gets the reason. It links to the admitted Job at delivery.

Queue and live capacity

  • The dispatcher picks the lowest admitted_seq whose session has live capacity. An ineligible session is skipped, so its head cannot block others.
  • queued to live releases the queue slot and takes the live slot in one transaction.
  • Only the process holding the worker lock may claim. Run tables live in that process, and function subprocesses and scheduled runs forward JobRunner calls to it. Several execution workers would need a separate scheduling design.

Parent and child budgets

  • A Job request may carry one limits object with token, cost, runtime and idle only. It cannot exceed session limits, parent limits or the parent scope's current remainder (quota.parent_budget_exhausted).
  • Without explicit limits, children join the shared parent scope. The budget is not divided up front and fan-out does not predict work.
  • Each reservation checks the Job's ceiling, every ancestor scope and the session scope; the first durable reservation gets the capacity.
  • Explicit child budgets are stricter local ceilings and deduct nothing up front. Actual reservations consume the parent.
  • The UI labels shared_remaining as a shared live balance, never an allotment.

  • Governed provider calls reserve through BudgetedRequest before credentials or network access. Production uses reserve_provider_request, not the standalone reserve_tokens or reserve_cost.
  • Exhaustion is enforced at request and tool boundaries; a budget loop polling every 0.25 s triggers cancellation for runtime and idle. An executing operation is not described as instantly ended.
  • The longest non-preemptible interval is the least of declared timeout, remaining runtime and cancel grace. In-process synchronous work that cannot meet that moves to a terminable subprocess or is refused under strict budgets. asyncio.wait_for returning does not mean the executor thread ended.
Accounting delay and crashes
  • Reservations go reserved, started, settled, or reserved, released before provider I/O.
  • Credential, configuration or generator-creation failure before start releases. After a successful start, cancellation, transport errors or missing usage keep conservative exposure for late settlement of the same reservation. No first stream event does not prove the provider never got the request.
  • Actual tokens and cost are never invented.
  • Budgeted Jobs fail closed if accounting is inaccessible before a call. A failed settlement errors the Job, stops further calls and keeps the reservation for reconciliation.
  • Non-budgeted legacy paths may keep best-effort recording.

  • A claim needs owner_instance_id and the worker lock, checked by probing the real advisory lock. Writes are fenced by lease_generation. The reconcile loop runs every 5 seconds.
  • A lease proves worker ownership, not rollback of external side effects.
  • Run tables are in-memory tables in the process that owns the profile. Each transaction appends one line to the session's log, and tables are rebuilt from it. budget_scopes use one global log. Unique keys make admission and reservation idempotent.
  • jobs.json is one document per session, in its log, written under a per-session lock and flock.
  • No cluster consensus or remote scheduler. Multiple workers would need leader election, clock assumptions and external-runtime fencing.

Compatibility
  • Old Jobs without the new fields are legacy/unmetered. Missing is not zero, and history is not rewritten.
  • Status enum, Job ids, broadcasts and cascading cancel stay compatible. Resource state and reason are optional additions.
  • Depth, message and fan-out semantics are unchanged; they guard topology and cycles.
  • Admission rows in an older usage file move to the run tables once, keeping limits set and unfinished work; those tables are then removed.
  • Usage-event migration adds nullable columns only. Usage events stay append-only.

Feature-matrix filled-circle gate

For the row “concurrency and per-session cumulative spawn limits”. Token, cost, runtime and idle are not required; as separate rows each would need its own gate. UI, schema or a single-process semaphore alone is not enough. Current status needs item-by-item evidence.

  1. Stable configuration schema; global defaults, session overrides and effective values visible in Web, TUI and CLI.
  2. Every creation entry uses admission: no Web, synchronous, target-inbox or direct-runner bypass.
  3. Per-session live and cumulative admission are atomic under contention, without overallocation or double counts.
  4. Queue, live, cumulative and stopping follow this page.
  5. Completion, failure, cancellation, timeout, worker crash and mid-admission crash release capacity without leaks.
  6. Web, TUI and CLI show effective limits, usage, queue, live, cumulative and reason codes.
  7. Migration, concurrency and crash tests, documentation links and matrix scoring checks pass.

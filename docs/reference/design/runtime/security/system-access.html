Unified system access

A host capability boundary, separate from model tool approval, workspace permission rules, account credentials and provider authorization. A status read never opens a native prompt. A model or remote client cannot grant an operating-system capability.

Responses are no-store and hold no secrets. The first two rows keep the old screen_recording and accessibility wire shape; old receipts are read with the legacy shape. An unknown id is a client error and opens nothing. Permission rules, Auto mode, profiles, Workers and ports are unaffected.

First run and operations

  1. Web settings shows the registry by product area, why each is needed, and one read-only check per page load.
  2. The user chooses “Set up all OpenProgram access” or a row's “Request authorization” / “Open System Settings”. Page mount, reconnect, polling, history replay and model output never send a request.
  3. The backend serializes one native request per executor, using the named runtime, then checks afresh. macOS may still show separate dialogs; the UI reports each result.
  4. Before an operation, the Worker runs one fresh report and creates a durable system_access wait only for missing required capabilities. Browser and VM operations bypass this.
  5. Returning to the app triggers a read-only refresh. A grant resolves the wait through Worker reconciliation and continues the same execution from its checkpoint: no fake answer, retry or new execution.

Identity and recovery

  • macOS checks and requests run through the signed runtime bundle ai.openprogram.runtime. A source checkout may fall back to its development interpreter. An installed App never registers a bare python3; anonymous python3, node and stale cache paths are not identities.
  • Status reads, startup reconciliation, retries and duplicate events never run tccutil and never reset another application.
  • A verified stale receipt can authorize one explicit migration for the fixed OpenProgram bundle identity; a marker written before the OS call prevents loops. Everything else (unverified code, unknown checks, unchanged requirements, Accessibility migration, other applications) goes through System Settings.
  • The product cannot pre-authorize an application it never targeted, a path never selected, or a revoked permission. Full Disk Access is never inferred or requested as a workaround.
  • Linux portals and Windows integrity rules stay platform-specific. Browser and VM surfaces use their provider or session boundary.

Trust and concurrency

  • Only the local owner on the execution host can request or open settings. Loopback and Origin checks are mandatory; forwarded requests and remote clients are rejected. The model can describe a missing capability, not invoke setup.
  • Probes run in a fresh bounded process, share one report per reconciliation pass and do not enumerate screen contents.
  • Wait resolution is guarded by execution id, generation, checkpoint version and cancellation. A failed probe keeps the wait open; a terminal or cancelled execution cannot resume.

Acceptance
  • One registry is the source for report, request, settings, waits, labels and package declarations; a consistency test fails on drift.
  • Repeated reports, reconnects, replay and model output cause zero prompts. Granted rows cause zero requests.
  • A GUI task missing a desktop capability pauses before planning, resumes the same execution exactly once after both are granted, and never uses the question or approval API.
  • Unknown, unavailable and unsupported display distinctly from denied. Optional failures do not make installation or chat unhealthy.
  • Installed /Applications/OpenProgram.app confirms executor identity, current grants, settings actions and no Python or Node identity migration.
  • Automated: registry, probe and request routes, wait recovery, Web rendering, no auto-request.

Activity and control

Activity counts conversation branches. Sending another message on the same branch does not add a History item.

Conversation branchOne path through a conversation; a real fork creates anotherOne counted Activity row

How branches are counted

ExampleCountDetails
Send a message, then say "continue"1Both executions in one branch

Branch details use a short heading and an execution count; the request appears only in its execution row. Membership comes from the conversation graph and message ids, and compaction keeps earlier associations. Missing records never produce a guessed branch.

Status comes from the branch's newest execution, plus real waits, active descendants and owned processes. Declined waits read Declined and open ones Waiting for your response; declining does not run the pending operation.

During first load, reconnect or cursor resync Activity shows no error: a notice needs a confirmed request failure owned by the current conversation. Failed reads keep saved records and retry.

Two branches running at once

Each branch of a conversation has its own run slot. The selected branch keeps the conversation's slot; a message that names another recorded branch (branch_id) takes that branch's slot, so it runs while the selected branch runs.

The branch a turn runs on is fixed at admission (branch_id); whether that branch is the selected one is read when asked, against active_branch_id.

Whether a turn may touch the conversation's state at all is frozen as owns_conversation_effects, false for a turn on another branch and for a background check-in, so a turn keeps its standing across a pause, a resume and a Worker restart. A request admitted before the flag existed derives it from side_branch and background.

Switching branches

Switching is a view change. It takes no slot and is never refused because a turn, a compaction or another operation runs on the branch left or the branch entered.

PartWhat a switch does
SelectionMoves the head to the entered branch's tip (compare-and-set), then re-keys the slots: the operation of the branch left goes to that branch's own slot and is reported with branch_running_task; the entered branch's operation becomes the selected one and is reported with running_task (switch_branch)
Running turnKeeps its branch. Its user message, history and reply stay on that branch, and its end moves only that branch's record: the writes of the head and the selected branch's fields carry expected_branch_id and are skipped once another branch is selected

One foreground operation per branch

A branch's run slot holds one foreground operation at a time. Every operation has an op_id, a kind and a version a Stop raises; a load, running_task and branch_running_task report the kind, so the run bar can say "Compacting context" with a Stop, also after a reload.

KindWhat holds the slotStop
reply, retry, edit, functionA turn, from reservation to its end; after its result a request waits for the slotOn its execution, exact by version

rewindA rewind, its undo and redooperation.cancel
branchA branch delete, for a moment; not shown while it runs. A switch takes no slotNone

Branches never block each other: an operation needs only its own branch to be free, and a second one there is refused (run_active) with the kind of what runs, which the client may queue. A delete of a tail holding the tip of a branch whose turn runs is refused naming that branch.

A turn that compacts its own context mid-run stays a reply; the page shows the step while compaction_started lasts.

Only a rewind that changes files is conversation-wide:

  • While any other branch runs, or a turn waits on an approval or a question, it is refused with code: branch_running and blocking: that branch's name, its execution id and version or its op_id.
  • The rewind dialog then offers "Stop it, then rewind": it stops that run and applies the same rewind once the run has ended.
  • While it runs, a durable record holds the conversation's files. No branch is admitted, and a new execution (a scheduled run, a queued Job, a turn admitted by another process) waits for it at admission.

Each running operation is also recorded on disk (state/store/session/operations.py). After a restart the first reader marks the operations of a process that is gone as cancelled with reason_code: restart; none is resumed.

Other operations hold only the branches they touch (reserve_branches_operation, taken in sorted order), and a refusal names the busy branch:

  • Deleting messages and the turn-file history actions: every branch whose line holds the node; a common ancestor touches every branch below it.
  • An Agent switch: its own branch.
  • A scheduled run: it reads its branch's durable record before it starts and skips the run while that branch is busy.
  • Commands, skills and Agent invocations: the branch the message names. Only /clear, /rename and starting a Goal change the whole conversation and stay with the selected branch.

Rewinding beside another branch

A rewind takes back only what its own branch's turns wrote after the chosen prompt. A scheduled run on its own branch counts as another branch.

The other branch edited the same fileWhat the rewind does
Not at allRestores the file to its state at the prompt
Before this branch's first editRestores the file to what the other branch left; its edit stays
After, or between, this branch's editsLeaves the file alone. The plan is blocked with changed_since_edit before any write; Conversation only stays available.
After this branch's first edit, and a rewind on the other branch already took that edit backThe edit no longer counts; the file is restored as in the rows above

A sub-agent's turn records in the point of the turn that spawned it. A turn the runtime started records in the nearest earlier prompt on its branch. Such a turn may first edit a file after a later prompt's turn did; a rewind past both returns the file to the state from before either. Rules for one file: File management.

Claude Code's rewind returns each tracked file to its checkpoint state, later Bash changes to it included. Codex has removed its undo; its thread/rollback drops turns from the context and leaves files as they are. Neither describes a check for a later edit by another session, so here such a file is left alone and named.

Claude Code and Codex branch by copying: a fork gets a new session or thread id and runs as its own conversation. Neither publishes a rule for two concurrent turns inside one session or thread; Claude Code bug reports describe concurrent resumes of one session writing interleaved branches without a lock.

Why this design

TopicWhy
Stopped replyThe model should see what the person saw: after a stop people say "continue" or "change that line", and dropping the cut text (Codex, Pi) makes the model start over. Finished calls are valid signed history. Anthropic refuses unsigned reasoning, so only the cut call's reasoning is left out.
Call resultsA call without a result makes the provider refuse the request. The elapsed time and the "not run" case let the model judge whether to run it again; a per-tool side-effect table (Hermes) costs upkeep the cut-call sentence already covers.
Note placementText in the assistant's place gets repeated by the model (Hermes found this), so the note rides on the user's turn block, by the same mechanism as the rewind note. Writing it at stop time keeps the cached prefix stable.
Stop keyCodex and Claude Code stop on the first press; a hint first reads as no response, and the second press then hit the exit flow. One line per stop is enough, but the resend stays because a first signal can be lost.
SignalEvery peer is event-driven; two polls cost a median of about 160 ms and a thread per turn. The Event stays plain because request options holding it are deep-copied.
Background agentsThe person asked for them to keep running. Without the notice the model waits for a result that never comes.
Queued messagesCodex and Pi put the queue back in the input because theirs cannot be edited; here queued messages are visible and editable above the input, as in Claude Code.
Stop before any replyA rewind is something the person does; taking the message back on a Stop would make one button do two things.
WindowsWindows has no SIGTERM; scripts send Ctrl-Break, and a closed console allows about 5 s before the process is killed with its execution left running.

Restart mechanics
  • Provider decisions and completed tool actions publish their checkpoint and effect receipt atomically during ordinary execution. The original execution id, immutable inputs, permissions, budgets and continuation commands stay authoritative; queued Jobs use the resource queue.
  • Restart intents are canonical execution events stored with the transition, and fixed command identities make repeated startup idempotent. There is no second database, scheduler, process owner or permission path.
  • Resume ownership records the exact inherited checkpoint; a second interruption before a new effect keeps it.
  • New Jobs own stable user and assistant message ids at admission. Pause completion releases resources by the attempt and lease identities the Job waiter retained.
  • Startup classifies abandoned ownership before the runner applies this policy. Provider-only or never-activated chat admissions can continue from immutable input inside the original activity deadline.

Who owns run state

Run state is folded from each session's log into in-memory tables; no database file exists. See Session storage. The process holding worker.lock owns the runs it starts. A function subprocess reads the tables and hands changes to its parent.

A scheduled task's turn, and a turn in a stand-alone ACP or MCP process, belongs to that process, which writes that turn's rows to its own log. A sub-agent a scheduled task starts is admitted and run by the Worker, the only process that can claim a queued Job.

Workflow questions

  • A question from a running Python Workflow waits in its current process, bound to the exact execution, attempt and generation. It uses the canonical wait store and question UI, and neither checkpoints the Workflow nor restarts its call stack.
  • The answer returns to the original call. A browser refresh reloads the pending request.
  • Only the live current owner may create or answer one. Cancellation, execution end or loss of the process owner invalidates it. Worker restart does not replay the Workflow.
  • The subprocess publishes through the existing queue bridge. Unexpected errors propagate rather than become an unanswered result. Agent tool questions with declared pre-wait checkpoints keep durable continuation.

A mark outlives a Worker restart and lapses after ten minutes.
Model errors and tool outcomesKnown model errors and aborts get response records. Unknown tool outcomes stay unresolved; the History label does not clear them.
ForksForks validate the saved point, immutable revision and permission. Program, model or tool contract changes keep their independent review.
JobsFor Jobs, job_id equals execution_id. Resource allocation stays separate from execution state.
Project locationThe current stored project location is read before loading a session. Reads and controls are restricted to the authorized conversation. Reconnect uses saved versions and event positions and creates no duplicate task.
Managed processesManaged processes keep identity, ownership and bounded output. Restart recovery checks the supervisor; a saved PID alone is not permission to send a signal.

Not yet for a turn on another branch:

  • The web pane: it shows and sends to the selected branch only.
  • Steer and queued page messages: they reach the selected branch's turn.
  • Continue after a pause or a Worker restart: the resumed turn's context is not yet proven to read its own branch.
  • Edit and retry while the selected branch's own turn runs: they wait, because the new branch would take the selected branch's slot.
  • Scheduled runs: their process does not take the server's branch slot; a message is refused while a run is open on that branch, not the other way round.

Not yet for branch settings and branch state:

  • Merge holds the selected branch's slot, not its source and target.
  • The menus' first item "Agent default (current: …)" and a badge beside the composer for runs on other branches: the data is sent (inherited, wait_state); the controls wait on an approved design.
  • An entry that names no branch (a channel) continues on the selected branch; the branch written last is recorded (last_branch_id) and not yet used.
  • Running the follow-the-Agent migration on real conversations.
  • Run state read only from the execution store: the slot table is still the live record of reservations and executionless operations, with the execution store consulted for paused and scheduled turns.
  • One branch record: names, turn counts and archive state still live in meta.branches, keyed by tip, beside branch_refs. Moving them needs a record for every tip a client names by message id (spawned branches, tips recorded before branch records existed) and a migration of the readers that key by tip.
  • Stopping a rewind from the terminal UI: its stop key reaches turns and /compact.

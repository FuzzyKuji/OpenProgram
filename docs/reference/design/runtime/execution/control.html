Activity and control

Activity counts conversation branches. Sending another message on the same branch does not add a History item.

ObjectMeaningAppears
Conversation branchOne path through a conversation; a real fork creates anotherOne counted Activity row
ExecutionOne task run, such as producing a replyIn branch details; its id is the exact control target
Managed processA command started by a toolUnder its execution, with its own output and stop control

How branches are counted

ExampleCountDetails
Send a message, then say "continue"1Both executions in one branch
Create an alternative reply from an earlier point2One row each
A later execution on the same branch fails1Kept in details
Two branches share earlier messages2Shared executions may appear in both details and add no rows

Branch details use a short heading and an execution count; the request appears only in its execution row. Membership comes from the conversation graph and message ids, and compaction keeps earlier associations. Missing records never produce a guessed branch.

Status comes from the branch's newest execution, plus real waits, active descendants and owned processes. Declined waits read Declined and open ones Waiting for your response; declining does not run the pending operation.

During first load, reconnect or cursor resync Activity shows no error: a notice needs a confirmed request failure owned by the current conversation. Failed reads keep saved records and retry.

What each control does

ControlResultBoundary
PauseStop at the next safe pointThe current action may finish; no arbitrary line is frozen
ContinueResume the same execution from saved progressOnly when saved state and capability permit
StepRun one declared step, then pauseA tool action or declared boundary, not a source line
SteerAdd instructions for work not yet runCompleted work is unchanged
CancelEnd the execution and its execution descendantsCannot undo completed external actions; a managed process has its own control
Fork / RetryCreate an independent child from an allowed saved pointOriginal history stays. Agent chat children start paused and need Continue; others follow their scheduler.

The UI offers only controls that execution supports. "Accepted" means saved; "applied" means it took effect. Command completion is idempotent when terminal reconciliation wins the race: after a compare-and-swap conflict the service accepts only an already applied command for the same execution and result version, keeps the stored receipt and propagates other conflicts.

Restart mechanics
  • Provider decisions and completed tool actions publish their checkpoint and effect receipt atomically during ordinary execution. The original execution id, immutable inputs, permissions, budgets and continuation commands stay authoritative; queued Jobs use the resource queue.
  • Restart intents are canonical execution events stored with the transition, and fixed command identities make repeated startup idempotent. There is no second database, scheduler, process owner or permission path.
  • Resume ownership records the exact inherited checkpoint; a second interruption before a new effect keeps it.
  • New Jobs own stable user and assistant message ids at admission. Pause completion releases resources by the attempt and lease identities the Job waiter retained.
  • Startup classifies abandoned ownership before the runner applies this policy. Provider-only or never-activated chat admissions can continue from immutable input inside the original activity deadline.

Continue keeps the call cursor and reuses committed steps. Crash recovery uses the last durable boundary and fences the former owner. Function subprocess startup holds no history-wide write transaction, and sequence backfill belongs only to the migration that adds the column. Standalone function progress frames address the existing code node, and completion releases foreground occupancy before optional session naming.

Who owns run state

Run state is folded from each session's log into in-memory tables; no database file exists. See Session storage. The process holding worker.lock owns the runs it starts. A function subprocess reads the tables and hands changes to its parent.

A scheduled task's turn, and a turn in a stand-alone ACP or MCP process, belongs to that process, which writes that turn's rows to its own log. A sub-agent a scheduled task starts is admitted and run by the Worker, the only process that can claim a queued Job.

Attempts and fencing

CaseRule
OwnerAn activated execution has one current attempt, owned by the worker.lock holder, with no heartbeat
Turn run in another processIts owner lease records that process's id and start time
Process exits, lock releasedA new Worker that takes the lock may close attempts the logs show as open, unless the recorded process is still running; it then reads how that turn ended once the process exits

Log recorded a turn's ending, a later line left it unfinishedStartup restores the recorded ending
Every owner write (tool result, safe point, wait, steering delivery, finish)Verifies inside its transaction that the attempt has not ended, its generation is current and the execution still names it. An owner that fails this check stops.

An attempt that fails keeps its readable error on the attempt row, with credential-shaped values scrubbed and at most 4000 characters. It stays out of snapshots and event payloads; only Activity's per-run events read it. An attempt closed by owner loss has no such text, and older rows read as none.

Workflow questions

  • A question from a running Python Workflow waits in its current process, bound to the exact execution, attempt and generation. It uses the canonical wait store and question UI, and neither checkpoints the Workflow nor restarts its call stack.
  • The answer returns to the original call. A browser refresh reloads the pending request.
  • Only the live current owner may create or answer one. Cancellation, execution end or loss of the process owner invalidates it. Worker restart does not replay the Workflow.
  • The subprocess publishes through the existing queue bridge. Unexpected errors propagate rather than become an unanswered result. Agent tool questions with declared pre-wait checkpoints keep durable continuation.

Identifiers and safety rules
session_idConversation scope and authorization; never a control target
run_idGroups related original, fork and retry executions
execution_idExact control target. Pause and Continue keep it; a fork or retry creates another.
attempt_idOne activation of a worker
revision_idImmutable version of the program and its contract
command_id + expected_versionPrevent duplicate actions and reject stale commands
  • All transports use one command service, which saves the command before the owner applies it. UI state does not authorize an operation.
  • Cancellation takes precedence over pause, step, continue and steering. Only the current owner publishes progress or a final state.
  • Known model errors and aborts get response records. Unknown tool outcomes stay unresolved; the History label does not clear them.
  • Forks validate the saved point, immutable revision and permission. Program, model or tool contract changes keep their independent review.
  • For Jobs, job_id equals execution_id. Resource allocation stays separate from execution state.
  • The current stored project location is read before loading a session. Reads and controls are restricted to the authorized conversation. Reconnect uses saved versions and event positions and creates no duplicate task.
  • Managed processes keep identity, ownership and bounded output. Restart recovery checks the supervisor; a saved PID alone is not permission to send a signal.

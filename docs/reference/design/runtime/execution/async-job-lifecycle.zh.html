后台 Job 生命周期

每个派生的子 Agent 都是 openprogram/runtime/jobs/ 中的 Job，job_id 等于 execution_id。控制走执行控制面；Job 增加的是准入、worker 池和结果投递。

终态不再变化，非法转换抛 ValueError。规范执行不镜像 running 转换，因此投影也可能 pending → running、queued → completed。

入口
agent(prompt, description, agent?, start_from="fresh", run_in_background=False, isolation?)模型工具。前台返回结果块；后台返回执行 id。send_message 以 Job 投递给已有 Agent。
read_conversation(execution_id)模型工具。不等待，返回 Job 的状态，结束后还返回回复。job_output(job_id, block, timeout) 仍为程序注册，对模型隐藏。
list_agents()模型工具。在分支旁列出当前会话运行中或排队的 Job，最新在前，最多 20 个。list_jobs() 对模型隐藏。
/task, /task --async, /spawn在聊天中输入。阻塞，或写入运行中占位后返回。
spawn_job, list_jobs, get_job (WS)创建和读取。回复：spawn_job_result、jobs_list、job。list_jobs 不带 session_id 表示所有会话。
execution.cancel (WS)取消；Job 动作不另设取消

客户端跟随 job_status 广播。分支视图显示 Job 状态，没有单独的 Tasks 面板。

场景

情形运行时结果如何返回停止和失败
单个前台调用调用方阻塞；attach 卡直接到最终状态回复作为工具结果停止会话会取消子 Agent 和父轮次；返回部分输出
单个后台调用调用方继续；显示运行中卡片以统一结果形状的通知轮次告知；read_conversation 可提前读取从界面取消或 close_agent；用户停止会告知调用方
多个后台调用按池宽运行，其余 queued，先进先出各自返回；一轮内同时结束的合并为一条通知各有状态和错误；父 Agent 自行处理部分结果
长任务被取消占用槽位直到 worker 退出部分输出30 秒后升级

Worker 池
池ThreadPoolExecutor，与聊天运行相同的线程模型。process_user_turn 自己开事件循环，不会嵌套冲突。
宽度OPENPROGRAM_JOB_WORKERS，默认 8
准入资源治理负责准入和限制，见资源分配
每会话限制无

持久化和恢复
存储每会话一个 jobs.json，{"jobs": {id: Job}, "version": 1}；每次写入是会话日志中的一行
加锁每会话一把锁：读、改、写
worker 丢失没有当前 attempt 或已接受命令的非终态 Job 变为 errored，worker died before completion。有规范 attempt 的按重启恢复处理。
通知待发通知在 <caller-session-dir>/notices.json，重启不丢；入队前崩溃的情况见跨崩溃的交接

跨崩溃的交接

一个子 agent 请求在父 agent 和运行之间经过三次交接。每次交接先写下要做的事再动手，下一步是幂等的，Worker 的资源对账（启动时和每 5 秒）把死掉的进程留下的半截做完。共用部分在 openprogram/runtime/jobs/handoff.py。

inbox 排空：已发布，条目未删除准入行记录 Job 已离开延迟状态再次投递已发布的 Job 直接返回它的 id排空时删掉残留条目；Job 只运行一次
spawn 已 held 准入，attach 卡或发布未完成Job.submitter 记下提交它的进程；attach_pointer_id 记下卡片卡片节点不存在时才写提交方进程不在后，补写缺失的卡片并发布 Job

agent 调用中途被切断的父轮次，会把这次调用读作“已中断、结果未知”（重启恢复）；attach 卡和之后的通知告诉它这个请求的去向。提交方仍在运行（本进程或别的进程）的 held Job 交给它自己处理。

为什么这样设计

主题原因
先写意图再动手Exo 的 beginTurn 在执行器动手前先持久接受输入；Maka 在工具运行前提交 dispatch（T1），在发布结果前提交 outcome（T2）。两者都让记录做权威、动作只是结果。这里的那份记录就是 Job：下一步需要的东西都随它保存，恢复读一行即可，不用猜。
按 Job id 幂等Maka 的图调度预分配运行身份，已有运行就观察它而不是再启动一次；Codex 在子线程存在之前先发布 spawn 边。按 Job id 做的重放可以在每次对账时运行，而不会多出 inbox 条目、卡片、运行或通知，所以恢复不需要额外状态来记住自己做过没有。
提交方是否还活着held spawn 和同步等待的结果在提交方进程活着时归它所有；只有它死了才交给恢复。进程身份是 pid 加启动令牌，和执行租约已有的记录相同，复用的 pid 不会被当成原来的等待方。
等待方死后的结果Claude Code 和 Codex 的前台子 agent 结果随进程丢失；Maka 会重投 supervisor 唤醒，直到根运行完成。用后台 agent 已有的通知告诉父 agent，不新增机制，工作也不会丢或重做。
运行请求而不是取消请求已带着预算准入；丢掉它会让模型去猜，而被中断的调用已经提示结果未知。运行一次再报告，正是父 agent 要的结果。

取消

  1. JobRunner.cancel_execution 持久化一条 execution.cancel 命令，并级联到子 Job。
  2. 所属 worker 消费命令并设置 cancel_event，process_user_turn 把它桥接进 Agent 循环；provider 流在下一个分块停止。
  3. 活跃子进程和 exec 运行时按确切执行 id 收到信号。Agent 方法在调用前钩子处检查。
  4. _CANCEL_ESCALATION_SECS（30 秒）后 owner 的宽限结束。

工具自身的原子操作会先完成。已取消或出错的 Job 不能作为同一工作继续；重试就是新的派生。

会话和 attach 卡

  • Job 只在一个会话中运行，即 parent_session_id，且不变。其他会话的调用方记为 caller_session_id，并有链接镜像用于可见性和所有权校验。
  • 输出落为该会话的分支；context="clean" 时是新的根。
  • attach 节点（function="attach"）在准入后写入，状态 running，带 job_id。runner 在终态更新同一节点。跨会话卡片存于来源会话并指明目标。
  • 上下文渲染跳过运行中的卡片。完成的卡片变成一条子 Agent 报告，含任务、最终回复和转录地址。

取消事件等运行时对象放在 runner 的映射里，不进记录。JobRunner 可注入 governor 和 driver 工厂，因此状态机可脱离真实模型运行。

不变量

  • 每个 Job 恰好以一个终态结束。
  • 状态只前进。
  • attach 卡随记录变化。
  • parent_session_id 不可变。
  • runner 的映射由锁保护。

范围之外

方面不提供

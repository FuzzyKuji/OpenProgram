Agent 工作树

Agent 在隔离目录中修改用户的真实仓库，底层是 git worktree add 和 remove。一个工作树属于一条会话分支，或一次子代理运行；其他分支仍在工作目录里工作。

工具

工具参数效果
worktree_createsource_repo、branch_name、base_ref = HEAD、label、pr创建并绑定为本轮所在分支的活动工作树
worktree_mergeworktree_id、strategy = ff-only（或 squash、no-ff、auto）、delete_branch = false合并到 source_repo，删除目录，保留分支
worktree_discardworktree_id、force = false、delete_branch = true不合并直接移除，记录保留
worktree_keepworktree_id解除绑定，目录和分支留给用户
worktree_liststatus_filter、scope = session列出记录
agentisolation = "worktree"派生的子代理在自己的工作树中运行（见分支与子代理）

其中只有丢弃需要审批。工具返回一行文本，或 [tool error] code: detail。WebSocket 提供 session_worktrees、create_branch_worktree、list、get、merge、discard、keep（ws_actions/worktree.py）。没有切换工具：每条分支一个活动工作树，更多只能通过子代理和 Job。

状态

从事件到磁盘
active开始合并（运行 git merge，阻止并发合并）committing不变
committing成功merged删除目录，默认保留分支
committingmerge_conflict、not_fast_forward、merge_failedactive，带 error保留目录供检查；冲突的合并会在 source_repo 中中止，工作目录不会停在合并中途
active、errored丢弃discarded删除目录，默认删除分支
active、errored保留kept不动，由用户接手
active、committing预留：状态机允许，当前没有路径写入errored不变，可回到 active

merged、discarded、kept 是终态。非法转换会抛错。工作区不干净时合并和丢弃都拒绝并报 worktree_dirty，除非丢弃带 force，或合并带 commit_pending（先提交工作树里的全部内容）。Agent 的工具从不设 commit_pending；合并按钮会设，因为用户要合并的就是工作树里现有的内容。丢弃没有备份。

合并Git适用
ff-onlymerge --ff-only默认，否则 not_fast_forward
squashmerge --squash，再做一次通用提交探索性小提交很多时
no-ff总是创建合并提交保留历史
autosource_repo 的 HEAD 是分支祖先时用 ff-only，否则 no-ff合并按钮：分支工作期间工作目录可能已有新提交

工具在哪里运行

上下文变量 _current_worktree_path（state/worktree/context.py）携带路径，工具没有 cwd 参数。worktree_create 为本轮余下部分绑定。每轮按顺序绑定第一个存在的（turn_context.py、runtime_location_for）：

  1. 本轮所属 Job 的工作树。
  2. 本轮所在分支的工作树（req.branch_id；没有时用选中的分支，store.current_branch_for）。
  3. 整个会话共用的工作树。
  4. 项目目录。
工具行为
bash每次在新子进程中从工作树开始。cd .. 可以离开：这是默认位置，不是沙箱。硬隔离用 docker 后端
read、write、edit、list、apply_patch（path_resolve.py）相对路径按工作树解析。工作树外的绝对路径得到 [outside worktree] 警告，不阻止
glob、grep不传 path 时搜索工作树；相对路径在工作树内解析（resolve_root）
分发时的路径检查（_host/execution.py）读写路径先锚定到工作树再做沙箱检查，检查的就是工具要打开的文件
terminal_useworkdir 相对于工作树
Runtime 子进程（--cd）优先使用工作树，其次会话工作目录
系统提示（environment_block）写明工作树、它的源工作目录和分支，并说明之前的路径按相对路径对应这里的同一文件，编辑前先重新读取
为什么这样设计
主题原因
所有工具读同一个绑定Claude Code 的工具都读 EnterWorktreeTool 移动后的会话 cwd，没有工具带目录参数。之前 glob 和 grep 搜默认工作目录，list 和 apply_patch 拒绝相对路径，分支在工作树里写了文件却找不回来
重新读取提示沿用 Claude Code 的 buildWorktreeNotice：继承的上下文指向工作目录里的文件，而从提交创建的工作树没有工作目录里未提交的修改

分支与子代理

谁怎么开始怎么结束
一条会话分支输入框的 worktree 标签选“独立 worktree”（create_branch_worktree），或在该分支上调用 worktree_create。分支的下一轮在那里运行在标签上合并、压成一个提交、保留为 git 分支或丢弃；也可由 Agent 自己的合并、丢弃工具完成
一个子代理agent(isolation="worktree")：从调用方本轮所在目录的仓库创建工作树，带 parent_job、调用方分支和 ephemeral没有改动：运行结束时删除（同步结果，或 Job 的终态投影）。有改动：结果里写明工作树，供 worktree_merge 使用；标签在“子代理的 worktree”下列出它

从隔离分支经编辑、重试或 fork 产生的新分支从工作目录开始：一个工作树只服务一条分支，并行的两条分支不会共用工作区。在工作树里运行的分支派生的子代理，从这个工作树再建工作树，并合并回它。Job 取消时仍以 force 丢弃其工作树。

为什么这样设计
主题原因
可选，按分支或子代理沿用 Claude Code：默认在工作目录，隔离按代理选择（isolation: "worktree"），未改动的工作树在代理结束时删除。这里按分支划分，因为分支并行运行。工具能写入的后台子代理在 git 仓库里默认得到一个，因为两个写入者共用一个文件夹会互相破坏修改；前台或只读的子代理共用工作目录（Agent 设置）
从下一轮开始生效Codex 的 --worktree 只用于新会话或 fork，不用于恢复的会话。分支就是 fork，所以工作树从它的下一轮开始生效，不在运行中途切换
git 分支而不是补丁Maka 为每个子会话租用工作树，结束时交回补丁产物；补丁丢掉了提交，还要单独应用。由 git 合并的 git 分支两者都保留
从提交开始Grok Build 把工作目录里未提交的文件复制进新工作树。把半成品复制进并行分支会让两边合并都冲突，所以工作树从提交开始，由本轮重新读取

在应用里

位置内容
输入框的环境行（worktree-chip.tsx）环境标签旁的一个标签：工作目录，或工作树的分支及改动文件数。菜单可选工作目录或独立 worktree；工作树打开时提供合并到工作目录、压成一个提交合并、保留为 git 分支和丢弃。丢弃会弹出确认框。会话目录在 git 仓库里，或分支有打开的工作树时才显示。分支运行时合并、保留和丢弃要等它停下
对话记录（worktree-branch-marker.tsx）分支顶部一行：在哪里运行、改了几个文件，或工作树已合并、保留、丢弃
Activity（running-panel.tsx）分支代理行上的 Worktree 标记，状态行上的改动文件数

三处读同一份会话工作树（lib/worktrees/session-worktrees.ts），每次 worktree_status 广播后重新读取。

为什么这样设计
主题原因
放在输入框Codex 把本地 / 工作树的选择放在决定下一轮在哪运行的地方。标签沿用环境标签的控件和菜单，不另做面板
合并放在同一个标签标签写着工作树的名字，操作就放在那里。只有丢弃会先确认：它会删除工作
标记在分支上对话记录里的这一行沿用子代理分支横幅的样式，分支在哪里被阅读都能看到它在哪运行

选择仓库

  1. source_repo 参数。
  2. 会话的默认工作目录（选中的 Project）。
  3. 从 worker 的 cwd 运行 git rev-parse --show-toplevel。

都找不到：source_repo_not_resolved。OpenProgram 不会替用户 git init。源仓库有未提交修改也没关系：工作树从 base_ref 创建。函数表单只含参数，Project 仍是源。

隔离与提交

  • source_repo 和工作树都不能位于会话存储 <state>/projects 下：worktree_in_sessions_dir。
  • 丢弃不影响 source_repo 的 HEAD 和工作区。
  • kept 的分支绝不删除。
  • Agent 通过 bash 提交，提交信息由它决定。只有用户点合并时，才用通用提交信息提交未提交的内容。
  • 文件差异归 git 管，工具结果照常进入上下文。

Job 与会话

场景流程结果
一次修改创建、编辑、测试、提交、合并merged
失败的尝试创建、丢弃（force）、创建、合并一个 discarded，一个 merged；每条分支同时只有一个活动
计划 Agent，三个 Job每个 Job 一个工作树；计划 Agent 自己不激活，列出后合并其一其余丢弃；若 HEAD 已移动，之后的合并可能需要换策略
用户接手worktree_keep；之后的轮次回到源仓库kept

Job 取消时以 force=True 丢弃其工作树（jobs/runner/projection.py）；其他方式结束时，没有内容的 ephemeral 工作树会被删除。Job 完成不会自动合并。轻量 Job 不需要工作树。工作树工具是同步 git 调用，并发创建由 git 自身的锁串行化。

从 Pull Request 打开

pr 接受 123、#123 或 GitHub PR URL（state/worktree/pr_ref.py），并忽略 branch_name 和 base_ref。

  1. gh pr view <n> --json headRefName,headRepositoryOwner,isCrossRepository。
  2. 获取：同仓库 git fetch origin <headRefName>:<ref>；fork 用 git fetch origin pull/<n>/head:<ref>，无需注册远端。
  3. 在分支 op/wt/pr-<n>-<id6> 上普通 git worktree add，临时引用随后删除。

.worktreeinclude

git worktree add 只检出已跟踪文件，.env 和本地覆盖配置会缺失。source_repo/.worktreeinclude 中的模式指定要复制的未跟踪文件，在 add 之后由 create_worktree 执行（include_sync.py），这是所有创建路径的唯一交汇点。

模式含义
#…、空行忽略
*、?、[...]通配
不含 /任意位置的文件名
含 /锚定到仓库根
结尾 /目录及其内容
!、**不支持
复制语义
  • 候选：git ls-files --others，不带 --exclude-standard，所以被忽略的文件也在内。
  • 目标已存在则不动。符号链接保持为链接。权限保留（shutil.copy2）。
  • 单个失败不影响其余；两份列表写入记录和工具返回值。
  • 没有该文件：不调用 git。
  • 匹配用 fnmatch 和 pathlib：git 没有包含过滤的底层命令，这里拒绝注入 core.excludesFile，pathspec 也不是基础依赖。

错误

代码发生了什么，怎么办
not_a_git_repo不是仓库；先 git init
source_repo_not_resolved传绝对路径或设置工作目录
already_active先合并、丢弃或保留当前活动的
worktree_dirty提交或暂存，或用 force 丢弃
not_fast_forwardrebase 或换策略
merge_conflict、merge_failed在工作树中用 edit 和 bash 解决后重试
worktree_in_sessions_dir选择会话存储之外的仓库
worktree_exists路径或分支已占用；换 label 或 branch_name
invalid_branch_name、invalid_base_ref为空、含 NUL 或以 - 开头
pr_ref_errorpr 无法解析；gh_not_found、gh_not_authenticated 或 gh 失败。绝不回退到 base_ref
pr_worktree_exists指出此 PR 已打开的工作树

base_ref 不存在时透传 git 的 stderr。

不在范围内

远程推送（用 bash）、工作树间 cherry-pick 或 rebase、冲突解决 UI、跨仓库工作树、丢弃前备份、chroot 或命名空间沙箱。

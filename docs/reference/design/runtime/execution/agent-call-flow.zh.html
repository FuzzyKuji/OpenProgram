一次 exec 就是一个 llm 节点：进入时 running，退出时写回复和 completed。内部的工具轮次不产生额外节点，所以每两个嵌套 code 节点之间都有 llm 节点。exec 位于循环之下，函数体才能调用模型；这也是自递归的来源。

提示词构建后，_call_id 切到 llm 节点（test_tool_loop_subcall_attributes_to_llm_node）。同步和异步路径一致。agent_loop 不知道 DAG。tool.before 只在 _execute_tool_calls 触发，任何路径都不丢失或重复事件。

为什么有两个入口

两边的外围互不重叠：一边是会话管理、WebSocket 广播、标题和压缩，另一边是 llm 节点和 AgentSession 重试。让 dispatcher 走 exec 有四个问题：

冲突说明
模型dispatcher 的 _resolve_model(agent_profile, req.model_override) 与挂接 Runtime 自动检测的 api_model 不同
上下文上下文引擎的 prep.agent_messages 与 exec 从 DAG 渲染相冲突
流式exec 的扁平 on_stream 字典与 dispatcher 的 WebUI 信封不同
重复节点dispatcher 的回复本身就是记录；再加 llm 节点会得到 [user, assistant, assistant]（test_dispatcher_integration.py::test_real_loop_text_only）

循环驱动器 LoopDriver 位于 exec 之下（exec → AgentSession → LoopDriver → agent_loop），只在一处构造，不是并行路径。

Callable 路径

Runtime(call=fn) 把 fn 包成替身 provider 模型（callable_model.py），像其他模型一样走 _call_via_providers，没有旧分支。适配器把消息转回 content，带 response_format 调用 fn，返回一条 assistant 消息，没有工具和工具循环。stream_fn 从 exec 经上下文变量传到 AgentSession（test_exec_stream_fn_injection）。

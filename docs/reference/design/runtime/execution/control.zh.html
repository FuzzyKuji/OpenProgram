活动与控制

Activity 统计会话分支。在同一分支上再发消息不会增加 History 条目。

对象含义位置
会话分支会话中的一条路径；真正分叉才产生另一条一行计数的 Activity
执行一次任务运行，例如生成一条回复在分支详情中；其 id 是确切控制目标
托管进程工具启动的命令挂在其执行下，有自己的输出和停止控制

分支如何计数

示例计数详情
发消息，再说“继续”1两次执行在同一分支
从较早位置创建另一回复2各一行
同一分支后续执行失败1保留在详情中
两个分支共享较早消息2共享的执行可出现在两边详情，不加行

分支详情用短标题和执行计数；请求只出现在执行行。归属来自会话图和消息 id，压缩保留较早的关联。缺失的记录不会被猜成新分支。

显示哪种状态

情况分区含义
审批、问题、暂停或未解决的工具结果Needs attention新消息不会消除它
执行、子任务或所属进程在运行In progressAgent 回复结束不代表后台进程停止
已结束，无活动或待处理History失败和输出保留在详情
owner 已结束，只缺模型响应记录，无活动等待或非取消控制History显示“已结束 · 响应记录不完整”。旧的 Cancel 不使其可操作；只有子任务仍活动时才提供 Cancel。不表示成功。

状态取分支最新执行，并检查真实等待、活动后代和所属进程。已拒绝的等待显示 Declined，未决的显示 Waiting for your response；拒绝不会执行待处理操作。

首次加载、重连或游标重新同步时 Activity 不显示错误：只有当前会话已确认的请求失败才提示。读取失败时保留已保存记录并重试。

两个分支同时运行

会话的每个分支有自己的运行槽。选中的分支沿用会话的槽；消息指名另一个已记录的分支（branch_id）时占用那个分支的槽，所以它能在选中分支运行时一起运行。

方面选中分支上的轮次其他分支上的轮次
槽会话的槽，按会话区分它所在分支的槽，按会话和分支区分；该分支有任何未结束的执行（包括定时运行）时拒绝
写入移动 head 和选中分支写在该分支末端下，只移动该分支的记录；head、选中状态和内存镜像不动
模型输入选中分支自己分支的历史和设置（Agent、模型、权限）
会话状态状态、未读点、模型、token 数、标题、频道回复都不改；仍是选中分支的
分支状态每一轮超出预算时压缩自己的链（摘要落在这条链上，head 不动），并把最后一次请求的占用记在自己的分支记录上（last_prompt_tokens）；会话上的数字是选中分支的。后台签到两样都不做：它只读有界的尾部。
运行状态running_task、run_active、run_task：含义不变branch_running_task 及其清除帧，带 branch_id；该轮的每个帧都标明分支
停止对一个执行的精确命令，只释放那一轮的槽
回退点每条 prompt 一个，不分分支。文件在某一轮第一次改它之前的状态，记在这一轮自己的回退点里，不记在最新的那个里。

一轮运行在哪条分支上，在准入时定下（branch_id）；那条分支是不是选中分支，在读的时候对照 active_branch_id 判断。

一轮能否改会话状态，在准入时冻结为 owns_conversation_effects：其他分支上的轮次和后台签到为 false，所以暂停、恢复和 Worker 重启后归属都不变。这个标志出现之前准入的请求，由 side_branch 和 background 推出。

切换分支

切换只是换个视图。它不占槽，也从不因为离开或进入的分支上有轮次、压缩或其他操作在运行而被拒绝。

部分切换做什么
选中把 head 移到进入分支的末端（比较后设置），再给槽换键：离开分支的操作移到那条分支自己的槽，用 branch_running_task 报告；进入分支的操作成为选中分支的操作，用 running_task 报告（switch_branch）
运行中的轮次留在自己的分支上。它的用户消息、历史和回复都在那条分支上，结束时只移动那条分支的记录：写 head 和选中分支字段时带 expected_branch_id，选中别的分支后就跳过
网页和终端界面只画选中分支，也只为它保留运行状态。一轮的每一帧都写明分支，其他分支的帧不画。切换的回复写明进入的分支，加载时交出那条分支正在运行的轮次，所以重新加载后停止键仍能停它
分支记录切回去时按末端找到这条分支的记录；记录的末端落后于它那条线时，取那条线上最近的记录（record_on_line）。旧数据不用迁移
仍然拒绝删除包含正在运行分支末端的尾部，以及在正在运行的分支上回退。改动文件的回退仍是整个会话范围

切换、重新开始和回退各自新建什么，以及哪些工作在切换后仍留在原分支：分支协作。

一轮用的设置

准入时还冻结每项设置的值、来源和它所属的 Agent，这一轮把它们写在自己的用户消息上，即 turn_settings。“这一轮用的什么模型、effort 和权限”由这条记录回答。

来源含义
request调用方随这一轮发来的值
parent取自同一会话里发起这一轮的运行中轮次
branch取自这一轮所在分支的记录
agent留空；运行时由 Agent 或它的回落层决定

分支没设的项从哪里来，哪些工具状态归分支：分支设置。

每个分支一个前台操作

一个分支的运行槽同一时间只放一个前台操作。每个操作都有 op_id、种类，以及停止时会加一的版本；加载、running_task 和 branch_running_task 都报告种类，所以运行条可以显示“正在压缩上下文”和停止按钮，刷新后也一样。

种类占槽的是什么停止
reply、retry、edit、function一轮，从预留到结束；发出 result 后到达的请求等槽位空出停在它的执行上，按版本精确停止
compact/compact；停止时摘要请求结束，什么都不写用它的 op_id 发 operation.cancel
rewind回退，以及回退的撤销和重做operation.cancel
branch删除分支，只占一瞬间；运行时不显示。切换不占槽无

分支之间互不阻塞：一个操作只要求自己的分支空闲；同一分支上的第二个操作被拒绝（run_active），拒绝里写明正在运行的种类，客户端可以自己排队。删除包含正在运行分支末端的尾部，会被拒绝并写明是哪条分支。

请求在槽位上看到自己的键，就是重复，不是第二个操作：

第一个请求占着槽位时重复发来的同一请求

执行回退idempotency_key等第一个结束（最多一分钟，与存储的锁预算相同），再占槽位；存储返回第一个记下的结果（存储一致性），文件和 head 只变一次，两个调用方拿到同一个结果
撤销、重新应用idempotency_key 加该轮

键不同或没有键任意拒绝，run_active。槽位比存储先检查，所以这一层也要认得重复

保留分叉点和它上面的一切：别的分支也在用

一轮在运行中途压缩自己的上下文时仍是 reply；网页在 compaction_started 持续期间显示这一步。

只有改动文件的回退作用于整个会话：

  • 只要其他分支在运行，或有一轮在等待批准或回答问题，它就被拒绝，返回 code: branch_running 和 blocking：那条分支的名字、它的执行 id 和版本，或它的 op_id。
  • 这时回退对话框提供“停止它再回退”：停掉那次运行，等它结束后再执行同一个回退。
  • 它运行期间，一条持久化记录占住会话的文件。任何分支都不准入，新的执行（定时运行、排队的 Job、另一个进程准入的轮次）在准入时等它结束。

每个运行中的操作也记在磁盘上（state/store/session/operations.py）。重启后，第一个读取方把进程已经不在的操作标为已取消，reason_code: restart；不会恢复任何一个。

其他操作只占用它们碰到的分支（reserve_branches_operation，按排序依次占用），拒绝时点名忙的分支：

  • 删除消息和轮次文件历史操作：线上含有该节点的每个分支；公共祖先碰到它下面的每个分支。
  • 切换 Agent：自己的分支。
  • 定时运行：开始前读自己分支的持久记录，分支忙就跳过这次。
  • 命令、技能和 Agent 调用：消息指定的分支。只有 /clear、/rename 和开始 Goal 改变整个会话，留在选中分支。

旁边有另一个分支时的回退

回退只撤回本分支的轮次在所选 prompt 之后写的内容。定时运行在自己的分支上，算作另一个分支。

另一个分支改过同一个文件回退怎么做
没改过把文件恢复到该 prompt 时的状态
在本分支第一次编辑之前把文件恢复到另一个分支留下的样子，它的改动保留
在本分支的编辑之后或之间不动这个文件。计划在写入前以 changed_since_edit 阻止；仍可只回退对话。
在本分支第一次编辑之后，且另一个分支的回退已经撤回了那次改动那次改动不再计入；文件按上面几行恢复

子 Agent 的轮次记在派生它的那一轮的回退点里。运行时发起的轮次记在本分支上最近的前一条 prompt 里。这样的轮次第一次改某个文件时，后面的 prompt 的轮次可能已经改过它；越过两者的回退把文件恢复到两者都没改之前的状态。单个文件的规则见文件管理。

Claude Code 的回退把每个被跟踪的文件恢复到 checkpoint 时的状态，之后 Bash 对它的修改也一并撤回。Codex 已经移除了撤销；它的 thread/rollback 只从上下文里丢掉轮次，不动文件。两者都没有说明会检查另一会话之后的编辑，所以这里遇到这样的文件就不动它，并指出是哪个文件。

Claude Code 和 Codex 用复制来分叉：分叉得到新的 session 或 thread id，作为独立会话运行。两者都没有公开同一 session 或 thread 内两轮并发的规则；Claude Code 的问题报告描述了并发恢复同一 session 时无锁写出交错分支。

每个控制做什么

控制结果边界
Pause在下一个安全点停止当前动作可能先完成；不冻结任意代码行
Continue从已保存进度恢复同一执行仅在保存状态和能力允许时
Step运行一个声明的步骤后暂停工具动作或声明边界，不是源码行
Steer为尚未运行的工作添加指令已完成工作不变
Cancel结束该执行和它在等的东西：同步子代理及其下的轮次不能撤销已完成的外部操作；托管进程有自己的控制。后台子代理和从保存点建的分支继续运行。由另一个存活进程持有的轮次（定时运行）通过该执行的函数日志收到请求，由它自己停下。
Fork / Retry从允许的保存点创建独立子执行原历史保留。Agent 聊天子执行以暂停开始，需要 Continue；其他按调度器。

界面只提供该执行支持的控制。“accepted”表示已保存，“applied”表示已生效。终态协调赢得竞争时命令完成是幂等的：比较交换冲突后，服务只接受同一执行和结果版本上已应用的命令，保留已存回执，其他冲突继续上抛。

停止一轮

停止结束一个分支上的前台操作，已经产出的内容保留。对比了 Codex、Claude Code、OpenCode、Pi、KimiCode、Grok Build、Hermes Agent、ZCode 和 Cline；每一项写明跟随哪家。

项目怎么做跟随
被停止的回复已完成的模型调用连同推理签名留在历史里。流式中被截断的文字作为最后一次不带签名的调用保留；它不带签名的推理只显示、不发送；参数还没收完的工具调用丢掉。OpenCode
每个调用都有结果运行中的调用：先放已有输出，再接 Stopped by the user after 3.2s.。已发出没运行的：Not run: the turn was stopped before this call started.。Worker 重启：Interrupted after 3.2s because the service restarted.。会话 id 不再发给模型。Codex，已有输出按 OpenCode
下一条消息上的说明停止时在回复上写 interruption（原因、阶段、是否截断了调用）。下一条消息的轮次块里加一句说明上一条为什么停了；截断过调用时再加 "A tool call that was stopped may have partly run."。它只写一次，存在这条消息的节点上，之后每次请求字节相同。文字跟 Codex，位置跟 Grok Build
空的被停止回复助手位置不写任何内容。Anthropic 和 Gemini 的请求把相邻的两条普通用户消息合成一条。Codex
终端界面的停止键一轮在流式输出、或发出后还没收到确认时，Ctrl-C 或 Esc 第一下就停止；否则按 op_id 停止这个分支上的 /compact。之后再按，用同一个命令 id 重发同一个停止，不再加行。空闲时双击 Ctrl-C 仍是退出。Claude Code；一键停当前任务跟 Codex
有 id 之前的停止聊天、函数运行和重试都带 client_request_id；确认之前的停止指明它。网页保留 _optimisticStops，免得确认消息把已停止的一轮重新显示成运行中。Claude Code 的 queryGuard；返回 id 跟 Codex
信号怎么到达停止设置这一轮的普通 Event，并执行登记在它旁边的动作（run_control/wakeups.py）：立即唤醒这一轮的事件循环，取消读取提供方的任务。为没走这一步就设置的信号保留一个 0.5 秒的检查；跨进程的停止仍经函数日志送达。Codex or_cancel(&token)
后台代理停止不连带它们。在它自己那一行停止时，给发起它的会话排一条 "Background agent … was stopped by the user."。Claude Code
排队的消息服务端释放被停止的一轮后发出。Claude Code
还没回复就停止消息保留，带"开始前已停止"那一行。要撤回用回退。Codex、Pi、OpenCode
等待状态停止取代暂停、打开的提问和待核对，它们随之关闭。Codex、Claude Code
Windows 上的 --printCtrl-C 和 Ctrl-Break 走停止路径；关闭控制台也一样，宽限 3.5 秒，在 Windows 允许的时间之内。Claude Code 所用的 Node 信号映射

为什么这样设计

项目原因
被停止的回复模型看到的应当就是用户看到的：停下后用户常说"继续"或"改一下那句"，丢掉截断的文字（Codex、Pi）会让模型从头再写。已完成的调用是合法的带签名历史。Anthropic 不接受不带签名的推理，所以只丢被截断那次的推理。
调用结果调用没有结果，提供方会拒绝请求。运行时长和"未运行"让模型判断要不要重跑；按工具维护副作用表（Hermes）要长期维护，那句"可能执行了一半"已经覆盖。
说明的位置放在助手位置的文字会被模型复述（Hermes 的经验），所以说明放在用户的轮次块上，和回退说明同一机制。停止时就写下，缓存前缀保持稳定。
停止键Codex 和 Claude Code 都是第一下就停；先给提示会让人以为没反应，第二下又误入退出流程。每次停止一行就够，但重发保留，因为第一次信号可能丢。
信号同行全是事件驱动；两层轮询让中位数约 160 毫秒，每轮还多一个线程。Event 保持普通对象，因为持有它的请求选项会被深拷贝。
后台代理用户让它们在后台继续跑。没有这条通知，模型会一直等一个不会来的结果。
排队的消息Codex 和 Pi 把队列放回输入框，是因为它们的队列不能编辑；这里排队的消息在输入框上方可见、可编辑，和 Claude Code 一样。
还没回复就停止回退是用户主动的操作；停止时撤回消息会让一个按钮做两件事。
WindowsWindows 没有 SIGTERM；脚本发 Ctrl-Break，关闭控制台只给约 5 秒，之后进程被杀，执行停在运行中。

情形恢复

Worker 中断不是助手失败：不追加错误回复，也不显示重启或恢复消息。真实的 provider 和工具失败照常显示。不需要专门保存或优雅退出。

自动继续窗口
execution.auto_resume_window_seconds默认 -1，无时间限制（空期限）。0 关闭自动重启。正数为时长。
起算有序关闭意图，或被放弃尝试的最后持久活动，不是下次启动。再次重启不延长；已有的有限意图升级后仍有限。
有序停止先在退出中的 runner 关闭调度和重启协调，再请求本进程拥有的那些轮协作暂停；定时对话在自己的进程里运行，不受影响。竞争的检查点版本在同一尝试和期限内最多重试三次。
尝试已结束启动恢复采用该轮日志记录的结局，并拒绝未完成的命令。没有记录结局时不发布检查点：运行变为 interrupted，未完成的暂停被拒绝。
自动恢复只有重启恢复拥有的暂停
保持显式用户暂停、取消、未答审批、未解决效果、过期检查点、不兼容运行时契约、没有重启意图的旧暂停记录
过期保留检查点供手动继续，绝不删除会话数据
自更新相同时长，从已完成更新的最后持久活动起算；期限和过期存于更新目录。恢复、契约修复规划和原会话后续都遵守。仍在运行的更新不被停止。维护模式仍控制准入和校验。
重启机制
  • provider 决定和完成的工具动作在普通执行中原子地发布检查点和效果回执。原执行 id、不可变输入、权限、预算和续接命令保持权威；排队的 Job 使用资源队列。
  • 重启意图是规范执行事件，与转换一起存储；固定的命令身份使重复启动幂等。没有第二个数据库、调度器、进程 owner 或权限路径。
  • 恢复归属记录确切继承的检查点；新效果之前的第二次中断保留它。
  • 新 Job 在准入时拥有稳定的用户和助手消息 id。暂停完成时按 Job 等待方保留的尝试和租约身份释放资源。
  • 启动时先分类被放弃的归属，再由 runner 应用此策略。仅 provider 或从未激活的聊天准入可在原活动期限内从不可变输入继续。

谁拥有运行状态

运行状态由每个会话的日志折叠成内存表，没有数据库文件。见会话存储。持有 worker.lock 的进程拥有它启动的运行。

函数子进程读取表，把变更交给父进程。定时任务的一轮，以及独立的 ACP、MCP 进程里的一轮，属于这些进程自己，这一轮的行写到它们自己的日志。定时任务启动的子 Agent 由 Worker 接纳并运行，只有 Worker 能认领排队的 Job。

尝试和围栏

情形规则
Owner激活的执行有一个当前尝试，由 worker.lock 持有者拥有，没有心跳
在别的进程里跑的一轮owner 租约记录该进程的 id 和启动时间

有序停止、自更新检查点都不碰别的进程拥有的一轮
日志记录过某一轮的结束状态，后面的行又写成未结束启动时恢复记录的结束状态
暂停或停止抢在启动方前面启动一轮的每一步都是比较并交换（租约、激活），或是驱动可能拒绝的交接。无论哪一步输了，都由同一个检查重新读取执行，给它看到的控制意图让路。其他情况是启动方自己的失败。
启动方输了时看到的情况已暂停、没有检查点也没有尝试：什么也不写，之后的 Continue 再启动这一轮。取消中或已取消、没有尝试：由停止自己结束排队中的这一轮。取消中、尝试是启动方自己的且没有驱动收到过：这个尝试报告自己丢失，执行以已取消结束，取消命令生效，尝试以 cancelled_during_activation 结束。
开始前已停止的一轮激活不返回结果。每个调用方都把这一轮报告为开始前已停止：子 Agent、合并、定时签到、渠道回复、MCP 调用和函数调用。
它的回复聊天的一轮在开始时才打开回复，所以由停止来写：在消息后面写一条空的、已停止的回复。页面实时和刷新后都显示已停止的回复，和刚开始就停止时一样。消息要到开始时才写的一轮没有可关闭的内容。
其他没有回复行的情况函数调用的行在准入后才写，可能稍后到达；已经开始却没留下回复的一轮是丢失了它。停止时记一条错误，事件效果重试五次，之后记下放弃。
每次 owner 写入（工具结果、安全点、等待、调整投递、结束）在事务内验证尝试未结束、代次为当前、执行仍指向它。未通过的 owner 停止。

失败的尝试把可读的错误文字留在尝试记录上，其中形似凭据的内容会被抹掉，最多 4000 字符。它不进快照和事件内容，只有 Activity 的单次运行事件读取它。因持有者丢失而关闭的尝试没有这段文字，旧记录读出来也是空。

Workflow 问题

  • 运行中的 Python Workflow 提出的问题在当前进程内等待，绑定确切的执行、尝试和代次。它使用规范等待存储和问题界面，不做 Workflow 检查点，也不重启调用栈。
  • 答案回到原调用。浏览器刷新时重新加载待处理请求。
  • 只有活动的当前 owner 能创建或回答。取消、执行结束或失去进程 owner 会使其失效。Worker 重启不回放 Workflow。
  • 子进程通过现有队列桥接发布。意外错误上抛，不会变成未答结果。声明了等待前检查点的 Agent 工具问题保持持久续接。

用户决定面板和回执

问题、确认、表单和权限审批是输入框上方按会话划分的面板。终态回执留在会话中。
输入框保留草稿、附件、函数表单、焦点和发送或排队行为。新请求绝不占用它或移动焦点。
导航Back、Next 和折叠保留草稿，不发送
Skip拒绝整个问题请求
提交立即显示提交的答案和发送中状态
已应用已回答回执
投递未知重试保持相同的命令身份和答案
被拒或过期不能暗示批准
多个请求独立分键卡片，按会话和执行划分，包括分屏

卡片复用共享的问题渲染器、规范问题事件和执行命令。每张卡片拥有自己的答案字段、提交控件和投递状态。回执不是 Workflow 检查点；刷新重新加载待处理问题，不增加历史回执持久化。

标识符和安全规则
session_id会话范围和授权；绝不是控制目标
run_id归组相关的原始、分叉和重试执行
execution_id确切控制目标。Pause 和 Continue 保持不变；分叉或重试创建新的。

规则行为
命令服务所有传输使用同一命令服务，在 owner 应用之前保存命令。界面状态不授权操作。
优先级取消优先于暂停、单步、继续和调整。只有当前 owner 发布进度或最终状态。
停止与版本停止指明执行，不指明版本。一轮对话的版本在开始后的十分之一秒内会变两次（租约，然后运行），所以刚发送就按停止，带的往往是旧版本。存储在一个事务里按当前版本受理停止，只把发送方看到的版本记进日志（cancel.version_moved）。
其他命令与版本暂停、继续、插话和回答仍需当前版本：它们是针对某个快照的决定。
同一个停止，按状态回答内部和对外的停止是同一个，结果只取决于状态。运行中：执行变为取消中，并通知拥有者。已在取消中：返回生效中的那次停止，并再通知一次拥有者，因为第一次信号可能丢了。不新写任何东西。已经结束：返回最终状态和 already_terminal，这不是拒绝。
同一命令 id同一个命令 id 停止同一个执行就是同一次停止，不论给出什么原因。
排队中的 Job排队中的 Job 会立刻结束，所以先按那个快照封住它的派发；停止写入前快照变了，就把封锁交给恢复处理。
哪些一起停"哪些跟着一起停"由一个函数回答。一个执行的上级是它的规范父执行；对 Job 来说，还有它的输入里写明的调用方和父 Job，不论在哪个对话。遍历会穿过已经结束的执行。
对外与内部停止对外的停止（网页、Activity、终端、--print、ACP 和 MCP 客户端）只停这一轮在等的：同步子代理及其下的轮次，不停后台子代理和分支。内部停止（渠道的 /stop、Goal、时间上限）停所有下级。
顺序下级先于上级停止，最深的先停，这样排队中的下级在上级结束、空出运行槽位之前就被拦下。上级停止期间新准入的下级，在上级之后再停。
交给拥有者一次停止只交给拥有者一次。重复的停止回答 already_delivered，不再调用已经收到的拥有者（它的句柄可能已经释放）；没收到的拥有者，或之后接手的拥有者，这时收到。
客户端客户端只发一次停止。网页在执行自己的帧报告已取消时才提示 "Stopped."，不看命令的应答。网页只知道 id、不知道版本的一轮，按停止会立即发出。
Worker 声明的能力连接时 Worker 发送 worker_capabilities：cancel_ignores_version（停止从不因版本过期被拒）和 cancel_by_request（停止可以指明一次发送）。终端界面和 --print 是否补发被拒的停止、是否按发送停止，只看当前连接上的 Worker 声明了什么；旧 Worker 或远程服务器保持原来的做法。
还没有 id 时的停止客户端还不知道这一轮的执行时按下的停止，指明这次发送：它的 session_id 和 client_request_id。准入时把请求 id 和执行一起记下，同一会话里一次发送只准入一个执行。由一个存储事务决定。发送已经准入，就像平常一样停掉它的执行。网页、终端界面和 --print 都这样发。终端界面的新对话和网页草稿一样，在发出第一条消息时就有了 id。
停止标记还没准入的发送被停止时，在会话的运行日志里写一条标记，回答 marked。这次发送准入时取走标记，这一轮在激活时、租约之前就以已取消结束，回复写成"开始前已停止"。标记在 Worker 重启后仍然有效，十分钟后失效。
模型错误与工具结果已知模型错误和中止有响应记录。未知工具结果保持未解决，History 标签不会清除它们。
分叉分叉校验保存点、不可变修订和权限。程序、模型或工具契约变更保留独立审查。
JobJob 的 job_id 等于 execution_id。资源分配与执行状态分离。
项目位置加载会话前读取当前存储的项目位置。读取和控制限于已授权的会话。重连使用已保存版本和事件位置，不产生重复任务。
托管进程托管进程保留身份、归属和有界输出。重启恢复检查 supervisor，仅有保存的 PID 不构成发信号的许可。

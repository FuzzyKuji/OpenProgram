Background Job lifecycle

Every spawned sub-agent is a Job in openprogram/runtime/jobs/, with job_id equal to its execution_id. Control goes through the execution control plane; a Job adds admission, a worker pool and result delivery.

Terminal states absorb; illegal moves raise ValueError. Since canonical executions do not mirror their running transition, the projection may also go pending → running and queued → completed.

Entry points

read_conversation(execution_id)Model tool. Returns the Job's status, and its reply once terminal, without waiting. job_output(job_id, block, timeout) stays registered for programs, hidden from the model.
list_agents()Model tool. Lists this session's running or queued Jobs, newest first, at most 20, beside its branches. list_jobs() is hidden from the model.
/task, /task --async, /spawnTyped in chat. Blocks, or writes a running placeholder and returns.

Clients follow the job_status broadcast. The branch view shows Job status; there is no separate Tasks panel.

Hand-offs across a crash

A sub-agent request crosses three hand-offs between the parent and the run. Each writes what it is about to do before doing it, the step after it is idempotent, and the Worker's resource reconciliation (at start and every 5 seconds) finishes whatever a dead process left half done. openprogram/runtime/jobs/handoff.py holds the shared pieces.

The parent turn that was cut off in the middle of the agent call reads that call as interrupted with an unknown outcome (restart recovery); the attach card and the later notice tell it what became of the request. A held Job whose submitter still runs, in this process or another, is left to it.

Why this design

TopicWhy
Intent before actingExo's beginTurn durably accepts the input before the executor acts, and Maka commits the dispatch (T1) before a tool runs and the outcome (T2) before the result is published. Both make the record the authority and the action a consequence. Here the Job record is that record: whatever the next step needs travels on it, so recovery reads one row instead of guessing.
Idempotent by Job idMaka's graph claims preallocate the run identity and observe an existing run instead of starting it again; Codex publishes the spawn edge before the child exists. A replay keyed by the Job id can run at every reconciliation pass without a second inbox entry, card, run or notice, so recovery needs no extra state to know it already ran.
Liveness of the submitterThe held spawn and the waited result belong to whoever submitted them while that process lives; only its death hands them to recovery. Process identity is the pid plus its start token, as execution leases already record, so a reused pid is not mistaken for the old waiter.
A dead waiter's resultClaude Code and Codex lose a foreground sub-agent's result with the process; Maka re-delivers its supervisor wake until the root run completes. Telling the parent by the same notice a background agent uses costs nothing new and keeps the work from being lost or redone.
Run the request rather than cancel itThe request was admitted with its budget; dropping it would make the model guess, and its interrupted call already warns that the outcome is unknown. Running it once and reporting is the outcome the parent asked for.

Cancellation

  1. JobRunner.cancel_execution persists one execution.cancel command, and cascades to child Jobs.
  2. The owning worker consumes it and sets cancel_event, which process_user_turn bridges into the agent loop; the provider stream stops at its next chunk.
  3. Live subprocesses and exec runtimes are signalled by exact execution id. Agent methods check at their pre-invocation hook.
  4. After _CANCEL_ESCALATION_SECS (30 s) the owner's grace ends.

A tool's own atomic operation finishes first. A cancelled or errored Job cannot be resumed as the same work; retry is a new spawn.

Session and attach card

  • A Job runs in exactly one session, parent_session_id, and that never changes. A caller in another session is caller_session_id, with a linked mirror for visibility and ownership checks.
  • Output lands as a branch of that session, or a new root with context="clean".
  • An attach node (function="attach") is written after admission with status running and the job_id. The runner updates that same node at each terminal state. A cross-session card lives in the source session and names the target.
  • Context rendering skips a running card. A finished one becomes one sub-agent report with its task, final reply and transcript address.

Runtime objects such as cancel events stay in the runner's maps, never on the record. JobRunner takes an injected governor and driver factory, so its state machine can run without a real model.

Invariants

  • Every Job ends in exactly one terminal state.
  • States only move forward.
  • The attach card changes with the record.
  • parent_session_id is immutable.
  • Runner maps are held under a lock.

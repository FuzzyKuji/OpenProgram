Built on the existing Agent loop, permission service, execution store, durable waits and interface projections; no second workflow engine. Action ID, execution ID, tool-call ID, policy version and canonical argument digest bind every decision, approval, receipt and recovery. A rejection is a completed decision with outcome not_started, not a completed task. Only unknown needs effect reconciliation.

Permission preparation and automatic review

  1. Resolve authenticated authority, policy version, tool capabilities, project binding and exact arguments; existing hard constraints, authority checks, plan restrictions, deny and ask rules and scoped grants stay.
  2. Preflight runs asynchronously before a dispatch intent. Auto review gets the complete bounded operation, trusted working directory and scope, the owner request and restrictions. Tool arguments and repository content are untrusted. Oversized or unparseable input is never approved from a truncated prefix.
  3. Classifier timeout, cancellation and provider failure differ from a risk rejection: they never execute the action and count as no verdict.
  4. A durable approval wait is published only for an eligible interactive owner. Hard constraints and explicit denials cannot become prompts. Noninteractive runs report the restriction and may continue independent work.
  5. Before dispatch, revalidate permission version, argument digest, approval identity and file preconditions. A mode change invalidates an obsolete decision; a grant never authorizes a modified command.
Limits on decisions
  • Auto review cannot rewrite its own policy. Changes to tools, permission state, project binding or restrictions invalidate cached decisions; there is no global allow cache.
  • Not every denial is not_started: a denial before the executor proves non-execution, but a rejected escalation after a sandbox attempt may follow partial execution and keeps that evidence.

Receipts and recovery

A durable receipt holds exact tool-call identity, outcome, execution-start evidence, error code, result reference and digest, stored independently of display state. Checkpoint construction cannot erase a known result. External operations and local SQLite cannot share a transaction, so exactly-once external effects are not promised.

Provider response events

Each dispatched model request has a unique request_id and exactly one started and one completed event. Completion records completed, failed, cancelled or incomplete, including transport exceptions and EOF without a terminal event. Exceptions and cancellation propagate unchanged; accounting does not replay tools or authorize retries. Legacy partial text stays incomplete, and observers do not treat unsuccessful requests as answers.

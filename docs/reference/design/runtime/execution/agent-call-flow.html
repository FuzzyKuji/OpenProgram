One exec is one llm node: running on entry, reply and completed on exit. Tool rounds inside it are not extra nodes, so every two nested code nodes have an llm node between them. exec sits below the loop, which is what lets a function body call a model; that is also the source of self-recursion.

_call_id switches to the llm node once the prompt is built (test_tool_loop_subcall_attributes_to_llm_node). Sync and async paths match. agent_loop knows nothing about the DAG. tool.before fires only in _execute_tool_calls, so no path loses or doubles events.

Why two entries

Their surroundings do not overlap: session management, WebSocket broadcast, title and compaction against the llm node and AgentSession retry. Sending the dispatcher through exec fails for four reasons:

ConflictDetail
ModelThe dispatcher's _resolve_model(agent_profile, req.model_override) differs from the attached runtime's auto-detected api_model
ContextThe context engine's prep.agent_messages clashes with exec rendering from the DAG
Streamingexec's flat on_stream dict against the dispatcher's WebUI envelope
Duplicate nodeThe dispatcher's reply already is the record; another llm node gives [user, assistant, assistant] (test_dispatcher_integration.py::test_real_loop_text_only)

The loop driver LoopDriver sits below exec (exec → AgentSession → LoopDriver → agent_loop) and is built in one place; it is not a parallel path.

Callable path

Runtime(call=fn) wraps fn into a stand-in provider model (callable_model.py) and goes through _call_via_providers like any model: no legacy branch. The adapter converts messages back to content, calls fn with response_format, returns one assistant message, and has no tools or tool loop. stream_fn threads from exec by context variable to AgentSession (test_exec_stream_fn_injection).

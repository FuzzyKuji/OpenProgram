Branch settings

Each branch of a conversation runs with its own settings and its own state, so two branches can run side by side.

Where a setting comes from

Every branch keeps its settings on its own record in branch_refs; the conversation's top-level fields are the selected branch's projection. resolve_branch_settings(session, branch) returns each setting's values, sources and inherited (what it follows when unset). Every entry reads through it: web, channels, scheduled runs, always-on, Goals and --print.

Setting left unsetFalls back to
Model, Web search, FastThe branch's Agent as it is now, then the product default
EffortThe Agent, then the project, then the product default
Permission mode, SandboxThe project, then the product default
AgentThe default Agent

Following the Agent

  • A new conversation and an Agent switch write no model, so an edit of the Agent's model reaches the next turn.
  • Admission records the model in turn_settings. When the Agent changed it since the last turn on that line, the user message carries model_change, the page shows a one-line note and the cache-break report names model_switch.
  • A move to a model with a smaller window compacts first, with the old model.
  • scripts/migrate_branch_follow_agent.py clears models and web-search switches that only copied the Agent's. It is a dry run by default and writes a backup before it changes anything.

Writing a setting

  • POST /api/sessions/{id}/branch_settings stores only what differs from inherited; an equal value is written as unset. reset_fields also puts a setting back to inherit.
  • GET on the same path and the reply to a write return the resolved values.
  • A message to an existing conversation sends no settings; a new conversation sends only the controls the person changed.

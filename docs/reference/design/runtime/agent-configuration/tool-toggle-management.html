Tool toggles and toolsets

The selected Agent decides which tools a branch may call. Each branch stores only intent, never an expanded list, so new tools remain available through the Agent template. Branches inherit intent once and then change independently.

No composer Tools switch or per-chat preset. A chat without tools uses an Agent with Programs set to none. The chat action reads only web_search from a message, never tools or tools_profile. A message without web_search (the CLI, the TUI) leaves the stored intent as it is.

Mechanics in programs/_host/runtime.py
PartBehaviour
apply_default_deferral()Runs once at import in programs/__init__.py and gives every entry its default tier. Idempotent. Entries registered later get theirs at registration.
split_tools_for_dispatch(tools, loaded)Partitions into (provider_tools, catalog) by tier and the request's loaded set
Loaded setNot stored anywhere. Each request reads it from its own messages (loaded_tools(messages) in shared/tool_loads.py): the load records of its tool results (details.loads) and the names a compaction summary among them carries (carried_tool_names). A nested run reads its own messages, a branch its own history, an edited-and-resent turn the history before the edit.
Discoverytool_search writes a load record on its result (record_loads), so the next provider request carries real schemas. A guide or an opened application names the tools and how to load them; it loads nothing. Schema as tool-result text alone is not enough for providers that accept only tools in the request array.
ExecutionUses the turn's resolved, permission-wrapped tools, not a new registry lookup. Without discovery the array is stable; discovery may change the cached prefix.
CheckpointsA continuation needs no loaded names: the resumed request reads them from the messages it resumes with. The journal's old loaded_deferred_tools field is no longer written or read for loading. Tool-result text is never read as authorization or loading state.
CatalogA conversation's own turn sends it as the turn_context section deferred_catalog beside the user message: in full with no baseline, then only what was added or removed. A call with its own system prompt (an Agent method, runtime.exec) keeps it inline there (_build_deferred_catalog in runtime/context/components.py). Empty when nothing is deferred.
_estimate_one_toolIn runtime/context/budget.py. Resident: description, parameters and a small wrapper. Deferred: bare name plus a newline. The two errors point in opposite directions, so test_budget.py checks each half against a real tokenized payload, within 15%.

Do not break

RuleWhy
Expansion is deterministicThe tool array is the root of the prompt cache prefix (models/providers/settings/cache_policy.py; first breakpoint at the last tool, Anthropic and Bedrock explicit mode). Any wobble misses the whole cache silently. No set() iteration or dict churn in agent_tools and _filter_agent_tools.
Never store the Agent's tools on a sessionThe list would freeze: tools added to DEFAULT_TOOLS later would never arrive. list[str] means only a /skill allowlist.
Never filter historyHistorical tool_use and tool_result render from messages regardless of context.tools. Breaking the pairing causes a provider 400.
Mid-turn array growth only through discoveryAnything else discards the cached prefix for the rest of the turn
Cost, cache and replay
QuestionAnswer
Do tools count as tokens?ContextCommit.total_tokens excludes the array (state/store/session/context_commit/types.py); the provider bills it. Invisible to the compaction budget, visible in input cost.
Cache?Any addition, removal or reorder misses the entire prompt cache.
Calls absent from the current array?They replay fine; the model just cannot issue that call this turn.
Commit replay?Unaffected: commits store no tool array.

Application runtime

An application has its own interface, business logic, data and dependencies, and opens from New tab without returning to the conversation that created it.

What this buys, and the limits
  • Interfaces are standard Web: HTML, CSS, JavaScript, compiled React or Vue, not assembled from fixed OpenProgram components. HTML is an interface technology, not a measure of completeness; backend, state, contracts and deployment dependencies decide what the software can do.
  • Value: business operations shared by buttons and Agents, model calls in existing execution records, business data independent of chat windows. A combination of product contracts, not a claim of uniqueness.
  • Applications run inside OpenProgram. A later minimal-runtime deployment stays possible; removing every OpenProgram dependency needs replacement model, storage and execution implementations, so standalone export is not promised.
  • Browser-executable JavaScript, Canvas, WebGL and WASM are available. System GUI, GPU drivers, arbitrary binaries and other-language services are not; those need explicit runtime adapters and dependency contracts.

Application contract

{
  "id": "local.paper-reader",
  "title": "Paper reader",
  "icon": "book-open",
  "version": "1.0.0",
  "ui": { "root": "web/dist", "entry": "index.html" },
  "backend": { "kind": "python", "entry": "paper_reader.app:operations" },
  "scope": "project",
  "capabilities": ["model.invoke", "storage.app", "files.project.read"],
  "dataSchema": 1,
  "operations": {
    "summarize": { "agent": true, "input": { "type": "object" }, "output": { "type": "string" } }
  }
}

Static applications omit backend. id is stable package identity, never title, path or creation-chat ID. Field rules and public APIs: Applications.

ObjectHolds
DefinitionManifest read from the source plus the content digest of the source tree, computed at load and on every reload
InstallationCatalog row: source directory, settings, reviewed data identity and trust. Package limit 100 MiB, no symlinks or special files.
InstanceApp ID, owner, project scope; business-data location. A window is not a database.
ViewTab, instance, UI route, displayed run. Disposable.
Operation runRun ID, instance, definition, input, request key, state, event sequence, result. Links existing execution records without copying the DAG.
  • Operations have input and output schemas. Clients cannot choose import paths, source paths or owners; the server resolves them. Trusted identity comes from the authenticated connection, not a JSON field.
  • Operation names exist only at the UI and process boundary. Python internals use ordinary imports, with no second string dispatcher.
  • Events have increasing sequences; clients resume by cursor. Results and errors persist. State is at most 4 MiB as JSON, an event 1 MiB; large outputs use references.
  • Project-path changes update bindings, not instance identity. Runtime databases hold execution facts; application state references run IDs. localStorage caches disposable view preferences only.
  • User data never lives in the source directory.
  • Python environments: one per application and pinned dependency set, created on first use, never installing into the main worker. Listing reads manifests only and starts no process. A static application starts no Python. Published UI uses build artifacts: no dev server, no latest dependencies, no regeneration per click.

Models and business operations

AspectRule
Shared pathA button and an Agent call share input validation, permissions and implementation. Only agent: true operations are exposed, as <id>__<operation>; internal database methods never become tools. Agent calls bind instances and cannot switch project data.
Model callsThe runner creates Runtime from the manifest's model name or host defaults, bound to run records (SessionNodeWriter under runs/). Context is operation input and explicitly supplied app data, independent of the active chat. No chat is needed before a button.
CredentialsThe page gets progress and results, never provider keys
Questionscontext.ask() emits a question event; an answer binds run and request ID and applies only to the pending question. No second ExecutionStatus.
CommitOrdinary code validates model output before a transactional commit. "Saved" in natural language is not evidence.
RetriesA request key dedupes submissions; reuse with different input is rejected. Non-idempotent external effects inspect existing records or ask the user; a network timeout never repeats execution.

Lifecycle

PathSequence
OpenRead verified definitions → select → resolve instance and project → reuse or create tab → load resources at the digest → connect capability port → read state and active runs. No business code imported, no model request.
TaskPersist input, request key and accepted event; the existing Attempt manages running; persist questions; finish completed, failed or cancelled. Stop terminates owned process trees and reports cancelled only after cleanup; late results cannot overwrite a terminal state. Process-tree ownership persists so children end after the parent exits. Concurrent writes need transactions or version checks, not disabled buttons.
RestartReopening restores view and state. After a worker restart, incomplete runs follow owner-loss rules: interrupted, or requested cancellation completes. Inputs, progress and results stay. Python stacks do not resume; an application may read saved state and submit a new operation.
Updateinstall --replace or Update from source: validate manifest and tree, check the backend in a separate process, recheck the digest, check dataSchema and scope, then switch the catalog row atomically. A changed source reloads with a fresh digest. Submitting from a view at an old digest is refused with "reopen".
UninstallCancels operations, hides the application, keeps the source directory, data and schema and scope identity. A compatible reinstall restores the instance. No business-data deletion API.

Incompatible dataSchema or scope is rejected; automatic migration, which would need backup, validation and explicit recovery, is not built.

Isolation and portability

  • Iframes use sandbox="allow-scripts" with a restrictive CSP and an opaque origin. Host and page talk through a validated MessageChannel handshake. Existing same-origin plugin pages prove no isolation; CORS is not authentication.
  • Resources are addressed by digest and restricted to the published UI directory, with a credential that permits UI reads only. The bridge rejects page-supplied owners, URLs and other-instance runs. Pages cannot reach /api/*. Capabilities are rechecked per operation; disabling or uninstalling revokes.
  • Separate Python processes isolate dependencies and crashes, not host files or network. Backends are explicitly trusted local code, and manifest capabilities are no malicious-code sandbox. Untrusted remote code would need platform restrictions or containers, covering children, install scripts and inherited environments.
  • Ordinary applications render only in their tabs and get a small stable API, not React stores or session managers. Global toolbars, chat editors, themes and system services are trusted host extensions.

Evidence limits
  • "Official repository description" means reading public descriptions, not auditing a repository. Compatibility without measurement does not count as accepted. Links support nearby claims, not whole implementations.
  • Relevant DSH distribution, worktable and OpenProgram code was checked; other projects rest on current official documents, public examples or repository descriptions. Not every product was installed and tested.
  • "Unverified" means insufficient evidence, not absence. Cursor and Windsurf internals are unknown. AutoGen and Semantic Kernel are treated within Microsoft Agent Framework's evolution.
  • The list is not closed: commercial products, community forks and private harnesses are not exhausted. Relevant Qwen Code and Strands pages could not be obtained; Trae, Kimi CLI and cloud software-generation services are outside the matrix. These gaps limit uniqueness claims, not the requirements here.
  • DSH details use installed distribution 0.1.5-rc.1, worktable source 0.3.3. Neither received full compatibility acceptance; one version's demo is not evidence for another's capabilities.

Acceptance
  • Sample applications: a non-model calculator, a paper reader saving annotations and generating summaries from pasted text, batch file analysis with progress and restart interruption.
  • Checked through public entries (API, CLI, real browser): install, update, disable, reinstall after uninstall, failures, repeated clicks, reopen and restart. Default-App checks: harnesses under Applications, management and menu reuse of an instance, preserved notes and analysis results, menu hiding and restoration, tabs and results restored after restart.
  • Integration tests cover model success and failure, cancellation, duplicate submission and interruption; offline tests do not guarantee live model availability.
  • Performance targets: listing New tab starts no business process; repeated opening creates no second same-scope instance; opening triggers no code generation or model request. No unmeasured latency commitments.

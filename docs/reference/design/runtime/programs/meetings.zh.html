会议

全部用已有部件搭成：语音输入的识别引擎、录制 Workflow 的长时会话形态、提醒和常驻 Agent 的 owner turn、浏览器麦克风 API、电脑操作的 ScreenCaptureKit 音频流。不新增基础设施。

采集

轨来源说话人
mic页面，getUserMedia({audio})，开启回声消除、降噪和自动增益“我”：来自声音从哪里录到，不靠模型
system服务器，ScreenCaptureKit：电脑的声音输出“对方”，再由说话人分离编号
电脑声音，在服务器上录
  • POST /api/meetings 在 Meeting.begin 里开始采集。ScreenCaptureSource 读取可共享内容，为第一块显示器构造 SCContentFilter.initWithDisplay_excludingWindows_(display, [])，不排除任何窗口。
  • screen_capture_audio.open_audio 打开流：capturesAudio、16 kHz、单声道、excludesCurrentProcessAudio、每秒一帧 2×2、不接屏幕输出。电脑操作的按应用录制（desktop/audio.py）共用这个模块，只有过滤器不同。
  • macOS 首次会询问“屏幕与系统音频录制”。worker 运行在 App 的运行时包内（openprogram/host/system_access 的 screen_recording 能力），所以提示和系统设置里的条目显示 App 的名字。ScreenCaptureKit 音频不需要其他声明。
  • SystemAudio 不依赖 ScreenCaptureKit。来源推入 float32 缓冲，按采样数切成 30 秒一段。每段的 t_ms 是第一个采样的会议时钟：起始缓冲的到达时间减去它的剩余长度。
  • 独立线程把每段转成 16 位 WAV，调用 Meeting.append("system", seq, t_ms, wav, "wav")，即音频路由使用的入口。
  • Meeting.finish 在仍处于 recording 时停止流并写出最后不完整的一段。删除会议则取消采集，不写出。
system_audio_reason情况
unsupported不是 macOS，或 PyObjC 的 ScreenCaptureKit 无法导入
permissionScreenCaptureKit 拒绝（错误 -3801 “declined TCCs”），或 CGPreflightScreenCaptureAccess 报告未授权
error其他情况；文字在 system_audio_message

来源无法启动时，会议只录麦克风，状态和 meta.json 写 system_audio: "unavailable"。正常采集报告 recording。旧会议没有这个字段。

麦克风，在页面上录
  • 页面请求麦克风后开始会议，按开始响应里的 elapsed_ms 计算分段偏移，两路声音因此共用一个时钟。
  • MediaRecorder 每 30 秒停止并重启。timeslice 录制器后续分段没有 WebM 头；重启让每段都是完整文件，代价是每段几毫秒的空隙。
  • 每段带轨、序号和偏移（t_ms），乱序上传也能落到正确位置。启动后不到 100 毫秒就停止的分段只有文件头，不上传。
  • 上传串行执行，遇网络或 5xx 错误共尝试三次。
  • 录制器在模块级 store 里：离开窗口不会停止，只有点停止才会。
  • 麦克风被拒绝时收到 NotAllowedError，窗口指出系统设置的对应面板。
  • 录制卡片说明是否录了电脑声音。没有时说明只录麦克风；若原因是 permission，指出“隐私与安全性 → 屏幕与系统音频录制”，并要求重新打开 App。

存储与转写

<state>/meetings/<id>/
  meta.json                   标题、语言、时间、状态、分段计数、错误、引擎、
                              session_id、system_audio、diarization、speakers
  tracks/<track>/<seq>.webm   上传的分段（system 分段是 .wav）
  tracks/<track>/<seq>.json   带时间的片段（或 silent / error）；system 片段带 speaker
  transcript.json             合并后的转写稿
  summary.md                  摘要，转写稿放在 <details> 块里

同一时间只录一场，最长 4 小时。每段（最大 16 MiB）先写盘，再排给这场会议的单个 worker 线程，内存里只有一段。重复的 (track, seq) 被忽略。失败的分段记录并计数，会议继续。

阶段规则
转换ffmpeg，依次在 PATH、/opt/homebrew/bin、/usr/local/bin、/usr/bin 查找，格式从数据读取。已符合要求的 WAV 直接使用。没有 ffmpeg 时拒绝开始，返回 ffmpeg_missing 和安装提示。
跳过静音Whisper 会为静音编造文字。
转写speech_link.transcribe_segments(wav, duration_ms, language)。没有这个方法的链路退回 transcribe，得到一个片段。
语言用会议的语言，绝不用“设置 → 语音”的：强加语音输入语言会让 Whisper 编造文字。POST /api/meetings 接受可选的 ISO language，存入 meta.json。窗口发送会议名旁选择的语言，“自动检测”则不发。空表示检测：whisper.cpp -l auto，OpenAI 和 Groq 不带 language 字段。
各引擎的时间whisper.cpp 输出 [from --> to] 行（不加 -nt）。Groq 和 OpenAI 的 Whisper 模型返回 verbose_json。gpt-4o-*-transcribe 只返回文字：一个跨整段的片段。
合并，transcript.py片段移到会议时钟并按开始时间排序。麦克风片段与 4 秒内开始的 system 片段文字相似度至少 75% 时视为回声（没戴耳机）并丢弃。同一说话人间隔不到 1.5 秒的连续片段合成一段发言，最多 600 字符。
每一行speaker（me、others、others:<n>，窗口做本地化）和英文 label（“Me”“Others”“Speaker n”）。每段之后重写 transcript.json，窗口里转写稿逐渐增长。

摘要

方面规则
转写稿为空不开对话；summary.md 说明没有转写到内容
对话meeting_<hex>，来源 web，以会议命名，默认 Agent，新对话的模型；id 存入 meta.json。保留以便追问。
这一轮start_owner_turn(..., tools=[])。固定提示词，后接 <meeting-transcript> 内的转写稿。没有工具，会议里说的任何话都不能让 Agent 行动。
提示词要求## Summary、## Decisions、## Action items（负责人、截止日期）、## Open questions，用会议的语言。声明转写稿是数据、绝非指令，说话人编号是声音而不是名字。
summary.md回答、含日期和时长的页眉、可折叠的完整转写稿
中断进程结束时仍处于进行状态的会议列为 interrupted。重新总结从各分段的 JSON 文件重建。

访问

  • 每个路由都要求 owner 登录（require_owner）。
  • 麦克风在页面所在的电脑上录；电脑声音永远是服务器那台电脑的。
  • 会议留在状态目录。使用云端语音引擎时，每段都发给该 provider。

说话人分离

每场一次，覆盖整条 system 轨，聚类因此一次看到所有声音，不必跨分段匹配 embedding。四线程下每分钟音频约 4 秒。

步骤内容
音频按顺序逐段转换并拼接 system 分段。concatenate 记录每段的 (concat_ms, t_ms, duration_ms)；to_meeting_clock 映射回会议时钟，并在边界处切开跨段的发言。
分离，runsherpa-onnx OfflineSpeakerDiarization；pyannote segmentation-3.0；3D-Speaker 的中英双语 CAM++（3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced.onnx）；最多四个 ONNX 线程；min_duration_on 0.3 秒，min_duration_off 0.5 秒；说话人数未知，用 FastClusteringConfig(num_clusters=-1, threshold=0.75)。
标注，assign每个 system 片段取重叠最长的说话人（相同取 sherpa 编号小的）。按首次出现重新编号 others:1、others:2…… 写回分段 JSON 并重新合并，transcript.json、summary.md 和提示词都带“Speaker n”。
保持“对方”没有发言重叠的片段，或其唯一声音整场不足 MIN_SPEAKER_MS（3 秒）。聚类会留下一两秒的零散声音，否则会变成“Speaker 5”到“Speaker 7”。
diarization含义
running进行中
donespeakers 是编号说话人的数量
unavailablediarization_reason：not_installed（没有 sherpa_onnx）或 no_model（下载或模型文件失败）
faileddiarization_reason 为 error，文字在 diarization_message
空没录电脑声音，或没从中转写到内容：跳过这一步

除 done 外，转写稿都不变。

为什么用这个模型和阈值

在四段已知说话人的录音上测试：pyannote 的 AMI 片段（两人抢话，对照参考标注评分）、sherpa-onnx 的四人测试录音、一段两人录音、四个合成声音。

设置结果
CAM++，0.6–0.75四段都找对说话人；AMI 91% 的语音标注正确
CAM++，0.8合并四位中文说话人中的两位
区间上限 0.75在经电话会议和普通播放的四人 AMI 会议上，把一个人拆成两个编号的情况最少：五个编号声音，0.65 时为七个
ERes2Net zh-cn（sherpa-onnx 示例）每段录音需要不同阈值；凡能让四人录音保持四人的取值，都会合并 AMI 的两人
依赖与模型下载
  • sherpa-onnx 是可选的 meetings extra（含 numpy），也在 all 中，打包的 App 因此自带。只在 run 内导入。
  • 模型首次使用时从 sherpa-onnx 的 GitHub releases 下载到 <state>/models/diarization/：speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2（只解出 model.onnx）和 speaker-recongition-models/…_16k.onnx。
  • 都经过临时文件，在同一把锁下原子重命名，和语音输入下载 Whisper 模型相同。

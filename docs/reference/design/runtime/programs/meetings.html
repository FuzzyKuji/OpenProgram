Meetings

Built from what exists: voice-input speech engines, the long-running session shape of workflow recording, the owner turn of reminders and check-ins, the browser microphone API and computer use's ScreenCaptureKit stream. No new infrastructure.

The computer's sound, on the server
  • POST /api/meetings starts capture in Meeting.begin. ScreenCaptureSource reads the shareable content and builds SCContentFilter.initWithDisplay_excludingWindows_(display, []) for the first display, no window excluded.
  • screen_capture_audio.open_audio opens the stream: capturesAudio, 16 kHz, one channel, excludesCurrentProcessAudio, a 2×2 frame once a second, no screen output attached. Computer use's per-application recording (desktop/audio.py) shares this module and differs only in its filter.
  • macOS asks for Screen & System Audio Recording the first time. The worker runs inside the App's runtime bundle (screen_recording capability in openprogram/host/system_access), so the prompt and the System Settings row name the App. ScreenCaptureKit audio needs no other declaration.
  • SystemAudio is independent of ScreenCaptureKit. A source pushes float32 buffers; it cuts 30-second chunks by sample count. A chunk's t_ms is the meeting clock at its first sample: the arrival of the buffer that starts it, less that buffer's remaining length.
  • Its own thread converts each chunk to 16-bit WAV and calls Meeting.append("system", seq, t_ms, wav, "wav"), the intake the audio route feeds.
  • Meeting.finish stops the stream and flushes the last partial chunk while still recording. Deleting a meeting cancels capture without a flush.
system_audio_reasonWhen
unsupportedNot macOS, or PyObjC's ScreenCaptureKit does not import

If the source cannot start, the meeting is microphone only and status and meta.json say system_audio: "unavailable". A working capture reports recording. Older meetings have no such field.

The microphone, on the page
  • The page asks for the microphone, then starts the meeting, and counts chunk offsets from the elapsed_ms in the start response, so both tracks share one clock.
  • MediaRecorder is stopped and restarted every 30 seconds. A timeslice recorder emits later chunks without a WebM header; restarting makes each a complete file, at a cost of a few milliseconds' gap per chunk.
  • A chunk carries track, sequence number and offset (t_ms), so out-of-order uploads land in place. One stopped under 100 ms after it started has only a header and is not uploaded.
  • Uploads are serialized and tried three times on network or 5xx errors.
  • The recorder lives in a module-level store: leaving the window does not stop it, only Stop does.
  • A refused microphone arrives as NotAllowedError; the window names the System Settings pane.
  • The recording card says whether the computer's sound is recorded. If not, it says microphone only and, for permission, names Privacy & Security → Screen & System Audio Recording and asks to reopen the App.

Store and transcribe

<state>/meetings/<id>/
  meta.json                   title, language, times, state, chunk counts, errors, engine,
                              session_id, system_audio, diarization, speakers
  tracks/<track>/<seq>.webm   the chunk as uploaded (system chunks are .wav)
  tracks/<track>/<seq>.json   timed segments (or silent / error); system segments gain speaker
  transcript.json             the merged transcript
  summary.md                  the summary with the transcript in a <details> block

One meeting at a time, at most 4 hours. Each chunk (up to 16 MiB) is written first, then queued for the meeting's single worker thread, so memory holds one chunk. A repeated (track, seq) is ignored. A chunk that fails is recorded and counted; the meeting goes on.

StageRule
Convertffmpeg, found on PATH, then /opt/homebrew/bin, /usr/local/bin, /usr/bin; it reads the format from the data. A WAV already in form is used as is. Without ffmpeg, start is refused with ffmpeg_missing and an install hint.
Skip silenceWhisper invents text for silent audio.
Transcribespeech_link.transcribe_segments(wav, duration_ms, language). A link without the method falls back to transcribe as one segment.
LanguageThe meeting's, never Settings → Voice's: a forced voice-input language makes Whisper invent text. POST /api/meetings takes an optional ISO language, stored in meta.json. The window sends the choice beside the meeting name, none for "Detect automatically". Empty means detection: whisper.cpp -l auto, no language field for OpenAI and Groq.
Timing by enginewhisper.cpp prints [from --> to] lines (no -nt). Groq and OpenAI Whisper models answer verbose_json. gpt-4o-*-transcribe answers text only: one segment spanning the chunk.
Merge, transcript.pySegments move onto the meeting clock and sort by start. A microphone segment at least 75% similar to a system segment starting within 4 s is echo (no headphones) and is dropped. Consecutive segments of one speaker less than 1.5 s apart join into one turn, up to 600 characters.
Linespeaker (me, others, others:<n>), which the window localizes, and English label ("Me", "Others", "Speaker n"). transcript.json is rewritten after every chunk, so the window shows it growing.

Access

  • Every route needs the owner's sign-in (require_owner).
  • The microphone is recorded where the page runs; the computer's sound is always the server computer's.
  • Meetings stay in the state directory. With a cloud speech engine each chunk goes to that provider.

Speaker diarization

Once per meeting, over the whole system track, so clustering sees every voice at once and no embeddings are matched across chunks. About 4 s per minute of audio on four threads.

StepWhat
AudioSystem chunks in order, converted one at a time and concatenated. concatenate records (concat_ms, t_ms, duration_ms) per chunk; to_meeting_clock maps turns back and splits one crossing a boundary.
Diarize, runsherpa-onnx OfflineSpeakerDiarization; pyannote segmentation-3.0; 3D-Speaker's bilingual CAM++ (3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced.onnx); up to four ONNX threads; min_duration_on 0.3 s, min_duration_off 0.5 s; FastClusteringConfig(num_clusters=-1, threshold=0.75), as the speaker count is unknown.
Label, assignEach system segment takes the speaker whose turns overlap it longest (ties: lower sherpa number). Renumbered others:1, others:2… by first appearance. Written back to the chunk JSON and merged again, so transcript.json, summary.md and the prompt carry "Speaker n".
Stays "Others"A segment no turn overlaps, or whose only voice was heard under MIN_SPEAKER_MS (3 s) in the whole meeting. Clustering leaves one- or two-second strays that would become "Speaker 5" to "Speaker 7".

Why this model and threshold

Tried on four recordings with known speakers: pyannote's AMI excerpt (two people talking over each other, scored against its labels), sherpa-onnx's four-speaker test, a two-voice recording and four synthesized voices.

SettingResult
CAM++, 0.6–0.75Right speakers on all four; 91% of AMI speech labelled right
CAM++, 0.8Merges two of the four Chinese speakers
Top of the range, 0.75On a four-person AMI meeting through a conference call and plain playback, splits one person into two numbers least often: five numbered voices, against seven at 0.65
ERes2Net zh-cn (sherpa-onnx's example)Needed a different threshold per recording; merged the AMI pair at every value that kept the four-speaker recording at four
Dependency and model download
  • sherpa-onnx is the optional meetings extra (with numpy), also in all so the packaged App carries it. Imported only inside run.
  • Models download on first use from sherpa-onnx's GitHub releases into <state>/models/diarization/: speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2 (only model.onnx extracted) and speaker-recongition-models/…_16k.onnx.
  • Each goes through a temporary file and an atomic rename under one lock, as voice input downloads Whisper models.

Implementation status

Everything above is built. Open: a check of the Screen & System Audio Recording prompt and permission classification in a freshly installed App.

How it is verified
  • Tests with a faked sample source, ffmpeg, speech, diarizer and summary turn.
  • The stable App recorded recordings played through the computer's sound output: sherpa-onnx's four-speaker test, an AMI two-speaker excerpt (both found), an AMI four-speaker excerpt (all four found, every line's number consistent with the reference).
  • A real call: two participants in a Jitsi Meet room, the second speaking the AMI four-person excerpt, the first playing it on this computer. Exactly four numbered speakers, every line consistent. Call audio reaches the recorder through the same path as Zoom or any other application.
  • Microphone track, from the Meetings window in a browser whose microphone was the AMI excerpt: seven chunks uploaded, six lines labelled "Me", summary written. The header-only last chunk was the one failure; the page now skips it.

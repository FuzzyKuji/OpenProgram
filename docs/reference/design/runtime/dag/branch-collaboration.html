Branch collaboration

A branch is a (session_id, head_id) pair, the same within a session and across sessions. Branching is not a special operation: checkout moves HEAD, and the next user turn becomes a sibling.

Switch, start again, rewind

OperationWhat it createsWhile a branch runs
Switch to an existing branchNothing; the view and the head move to that branch's tipAlways allowed
Start again from an old point: edit and resend, retry, send from a message selected in the graphA new branch beside the original, with its own record (branch_identity of the new message). Both stay and both can run. A retry of a prompt that never got a reply reruns that prompt insteadAllowed from any point while other branches run; waits while the selected branch's own turn runs
RewindNothing. The tail of the current branch is retracted in place: same branch id, name, settings and usage; the tip moves back before the chosen prompt, which returns to the composerRefused while that branch runs; one that changes files, while any branch runs

The DAG is append-only, so a rewind deletes nothing. It lists the retracted nodes in the session meta (rewind_hidden_nodes; the old tip in rewind_hidden_heads), written in the head's compare-and-set by rewind_view.view_update. Every reader skips them:

  • transcript, message reads and search;
  • branch list and version counts, so a message sent after a rewind continues the branch instead of adding a version;
  • the request's context, which walks back from the tip;
  • compaction: a summary of retracted turns is retracted too, and the summary before it applies again (active_summary_for_chain skips the graph's retracted set);
  • the context-commit timeline.

Undo and Redo of a rewind take the nodes off and back on the list. A switch to a retracted tip is refused and points to Undo. Conversations whose earlier rewinds left an extra branch keep it; nothing is migrated. File restoration: File management.

Peers agree that a rewind removes recent turns from the current line rather than starting a new one. Claude Code's /rewind slices the conversation in place and gives the prompt back; forking copies the session. Codex writes ThreadRolledBack with a turn count; the turns stay in the rollout file, leave the history and cannot anchor a fork.

The retracted list plays the part of Codex's rollback marker and keeps an Undo, which neither peer has in-session. Starting again stays a separate operation, so a person never loses the original by rewinding, and never gets a stray version by retracting.

Work that belongs to a branch

Work started on a branch keeps acting on it after the person selects another:

  • A Goal records the branch it was started on (branch_id). Its check-ins and verification continue and read that branch; a turn on another branch gets neither its instructions nor its accounting. A Goal saved before this follows the selected branch.
  • /merge and merge_branches write the reply to the branch they started on (target_branch_id) and move the head only while that branch is still selected.
  • A send_message queued for a busy conversation continues the branch it addressed, from that branch's tip.

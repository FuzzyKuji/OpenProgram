磁盘布局

<state>/projects/
├── projects.json                       项目注册表
├── <project_id>/                       `default` 是主目录项目
│   ├── settings.json                   项目默认设置
│   ├── memory/                         项目的记忆工作区
│   └── chats/
│       ├── <session_id>/
│       │   ├── main.jsonl              session 日志，由 Worker 写
│       │   ├── agents/<pid>-<id>.jsonl 其他写入进程的日志
│       │   ├── functions/<id>.jsonl    一个持久函数已完成的步骤
│       │   ├── large_nodes/            放不进日志行的大内容
│       │   ├── context/                持久化的上下文产物
│       │   └── workdir/attachments/    上传的文件
│       └── .file-recovery/<session_id>/<turn>/   按轮文件撤销
├── .chats-index.json                   注册表（摘要缓存）
├── .chats-locations.json               持久的 session-id → 目录映射
├── .migration/                         迁移 journal 和暂存
├── .deleted/                           持久的删除意图
├── .quarantine/                        启动时移走的无日志空壳
└── .locks/ .session-locks/             进程间协调
  • 没有项目的 session 放在 default/chats/。在其他根目录打开的 store（应用运行、嵌入宿主）用同样的结构。
  • 移动会重命名目录并记录到 .chats-locations.json，它在迁移或重定位期间是持久的权威来源。
  • 工作文件夹永远不是对话目录。<project>/.openprogram/sessions/<id>/ 只作为旧数据迁移来源读取。

Session 日志

每行是 {"ts", "type", "data", "crc"}：纳秒时间戳和该行的 CRC。只追加。

行类型记录
node.put、node.patch、node.delete写入、修改或移除 DAG 节点
meta.patch标题、设置和其他 session 元数据
file.put一个完整的小文档：jobs.json、notices.json、inbox.json、todos.json、open_work.json、always_on.json、always_on_reports.jsonl
turn.*Agent journal：快照、模型决策、启动的工具及其结果
turn.rows运行表的变更
function.*在 functions/ 中：持久函数的步骤、请求和保存的状态
  • 每个文件一个写者：Worker 写 main.jsonl，其他进程写 agents/ 下自己的文件。
  • 读取时按时间戳折叠所有文件，跳过 crc 失败的行，这只可能是已停止写者的最后一行。
  • 进程保留折叠结果，只读新增内容。已知文件被替换或变短，或新行排在已折叠内容之前时，从头重新折叠。
  • 只有实时推送片段不保留。

运行状态

执行、尝试、副作用、等待和命令从同样的日志折叠成 Worker 内存中的普通 Python 表，有自己的事务、撤销和唯一性规则。不用数据库。已提交的变更是一条 turn.rows。

项作用
~/.openprogram/active/<session>标记有未完成运行，启动时折叠。其他 session 首次用到时折叠
run_index.jsonl执行 → session
revisions.jsonlWorkflow 版本和审批，以及全局预算
空闲 session最后变更一小时后离开内存，需要时从日志恢复
函数子进程只读表。步骤写到 functions/ 下自己的日志；运行状态变更（启动子 Agent、Auto 审查结论、暂停、提问）经 runtime/execution/worker_calls.py 交给父进程
定时运行任务的那一轮在自己的进程里跑，这一轮的行写到 agents/ 下自己的文件。它启动的子 Agent 经 worker_calls.py 交给 Worker，由 Worker 运行。进程结束时 Worker 重新读取这一轮的行
worker.lock持有者拥有所有运行，租约写明属于别的进程的那一轮除外（定时运行、ACP、MCP）。没有心跳，进程退出时操作系统释放
Job 准入、预留运行表，在 session 日志中
usage.db 结算事件先提交，预留后结算。启动时结算事件已存在的预留，不重复计数

仍是数据库的存储

存储原因
usage.db只存记账（事件、请求、路由、探测），按时间、模型和范围分组
memory/index.sqlite全文搜索；可从记忆文件重建
processes.db分离的 supervisor 比 Worker 活得久，写同一条记录
session-resources.db工具进程上报资源；Page 写入跨进程隔离
programs/.runtime/应用子进程和宿主共享状态
project-file-history/history.sqlite3版本和它的分组一起提交

按键读取的小存储（user_errors.jsonl、file_operations.jsonl）是经 state/store/record_log.py 的键控只追加日志。

Worker 停止之后

进行中的事新 Worker
模型调用重新发送
只读工具重新运行
文件编辑对比文件哈希和记录的前后哈希
其他工具告诉模型工具被中断、不确定是否完成，由模型检查

中断不是存储的状态，而是日志里某轮没有最后一行。计划内升级先等运行结束。

状态

值含义侧栏
idle没有轮次在执行灰点
running轮次正在执行绿色旋转弧
needs_inputAgent 在等用户琥珀点
done后台任务完成蓝点，配合 unread
failed轮次失败红点，配合 unread；打开后变灰
interruptedWorker 在轮次中途退出灰点，不算运行中
cancelling、cancelled取消进行中，或跨重启完成取消

被杀死的 Worker 不会清除 running，聊天会卡在 data-run-active="true"。加载注册表时 running 重置为 idle；reconcile_interrupted_runs() 再把仍为 running 的行改成 interrupted、cancelling 改成 cancelled，它独立于节点清扫，因为在写状态和插入占位之间被杀的 Worker 会留下运行中的行，却没有运行中的节点。

移动 HEAD

_set_active_head（interfaces/server/server_runtime/session_persistence.py）是唯一途径。_save_session 会把每个 session 镜像的 head_id 和 messages 写回 SessionStore，镜像落后时下次保存就撤销移动。

  1. 写 SessionStore。
  2. 把新分支重新读入镜像。
  3. 丢弃消息缓存。
  • 用于 retry、edit、兄弟切换、跳到最深叶子、分支切换、分支删除、attach、rewind。
  • 运行中拒绝（_is_run_active）：RUN_ACTIVE_ERROR，code: "run_active"。否则回复会落到用户离开的分支，或正被删除的末端。

缓存和附件

  • SessionStore 在有界 LRU 缓存里惰性持有 (SessionLog, SessionMemoryIndex)。SessionLog 管文件，索引持有折叠后的节点、边和活动 head。
  • 浏览器上传在分发前复制到 workdir/attachments/，标记保留保存的绝对路径。
  • Channel 文件留在 <state>/channels/*/accounts/*/attachments，由附件路径策略单独允许读取。
  • 只有 <project>/.openprogram/sessions/<session_id>/workdir/attachments/<relative> 这一确切形式可重定到该 session 的当前目录（附件 UI、文件读取、send_file）。结果必须在允许的根内，不能经 .. 或符号链接逃逸。其他旧路径不重映射。

注册表时间与快照

updated_at 是最后一次内容追加的时间，不是最后一次元数据写入的时间。

操作合同
_persist_meta改名、置顶、已读、分支标记和 HEAD 不改变时间；追加才推进。分支记录取盘上的（分支记录）。
_index、list_sessions()读者拿到每行的点时副本；并发创建、更新、删除不撕裂字段，也不破坏迭代。
延迟 flush旧快照不能覆盖新快照；发布期间的更新保持 dirty，由下一次 flush 保存。

状态流

  1. 追加时生成一个时间值，同时写入会话元数据和注册表条目。
  2. 注册表更新持有状态锁；列表在锁内复制行，在锁外过滤和排序。
  3. 保存者取得写锁，在状态锁内捕获 JSON 并只清除已覆盖的 dirty，然后释放状态锁。
  4. 原子发布在状态锁之外执行。
  5. 并发更新重新标记 dirty，由定时器或退出 flush 发布。

失败与兼容

情况行为
写盘失败告警；内存继续服务；下一次更新或 flush 重试。
返回的行是副本，调用方修改不影响注册表。
创建保留显式传入的历史时间；重建不迁移 schema。
排序按 updated_at 降序，缺失视为 0；wire shape 不变。

分支记录

分支记录（meta["branches"][tip]：名字、自动命名状态、轮数、归档标记）有几个可能同时落下的写入者：close_agent 归档正在运行的 Agent、被它打断的那一轮收尾（carry_branch_entry、bump_branch_turns）、后台自动命名（set_branch_name）、Web 端改名、删除。每个写入者只改自己负责的字段，改的是盘上的那份记录。

规则做法
唯一合并点_update_meta 在会话写锁内读 meta.json，应用写入者的改动并写盘，再只把写过的键复制进缓存。没有写入者用早先读到的副本整条替换记录。
整份缓存写入_persist_meta、commit_turn、追加和删除节点写缓存时，branches、branch_refs、active_branch_id 取盘上的（_meta_for_write），漏掉别的写入者的缓存不会把旧记录写回去。追加在锁内读到的盘上那份上移动分支记录。
切换与回退切换分支和回退只说明要做的改动，不带整张表的副本：compare_and_set_head 在锁内读到的记录上应用 branch_checkout（apply_checkout）和 branch_record_moves。更新里整份的 branches、branch_refs、active_branch_id 一律丢弃，包括这条规则之前记进意图日志的。
名字只有一处所有读取者，包括分支列表，不论分支是否选中，都从分支末端的记录取名字（branch_record）。末端记录总是优先于暂存副本；后台运行带着未选中分支往前走时，记录一起带走。
记录跟着末端走分支每加一条消息，同一次写入就移动它的记录：选中分支在 advance_branch 里用 follow_line，其他分支用 carry_branch 和 point_branch。新末端上已有的记录合并进来，以它自己的字段为准。
迟到的末端写给分支已经越过的末端（最近一轮延伸的那条消息，或这一轮的用户消息）的写入，落到分支现在的记录上（_record_tip）。设置和 worktree 绑定按分支 id 存，不随末端移动。
共用末端回退到同一条消息的几个分支没法共用一条末端记录：选中的那个拥有它，其余的把自己的暂存在各自的 ref 上（label，离开时在锁内写下，再次选中时放回）。
归档不可撤销已归档的记录保留 archived、archived_at、archived_reason，之后的写入设什么都不变。
不复活对已不在会话里的消息计轮数或自动命名，什么都不写。分支写入从不创建会话。归档和普通命名可以给已受理、尚未写入的回复开记录。
归档为什么会丢

旧的写入者先在缓存里合并记录，再把整份缓存写盘。两步之间，一个在锁内读 meta.json 的写入者（收尾那一轮的 update_branch_fields）用盘上还没有归档的副本替换了缓存；归档自己的写入随后保存了不含归档的缓存，自动命名再开了一条新记录。

分支设置（update_branch_config）、worktree 绑定（update_session）和 Goal（带版本检查的 update_session_dict）本来就在锁内对盘上数据读改写。

切换分支时名字也是这样丢的。切换在加锁前读了整张 branches 和 branch_refs，用离开时暂存的副本覆盖了目标的记录，再随 HEAD 移动把两张表写回。

所以未选中分支的改名（列表只读暂存副本，看不到）在切换时连同锁一起丢了，自动命名也一样。

一轮运行时改名会丢掉分支的轮数。选中分支的记录一直留在旧末端直到这一轮结束，改名在屏幕上的末端另开一条记录，轮末带走的是这条。

Worker 在移动分支 ref 和记录之间卡住时，会留下两行：一行在旧位置、用原始 id 命名，一行在回复上、有名字但没有分支 id。

加载时不修复这一对。ref 落在一段延续之后，回退也会留下同样的形状，读取方不靠猜测分不开两者。现在 ref 和记录在同一把锁内一起移动。

验收：两个线程写会话、计轮数的同时归档 60 个 tip，一个不丢；同一目录上的两个 store（两个进程）对同一批 tip 归档和命名，两个字段都在；删除后迟到的取消归档、命名和计轮数都不改变任何东西。

Merged heads 原子更新

mark_merged(session_id, head_ids) 是集合并集。子 Agent 完成、task runner 和 Web 分支操作可能同时调用，每次更新都要保留。

属性要求
原子性在会话写锁内的同一个 _update_meta 中读盘、去重、追加并写盘。
顺序保留既有顺序；新的非空、strip 后的 ID 按输入顺序追加。
幂等重复不新增；没有新值就不写盘。
范围与验收
  • 两个调用方并发写入不同 head：内存和重载后都含两者。
  • 空白和重复输入保持清理与幂等语义。

Store 锁范围

一个会话的慢 I/O 不能阻塞其他会话。

资源锁要求
_locations、_sessions、LRU 顺序_lock只碰内存：不扫目录、不原子写、不 fsync、不递归删除。
单个会话的加载、重建、删除和失效会话的进程锁（conversation_lock）同一会话串行，不同会话并行。每个进程每个会话一把，所有 store 共用；它是写锁的前一半。没有 transaction 层。
locations.json 发布_locations_write_lock在状态锁内捕获，释放后写入；旧快照不能覆盖新快照。
SessionMemoryIndex 持久化_persist_lock，然后 idx._lock保持锁序和 stale rebuild 语义；idx._lock 内不做 I/O。
范围与验收

文件格式、LRU 容量、删除语义、跨进程 stale 检测和 Windows 行为不变。

  • A 阻塞在 read_meta 或 list_history 时，B 的缓存读取在有界时间内完成。
  • A 的递归删除阻塞时，B 的读取不等待。
  • 并发首次加载只发布一个缓存对象；加载不会重新发布已删除的对象。
  • 两个会话并发更新位置后，重载的 locations.json 含两项。

会话锁的顺序

所有路径按同一顺序取一个会话的锁；持有任何一把时都不等模型、网络或另一个会话的锁。

  1. 进程锁：每个会话一把可重入锁，本进程的 store、服务端和 job、事件、checkpoint 辅助代码共用。
  2. projects/.locks/<id>.lock 上的 flock，经 session_interprocess_lock 获取，它先取第 1 步。持有者只用一个文件描述符；同一线程里嵌套获取在它上面计数，不再打开第二个描述符（第二个会等第一个）。
  3. 内层锁：索引的 _persist_lock 和 _lock、store 的映射、注册表文件、回退 intent 锁和工作区锁。

回退，以及一轮文件的撤销和重做，从查幂等键开始，经过计划和写 intent，到出结果，一直持有第 1、2 步；恢复也在它们之下重放日志，所以恢复不会重放一个仍在执行的回退。

同一个键的第二个请求等第一个结束，返回它记下的结果，不论提交还是失败：不会按第一个留下的状态重新计划，不会把未完成的 intent 当成待恢复的，也不会再执行一次。

回退和撤销也在恢复范围内执行：持有工作区锁期间会话被挤出 store 缓存时，检查 head 引起的重新打开不会重放它自己的 intent；否则会第二次去拿工作区锁，等的是它自己。

两步等待都有上限（默认 60 秒，调用方传了超时就用更短的）：超过后抛 SessionLockTimeout，写明会话和持有者（本进程的某个线程或另一个进程），请求失败，而不是让 Worker 线程一直卡住。

原因与验收

分支记录合并把更多写入放进 flock 之下后，两条路径以相反顺序取这两半：切换分支持有 store 的锁、等 flock，页面加载持有 flock、等 store 的锁来读会话；运行准入也一样。

之后这个会话上的所有请求都排在这一对后面，Worker 不再响应。

  • 十六个线程同时操作一个有五个分支的会话：两个分支上的轮次、改名、换模型、删分支、并发切换、回退计划、页面加载、运行准入和缓存失效，全部完成，连续 200 次；看门狗在卡住时带着各线程栈让测试失败，而不是挂住。
  • 会话被一个卡住的线程持有时，下一个写入者在等待期内拿到写明该会话的错误；其他会话不受影响。
  • 获取与释放之间出错（被拒的切换、过期的计划）会释放锁。
  • 两个进程和两个线程同时往一个会话追加，每条消息都写入；持有 flock 的进程被杀后，已在等待的写入者继续；执行中途会话被挤出缓存的撤销照常提交。
  • 同一个键的两次回退或两次撤销：第一个在写 intent 之前或之后暂停时，第二个等它，然后返回它提交的结果；第一个已提交或已失败时，第二个返回那个结果；文件和 head 只变一次。

缓存快照新鲜度

  1. 缓存重建和首次加载在读取历史与元数据之前获取磁盘指纹。
  2. 重建后的索引只记录这个指纹，绝不记录更新的指纹。
  3. 并发原子替换会改变指纹，下一次公共读取因此重建。
验收

两个真实 SessionStore 实例。写入发生在读者加载旧快照之后、标记同步之前；下一次 get_nodes 或 get_session 看到新值，缓存和首次加载路径都覆盖。取消重试保留原有时限，并读取实际的取消文件。

Storage consistency

Data model: Session storage.

Registry timestamps and snapshots

updated_at is the last content append, not the last metadata write.

OperationContract
_persist_metaRename, pin, read markers, branch markers and HEAD keep the timestamp. Append advances it. Branch records come from disk (Branch records).
_index, list_sessions()Readers get a point-in-time copy of each row. Concurrent creation, mutation and deletion cannot tear fields or break iteration.
Deferred flushAn older snapshot cannot overwrite a newer one. Mutations during publication stay dirty for the next flush.

State flow

  1. Appending generates one timestamp for session metadata and its registry entry.
  2. Registry mutations hold the state lock. Listing copies rows under it, then filters and sorts outside.
  3. A writer takes the write lock, captures JSON and clears only the covered dirty state under the state lock, then releases that lock.
  4. Atomic publication runs outside the state lock.
  5. A concurrent mutation marks the registry dirty again; a timer or exit flush publishes it.

Branch records

A branch record (meta["branches"][tip]: name, auto-name state, turn count, archive flag) has several writers that can land at once: close_agent archiving a running agent, the turn it cut off finishing (carry_branch_entry, bump_branch_turns), the background auto-namer (set_branch_name), a rename from the Web, a delete. Each one changes only the fields it owns, on the record as it is on disk.

RuleHow
One merge point_update_meta reads meta.json inside the session write lock, applies the writer's change, writes, then copies only the written keys into the cache. No writer replaces a record with a copy it read earlier.
Whole-cache writes_persist_meta, commit_turn, append and node deletion write the cached meta with branches, branch_refs and active_branch_id taken from disk (_meta_for_write), so a cache that missed another writer cannot put an old record back. Append moves the branch records on the disk copy it read inside the lock.
Switch and rewindA branch switch and a rewind name their change instead of carrying copies of the maps: compare_and_set_head applies branch_checkout (apply_checkout) and branch_record_moves to the record it read inside the lock. Whole branches, branch_refs or active_branch_id values in its update are dropped, including ones in an intent journaled before this rule.
One name sourceEvery reader, the branch list for selected and unselected branches alike, takes a branch's name from its record at its tip (branch_record). A tip record always wins over a parked copy, and a background run carries its unselected branch's record along.
Record follows the tipEvery message a branch adds moves its record in the same write: follow_line for the selected branch (inside advance_branch), carry_branch and point_branch for another. A record already at the new tip is merged into it, its own fields winning.
Late tipA write addressed to a tip the branch has moved past (the message its latest turn extended, or that turn's user message) goes to the branch's record now (_record_tip). Settings and the worktree binding are keyed by branch id and never move.
Shared tipsBranches rewound to one message cannot share a tip record: the selected one owns it; each other parks its own on its ref as label (written inside the lock when left, put back when selected).
Archive is finalA record that is archived keeps archived, archived_at and archived_reason whatever a later write sets.
No resurrectionA turn count or automatic name for a message that is no longer in the conversation writes nothing. A branch write never creates a conversation. An archive or a plain name may open a record for a reply admitted but not yet written.
Why the archive was lost

The old writers merged the record in the cache, then wrote the whole cache. In between, a writer that reads meta.json under the lock (the finished turn's update_branch_fields) replaced the cache with the disk copy, which did not hold the archive yet. The archive's own write then saved a cache without it, and the auto-namer later opened a fresh record.

Branch settings (update_branch_config), the worktree binding (update_session) and the Goal (update_session_dict with a version check) were already read-modify-write on disk under the lock.

Names were lost the same way on a branch switch. The switch read the whole branches and branch_refs maps before the lock, overwrote the target's record with the copy parked when it was left, and wrote both maps back with the HEAD move.

So a rename of an unselected branch, which the list did not show because it read only the parked copy, lost its name and lock on the switch; automatic names too.

A rename while a turn ran lost the branch's turn count. The selected branch's record stayed at the old tip until the turn ended, the rename opened a second record at the tip on screen, and the turn's end carried that one.

A Worker that hung between moving a branch's ref and its record left two rows: one at the old position named by a raw id, one at the reply with a name and no branch id.

Loading does not repair the pair. A ref behind a continuation is also what a rewind leaves, and the reader cannot tell the two apart without guessing. Ref and record now move under one lock.

Acceptance: archiving 60 tips while two threads write the session and count turns loses none; two stores on one folder (two processes) archiving and naming the same tips keep both fields; a late un-archive, a late name and a late turn count after a delete change nothing.

Atomic merged-head updates

mark_merged(session_id, head_ids) is a set union. Child-agent completion, task runners and Web branch actions can call it at once; every update survives.

PropertyRequirement
AtomicityRead from disk, deduplicate, append and write in one _update_meta section under the session write lock.
OrderExisting order kept; new, nonempty, stripped IDs follow in input order.
IdempotencyRepeats add nothing. No new value, no disk write.
Scope and acceptance
  • Two concurrent callers with different heads: both present in memory and after reload.
  • Whitespace and duplicates keep normalization and idempotency.

Store lock scope

Slow I/O for one session must not block others.

ResourceLockRequirement
_locations, _sessions, LRU order_lockMemory only: no directory scan, atomic write, fsync or recursive delete.
Load, rebuild, delete and invalidate one sessionThe conversation's process lock (conversation_lock)Same session serialized; different sessions concurrent. One lock per conversation per process, shared by every store; it is the first half of the write lock. No transaction layer.
locations.json publication_locations_write_lockCapture under the state lock, write after release. An old snapshot cannot overwrite a newer one.
SessionMemoryIndex persistence_persist_lock, then idx._lockLock order and stale-rebuild semantics kept. No I/O under idx._lock.
Scope and acceptance

File formats, LRU capacity, deletion semantics, cross-process stale detection and Windows behaviour do not change.

  • While A blocks in read_meta or list_history, B's cached read finishes in bounded time.
  • While A's recursive delete blocks, B's read does not wait.
  • Concurrent first loads publish one cached object; loading cannot republish a deleted one.
  • After concurrent location updates for two sessions, reloaded locations.json holds both.

Conversation lock order

Every path takes a conversation's locks in one order, and no path holds one while waiting on a model, the network or another conversation's lock.

  1. The process lock: a reentrant lock per conversation, shared by the store, the server and the job, event and checkpoint helpers of this process.
  2. The flock on projects/.locks/<id>.lock, through session_interprocess_lock, which takes step 1 first. The holder keeps one descriptor; nested acquisitions in its thread count on it instead of opening a second descriptor, which would wait on the first.
  3. Inner locks: the index's _persist_lock and _lock, the store's maps, registry files, the rewind intent lock and the workspace lock.

A rewind, and a revert or reapply of a turn's files, holds steps 1 and 2 from looking up its idempotency key, through its plan and intent, to its outcome, and recovery replays the journal under them, so recovery never replays a rewind still being applied.

A second request with the same key waits for the first and returns its recorded outcome, committed or failed: it never plans against the state the first one left, never reads an unfinished intent as one needing recovery, and never applies a second time.

A rewind or a revert also applies inside its recovery scope: when its conversation leaves the store cache while it holds the workspace lock, the reopen its head check makes does not replay its own intent, which would take the workspace lock a second time and wait on itself.

Both waits are bounded (60 s by default, shorter where a caller passes a timeout): past it, SessionLockTimeout names the conversation and the holder, a thread of this process or another process, and the request fails instead of blocking a Worker thread.

Why, and acceptance

The branch-record merge put more writes under the flock, and two paths took the halves in opposite orders: a branch switch held the store's lock and waited for the flock, while the page load held the flock and waited for the store's lock to read the conversation. A run's admission did the same.

Every later request on that conversation queued behind the pair and the Worker stopped answering.

  • Sixteen threads on one conversation with five branches, turns on two branches, renames, a model change, a branch deleted, concurrent switches, a rewind plan, page loads, run admissions and cache misses all finish, 200 runs in a row; a watchdog fails the test with the stuck stacks instead of hanging it.
  • A conversation held by a stuck thread gives the next writer an error naming it within its wait; other conversations are not held up.
  • An error between acquire and release (a refused switch, a stale plan) releases the lock.
  • Two processes and two threads append to one conversation and every message lands; a process killed while it holds the flock frees it for a writer already waiting; a revert whose conversation leaves the cache mid-apply commits.
  • Two rewinds, or two reverts, with one key: while the first is paused before or after writing its intent, the second waits and then returns the first's committed outcome; after the first committed or failed, the second returns that outcome; files and head change once.

Cache snapshot freshness

  1. Warm rebuilds and first loads capture the disk fingerprint before reading history and metadata.
  2. The rebuilt index records that captured fingerprint, never a newer one.
  3. A concurrent atomic replacement changes the fingerprint, so the next public read rebuilds.
Acceptance

Two real SessionStore instances. A write lands after a reader loads the prior snapshot and before it marks synchronization; the next get_nodes or get_session sees the new value, on cached and first-load paths. Cancellation retry keeps its deadline and observes the actual cancelled file.

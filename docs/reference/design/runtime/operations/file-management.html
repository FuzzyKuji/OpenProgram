File changes, Review and recovery

A historical rewind marker is shown only beside its anchor message in the loaded history window. An offscreen anchor must not move its marker to the latest message. Pending rewind controls remain at the current end.

Shared workspace and same-branch rewind

A conversation branch records a route through messages, not a private filesystem. Fork and retry retain their existing explicit conversation versions; switching them never restores files, pauses tools or asks which files to use. The model receives a current-workspace note and must reread files before editing.

Rewind is a different operation: withdraw the selected prompt and its suffix on the current branch, and restore its recorded file changes when code recovery is selected.

Existing sibling branches and their shared messages remain intact. Withdrawn messages remain in durable recovery storage for Undo and crash recovery, but disappear from branch lists, version navigation, the conversation graph and normal context.

A later message extends the same named branch. Undo and Redo change the withdrawal view on that same branch; their existing message-only semantics are stated explicitly and do not restore files.

Recovery must not overwrite later writes by another branch, another session or a human. A code recovery with an unsafe, missing or conflicting file is blocked before any file or conversation change; conversation-only recovery remains an explicit alternative.

Previews bind the head, target, file states and mode. Duplicate requests replay their recorded outcome; failures roll back and interrupted operations recover before exposure. Existing legacy intents retain their original recovery semantics. Old workspace-alignment flags have no authority to stop a message or tool.

Branch identity is independent of its head message. When two rewinds converge at one checkpoint or ROOT, each ref retains its name and remains selectable by branch id. Undo marks belong to that identity. Selecting by head alone remains compatible for unambiguous legacy clients.

Back and Forward

Each tab keeps its own page history: Folder A, subfolder B, file 1, file 2. Opening somewhere new after Back replaces forward history. Folders restore path, expansion and scroll; files keep autosave.

Only explicit positioning, search navigation or restoration moves the viewport; list paging, background refresh and size updates do not. Navigation history never mixes with file-version History, writes to disk or polls.

Save order and publication
  1. Write each before and after as an independently complete file; verify it; fsync the version directory.
  2. Publish the manifest. A failed update leaves referenced content intact; a failed attempt never overwrites published versions.
  3. Retry rereads the current file as before only after explicit cancel of an unsuccessful attempt. A success keeps the turn's first before.
  • Regular-file snapshots compare descriptor metadata before and after reading, and path metadata before opening and after reading.
  • Device and inode must agree; metadata from different OS APIs is never compared as if alike. Any change aborts publication.
  • The path observation supplies the stored mode.
  • Legacy migration on Windows opens staged files writable before flushing and keeps the source until publication succeeds.

Old manifests and blob_ref stay readable without bulk rewrites. Lost history is not reconstructed. OS crashes and programs ignoring locks may need manual recovery: evidence is kept, uncertain overwrites refused.

Publishing documents: write(file_path, source_path=...)
  • Exactly one of content or source_path. The source is a local regular file under read permission, up to 64 MiB. Identical paths, directories, links and oversized or unreadable sources fail before any change.
  • Targets keep write authorization, read baseline and approval fingerprint. Source and target fingerprints join approval waits and are rechecked before publication.
  • Bytes go to a complete temporary file in the target directory, then replace. Failure cleans up and keeps the target. Raw bytes, never text-converted.
  • Advisory locks serialize cooperating writers only. Windows closes handles lacking delete sharing before replacement and revalidates; no OS conditional replace.
  • Read first: models read originals, then generate staged versions. Binary reads return type and byte count. New files need no prior read.
  • Generators call this path; text tools keep write, edit and apply_patch and share prepare, commit and abort. CheckpointStore owns state; Review and summaries are projections.
  • Not provided: Word tracked changes, PPT visual diffs, Office semantic diffs, remote stores (these need conditional writes and verifiable version IDs before claiming recovery), full-disk scans, polling, plugin registry.

Mutation journal

One manifest per turn, under CheckpointStore (openprogram/state/store/snapshot/checkpoint/). Each file entry:

path, operation
create, modify, delete, rename
before, after
{kind: "regular", digest, blob_ref, mode, size} or {kind: "absent"}
status
Prepared, committed or aborted, with prepared_at, committed_at
stats, diff_state
Lines added and removed, binary; available, large, binary or timeout
recoverability
Exact or unavailable, with unavailable_reason
mutation_sequence
Durable and monotonic; multi-turn folding uses this, not DAG order
Invariants
  • Prepared persists before the write; committed only after confirming the after state. If preparing fails, the mutator stops before touching disk.
  • absent means absence was confirmed. A baseline read failure is recoverability=unavailable, never absent.
  • unavailable applies only to journaled mutations whose size or type policy omits blobs, never to hide journal failures.
  • Same-file edits in a turn fold to net first-before to last-after; rename keeps lineage. Regular before and after both keep blob refs.
  • Paths are recanonicalized at capture, plan and apply; parent chain, leaf lstat, device, inode and link count are checked with validated handles or no-follow primitives.
  • Revert, Restore and Reapply are also transactions; originals are immutable. Current branch folds the active lineage only.
  • Each prompt defines before_turn, assistant completion after_turn; the UI names the restored boundary.

Cursors and Workspace snapshots
  • Cursors are opaque and valid only for the same snapshot, owner, query kind, filter and sort. Offsets, path anchors and cross-project tokens are rejected. Directory, search, Review list and diff cursors are not interchangeable.
  • Snapshots keep a stable candidate order. Later pages never rescan. Capacity and TTL eviction report stale.
  • A Workspace snapshot fixes staged, unstaged, untracked and rename or delete paths by relative path, pinning HEAD base, index blob and worktree identity, and old and new paths. Diffs render from that pair, never a later git diff.
  • Before later pages or diffs: status vector, index tree and no-follow worktree identity are reread. Any change is stale.
  • The worktree side compares as Git does: when text, eol or core.autocrlf clean line endings, CRLF becomes LF first (for auto, only when the indexed blob has no CR), so a CRLF checkout of an LF blob shows only edited lines.
  • Hunk revert edits the file in its own line endings.
  • Snapshot blobs share Review quotas; missing or expired blobs report stale, never approximate from the worktree.

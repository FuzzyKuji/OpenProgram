How ask_user finds an answer
  1. A handler set by run_with_follow_up, scoped to the execution context and inherited by its background thread, or the global CLI handler. The scoped handler neither replaces the frontend handler nor captures another concurrent Workflow's question.
  2. runtime.ask, when the runtime has a question transport or a connected session.
  3. Terminal input, on a TTY.
  4. None.

Each FollowUp accepts one answer; a second fails at once.

Live Workflow ownership

The subprocess runner binds execution ID, attempt ID, generation and producer identity for the call. A runtime without this binding cannot create a live question.

Creating and answering both verify, in one transaction, that the execution is running, the attempt is the current active owner and its lease is valid.

Verification

Tests use public ask_user with the real Runtime and canonical wait commands: same-call continuation, cancellation, invalid owner or session, transport failure, producer cleanup. Native acceptance needs a question in the installed App, a browser refresh, and an answer that lets the Workflow finish. A returned WAITING_USER object does not show the UI worked.

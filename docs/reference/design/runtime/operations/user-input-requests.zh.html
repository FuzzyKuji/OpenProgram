runtime.confirm 和 runtime.form 使用同一提问通道。

ask_user 如何取得回答
  1. run_with_follow_up 设置的 handler（作用域为执行上下文，后台线程继承），或全局 CLI handler。作用域 handler 不替换前端 handler，也不会截获其他并发 Workflow 的问题。
  2. runtime.ask，当 runtime 有提问通道或已连接会话时。
  3. 终端输入，当运行在 TTY 上时。
  4. None。

每个 FollowUp 只接受一次回答，重复回答立即失败。

运行中 Workflow 的归属

子进程执行器在调用期间绑定 execution ID、attempt ID、generation 和进程实例身份。没有该绑定的 runtime 不能创建运行中问题。

创建与回答都在同一事务里检查：execution 正在运行，attempt 仍是当前有效执行者，租约有效。

发布
子进程通过 QueueTransport 发送 question.asked；父进程从已保存的请求生成前端事件，并转发正式回答通知
回答依据
正式等待存储。registry 只负责唤醒本地等待。
拒绝
重复回答和其他 execution 的回答，由命令协议拒绝

事件结果

执行者失效取消遗留问题；迟到回答不能继续已结束的调用

验证

测试使用公开 ask_user、真实 Runtime 和正式等待命令：原调用继续、取消、归属或会话无效、传输失败、进程清理。本机验收要求安装版 App 中出现问题、刷新浏览器、回答后 Workflow 完成。返回 WAITING_USER 对象不能说明界面可用。

Agent 协作

保存的 AgentSpec 是可复用的配置（Agent 配置）。运行时分支是对话状态，可以运行多个 Job；创建分支不会创建 AgentSpec。隔离代码修改：worktree 工具。21 个参考框架怎么做：对比。

工具

模型看到五个协作工具。其余工具仍为已存的对话记录和程序运行，但不再提供给模型。

工具作用

send_message把工作或问题交给已有的 Agent：按名称找保存的 Agent、对话、助手、分支。配合 notify_when_idle 也可以只等它空闲。

read_conversation读历史；给它 execution_id 时报告该 Job 的状态和结果
close_agent停止本对话启动的助手并归档其分支；给地址时归档该分支

权限

对每个助手和送达的消息，调用方的模式、规则、额外文件夹和沙箱在 Job 接纳时冻结进去（spawn_permission_snapshot；交给项目决定的沙箱按调用方的对话解析），再由 Agent 的 permissions 收窄。

设置助手得到
模式两者中更严的，顺序为 Plan、Ask、Accept edits、Auto、Bypass
拒绝和询问规则调用方的加上 Agent 的
允许规则调用方的；Agent 列了允许规则时，只留它也列的。只有 Agent 自己的允许规则不放行任何东西。
额外文件夹调用方的；Agent 列了文件夹时，只留它也列的
沙箱任一方开启即开启
需要批准的调用，发生在结果
人发起的回合的前台助手（全新或分叉）调用方对话里现有的批准卡片，提示以助手名开头，例如 [scout]。回答让助手继续；调用方的工具调用一直等着。“总是允许”照常为对话保存规则。
后台助手、送达的消息、分叉到另一个对话，或调用方背后没人回答立即拒绝（HELPER_CANNOT_ASK）：工具结果让它不做这一步继续，并在最终回复里写明需要什么。不会有东西在等。

这条路线在接纳时冻结在助手存下的输入上（asks_through），只在它的调用方就是它继承策略的那个正在运行的所有者回合时才有。这只是把已有的询问换个地方显示，不增加询问。

结果

助手完成、失败、被停止或卡住时，无论作为工具结果还是通知送回，都用同一个块报告：

<agent name="scout" id="j_4f2…" status="completed">
Found the leak in pool.py: the reader never closes on timeout.
files: 2 changed (+14 −3): pool.py, test_pool.py
usage: 2 min 10 s · 18 tool calls · 41.2k tokens · $0.084
</agent>
部分规则
statuscompleted、failed、stopped 或 stalled；限制导致的会加 reason（user、spend cap、timeout、idle limit）
回复最终回复，超过 20,000 字符截断并附 read_conversation 指引；后台派生的回复在它的卡片上，通知只说明这一点，不重复；被停止的助手无论是等待中还是后台运行，都没有最终回复，结果写 (no reply) Its work so far: read_conversation("<id>")，分支末端是它正在写的那条回复，和 Claude Code 只告诉调用方任务已停止一样
文件助手有自己的 worktree 时：改动的文件和行数
用量时长、它分支上的工具调用、来自用量账本的 token 和成本；价格未知的成本不写，不估算
阶段行为
排队每条结束路径都经过 JobRunner._update_attach_card：在卡片上写状态和用量，执行 archive_when_done，在调用方的 notices.json 里排一条。包括完成、出错，以及被人或限制停止的后台 Job；卡住作为单独一条只排一次。
送达run_job_notices 每 2 秒扫描；前台执行在跑时会话算忙。所有待发条目合成一个自动通知回合（source="job_followup"）。通知没有超时，调用方忙时回复也不会丢。
失败同样报告；通知提示缩小范围用 send_message 重试，或告诉用户。不会自动重新提交。

已存的交接

已移除的 handoff 工具把它的回合存在 <state>/always_on/handoffs.json。Worker 启动时，在旧重放读这个文件之前，每条还在等忙碌对话的记录转到 send_message（always_on/handoff_migration.py）：

记录变成
等待中的消息从发送方到目标的一次投递，保留跳数；回复以通知返回
等待中的回复从作答的对话（回复里写明）到提问对话的一次投递
运行中或暂停的回合保留；它欠的回复照旧在结束时发出
还欠更早对话回复的等待消息（owed_after）保留；send_message 没有转交链，由旧的重放接着送
已结束的，或没写明对话的回复保留，照旧一天后过期

先把文件复制一次到 handoffs.before-migration.json。每条迁走的记录原样留在 handoffs.migrated.json，附投递状态和 execution_id。每次投递的 Job id 由记录决定，Worker 中途停下也只送达一次。

send_message 拒收的投递换一个 Job id 保持待送，下次 Worker 启动再试；对话已不存在的记为失败。不带 apply 的 migrate() 只报告。记录里的 📨 和 ↩️ 行不变。

接收方在最终回复里作答；再用 send_message 回发会送达两次，回执里写明了这一点。来自另一个对话的消息标为另一个 Agent 的输入，而不是接收方的用户。

附着指针和跨会话派生

派生会写一个附着指针，predecessor = caller_msg_id；子分支从不并入调用方。send_message 不写指针，所以回复内联在通知里。

S 中的调用节点 A 用 start_from="T:M" 时在 T 中运行。Job 记录 parent_session_id=T、parent_msg_id=M、caller_session_id=S、caller_msg_id=A。S 中的卡片按 extra.attach.session_id 和 head_id 查找；创建或完成它都不移动 S 或 T 选中的 HEAD（DAG 附着渲染）。

目标正忙

发给运行中分支的消息绝不打断它，也绝不丢弃。

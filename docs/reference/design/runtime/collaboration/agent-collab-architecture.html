Agent collaboration: tool surface

Contract: Agent collaboration. Eight implementations compared: comparison.

Four domains

DomainWhat it isTools
Planning: todoA hand-kept plan. Editing runs nothing.todo_create, todo_update, todo_list
Execution: jobAn admitted record with execution_id, state and resultread_conversation(execution_id), list_agents, close_agent; execution.cancel is a command for the UI and API
Entities: agentA running conversation branch. A saved AgentSpec is separate configuration chosen by agent.agent, list_agents, close_agent
Communication: messageContinues a branch or reads its historysend_message, read_conversation

The domains describe resources, not disjoint namespaces. Cancelling work neither archives the branch nor deletes its configuration.

Background dispatch returns execution_id. details.job_id and attach.job_id keep their names: pass the execution ID there. No task_id aliases.

Automatic completion notice
  • Every path ending a job goes through _update_attach_card: patches the card, finalizes archive_when_done, then notices.queue(job).
  • A finished, failed or stopped background agent, or the reply to a send_message, starts a notice turn in the sending conversation, in one result shape. Nothing is said for an agent the sender closed with close_agent.
  • A mid-turn conversation gets it when the foreground turn ends; everything finished meanwhile shares one notice. Pending notices live in <caller-session-dir>/notices.json and survive a restart.
  • The notice lands at the delivery session's HEAD and advances it, so results form one serial chain. A spawn's report is in context through its attach pointer; a delivery to an existing branch carries the reply inline.
  • send_message(to=…, notify_when_idle=true) with no message rides the same queue and reports the target's latest reply once it goes idle.

Live, stored in the agent section of ~/.openprogram/config.json, and in Settings → Agent.

  • A completion notice re-binds the finished job's message count without adding one. Generation depth returns to the dispatcher's value: reading results is not creating, so a coordinator can start the next batch.
  • Admission is independent: max_jobs_per_session, max_queued_per_session, max_live_per_session; see resource governance.
  • Self-messaging is always refused: to= addressing the initiator's current branch is a direct cycle.

Archiving

Branches stay in the session DAG. Archiving writes archived: true into the branch's shared metadata, seen by every sender. Set by archive_agent(to="name") or by agent(archive_when_done=true) on completion.

Call on an archived branchResult
send_message(to=…)Refused by the shared address resolver, once the address resolves to the tip
list_agents default viewLeft out
list_agents(scope="archived")Listed
read_conversation(…)Full transcript
agent(start_from="SID:MSG_ID")Forks a new branch. This is the only way on; there is no unarchive.

Scenarios

Dispatch a batch of tasks
  1. todo_create(subject=…), with blocked_by for dependencies.
  2. One background agent(prompt, description, run_in_background=true) call per task; each hands back its execution_id immediately.
  3. list_agents() for running work; read_conversation(execution_id) for output; close_agent or the UI to stop.
  4. Completion notices arrive in the caller.
  5. todo_update(todo_id, status="completed").
Reuse an existing agent
  1. list_agents(scope="all"): grouped by session, with name, usable to="SID:HEAD", turn count, approximate word count and tail preview.
  2. send_message(to="name", message=…) to ask, notify, or give it work; its reply comes back as a notice.
  3. A busy target queues the work, without interruption or loss, until the current turn finishes.
Inspect an old conversation
  1. list_agents(scope="all") for the address and size.
  2. read_conversation(session_id="SID:HEAD", start_turn=-10): negatives count from the end.
  3. include_function_calls=false for text only; the default includes tools, arguments and results.
  4. max_chars=60000 drops later turns past the limit. Archived branches stay readable.

Attach cards

A call at message A in source session S creating a branch in T persists an attach node in S with predecessor=A, extra.attach.session_id=T, extra.attach.head_id=H. Stream data.session_id=S picks the conversation; card_id is stable. There is no attach.caller_session_id.

The mapper attaches cards to caller messages in S; AssistantBubble separates same-session and external cards. A cross-session target is not a DAG node in S: resolve H in T, never search S for H or move the card.

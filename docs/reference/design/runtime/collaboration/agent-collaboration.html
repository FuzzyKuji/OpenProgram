Agent collaboration

A saved AgentSpec is reusable configuration (Agent configuration). A runtime branch is conversation state and can run many Jobs; creating one creates no AgentSpec. To isolate code edits: worktree tools. How the 21 reference harnesses do this: comparison.

The model sees five collaboration tools. The others still run for stored transcripts and programs, but are not offered to the model.

Each choice follows one of the 21 reference harnesses (comparison).

Saved Agent settings

SettingRule
delegationon: listed in the agent description and startable by other agents. Empty: on for an Agent with tools, off for one without (tools.mode="none"). Editing the list announces a prefix-cache break (agent_roster).
isolationworktree or none when started by another agent. Empty: a background helper whose tools can write gets its own worktree in a git repository, otherwise shares the folder. A call's isolation wins.
permissionsWhat it may do when another agent starts it: mode, allow, deny, ask (rules), additional_directories, sandbox. Each key only narrows its caller (Permissions). Empty: it runs as its caller. Its tool policy narrows the same way.
ExplorerBuilt-in, read-only (read, search, web, read_conversation)

Both settings are stored on agent.json and travel through PATCH /api/agents/{id} and AgentConfigDTO. Empty means the default, so no stored Agent is rewritten.

Permissions

For every helper and delivered message, the caller's mode, rules, extra folders and Sandbox are frozen into the Job when it is admitted (spawn_permission_snapshot), a Sandbox left to the caller's project resolved against the caller's conversation; the Agent's permissions block then narrows them.

SettingThe helper gets
ModeThe stricter of the two, in the order Plan, Ask, Accept edits, Auto, Bypass
Deny and ask rulesThe caller's plus the Agent's
Allow rulesThe caller's; when the Agent lists allow rules, only those it also lists. An Agent's allow rule alone allows nothing.
Extra foldersThe caller's; when the Agent lists folders, only those it also lists
SandboxOn when either turns it on
A call that needs approval, inResult
A foreground helper (fresh or fork) of a person's turnThe existing approval card in the caller's conversation, its prompt starting with the helper's name, e.g. [scout]. The answer resumes the helper; the caller's tool call keeps waiting through it. "Always allow" saves the rule for the conversation as usual.
A background helper, a delivered message, a fork into another conversation, or a caller no person answers forRefused at once (HELPER_CANNOT_ASK): the tool result says to go on without it and name what was needed in the final reply. Nothing waits.

The route is frozen on the helper's stored input (asks_through) at admission, only when its caller is the live owner turn whose policy it inherited. This moves where an existing question is shown; it adds none.

Closing and archiving

close_agent(execution_id) checks the Job belongs to this conversation, stops it with its descendants (cancel.parent, so no stop notice comes back about the caller's own act), archives its branch and drops its pending notice. Archiving writes archived: true to the branch; history is kept and there is no unarchive.

On an archived branchResult
Normal list_agentsHidden; scope="archived" shows it
New send_messageRefused
Running executionContinues, unless closed with close_agent
read_conversation, historical forkAllowed; archive grants nothing
agent(archive_when_done=True)Archived by the terminal hook once its result is back

Results

A finished, failed, stopped or stalled helper reports in one block, whether it comes back as the tool result or as a notice:

<agent name="scout" id="j_4f2…" status="completed">
Found the leak in pool.py: the reader never closes on timeout.
files: 2 changed (+14 −3): pool.py, test_pool.py
usage: 2 min 10 s · 18 tool calls · 41.2k tokens · $0.084
</agent>
PartRule
statuscompleted, failed, stopped or stalled; a limit adds reason (user, spend cap, timeout, idle limit)
ReplyThe final reply, cut at 20,000 characters with a read_conversation pointer; a background spawn's reply is on its card, so the notice says so instead of repeating it; a stopped helper, waited on or in the background, has no final reply and reads (no reply) Its work so far: read_conversation("<id>"), with its branch tip set to the reply row it was writing, as Claude Code tells the caller only that the task was stopped
FilesWhen the helper had its own worktree: changed files and line counts
UsageDuration, tool calls on its branch, tokens and cost from the usage ledger; a cost with an unknown price is left out, not guessed
StageBehaviour
QueueEvery terminal path goes through JobRunner._update_attach_card: patches the card with status and usage, applies archive_when_done, queues an entry in the caller's notices.json. Background Jobs that completed, errored, or were stopped by the person or a limit; a stall is queued once as its own entry.
Deliverrun_job_notices sweeps every 2 s; a session is busy while a foreground execution runs. All pending entries become one automated notice turn (source="job_followup"). A notice has no timeout, so a reply is never dropped while the caller is busy.
FailureReported the same way; the notice says to retry narrower with send_message or tell the user. Nothing is resubmitted automatically.

Stored hand-offs

The removed handoff tool kept its turns in <state>/always_on/handoffs.json. When the Worker starts, before the old replay reads the file, each entry still waiting for a busy conversation moves to send_message (always_on/handoff_migration.py):

EntryBecomes
Waiting messageA delivery from its sender to its target, keeping its hop count; the reply comes back as a notice
Waiting replyA delivery from the conversation that answered (named in the reply) to the one that asked
Running or paused turnStays; the reply it owes is sent when it ends, as before
Waiting message that also owes earlier conversations (owed_after)Stays; send_message has no relay chain, so the old replay carries it on
Finished, or a reply naming no conversationStays, and ages out after a day as before

The file is copied once to handoffs.before-migration.json first. Every moved entry is kept as it was in handoffs.migrated.json with its delivery state and execution_id. Each delivery's Job id is fixed by its entry, so a Worker that stops midway delivers each one once.

A delivery send_message refuses stays pending under a new Job id and is tried again at the next Worker start; one whose conversation is gone is marked failed. migrate() without apply only reports. The transcripts' 📨 and ↩️ rows are unchanged.

The recipient answers in its final reply; a send_message back would deliver it twice, and the receipt says so. A message from another conversation is marked as another agent's input, not the recipient's user.

Attach pointers and cross-session spawns

A spawn writes an attach pointer with predecessor = caller_msg_id; the sub-branch never merges into the caller. send_message writes none, so its reply stays inline in the notice.

Caller node A in S with start_from="T:M" runs in T. The Job records parent_session_id=T, parent_msg_id=M, caller_session_id=S, caller_msg_id=A. The card in S is looked up by extra.attach.session_id and head_id; neither creating nor finishing it moves the selected HEAD of S or T (DAG attach rendering).

Busy targets

A message to a running branch is never interrupted in or dropped.

The spend, stall and hour bounds are watched from outside the Job (runtime/jobs/delegation_watch.py, every 5 s) rather than set as resource-governance limits: a governance limit makes a Job strict, which refuses every synchronous tool and every model with an unknown price, right for a limit set on purpose and wrong for a default (resource governance).

Cancellation

  • Follows parent_job_id: prevents unstarted descendants, requests cancellation of active ones, stays stopping until exit is acknowledged.
  • A stop by the caller itself (close_agent, cancel.parent) sends it no notice.
  • A terminal Job stays queryable; cancellation is idempotent.

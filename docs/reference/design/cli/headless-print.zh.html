无头 --print 运行

代码：interfaces/cli/chat.py _run_oneshot；interfaces/cli/worker_turn.py；interfaces/cli/print_turn.py；interfaces/cli/print_stop.py；interfaces/cli/print_events.py；interfaces/cli/print_input.py；interfaces/cli/print_session.py；runtime/conversation/local_commands.py；interfaces/server/handshake.py；runtime/conversation/turn_input.py；runtime/execution/execution_tree.py。

两条传输，一种请求

这个 profile 有 Worker 时，这一轮作为 Web UI 的 chat 命令交给它，CLI 只转发帧；没有时在本进程里接纳并启动。加 --standalone（或设 OPENPROGRAM_PRINT_IN_PROCESS=1）会强制走本进程。

部分规则
请求凡是接收人输入文本的入口都用 turn_input.build_turn_request 构造请求：Worker 的 chat 命令、重试或编辑、--print、ACP、聊天渠道、主人自动化发起的轮次。它依次放入权限主体、会话的权限、该入口取用的运行设置，最后放入口自己的字段。Job、定时运行、子 agent 和合并的输入是任务定义，自己构造请求。
运行说明没人看着的运行带上 runtime/conversation/run_note.py 的 RUN_NOTE：进程内的 --print，以及权限主体带 interaction="non-interactive" 的 Worker 聊天命令。由入口提出（build_turn_request(unattended=True)），不看权限主体本身：聊天渠道把配对的发送者按非交互准入，但每条回复都有人在读。这段说明告诉模型没人能回答，第一条不带工具调用的回复就结束运行。
每轮设置chat 命令能覆盖的设置写在一张表里（ws_actions/chat/turn_request.py 的 TURN_OVERRIDES）：强度、网页搜索、权限模式、沙盒和速度档会存到分支上，之后的轮次沿用；桌面界面只用于这一轮；turn_model、turn_effort、turn_permission_mode 也只用于这一轮，--print 用它们传 --model、--effort、--permission-mode，优先于分支和 Agent 试用保存的值。服务商列出但没人启用的模型，只在这个进程里给这一轮用（enabled_models.use_model_in_process）。
没给的值帧里没给或给了 null，就用会话原来的值。输入的 /task 或 /merge 记在 slash_action 里，interaction 保留权限主体的值；这个字段出现之前存下的请求用 slash_action_of 读。
两端是谁Worker 在连接时（worker_capabilities 帧的 server）和每个 chat_ack 里说明自己：名字、版本、支持的最高历史协议、能力（handshake.server_identity）。chat 命令说明发送方（client）。Worker 没声明的能力，CLI 保留对应的兜底：从回复文字里读结构化输出、按拒绝里给出的版本补发停止。运行记录写明走的传输和 Worker 的版本。
停止两种传输都按 print_stop 停止：第一个 Ctrl-C、SIGTERM、SIGHUP 或 SIGBREAK 抛出并记下名字，之后的只记下。从停止开始，轮次有 30 秒结束；又来一个信号后，从发出取消算起只剩 2 秒（StopClock）。版本过期的拒绝最多补发三次。停止时退出码为 128 加信号编号（STOP_EXIT_CODES）：SIGINT 为 130，SIGTERM 和 SIGBREAK 为 143，SIGHUP 为 129。
ack 之前的帧ack 给出 execution 之前，转发只接收回显本次 client_request_id 的帧（拒绝、斜杠命令的回答）。同一会话的另一个分支在这期间结束或被停止，不会结束这次运行。
Worker 重启转发重新连上并读取 execution 的状态。被中断的轮次，只要最新的重启意图要求开新一轮，就继续跟随，不管中断原因是什么（Worker 死掉是 owner_lost，重启先暂停再中断是 restart_new_turn）。意图还没结算时，转发在重连窗口内反复读取状态。结算为 new_turn_admitted 时，由意图算出新一轮的 id（execution_tree.continuation_key），跟到它回复为止，并记下 restarted。其他结算结果算失败。

无头接口

脚本调用 openprogram -p 的方式和调用其他 agent CLI 一样，所以每个参数都沿用多数脚本已经在用的那家的做法。退出码：0 运行完成，1 运行失败，2 用法错误，3 和 4 结构化输出不支持或失败，128 + N 被信号 N 停止。

主题规则原因
审批--print 运行没人回答，需要询问的调用立即被拒（policy._ask_or_nobody，沙盒升级在 approval.py），代码为 NON_INTERACTIVE，并给模型一段固定说明：这个调用没有执行，不用它继续。被拒的调用列在记录里（permission_denials），也作为 permission_denied 事件出现，并在 stderr 各打一行 permission denied: TOOL (WHAT)；运行仍退出 0。OpenCode 的无头运行也这样；模型读得到拒绝，就能换条路完成任务，等待会让脚本挂住，直接失败会浪费剩下的运行。更宽的权限在开始时用 --permission-mode（ask、acceptEdits、plan、auto、bypass）给这一轮。
斜杠命令输入的文本按 Worker 的方式处理（local_commands）：注册的内置命令直接回答，不跑模型；/compact [N] 压缩会话（Worker 的 compact 动作，或本进程的 trigger_compaction）；/task 和 /merge 标记这一轮；其他文本，包括不认识的 /name，原样发给模型。记录在 local_command 里写明命令。Claude Code 和 Pi 在 print 模式下运行本地命令；两个入口共用一个解析器，命令在脚本里和在 App 里表现一致。
传输--standalone 即使有 Worker 也在本进程里跑。OpenCode 把连接服务器和独立运行分开；评测或 CI 需要一次不和用户正在用的 App 共享状态的运行。
输出--output-format text（默认）打印回复；json 打印一条记录（下文的结束信息、reply、structured_output）；stream-json 每行一个运行事件，第一条是 init（传输、Worker 版本、模型、强度、权限模式、会话、execution、工具），最后一条是 result，seq 贯穿全部、没有空号。--include-partial-messages 在收到时加上 text_delta 和 reasoning_delta。这是 Claude Code 的名字和格式，现有 harness 已经会解析。
会话--resume ID 继续一个会话，不存在就失败（退出 1）；--continue 取这个文件夹最近的会话，范围是它的项目在登记表里列出的会话（session_ids；会话列表的行不带项目），在主目录里还包括没有任何项目列出的会话；--session-id ID 用这个 id 新开会话，已被占用就失败。Claude Code 和 Pi 用这些参数；它们要避免的是 id 打错时悄悄开了新会话。
分支位置--at REF 指定一个分支、分支的末端消息，或分支中间的一条消息（print_session）。在另一个已有分支上跑的一轮只移动那个分支，不动选中。从分支中间的消息开始时，这一轮像编辑一样开新分支，新分支成为选中的分支；离开的那条分支保留它的消息。目标分支正在跑一轮时被拒，error_kind 为 branch_busy。已有分支和选中分支并行。新分支只有在 head 移到它上面时才被登记（compare_and_set_head 写 branch_refs）；不移动 head 的分叉会留下一个没有名字的末端，之后的 --at 和分支面板都找不到。所以它跟编辑、重试用同一条 owner 定的规则。
模型--model 和 --effort 只用于这一轮：不固定到会话上，也不在配置里启用。模型没有的档位按它有的最近一档发送，先往强的方向找（thinking_spec.normalize_reasoning_level）：在从 low 起步的模型上，minimal 发送 low。Claude Code 和 Kimi 把这个参数当作本次运行的；脚本不能改变 App 之后用的东西。
指令-p 就是 --print。-p -，或有管道时只写 -p，从 stdin 读指令；有管道时 -p TEXT 把 0.2 秒内管道里的内容作为 <stdin> 块接在后面，所以开着但没人写的 stdin 不会让运行挂住（print_input）。空指令退出 2，-p "" 也是：只有没给 -p 才打开聊天（application._runs_print）。-p 是 Claude Code、Pi 和 Kimi 的写法；把文件管道接在指令下面是 Codex 和 OpenCode 的常见用法。
文件夹和密钥--no-project-binding 不在文件夹里写任何东西，会话留在 profile 里。凭据库没有密钥时，服务商的标准环境变量（OPENAI_API_KEY 等）可用，只在这个进程里、不写入（read_env_keys_in_this_process）。Codex 在不能弄脏的检出里运行，并从环境里取密钥；容器里没有存好的凭据。
网页--no-web 关掉这一轮的网页工具：名字里带 web 的工具都不加载，延迟加载的也算，服务商端搜索也不开；在 Worker 上是只管这一轮的 turn_no_web，并声明为 no_web 能力。Harbor 用一个开关关掉 Codex 和 Claude Code 的网页工具；评测因此能对两边提同样的要求。
轮数上限没有 --max-turns。对比的多数 harness 都没有；模型回复不带工具调用时运行就结束，其余靠调用方的超时和停止来限制。
退出码0 完成，1 失败，2 用法错误，3 和 4 是结构化输出；停止时 SIGINT 退 130，SIGTERM 和 SIGBREAK 退 143，SIGHUP 退 129，再来的信号沿用第一个的码。照 Kimi Code：它同样区分三种信号，Ctrl-C 保留 130；Codex 任何停止都退 1，脚本分不清被杀和失败。
失败原因error_reason 只取封闭集合里的原因；更细的类别放进 error_kind。照 Codex 的封闭错误枚举：集合外的值会落进调用方的默认分支。

按 execution 树统计用量和过程记录

每次模型请求在用量账本里都记着发出它时上下文绑定的 execution（models/usage/context.py call_context）。在独立线程上发出的调用，比如 Worker 在一轮结束后写的标题，不带 execution。

成员怎么找到
本轮为它接纳的 execution。没开始的运行没有 execution，什么都不统计。
子 agent按 parent_execution_id 的子 execution，以及本轮调用的 Job，任意深度，按会话自己的 execution 范围归属。
重启续跑成员上每条重启意图对应、以 restart:{execution}:{sequence} 接纳的 execution，连同它的后代。

--usage-file 汇总这些 execution 的账本行。--transcript-file 就是本次运行的事件（见下）：它们的请求、它们接纳时指定的指令和回复消息，以及模型读到的工具结果。同一会话里同时在跑的另一个分支不算在内。

运行事件

{"schema_version": 1, "seq": 7, "execution_id": "…", "parent_execution_id": "…",
 "type": "tool_result", "data": {"tool_call_id": "…", "content": "…", "complete": true, …}}

print_events.run_events 把各个存储映射成一份带版本的格式：seq 从 1 开始、没有空号；每个事件写明所属的 execution 和它的父 execution（本轮自己的为 null）。子 agent 的回复只带它自己的请求。过程记录文件把每个事件写成 {"type": …, **data}。

类型内容
run会话、模型、运行说明，以及运行怎么结束的。
user、reply本次运行的某个 execution 接纳的指令，以及它回复的结束。
request账本里的一次请求和它的 token，放在它返回的内容之前。
reasoning、assistant_text、tool_call、tool_result请求返回的内容。工具结果按模型读到的样子保存，所以是 complete。
permission_denied被拒的调用，跟在它的 tool_result 后面：调用 id、工具、代码、层、规则和参数。
init、text_delta、reasoning_delta、result只出现在 stream-json 流里：运行开始的信息、要求时的部分文本、结束时的记录。其中的权限模式是这一轮准入时用的：进程内取请求里的，Worker 上取 chat_ack 里的（--permission-mode，没给就是分支自己的）。流里不写 run，它的内容由 init 和 result 带着。
gap存储里没有的内容，就地标出：tool_result 表示调用没有存下结果，requests 表示账本读不出来，messages 表示找不到本次运行的消息。

运行怎么结束的

{"ended": "failed", "error": "…", "phase": "in_turn",
 "error_reason": "transport", "error_retryable": true, "error_kind": null,
 "restarted": false, "stopped_by": null, "transport": "worker",
 "worker_version": "…", …}
字段含义
phase接纳了 execution 之后为 in_turn，之前为 not_started：模型无法启用、Worker 在 ack 之前拒绝。
error_reason、error_retryableruntime 对失败轮次的分类，本进程时取自轮次结果，Worker 时取自 error 帧。
error_kind失败的稳定类别，比原因更细：流卡住和连接被重置都是 transport，只有前者是 stream_idle。runtime 用 errors.error_kind 给出（stream_idle、stream_total、memory_unavailable、auth），在异常本身或它包着的异常上找，写进轮次结果和 error 帧（kind）；CLI 原样转交，并自己给出 model_unavailable 和 branch_busy。必需的记忆失败时，原因为 unknown、不可重试，类别为 memory_unavailable。
被拒的输入准入拒绝的输入（AgentDriverError：input_too_large、image_too_large、invalid_input）以 error 帧结束这次发送，code 和 kind 都是这个代码，不会是只有 handler_error 的帧。用户的消息按单条消息的上限（1,048,576 个字符，agent_input_budget.AGENT_USER_TEXT_MAX_CHARS）衡量，不计入 256 KiB 的信封预算，所以 print_input 接受的提示都会被准入。
stopped_by第一个要求命令停下的信号：SIGINT、SIGTERM、SIGHUP 或 SIGBREAK。
permission_denials、local_command因为没人能批而被拒的调用（工具、调用 id、代码、规则），以及代替模型轮次作答的本地命令。
transport、worker_versionworker 或 in_process，以及 Worker 给出的版本（进程内运行、或 Worker 没给时为 null）。
effort_requested、effort、tools_count--effort 要求的强度（只用于这一轮，不保存；不给时用 Agent 自己的），以及本轮首个请求实际发出的强度和工具数。进程内运行在服务商 adapter 组请求体的地方读取（capture.observing）；在 Worker 上，chat 命令盯住它这个 execution 的请求（wire_facts.watch），由 result 帧带回（wire_facts），两种传输都能填上。Worker 接受 minimal 到 max；off 只能在进程内运行。

过程记录开头的 run 记录带同样的字段，另有版本、权限模式、运行说明和系统文字的哈希，以及首个请求的模型、include、store 和全部工具名。

它还写 no_web、工具输出权重，以及启动器构建在 openprogram/_build_info.py 里带的提交和构建时间（源码检出里为 null；--version 也会显示提交）。

本进程看到发出的每条 request 记录，加上它的强度、include、store 和工具列表哈希。

openprogram transcript [--state DIR] [--session ID] [--output FILE] 从被杀运行留下的状态写出它的转录（取那里唯一的会话，或指定的那个），只少了只有进程看到的请求体。

为什么：Codex 和 Claude Code 的 Harbor 适配器都从各自 CLI 逐条写下的会话派生轨迹；同一条代码路径让被杀的运行得到正常结束时会写的转录。

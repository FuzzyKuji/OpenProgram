Prompt cache prefix

A provider reuses a cached prompt only while every byte before the new part matches an earlier request. Each request is captured as its adapter writes it and compared, unit by unit, with the last answered request on its lane. The first unit that differs is where the cache stops reading; it names the cause on the usage event.

One capture point

Every adapter calls capture_request(model, body, wire=…) with the body it is about to send, after on_payload and before any byte leaves the process. Nothing else observes request bytes; the prefix check, the request-bytes contract test and the turn benches all read them from here.

Units

A captured body is cut into units in the order a provider reads a prompt: each tool, then each system text, then each history item.

Anthropic and Bedrock messages are cut per content block, so a message that grows by a block still extends the one before it. Units match by the digest of their bytes alone; a label never decides a match.

LabelUnit
tools:<name>One tool definition
systemOne system text, with the sections it was composed from: each a name, an end and a digest up to there. The runtime names them (components.prompt_parts, registered through runtime/lower_layers.py): the built sections such as environment, agents_md, memory, open_work, capabilities, plan_mode, then what a turn appends: goal, goal_verification, pages. A prompt it does not know as composed (sent again after a restart, or from a saved contract) has one section, prompt; its bytes still match
history:<kind>One history item: a role, or an item type such as function_call_output

Breakpoint markers (cache_control, cachePoint) move from request to request by design and are left out of the units. The lifetime they ask for is a setting.

Two checks

Before the request
check_request compares the request with the last answered one on its lane, and only reads. A changed setting comes first: model, then setting:cache_key, setting:ttl, setting:effort, setting:format, setting:tool_choice.
Then the units: the first that differs gives break_at, and its label gives break_cause.
A changed system text is named by its first section past the longest start both texts share at a section end they both have: system:open_work. A request shorter than the previous one gives removed:<label>. No provider usage is needed, so a provider that reports no cache tokens is checked the same way.
After the reply
settle_check looks at cached input. When the request was intact and cached input fell by more than 5% and more than 2,000 tokens since the previous request, the cause is ttl if more time passed than the cache lifetime (5 minutes, or the 1-hour or 24-hour setting), otherwise server.
The answered request, with its cached input, then becomes the lane's baseline; a request that got no reply leaves the baseline as it was.

Lanes

A lane is the session, the kind of call, the lane label, the Agent and the conversation branch. Only conversation-shaped calls have one: chat, Agent-method and subagent turns. Requests are compared only within one lane, so calls with other instructions do not report each other as breaks.

CallLane
A conversation's own turnschat with no label. Turns from the App, the TUI, a channel or a check-in share it, so a prompt that changes with the source is reported
A Goal verification turnLabel goal_verification (UsageContext.prefix_lane, set where the turn binds its usage context)
A self-update turnLabel from its source, self_update_*
An Agent method or subagent turnIts call_kind and call_label
Another branch of the conversationThe branch is the session's active_branch_id, bound once the turn's message is stored (UsageContext.branch_id). A new branch's first request is compared with the last request of the branch it left and records branch as expected; back on the old branch, a request is compared with that branch's own last request
A side call, or a call outside any sessionNone. A permission check, memory writing, a summary, a title, a prediction or a tool's own call sends a prompt of its own each time: it gets a prefix hash but is not compared

Each lane's last answered request is kept in memory and in prefix_baselines in the usage database, written when the reply settles. The database is read only for a lane's first request in a process, so the first request after a Worker restart is compared with the last one before it. A lane not written to for 30 days is dropped.

Breaks made on purpose

The runtime announces a break it makes with expect_break(session, cause). With a session, every lane of that session is told; with none, only the lane of the call being prepared, as compaction rewrites the request about to go out.

The next request on the lane records the cause in expected when it breaks; an announcement is used once, by the next answered request.

What keeps the prefix

A conversation's system prompt changes only when something the model must read there changes. Everything else reaches the model beside a turn's message, stored on that message, so later requests send the same bytes.

Why this design

Anthropic's preserved-thinking models check the request: a rebuilt system prompt is system_rerendered, a tool added or removed is tool_set_changed, and either is refused or drops the model's reasoning. Every other provider re-reads everything after the first changed byte. So what changes during a conversation goes beside a message, and the system prompt and the tools stay as they were.

The Goal

Follows Kimi Code's two Goal reminders: the full one when the Goal's state changed or after a compaction, a short one with the usage otherwise.

Codex repeats the whole rules in every continuation message, which costs more tokens each turn. Any Goal text left in the system prompt would rebuild it when a Goal starts or ends.

The todo list follows Claude Code: the model sees it in its todo tools' results, so it comes back only after 10 turns without them.

The tools array

Follows Codex, which refuses at dispatch and states permission changes as a message section, and Hermes, which pins a session's tools[] and says which pinned tools are inert where they are.

Claude Code removes tools that a deny rule names, but its rules are set at start; ours change mid-conversation, and the refusal at dispatch is what enforces them either way.

Plan mode

Follows Claude Code's schedule (Kimi Code has the same two notes): full on entering, a note every five turns, every fifth note full. Codex sends its collaboration mode once per change, which leaves a long conversation without a reminder that it is still planning.

The date

Claude Code, Codex, Kimi Code and OpenCode all send the date only when it changed. Repeating it every turn tells the model nothing and fills a small window.

Memory turned off

Hermes rereads memory only at a rebuild such as a compaction, and Codex and Claude Code keep what was recalled.

Content already sent has reached the provider; taking it out of the history is a rewrite that breaks the prefix and, on the models above, is refused. Turning memory off means nothing more is read or written, which stopping recalls and refusing the memory tools achieves.

Effort and cache lifetime

Claude Code, Codex and Pi apply a new effort at once and show no warning; Claude Code records it as the cause of the break. A change of either is applied at once and announced as expected, with no prompt to the person.

Recall and date as loop settings

Follows Codex, which passes each turn's state in an explicit TurnContext. A context variable set by one caller reached nested and parallel calls it was not meant for.

One record of the prompt

Codex resumes from the base_instructions it persisted, and Hermes replays a session's pinned prompt and tools until a compaction. Two copies (checkpoint and branch) drift apart across compactions, restarts and resumes, so the branch keeps the text and the checkpoint a hash that the resume check compares.

Request bytes contract

A finished turn renders, in the next turn, the bytes its own requests sent. tests/support/request_bytes.py runs real turns (dispatcher, agent loop, DAG render) with a scripted reply and serializes each request with the real adapter in capturing(send=False). Two suites use it.

A known place where a later render differs is marked xfail(strict=True) with the gap it shows. The change that closes a gap removes its mark.

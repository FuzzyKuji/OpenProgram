概览

每次调用把会话执行 DAG 的一部分渲染成 Context（system、messages、tools）：它延续的那条分支，每个工具结果按它那一轮发出的样子，窗口快满时最早的若干轮换成一段摘要。本层决定喂什么；模型服务层决定怎么发。

DAG 渲染是唯一流程，渲染失败时本轮明确失败。辅助调用（摘要、记忆整理、分支摘要、mixture-of-agents）绕过 engine.prepare，自建最小 Context：一段系统提示和一条用户消息，不带工具。

engine.prepare 做什么

process_user_turn（openprogram/runtime/conversation/turn_runtime/）调用 openprogram/runtime/context/engine.py：

  1. 扫描引用：后文引用的 tool_use id。
  2. 解析 head，然后 render_context，再 render_dag_messages。
  3. 取调用方组装的系统提示（身份、AGENTS.md 链、技能、工具）。
  4. 计算令牌预算：系统、历史、工具、输出预留。
  5. 对账用量：上次模型服务实测，加上此后新增内容的本地估算。
  6. 返回 TurnPrep。

存储：DAG

基于 git、只追加的会话存储（openprogram/state/store/session/）。没有规则会改写节点。每轮是一个提交，predecessor 指向它回应的对象。

渲染与压缩

阶段规则
选取render_context 从 head 沿 predecessor 链回溯，按帧和 expose 规则纳入每轮的调用子树，不写任何东西。render_dag_messages 把选中的节点变成发给模型服务的消息；直接函数调用变成文本对。
已结束的轮次按这一轮的请求当时发出的样子渲染：存下的轮次块（召回的记忆、运行说明）放在用户消息上，然后每次模型服务的响应是一条助手消息，用回复自己的 provider、api、model，后接这些调用的结果。这条消息含这次响应的推理、用模型服务给的消息 id 的文字，以及调用。
推理已结束轮次的推理项整个发回给写这条回复的模型（有摘要时才显示）。换了模型就一项都不发：它用不了这些推理项，还会把摘要当成助手说过的话。
响应标记回复的有序块标出每次响应从哪里开始（round_start）；从检查点恢复的轮次从日志里取这些标记，每个决策一个。没有这些标记的回复（更早记录的、文字被转存的）每个调用单独一条消息，文字放最后。
旧工具结果不管后面跟了多少轮，都按它那一轮发出的样子完整发送。没有老化；只有压缩会替换旧轮次。旧版本记下的 render_manifest 不再读取，那样的轮次也完整渲染。
压缩达到 context.auto_compact_percent（默认 80）、执行 /compact 或模型服务拒绝过长请求时，engine.compact 把最早的完整轮次总结成一个 context/summary，其 covers_ids 列出被替代的轮次。每个分支读完整位于自己链上、覆盖最远的那份摘要加保留尾部；没有的分支渲染原文。摘要必须非空且严格更小；被总结的内容里不带图片。压缩

工具输出

一条规则贯穿始终：之后的请求发出的字节和这一轮发出的一样。结果只在产生的地方截一次，历史存的就是截过的样子。代码：runtime/agent/loop/tool_dispatch.py（_as_stored）、state/store/session/spill.py、models/providers/shared/tool_attachments.py。

设置效果
结果形式本轮把结果作为一个文本块发出，拼法与节点存的一致，图片留在原位，所以之后每个请求在任何提供商上发出的字节都一样
结果大小按权重计（state/store/session/weight.py：中日韩字符和全角字符算 1，其余算 0.25，约等于一个 token）。上限是模型的 tool_output_weight，默认 10,000（Codex 的 truncation_policy），不超过窗口的 30%；工具自己声明的 max_result_weight 更小时取它（spill.result_cap）。放得下 10,000 个汉字或 40,000 个英文字符；8,000 token 的窗口上限是 2,400
只截一次工具从不自己截断：@function(max_result_weight=…) 把上限记在 details["cap"]，由循环来截。截断在换行处保留开头（60%）和结尾，再写出完整文字的路径和要读的行，形如 read("…", offset, limit)。先量好说明的长度再定结尾，所以结果从不超过上限，行号范围也准确
完整文字按内容只存一份，在 <对话>/tool_results/<sha256>.txt，随对话删除和备份。不在对话里时存到 profile 的 tool_results/，Worker 每天清理一次：超过 24 小时、没有任何对话记录提到的文件被删除；只要有一份记录读不了，就一个都不删（tool_output_gc.py）
空结果既没有文字也没有媒体的结果写成 (name completed with no output) 或 failed；只有媒体时不带空文本块
引导和 AGENTS.md记在结果的 details["attachment"]（{text, paths, guides}）上，单独截断，每组结果之后作为一条消息发出：Anthropic 和 Bedrock 上是同一条用户消息里的文本块，其他提供商是一条用户消息。已经附过的 AGENTS.md 从请求自己的消息里读出，所以分支、压缩、重启后的 Worker 各看各的
读取大小read 自己按上限分页：一次放不下的范围给出连续的一页，停在完整的一行（PDF 停在完整的一页），并给出接着读的 offset。附件不再占这一页的地方
媒体一轮发出的图片、音频、视频块按内容存在 <对话>/media/<sha256>.<ext>；节点记下 metadata.media = [{sha, mime, index, path}]，渲染时把每块放回原来的位置。用户粘贴的图片也一样
图片预算构建请求的最后一步（media_budget.bound_images）：图片超过 25 MiB 时，最早的换成一句说明，直到剩 15 MiB，所以截断点每 10 MiB 才动一次，不是每个请求都动。发给不收图片的模型时，用户的图片换成一句说明
用户的消息从不截断：本轮和之后每轮都完整发送。超过 1,048,576 个字符时拒绝发送（input_too_large），文字留在输入框里；--print 以 2 退出
卡片显示工具自己输出的开头（details["preview"]，4,000 字符），不显示写给模型的说明，并标出"共 N 行，全文已保存"；打开时读保存的文件（details["output"]）
为什么这样设计
主题原因
不老化把旧结果换成占位，边界每动一次就改写一次缓存前缀；成批前进只是缓解，每隔几轮还是要整段重读不走缓存。Codex、Claude Code、Pi 和 OpenCode 1.19 都把结果留到压缩为止；旧输出是压缩的问题，不是渲染的问题
只截一次，按权重两道上限（工具按字符，再加循环）会把一些结果截两次，中文结果的 token 还是英文的四倍。Codex 在记录结果时按 token 截一次；权重就是不用分词器的这个计数，同一个上限在每个模型上都成立
附件放在结果旁边把引导和 AGENTS.md 拼进结果，read 就得预测它们的长度，过长的 AGENTS.md 还会剪掉一页。Claude Code 把它们作为结果之后单独的消息发出。它们存在结果上而不是新节点里，所以留在分支历史中，不需要新的节点类型，每个适配器放的位置都一样
历史里的媒体不存的话，之后的请求会丢掉这一轮发过的截图，字节变了，模型看过的东西也没了。Codex 和 Claude Code 都把图片留在历史里；预算沿用 OpenCode boundImages 的滞回，两次截断之间缓存不失效
长消息渲染时剪掉用户的粘贴，发出的文字就和这一轮不同，还藏掉了一部分。Codex、Claude Code、OpenCode 和 Pi 都完整发送输入；Codex 超过 1 MiB 字符就拒绝，这里也一样
清理共享目录结果的文字里写着它的文件名，之后每个请求都会再发这个名字，所以文件是记录，不是缓存。Hermes 按引用清理持久化的结果，读不全就不删；一天的宽限覆盖已经写了文件、还没写节点的运行
卡片人看工具做了什么，模型看有界的版本；混在一起时，人会看到一句写给模型的“去读某个文件”。Claude Code 和 Pi 都显示工具原文、剥掉这句说明。
空结果有的提供方拒绝空的工具结果，有的模型会当作调用没有返回；Claude Code、Pi 和 OpenCode 都补一句，我们用 Claude Code 的写法。

图片和长消息

图片进入会话的每条路都写同一种记录，所以下一个请求带着本轮带过的图片，每个适配器都一样。代码：state/store/session/media.py、runtime/conversation/branch_fork.py、models/providers/shared/google.py。

路径保留什么
发出的消息网页、桌面 App 和 TUI 用 chat 发图片；频道、ACP 和 --print 走本轮的准备步骤。两处都按本轮给每张图的位置记录：在文字之后，消息只有图片时从 0 开始。只有图片的消息渲染时没有文字块
重试和编辑重试把消息的 media 复制到新分支，并从保存的文件里读出同样的图片再发一次。编辑只发送、只保留这次编辑带的附件
插话运行中发出的消息先送文字，再送图片；节点按这些位置记录
适配器每种内置线路格式都带上保留的图片，不论是人发的还是工具返回的：Anthropic、OpenAI chat 和 Responses、Codex、Azure、Bedrock、Gemini 和 Gemini 订阅。Gemini API 适配器通过共享的 Gemini 转换生成内容，所以也有图片体积上限、工具结果之后的说明和工具结果里的图片
旧会话在保留图片之前存下的消息没有 media，照旧只发文字。它的文字写着上传文件保存的路径，模型可以再读
长粘贴完整保存，每个请求都完整发送；只有 1,048,576 字符的上限会拒绝发送
为什么这样设计
话题理由
按内容存在历史旁边Codex（ImageReference::Inline）、Pi 的会话文件和 OpenCode 的 file 片段都把 base64 内联在历史里。这里一个节点是一行历史，搜索索引也读它，内联字节会让两者都膨胀；文件按 sha256 命名，和 Claude Code 的粘贴存储给粘贴文字命名一样，所以同一张截图在几个分支上发过或被重试，也只有一个文件
什么时候去掉图片压缩时不放进摘要的输入，同 Claude Code；超过 25 MiB 时最旧的换成一句说明（OpenCode 的滞回）；模型不收图片时换成说明（Codex）。别的情况都不去掉，所以前缀在这几处之间不动
重试再发图片重试的新分支就是同一条消息再发一次。不带图片，重试的那轮回答的是另一个问题，而且它之后的请求会带着第一次请求没带的图片
不回填旧消息保存的上传是原文件，不是发给模型的那份，后者可能缩小过；发原文件就是发本轮从没发过的东西。这些会话之后本来就只重发文字，不动它们就不改变任何字节

附着与合并

同一机制：附着指针，一个 function="attach" 的节点，作为旁支子节点挂在用户轮下。渲染为 [Attached from "label"] 和 [End of attached content] 之间的文本。

用途行为
附着被动：暂存，下次模型调用时读取
子智能体汇报指针含任务、最终回复和完整记录的 read_conversation(session_id, head_id) 地址。同步派生在 agent 工具结果里返回回复。
合并process_merge_turn() 在目标 head 后为每个对等分支写一个指针，加一条合并指令，运行普通轮次。基准分支保持原文，其他可摘要。被合并的 head 打标，一个多父上下文提交记录来源。

不变量

对象不变量
DAG只追加；压缩不改节点内容
渲染不写任何东西；转存发生在写入时。只读存下的节点：循环截过的工具结果、用户的消息和回复完整渲染；其他节点按转存标记里记下的上限截断（没有标记的按 32,000），不读当前上限或环境变量；工具结果带着存下的失败标记和媒体渲染
已结束的轮次模型不变时，下一轮的第一个请求以上一轮的最后一个请求开头，推理项和文字 id 也在内；只有模型服务自己执行的搜索除外，这一轮不存它。工具结果按模型读到的样子存下，以后照存下的样子再发，失败标记、附件和媒体也在内；只有旧版本打过标记的节点按标记里的截断发送。没有响应标记的回复重新渲染时顺序不同。
历史调用按存下的节点逐字节重渲染；没有随时间变化的策略参与
摘要一个会话最多一个活动摘要，下次压缩吸收它。不移动 HEAD，不改边
分支不读兄弟分支或派生子智能体的内部；它们只经附着指针进入
检出不重跑，不回滚工作目录

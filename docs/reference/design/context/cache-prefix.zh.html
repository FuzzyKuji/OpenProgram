提示缓存前缀

只有新内容之前的每个字节都和更早的请求相同，provider 才会复用缓存的提示。每个请求在适配器序列化它的地方被采集，切成单元，再和同一通道上一次得到回复的请求比较。第一个不同的单元就是缓存停止读取的位置，它给出用量事件记下的原因。

唯一的采集点

每个适配器在 on_payload 之后、任何字节离开进程之前，用要发送的请求体调用 capture_request(model, body, wire=…)。没有别的地方观察请求字节；前缀检查、请求字节契约测试和轮次测试台都从这里读取。

接收方怎样拿到请求
流的汇合点streaming/stream.py 每次尝试绑定一个 RequestSlot；适配器填入它，于是检查在请求发出前运行。一个 slot 只接一个请求，所以在汇合点之外调用的适配器不会碰它。provider 拒绝请求形状、这次尝试修好后重发时（request_repair.py），先重新打开 slot，所以 slot 里是得到回复的那个请求
测试和脚本capturing() 收集块内的每个请求体。send=False 时每个请求在采集点以 RequestNotSent 停下，所以整段对话可以不联网地经过每个适配器序列化

单元

采集到的请求体按 provider 读提示的顺序切成单元：每个工具，然后每段系统文本，然后每条历史。

Anthropic 和 Bedrock 的消息按内容块切，所以多了一个块的消息仍然延续上一条。单元只按字节的摘要匹配，标签从不决定是否匹配。

标签单元
tools:<name>一个工具定义
system一段系统文本，带着它由哪些节拼成：每节记名字、结束位置和到此为止的摘要。运行时给出这些节（components.prompt_parts，经 runtime/lower_layers.py 注册）：先是构建出的节，如 environment、agents_md、memory、open_work、capabilities、plan_mode，再是一轮追加的部分：goal、goal_verification、pages。运行时不认得是自己拼成的提示（重启后再次发出的，或来自保存的 contract）只有一节 prompt，字节照样匹配
history:<kind>一条历史：一个角色，或一种条目类型，如 function_call_output

断点标记（cache_control、cachePoint）本来就会随请求移动，不计入单元。它们要求的缓存时长算作一项设置。

两道检查

请求发出前
check_request 把请求和同一通道上一次得到回复的请求比较，只读不写。先看设置：model，然后 setting:cache_key、setting:ttl、setting:effort、setting:format、setting:tool_choice。
再看单元：第一个不同的单元给出 break_at，它的标签给出 break_cause。
变化的系统文本按节命名：两段文本在双方都有的节结束位置上共有的最长开头之后的第一节，例如 system:open_work。比上一次短的请求给出 removed:<label>。这一步不依赖 provider 的用量，所以不报缓存 token 的 provider 也一样检查。
回复之后
settle_check 看缓存读取。请求完好、缓存读取比上一次下降超过 5% 且超过 2,000 token 时，若间隔超过缓存时长（5 分钟，或设置的 1 小时、24 小时），原因是 ttl，否则是 server。
随后这个得到回复的请求连同它的缓存读取成为通道的基线；没有得到回复的请求不改基线。

通道

通道由会话、调用类型、通道标签、Agent 和对话分支组成。只有对话形态的调用有通道：chat、Agent 方法和子 agent 的轮次。请求只在同一通道内比较，所以指令不同的调用不会互相报成断点。

调用通道
对话自己的轮次chat，没有标签。来自 App、TUI、渠道或 check-in 的轮次共用它，所以随来源变化的提示会被报出
Goal 验证轮标签 goal_verification（UsageContext.prefix_lane，在轮次绑定用量上下文处设置）
自更新轮标签取自来源 self_update_*
Agent 方法或子 agent 轮次它的 call_kind 和 call_label
对话的另一个分支分支取会话的 active_branch_id，在这一轮的消息存下后绑定（UsageContext.branch_id）。新分支的第一个请求和它离开的分支的最后一个请求比较，并把 branch 记为预期；回到原分支后，请求和该分支自己的最后一个请求比较
旁路调用，或不属于任何会话的调用没有通道。权限检查、写 memory、摘要、标题、预测或工具自己的调用每次发的都是自己的提示：有前缀哈希，但不比较

每个通道上一次得到回复的请求存在内存里，也在回复结算时写进用量数据库的 prefix_baselines。只有一个进程里通道的第一个请求才读数据库，所以 Worker 重启后的第一个请求和重启前最后一个请求比较。30 天没有写入的通道会被删除。

有意的断点

运行时用 expect_break(session, cause) 预告自己造成的断点。给了会话就告诉该会话的每个通道；没给就只告诉正在准备的这个调用的通道，因为压缩改写的是即将发出的请求。

通道的下一个请求如果断开，就把原因记进 expected；一次预告只由下一个得到回复的请求用一次。

原因预告方
compactionengine.compact 存下摘要之后；compaction/request.py 在请求摘要自己的一部分历史时
rewindrewind_marks.take_rewind_note，把说明取到下一轮的消息上时

branch检查本身，用于新分支的第一个请求

前缀靠什么保住

对话的系统提示只在模型必须从那里读到的东西变了时才变。其余内容放在一轮消息旁，存在那条消息上，之后的请求发出同样的字节。

规则做法
记录的提示只有一个 owner只有对话自己的一轮记录并保留它所在分支的提示（loop_runner.owns_conversation_contract）。Goal 验证和后台 check-in 自己组装提示，既不读也不写
可移动的节新提示和记录的提示只在 environment、agents_md、memory、open_work 或 capabilities 上不同时，原样再发记录的提示，每个变了的节把整节文字放在消息旁（turn_context.kept_sections）。打开的页面从不进对话自己的提示，而是消息旁的一节。其他变化会重建提示
整节替换，不发补丁一节的文字和本请求渲染出的最后一条该节说明不同，或者没有渲染出说明（被压缩、干净历史、有界尾部）而和提示里的该节不同，就发出。消失的节发一条“不再适用”的说明
一种存储用户节点上的 turn_context 列表：日期、中断说明、回退说明、各节说明、计划模式说明、Goal 说明、待办提醒、召回的 memory、运行说明，按这个顺序。列表出现之前的节点按旧键以同样顺序渲染；新节点也同时写旧键
事件发生时写入召回的 memory、运行说明和待发的回退说明在消息存储时写入；各节说明和按视图决定的说明在这一轮第一个请求组装时写入。再次发送的消息保留它的回退说明，其余按同一个视图重新决定
按视图决定的说明由本请求渲染出的历史决定（turn_context.turn_view）：日期只在和视图里最后一个日期不同时发；计划模式说明在进入时发，之后每 5 轮发一次，每第 5 条发完整版、其余发简短版，退出时发一条退出说明
Goal 和待办说明由同一视图决定：Goal 说明在视图里没有一条目标、状态、修订号、预算档位（75%）和验证反馈都相同的完整说明时发完整版，否则发一条带用量的简短版；Goal 的待办列表在 10 轮没有 todo_* 调用、也没有提醒之后发。压缩丢掉某条说明后，下一轮重新发完整版
一个纪元一份工具数组对话自己的一轮发出它可能用到的所有工具。取决于这一轮的条件不再把工具拿掉：不在渠道里的 chat_send、没人回答时的提问工具、不在头部时的 handoff、定时运行的 always_on_report、外部文字驱动的报告偏好、memory 关闭时的 memory 工具、没有页面时的 computer_use_agent、provider 自己搜索时的本地 web_search
拒绝而不拿掉对这些工具的调用被拒绝（TOOL_UNAVAILABLE，不询问任何人），消息旁的 tool_availability 节列出它们一次。计划模式和 deny 规则也在派发时拒绝（延迟工具）。验证、check-in 和自更新步骤从自己的数组里去掉这些工具
关闭 memory 不撤回关闭 memory 后不再召回，memory 工具被拒绝。已经召回的内容和 memory 节说明留在历史里，记录的提示保留它的 memory 节，下一条消息说明它不再适用。压缩的输入不含召回内容（turn_context.without_recall），压缩之后第一次重建的提示没有 memory 节
一条回放规则每次渲染都显式传入 audience。只有对话自己的请求显示各节说明；带自己提示的调用一律不显示。请求是否召回 memory、是否带日期是循环自己的设置（AgentLoopConfig.recall、dated），不是 context variable
分支记录是提示的权威对话自己一轮的 checkpoint 只存分支上记录的提示的哈希（system_prompt_sha256），不存正文；续跑从记录读正文，记录对不上就拒绝续跑。带正文的 checkpoint（旧的，或带自己提示的轮次）按正文续跑
哈希对哈希两份都按哈希指向提示的契约，比如加载 checkpoint 时拿它和自己比，按哈希比较（runtime_contract.validate_runtime_contract）。只有开始前分支上已有记录的轮次按哈希存；第一轮的记录在它自己的回复上，所以它的 checkpoint 存正文
一次性调用只有一个 key不属于任何对话的调用按 provider、模型、instructions 和工具名取 key（providers.shared.cache_key），无论经过 Runtime 还是直接调 adapter

为什么这样设计

Anthropic 的 preserved-thinking 模型会检查请求：系统提示被重建是 system_rerendered，增删工具是 tool_set_changed，两者都会被拒绝或丢掉模型的推理。其他 provider 从第一个变化的字节起整段重读。所以对话过程中变化的东西放在消息旁，系统提示和工具保持原样。

Goal

照 Kimi Code 的两档 Goal 提醒：状态变了或压缩之后发完整版，其余发带用量的简短版。

Codex 在每条续跑消息里重复整段规则，每轮花的 token 更多；系统提示里只要留一个 Goal 的字，开始或结束 Goal 都会重建它。

待办列表照 Claude Code：模型在 todo 工具的结果里已经看得到，所以 10 轮没用才再提醒。

工具数组

照 Codex（派发时拒绝，权限变化作为消息里的一节）和 Hermes（每个会话固定一份 tools[]，当前用不了的工具在消息旁说明）。

Claude Code 会删掉 deny 规则点名的工具，但它的规则在启动时就定了；我们的规则会在对话中途改，而且无论哪种做法，真正起作用的都是派发时的拒绝。

计划模式

照 Claude Code 的节奏（Kimi Code 也是同样的两档）：进入时完整版，每 5 轮一条，每第 5 条完整版。Codex 只在模式变化时发一次，长对话里模型会忘了自己还在计划。

日期

Claude Code、Codex、Kimi Code 和 OpenCode 都只在日期变化时发。每轮重复没有信息量，还占小窗口。

关闭 memory

Hermes 只在压缩这类重建时重新读 memory，Codex 和 Claude Code 保留已召回的内容。

已经发出的内容已经到过 provider；从历史里删掉是一次改写，会断开前缀，在上面那些模型上会被拒绝。关闭 memory 的意思是以后不再读写，停止召回、拒绝 memory 工具就做到了。

推理强度和缓存时长

Claude Code、Codex 和 Pi 都立即应用新的推理强度，不提示；Claude Code 把它记为断点原因。两者改变时立即生效，登记为预期断点，不给用户加任何提示。

召回和日期是循环的设置

照 Codex：它把每轮的状态放在显式传递的 TurnContext 里。由某个调用方设置的上下文变量，会传到不该影响的嵌套调用和并行调用里。

提示只有一份记录

Codex 从持久化的 base_instructions 恢复，Hermes 回放会话固定的提示和工具，直到压缩。两份副本（checkpoint 和分支）会在压缩、重启和续跑交错时分叉，所以正文只存在分支上，checkpoint 存一个哈希，由续跑检查比对。

请求字节契约

一轮结束后，下一轮渲染出的是这一轮自己发过的字节。tests/support/request_bytes.py 用脚本化的回复跑真实轮次（调度器、agent 循环、DAG 渲染），在 capturing(send=False) 里用真实适配器序列化每个请求。两组测试用它。

压缩

摘要在包含它覆盖的全部轮次的每条链上代替这些轮次，每条链读自己的那份。一条规则 active_summary_for_chain（state/store/session/summaries.py）同时服务渲染、压缩输入和图构建器，所以它们从不分歧。摘要的胶囊画法：DAG 渲染第九节。

  • 只追加。一次写入一个完整的节点：不克隆尾部，不改边，不动 HEAD，事后不补写元数据，也没有会话字段指向它。忽略摘要即可重建原视图。
  • 用 id，不用 seq 区间。兄弟分支的 seq 交错，区间会卷入死分叉，还会随 HEAD 变化。
  • covers_ids 是真实轮次的连续段。绝不包含摘要：再次压缩时在旧段上延伸新轮次。

用哪份摘要

在覆盖轮次全部位于某条链上的摘要中，这条链读覆盖范围沿链延伸最远的那份；相同时按 seq 决定。滚动摘要覆盖前一份加更新的轮次，所以在它的链上胜出，旧的那份只服务更早分出的链。

情形链读到
两个分支先后压缩各读自己的摘要。在它们之间切换，各自按自己的摘要渲染，不写任何东西
分叉点之前写的摘要两个分支都读
回退原地撤回轮次被撤回的消息不在链上，被撤回的摘要不存在；所以回退进摘要范围时，退回到仍完整位于链上的更早摘要，或原始轮次
在被覆盖段内编辑、重试或分叉新分支缺少该段的一部分：读一份合适的更早摘要，或原样
两个分支加载了不同工具每份摘要带自己的 carried_tool_names
为什么这样设计
每条链一份摘要
沿用 Pi：取从叶子出发路径上的最后一次压缩。对比过：每个会话只有最新一份摘要（Claude Code、Codex，只有一条线性历史），其他分支都原样渲染、要再压缩。这里分支并行运行，所以摘要属于链。
回退时退回
Codex 在回滚越过压缩时丢弃那次压缩；这里同一规则让被撤回的摘要不再指向链上已没有的轮次。

渲染规则

context/nodes.py 的 render_context 决定模型读什么。设 S 为这条链的摘要，L 为其 covers_ids：去掉 L，在其位置放入 S，作为一条用户消息（摘要，然后是恢复的状态）；在 Anthropic 上它和下一条用户消息合并。

流水线

/compact（trigger_compaction）、自动压缩（预算达到 context.auto_compact_percent，默认 80%，在轮次开始前和轮次的步骤之间）和超长恢复都在调用方用链尾指定的链上运行 engine.compact：/compact 用它读到的会话 head，其余用该轮自己的分支。除 /compact 外都传入该轮的停止信号。

  1. 冻结这条链的渲染输入。compaction.view.load_compaction_view 使用 render_context 和 render_dag_messages，包含工具结果、expose 和 spill 引用。顶层轮次决定覆盖范围；可见的子调用计入输入和预算。
  2. 选整轮。保留窗口的 10%，限定在 8,000–40,000 token（显式覆盖优先）。优先在用户边界处保留至少四条对话消息；已发布的报告也算边界。低于目标：不操作。若最后两轮超过目标，切点可前移到最近的用户边界。除非其后只有报告，最近一轮保持完整。
  3. 用摘要提示词总结整个被覆盖前缀（摘要提示词与角色）：每个被替换的轮次、最初的请求、这条链之前的摘要、渲染出的子调用。非文本媒体变为引用说明。
  4. 写入前校验。拒绝空的、失败的、被取消的、缺段的、碰到上限的或没有缩小的摘要；按同样方式在内存中渲染的候选必须严格更小。模型调用后重新检查这条链的渲染节点；有变化就作为可重试的空操作，其他分支和移到别处的 head 不算。provider 失败时保留历史，没有有损的结构化兜底。
  5. 持久化并报告。连同恢复的状态一次写入；covers_ids 把之前的摘要展开成真实轮次 id。之前的数字是上下文面板对这条链的读数；之后的数字是该读数减去候选节省的部分。空操作不写入、不计数。

上下文显示使用 provider 的输入用量。每个请求还记录同样消息的本地估算，所以之后编辑图时按实测比例缩放估算，在下次报告前标为估算。没有匹配估算的旧用量不参与校准。

/compact 是这个分支的前台操作（op_kind: compact，compaction_started 上带 op_id）。页面的停止按钮和终端的 Ctrl-C 都用这个 id 发送 operation.cancel；摘要请求结束，不写任何东西，那一行显示"已停止"。自动压缩失败时不提示，下一个请求会再试。

原因：Claude Code、Codex 和 Kimi Code 都用停止一轮的那个键取消手动压缩；照 Claude Code 做，它的终端同样基于 Ink。

自动压缩反复失败

每次失败的尝试仍要为整个对话付费。同一分支在同一模型上连续失败 FAILS_MOST（3）次、每次距上一次在 HELD_FOR_S（5 分钟）内后，这个分支的自动压缩从最后一次失败起等待五分钟，再尝试一次（runtime/context/compaction/hold.py，按会话、模型和分支计，由 DefaultContextEngine.compact 查询）。其他分支照常压缩。

  • 算失败：摘要器出错（例如 429）、提醒后仍缺段、碰到输出上限、带错误的空摘要、没有缩小。
  • 不算失败：取消、源已变化。
  • 摘要成功写入后清零计数。/compact 总会执行。
  • 沿用 magpie 的压缩保护（yetone/magpie，MIT）。

超长恢复

agent 循环（runtime/agent/loop/loop.py）在两处压缩该轮的链；该轮自己的步骤保持原样。

时机做什么
provider 以过长拒绝请求丢掉被拒的回复，压缩（reactive），重新渲染，再发送同一个请求。每个请求一次压缩，每轮两次；第二次超长或没有释放空间，该轮以 provider 的错误失败。该轮从不从头重跑，所以工具不会再被调用
一轮工具结果超过自动压缩阈值每轮压缩一次（mid_turn），在重新渲染的请求上继续
期间停止该轮以已停止结束
不能持久压缩的调用切换到更小窗口的备用模型、Runtime.exec、后台和 clean 运行、覆盖历史：使用下面的请求检查点
为什么这样设计
只重试那个请求
沿用 Claude Code 和 Codex：两者遇到上下文长度错误时压缩，再重发失败的请求，并限制次数。对比过：重跑整轮循环，那会重复所有已完成的步骤，包括有副作用的工具调用。
步骤之间压缩
Codex 在一次采样后用量超过上限时于轮次中途压缩；Claude Code 在每个请求前检查。否则一条消息里的长工具循环只会一直增长，直到 provider 拒绝。

摘要提示词与角色

一份提示词（compaction/prompts.py）写每一份摘要，无论首次还是滚动，要求这些 ## 段：User intent、All user messages、Decisions and constraints、Completed work、Current work、Next step、Relevant files。它省略每个请求本来就会发送的内容（系统提示、AGENTS.md、指南、记忆），标明被取消的请求，并注明说法的出处。

  • 缺段的回复带提醒（NUDGE）再问一次；仍不完整，压缩失败，不写入，计入 hold。
  • 输出上限 20,000 token，窗口较小时为窗口的四分之一。碰到上限的摘要算失败，不保留截断的结果。
  • 摘要是用户输入，带一个说明其身份的前缀。
为什么这样设计
分段和提醒
沿用 Claude Code 的分段摘要，保留用户自己的消息，并检查摘要是否漏掉它们。对比过：两份提示词（首次和更新）加五个松散部分，滚动摘要会丢掉用户早先的指示。
用户角色，带前缀
沿用 Codex 和 Pi，它们把摘要作为说明自身身份的用户输入交回。assistant 角色的摘要读起来像模型自己说过的话，会被当成它自己的结论。
碰到上限算失败
Claude Code 把不完整的摘要当作失败；被截断的摘要丢掉 Next step 和 Relevant files，正是继续工作最需要的部分。

压缩恢复什么

摘要正文之后、在同一条消息里，节点带一个 <restored-state> 块（compaction/restore.py），在 10,000 token 以内，每个请求字节相同：

段来源
Approved plan链上用户批准的最后一个 exit_plan_mode，之后又进入计划模式则不算；超过 6,000 token 截断并注明
Todo list对话的待办板，带每项状态
Background jobs still running尚未结束的任务
Files read、Files changed被覆盖调用读、写或编辑过的路径，追加到上一份摘要的列表上，各保留最近 30 个。存下来的调用把参数保存为模型发来的 JSON 文本，路径（和计划）从这段文本里读
为什么这样设计
写状态，不重读内容
沿用 Claude Code：压缩后重新附上计划、待办、运行中的任务和读过的文件。对比过：重读文件内容，字节最多，文件一变就过期；有路径，模型可以再读。状态存在节点里，保持在缓存中。

摘要请求

摘要把上一个请求再发一次，多加一条摘要提示词作为用户消息（compaction/fork.py）：系统提示、工具和缓存键都相同，provider 从缓存读前缀。回复里的工具调用不执行；再问一次摘要。

这条消息开头先说明它来自系统而不是用户（FORK_SUMMARY_PROMPT）：每一节都不列它，Next step 引用的最近请求是它之前的那条用户消息。摘要覆盖到它为止的整段对话，保留的轮次也在内；保留的轮次仍在摘要后按原文渲染。

以下情况改为读被覆盖的文本：模型不同、请求加摘要放不下、请求不在这条链上、或这次压缩是在从超长中恢复。

为什么这样设计
分叉已缓存的前缀
沿用 Claude Code 的分叉摘要和 OpenCode 在同一消息列表上的压缩：对话已在缓存里，摘要按缓存读计费而不是全新输入。对比过：把被覆盖轮次渲染成文本放进新请求，每个 token 都按全价；它保留为兜底。
提示词先说明自己
沿用 Codex（压缩提示词以“上下文检查点”开头）和 Claude Code（要求总结“到目前为止的对话”）。不加说明时，提示词就是请求里最新的用户消息，模型曾把它当作用户的最近请求列出并引用。对比过：只覆盖保留尾部之前的轮次，这会改变前缀、丢掉缓存。

模型降级

跟随其 Agent 换到更小窗口模型的分支，在下一轮前用写这段历史的模型压缩（trigger: model_downshift）。该模型失败时，由该轮自己的模型总结一次。窗口不更大的模型不参与。

为什么这样设计
由更大的模型总结
沿用 Codex 的模型降级压缩。小模型可能装不下要它总结的历史；读过这段历史的模型仍装得下。

HEAD 完整性

写入者规则
SessionStore.set_head用于显式移动：发送轮次前进、重试或编辑分叉、检出、回退、删除分支。压缩、加载会话、worker 重启、切换模型和保存元数据都不调用
append_message只有节点前驱等于当前 HEAD 时才移动。摘要拼接、侧分支写入和遗迹都不动 HEAD
派生轮次同会话子 agent 轮次以 TurnRequest.advance_head=False 运行；内部写入都不动 head，用户窗口不会中途被切走。跨会话发送仍推进目标会话的 head
不算移动的写入attach 卡片、inbox 和子 agent 路径通过 store 追加后恢复 head_before
TurnWriter（turn_runtime/turn_writer.py）执行一轮的链写入，只有它应用 advance_head。该包内只有这个文件移动 HEAD，另有 forced_tool.py 中用户发起的函数运行路径和 slash_actions.py 的恢复
镜像webui 的 conv 镜像和一次性 load_session 快照只读。React 会话 store 是唯一的实时转录。save_meta 去掉 head_id；镜像行不会变成存储
存储的 HEAD 落在调用上旧会话可能有；调用没有前驱，下一请求将没有历史。store/session/memory_index.py 的 _conversation_head 把它读成产生该调用的回复

图契约

  • 对每个分支尾，它的链读的那份摘要带 covers_ids：metadata.covers_ids，加上被覆盖轮次的调用子树，去掉已不存在的 id。
  • 没有分支读的摘要带 superseded_summary: true，没有 covers_ids。
  • 构建器不做 seq 运算，也不按 head 过滤。
请求检查点

每个 AgentLoop provider 请求，包括工具续写和函数内的 llm()、agent()，都会做预算（compaction/request.py）。超过限额时请求得到一个检查点；消息和 DAG 保持不变。

步骤规则
输出上限未指定时：取模型能力、16,384 和窗口四分之一中的最小值，预算和发送都用它。显式上限从不降低
检查点较早的完整纯文本历史变成一份任务摘要。所有用户消息和最近的 assistant 段保持原样。不完整的工具组、多模态输入和当前轮的签名推理不参与；已完成轮次的推理按其摘要文本总结，不含加密载荷和 id
复用在同一次调用内，模型相同且源前缀未变
摘要调用分块且有上限，超长时缩小重试；最多 32 个请求；绕过 AgentLoop。每个请求在流持续产出时运行，60 秒无事件则失败；停止会立即关闭它。失败时历史不变
超预算只用本地估算。放不下的受保护内容明确失败；估算超预算的请求不发送
为什么这样设计
不逐个总结结果
Codex、OpenCode、Pi 和 Kimi Code 都没有，Hermes 也把自己的关掉了：逐个替换工具结果会改写请求中段，之后每个请求都错过提示缓存，而且下一轮什么也没留下。改由步骤之间的持久压缩承担。
不用缓存编辑清除
Anthropic 的 clear_tool_uses 上下文编辑在 provider 端清除旧结果，对缓存的影响相同，且只适用于一家 provider；不再发送。
按用户自己的调用选择比例

压缩得早，每次调用读得少，但要为更多摘要和返工付费。context.auto_compact_percent（设置 → 系统 → 模型 → 长对话在多满时总结，50–95，每次决策时读取）由 GET /api/usage/tuning?days=30（runtime/context/tuning.py）给出建议：按模型在该时段的 chat、exec、subagent 调用上回放 50% 到 95% 的每个比例。沿用 magpie 的 tune（yetone/magpie，MIT）。

  • 按顺序回放，每个 prompt 按实际增长，去掉记录到的压缩（降到至少 20K prompt 的 60% 以下）。
  • 超过阈值（窗口比例减回复预留）时，压缩读完整 prompt，写一份和所见摘要一样长的摘要（没有时比对话开头多 10K）。下一次调用把它写入缓存，之后读回记录的压缩后的内容（见到五次前至少 10K）。
  • token 按目录价格或厂商常见比例换算成普通输入。
  • 余量不足半份摘要或二十次调用增长的比例不尝试。与最便宜相差 1% 内的取最大，且比当前至少省 3% 才建议。少于 50 次调用：不建议。
  • 同一端点为 Anthropic API 和 Bedrock 调用建议 models.prompt_cache_ttl（5m 或 1h）：一小时写入价格是输入的两倍，过期后的调用重写整个 prompt。该设置只延长普通缓存（providers/settings/cache_spec.py 的 with_lifetime_setting）。
其他压缩方案

每条链一份滚动摘要让缓存前缀稳定。这是策略，不是存储：各方案只在哪些摘要现役、渲染器如何替换上不同，切换不用迁移数据。

方案改动
分段（一条链上多份现役）N 个节点覆盖不相交的段；规则对每条链返回一个集合
嵌套covers_ids 允许摘要 id；替换递归
外部记忆节点相同；渲染器不再内联

任何方案都保留两条契约：上下文是只追加节点上的确定性视图，进入 prompt 的 id 以 reads 记在调用上。

压缩

一个会话最多一份现役摘要。再次压缩时把上一份摘要交给摘要器并替换它。extra_meta._last_summary_id 指向现役摘要，_last_summary_text 保存文本供链式使用；旧节点作为无效遗迹留在磁盘。摘要的胶囊画法：DAG 渲染第九节。

  • 用 id，不用 seq 区间。兄弟分支的 seq 交错，区间会卷入死分叉，还会随 HEAD 变化。
  • covers_ids 是真实轮次的连续段。绝不包含摘要：再次压缩时在旧段上延伸新轮次。

渲染规则

context/nodes.py 的 render_context 决定模型读什么，聊天和 runtime.exec 都一样。设 S 为现役摘要，L 为其 covers_ids。从 head H 渲染：若 L 的每个节点都在 H 的前驱主干上，去掉 L，在其位置放入 S；否则原样渲染主干。

情况结果
已压缩的分支[ROOT, S, 保留尾部…]
不含完整段的分叉（段内重试、死兄弟）原样；不继承它没有过的轮次的摘要
任何时候检出任何分支由数据确定；不取决于 HEAD 当时在哪
被取代的摘要不省略任何内容

DAG 胶囊按同一规则、同一 covers_ids 折叠。

流水线

/compact（trigger_compaction）、自动压缩（轮次前预算达到 context.auto_compact_percent，默认 80%）和响应式压缩（provider 溢出）都运行 engine.compact：

  1. 冻结渲染输入。compaction.view.load_compaction_view 使用 render_context 和 render_dag_messages，含工具结果、expose、spill 引用和老化边界。顶层轮次决定覆盖；可见子调用计入输入和预算。
  2. 选择整轮。保留窗口的 10%，限制在 8,000–40,000 token（显式覆盖优先）。优先在用户边界保留至少四条对话消息；已发布的汇报也是边界。低于目标：不操作。最后两轮超过目标时，切点可前进到最新用户边界。最新一轮保持完整，除非其后只有汇报。
  3. 摘要整个被覆盖前缀：每个被替换轮次、最初的请求、适用的上一份摘要、渲染出的子调用。不注入其他分支的缓存。非文本媒体用引用说明代替。用户取消或替换的请求要标明；助手或工具说的话保留出处，不写成事实。
  4. 写入前校验。拒绝空、失败、取消、超大或不减小的摘要；候选在内存中按相同老化边界渲染，必须严格变小。模型调用后复查 head 和渲染出的节点；有变化则为可重试的空操作，其他分支不算。provider 失败保留历史，不用有损的结构化兜底。
  5. 持久化并报告。一个节点；covers_ids 把上一份摘要展开成真实轮次 id。覆盖数和前后估算用上下文面板的渲染器。空操作不写入、不计数。

上下文显示使用 provider 的输入用量。每个请求还记录同一批消息的本地估算，之后图编辑时按实测比例缩放估算，下次上报前都标为估算。没有匹配估算的旧用量不用于校准。

自动压缩反复失败

每次失败仍要为整个对话付费。同一对话在同一模型上连续失败 FAILS_MOST（3）次，且每次距上次不超过 HELD_FOR_S（5 分钟）后，自动压缩从最后一次失败起等待五分钟，再试一次（runtime/context/compaction/hold.py，由 DefaultContextEngine.compact 查询）。

  • 算失败：摘要器错误（如 429）、带错误的空摘要、超渲染预算、没有减小。
  • 不算失败：取消、源变化。
  • 摘要成功安装后清零。/compact 总是执行。
  • 沿用 magpie 的压缩保护（yetone/magpie，MIT）。

一条用户消息内的压缩

每次 AgentLoop provider 请求之前，包括工具续跑和函数内的 llm()、agent()，运行时都对转换后的消息、实际工具、系统提示、输出上限和安全余量做预算。这个视图只属于该请求：执行消息和 DAG 不变，也不创建摘要节点。

步骤规则
输出上限未指定时取模型能力、16,384 和窗口四分之一的最小值，预算和发送用同一个值。显式上限绝不降低
工具结果完整工具组的纯文本结果直接摘要，不等下一条用户消息。用户消息、工具参数、结果 id、错误标志和多模态内容不变
检查点仍超：较早的完整纯文本历史变成任务摘要。所有用户消息和最新助手段原样保留。不完整的工具组、多模态输入和签名推理不适用
复用在同一次调用内，原文和模型设置匹配；检查点还要求源前缀不变
摘要调用分块，溢出时用更小的块重试；最多 32 次请求、60 秒；绕过 AgentLoop。失败时历史不变
超预算只是本地估算。放不下的受保护内容明确失败；估算超预算的请求不发送
按用户自己的调用选择比例

压缩得早，每次调用读得少，但要为更多摘要和返工付费。context.auto_compact_percent（设置 → 系统 → 模型 → 长对话在多满时总结，50–95，每次决策时读取）由 GET /api/usage/tuning?days=30（runtime/context/tuning.py）给出建议：按模型在该时段的 chat、exec、subagent 调用上回放 50% 到 95% 的每个比例。沿用 magpie 的 tune（yetone/magpie，MIT）。

  • 按顺序回放，每个 prompt 按实际增长，去掉记录到的压缩（降到至少 20K prompt 的 60% 以下）。
  • 超过阈值（窗口比例减回复预留）时，压缩读完整 prompt，写一份和所见摘要一样长的摘要（没有时比对话开头多 10K）。下一次调用把它写入缓存，之后读回记录的压缩后的内容（见到五次前至少 10K）。
  • token 按目录价格或厂商常见比例换算成普通输入。
  • 余量不足半份摘要或二十次调用增长的比例不尝试。与最便宜相差 1% 内的取最大，且比当前至少省 3% 才建议。少于 50 次调用：不建议。
  • 同一端点为 Anthropic API 和 Bedrock 调用建议 models.prompt_cache_ttl（5m 或 1h）：一小时写入价格是输入的两倍，过期后的调用重写整个 prompt。该设置只延长普通缓存（providers/settings/cache_spec.py 的 with_lifetime_setting）。
其他压缩方案

单一滚动摘要和 Claude Code、Codex CLI、Gemini CLI 一致，也让缓存前缀稳定。这是策略，不是存储：各方案只在哪些摘要现役、渲染器如何替换上不同，切换不用迁移数据。

方案改动
分段（多份现役）N 个节点覆盖不相交的段；规则按摘要应用；用现役集合取代 _last_summary_id
嵌套covers_ids 允许摘要 id；替换递归
外部记忆节点相同；渲染器不再内联

任何未来的上下文都保留两条契约。DAG 是账本，不是上下文：上下文是只追加节点上的确定性视图，现有偏离（render_range、expose、attach 与 merge、记忆预取）都是数据，不是隐藏状态。来源必须记录：进入 prompt 的 id 以 reads 记在调用上，用于回放、审计和按节点标记。

摘要是第一种视图节点：替代其他内容的节点。检索的记忆、注入的文档和跨会话引用是它的推广，胶囊是通用呈现。在出现第二种方案前，不提前建通用的视图组合框架。

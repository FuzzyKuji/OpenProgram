Compaction

A summary stands in for the turns it covers on every chain that holds them all, and each chain reads its own. One rule, active_summary_for_chain (state/store/session/summaries.py), serves the render, the compaction input and the graph builder, so they never disagree. The capsule that draws a summary: DAG rendering §9.

  • Ids, not seq intervals. Sibling branches interleave seqs, so an interval would drag in dead forks and change with HEAD.
  • covers_ids is a contiguous segment of real turns. It never names a summary: re-compaction extends the old segment by the new turns.

Which summary

Of the summaries whose covered turns all lie on a chain, the chain reads the one whose coverage reaches furthest along it; seq breaks a tie. A rolling summary covers the one before it plus newer turns, so it wins on its chain and the older one serves only chains that branch off earlier.

CaseChain reads
Two branches compacted one after the otherEach its own summary. Switching between them renders each with its own and writes nothing
A summary written before the fork pointBoth branches
A rewind retracts turns in placeA retracted message is not on the chain and a retracted summary does not exist, so a rewind into a summary's range falls back to an earlier summary still wholly on the chain, or to the raw turns
Edit, retry or fork inside a covered segmentThe new branch lacks part of the segment: it reads an earlier summary that fits, or raw
Two branches that loaded different toolsEach summary carries its own carried_tool_names
Why this design
A summary per chain
Follows Pi: the last compaction on the path from the leaf. Compared: one newest summary per conversation (Claude Code, Codex, with one linear history), which leaves every other branch raw to compact again. Branches here run in parallel, so the summary belongs to the chain.
Rewind falls back
Codex drops a compaction when the rollback goes behind it; the same rule here keeps a retracted summary from naming turns the chain no longer holds.

Pipeline

/compact (trigger_compaction), auto-compact (budget at context.auto_compact_percent, default 80%, before a turn and between a turn's steps) and overflow recovery all run engine.compact on a chain the caller names by its tip: /compact the session head as it reads it, the others the turn's own branch. All but /compact pass the turn's stop signal.

  1. Freeze the rendered input of that chain. compaction.view.load_compaction_view uses render_context and render_dag_messages, with tool results, expose and spill references. Top-level turns define coverage; visible child calls count toward input and budgets.
  2. Select whole turns. Retain 10% of the window, bounded to 8,000–40,000 tokens (an explicit override wins). Prefer at least four conversational messages at a user boundary; a posted report is a boundary too. Below target: no-op. If the last two turns exceed the target, the cut can advance to the latest user boundary. That latest turn stays intact unless only reports follow it.
  3. Summarize the whole covered prefix with the summary prompt (Summary prompt and role): every replaced turn, the initial request, the chain's previous summary, rendered child calls. Non-text media becomes a reference notice.
  4. Validate before writing. Reject empty, failed, cancelled, incomplete, capped or non-reducing summaries; a candidate, rendered in memory the same way, must be strictly smaller. After the model call, recheck the chain's rendered nodes; a change is a retryable no-op, other branches and a head moved elsewhere do not count. Provider failure keeps the history, with no lossy structural fallback.
  5. Persist and report. One write, with the restored state; covers_ids expands any previous summary to real turn ids. The before figure is the context panel's reading of the chain; the after figure is that reading less what the candidate saves. No-ops write nothing and do not count.

The context display uses provider input usage. Each request also records a local estimate of the same messages, so a later graph edit scales its estimate by the measured ratio, labelled as an estimate until the next report. Legacy usage with no matched estimate does not calibrate.

/compact is the branch's foreground operation (op_kind: compact, an op_id on compaction_started). The page's Stop and the terminal's Ctrl-C both send operation.cancel with that id; the summary request ends with nothing written and the row reads "stopped". An automatic compaction that fails says nothing; the next request tries again.

Why: Claude Code, Codex and Kimi Code all cancel a manual compaction with the key that stops a turn; follows Claude Code, whose terminal is also Ink.

Automatic compaction that keeps failing

Each failed try still pays for the whole conversation. After FAILS_MOST (3) failures in a row of one branch on one model, each within HELD_FOR_S (5 minutes) of the last, automatic compaction on that branch waits five minutes from the last failure, then tries once (runtime/context/compaction/hold.py, keyed by conversation, model and branch, consulted by DefaultContextEngine.compact). Another branch keeps compacting.

  • Failures: summarizer error (a 429, for example), a summary missing sections after the reminder, one that reaches its output cap, empty with an error, no reduction.
  • Not failures: cancellation, changed source.
  • A summary that installs clears the count. /compact always goes.
  • Follows magpie's compaction guard (yetone/magpie, MIT).

Overflow recovery

The agent loop (runtime/agent/loop/loop.py) compacts a turn's chain in two places; the turn's own steps stay verbatim.

WhenWhat happens
The provider rejects a request as too longDrop the rejected reply, compact (reactive), re-render and send the same request again. One compaction per request, two per turn; a second overflow, or nothing freed, fails the turn with the provider's error. The turn never reruns from its start, so tools are not called again
A round of tool results passes the auto-compact thresholdCompact once per turn (mid_turn) and continue on the re-rendered request
A stop during eitherThe turn ends as stopped
A call that cannot compact durablyFailover to a smaller window, Runtime.exec, background and clean runs, an override history: the request checkpoint below
Why this design
Retry the one request
Follows Claude Code and Codex: both compact on a context-length error and resend the request that failed, with a bound on attempts. Compared: rerunning the whole turn's loop, which repeats every step already done, tool calls with side effects included.
Compact between steps
Codex compacts mid-turn when usage passes its limit after a sampling step; Claude Code checks before each request. A long tool loop inside one message otherwise only grows until the provider refuses it.

Summary prompt and role

One prompt (compaction/prompts.py) writes every summary, first or rolling, with these ## sections: User intent, All user messages, Decisions and constraints, Completed work, Current work, Next step, Relevant files. It leaves out what every request sends anyway (system prompt, AGENTS.md, guides, memory), marks cancelled requests, and attributes claims.

  • A reply without every section is asked once more with a reminder (NUDGE); still incomplete, the compaction fails, writes nothing and counts toward the hold.
  • The output cap is 20,000 tokens, or a quarter of a smaller window. A summary that reaches it fails instead of being kept cut off.
  • The summary is user input with a prefix that says what it is.
Why this design
Sections and a reminder
Follows Claude Code's sectioned summary, with the user's own messages kept, and its check for a summary that left them out. Compared: two prompts (first and update) with five loose parts, which let a rolling summary drop the user's earlier instructions.
User role, with a prefix
Follows Codex and Pi, which hand the summary back as user input that names itself. An assistant-role summary reads as something the model said and was believed as its own claim.
A capped summary fails
Claude Code treats an incomplete summary as a failure; a cut-off summary loses the Next step and Relevant files, the parts a continuation needs most.

What a compaction restores

After the summary text, in the same message, the node carries a <restored-state> block (compaction/restore.py), within 10,000 tokens and the same bytes on every request:

SectionSource
Approved planThe last exit_plan_mode the user approved on the chain, unless plan mode was entered again after it; over 6,000 tokens it is cut with a note
Todo listThe conversation's todo board, with each item's status
Background jobs still runningJobs that have not ended
Files read, Files changedPaths the covered calls read, wrote or edited, added to the previous summary's lists, the latest 30 of each. A stored call keeps its arguments as the JSON text the model sent, and the path (and the plan) are read from it
Why this design
State written, not re-read
Follows Claude Code, which re-attaches the plan, todos, running tasks and read files after compacting. Compared: re-reading file contents, the most bytes and stale once the file changes; paths let the model read again. Kept in the node, the block stays cached.

Summary request

The summary sends the last request again with the summary prompt as one user message more (compaction/fork.py): same system prompt, tools and cache key, so the provider reads the prefix from its cache. A tool call in the reply is not run; the summary is asked once more.

That message opens by saying it comes from the system, not the user (FORK_SUMMARY_PROMPT): it is left out of every section, and the latest request quoted under Next step is the user message before it. The summary covers the whole conversation up to it, kept turns included; the kept turns still render raw after it.

It reads the covered text instead when the model differs, the request plus the summary would not fit, the request is not on the chain, or the compaction recovers from an overflow.

Why this design
Fork the cached prefix
Follows Claude Code's forked summary and OpenCode's compaction on the same message list: the conversation is already cached, so the summary pays cache reads instead of a fresh input. Compared: rendering the covered turns as text in a new request, which pays every token at full price; it remains the fallback.
The prompt names itself
Follows Codex, whose compaction prompt opens as a context checkpoint, and Claude Code, which asks for "the conversation so far". Sent bare, the prompt is the newest user message, and a model quoted it as the user's latest request. Compared: covering only the turns before the kept tail, which changes the prefix and loses the cache.

Model downshift

A branch that follows its Agent onto a model with a smaller window is compacted before its next turn with the model the history was written with (trigger: model_downshift). If that model fails, the turn's own model summarises once. A model whose window is not larger takes no part.

Why this design
The larger model summarises
Follows Codex's model downshift compaction. The smaller model may not hold the history it is asked to summarise; the one that read it still does.

Graph contract

  • For each branch tip, the summary its chain reads carries covers_ids: metadata.covers_ids, extended with covered turns' caller subtrees, minus ids no longer present.
  • A summary no branch reads carries superseded_summary: true and no covers_ids.
  • The builder does no seq arithmetic or head-dependent filtering.
Request checkpoint

Every AgentLoop provider request, tool continuations and function-local llm() and agent() included, is budgeted (compaction/request.py). Over the limit, the request gets a checkpoint; messages and the DAG stay intact.

StepRule
Output capUnspecified: the smallest of model capability, 16,384 and a quarter of the window, used for budgeting and dispatch alike. Explicit caps are never reduced
CheckpointOlder complete text-only history becomes one task summary. All user messages and the latest assistant segment stay verbatim. Incomplete tool groups, multimodal input and the current turn's signed reasoning are not eligible; a finished turn's reasoning is summarized by its summary text, without the encrypted payloads and ids
ReuseWithin the invocation, for the same model and an unchanged source prefix
Summary callsBounded chunks, retried smaller on overflow; at most 32 requests; bypass AgentLoop. Each request runs while its stream keeps producing and fails after 60 seconds without an event; a stop closes it at once. Failures leave history intact
Over budgetLocal estimates only. Protected content that cannot fit fails explicitly; a request estimated over budget is not sent
Why this design
No per-result summaries
Codex, OpenCode, Pi and Kimi Code have none, and Hermes turns its own off: replacing tool results one by one rewrites the middle of the request, so every later request misses the prompt cache, and nothing is kept for the next turn. A durable compaction between steps does the work instead.
No cache-edit clearing
Anthropic's clear_tool_uses context edit cleared old results on the provider side with the same effect on the cache and only on one provider; it is not sent.
Choosing the share from the user's own calls

Compacting sooner reads less per call but pays for more summaries and rework. context.auto_compact_percent (Settings → System → Models → Summarize long conversations at, 50–95, read at each decision) is advised by GET /api/usage/tuning?days=30 (runtime/context/tuning.py), replaying every share from 50% to 95% on the period's chat, exec and subagent calls, per model. Follows magpie's tune (yetone/magpie, MIT).

  • Calls replay in order, each prompt growing as it really grew, with recorded compactions (a drop to under 60% of a prompt of at least 20K) removed.
  • Past the threshold (the share of the window less the reply reserve), a compaction reads the whole prompt and writes a summary as long as those seen (or 10K over the start when none were). The next call writes it to cache; later ones read back what recorded compactions were followed by (at least 10K until five were seen).
  • Tokens are weighed against plain input with catalog prices or the vendor's usual ratios.
  • Shares leaving less than half a summary, or twenty calls' growth, of room are not tried. Of those within 1% of the cheapest, the largest is advised, only if it saves at least 3% over the current one. Fewer than 50 calls: no advice.
  • The same endpoint advises models.prompt_cache_ttl (5m or 1h) for Anthropic API and Bedrock calls: hour-long writes cost twice input, and a call after expiry writes its whole prompt again. The setting lengthens only a plain cache (with_lifetime_setting in providers/settings/cache_spec.py).
Other compaction schemes

One rolling summary per chain keeps the cache prefix stable. It is policy, not storage: schemes differ only in which summaries are active and how the renderer substitutes them, so switching migrates no data.

SchemeChange
Segmented (several live on one chain)N nodes over disjoint segments; the rule returns a set per chain
Nestedcovers_ids admits summary ids; substitution is recursive
External memorySame node; the renderer stops inlining it

Any scheme keeps two contracts: context is a deterministic view over append-only nodes, and the ids that entered a prompt are stamped on the call as reads.

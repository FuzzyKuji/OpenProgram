Claude Code 压缩

研究笔记，不是 OpenProgram 的设计。Anthropic API 文档只描述单一压缩机制（超过 token 阈值，LLM 摘要）。下面的级联是客户端实现细节，来自第三方逆向，以 Inside Claude Code 为准；各来源对顺序略有分歧，数字随版本变化。

层级动作触发LLM破坏缓存损失
Budget Reduction（例行，不在级联内）截断单个超大输出tool_result 超过 4000 字符否否中段
1 Microcompact清理旧工具输出50 次工具调用，之后每 25 次；或空闲 90 分钟否cache-aware：否旧输出
2 Snip删除最老轮次第 1 层后仍超否是整轮
3 Context Collapse分段摘要第 2 层后仍超，约 90%是是细节
4 Auto-Compact全量摘要第 3 层后仍超，或 /compact是是大部分，留摘要
5 Reactive紧急压缩API 返回 413 prompt_too_long是是同第 4 层

每次 LLM 调用前：Budget Reduction，再从第 1 层检查；每层后复查，仍超则前进。遇 413 走第 5 层并重试，失败则终止。第 3、4 层被描述为有重叠的策略：有些配置跳过第 3 层，/compact 跳过 1–3 层。

原则

原则含义
懒惰降级便宜的先做
旧工具输出先清旧的 grep、read、bash 输出最大也最不重要
日常靠 MicrocompactSnip 和 Compact 很少触发
缓存保护cache-aware 在服务端清理；截断后内容固定
只动整轮用户和助手消息不单独截断：整轮删除或摘要
CLAUDE.md从磁盘重新加载，不参与压缩
用户主导/compact 和 /context；自动只是兜底

层级细节

Budget Reduction

只处理工具输出。超过 4000 字符（约 1000 token）：保留前 2400 和后 1600。

截断前（50000 字符）："src/a.py:12: TODO fix this\nsrc/b.py:34: ..."
截断后（4000 字符）："src/a.py:12: TODO fix this\n...[46000 chars removed]...\nsrc/z.py:99: TODO cleanup"
第 1 层 Microcompact

处理 FileRead、Shell、Grep、Glob、WebSearch、WebFetch、FileEdit、FileWrite。

Cache-aware（主路径）Time-based（兜底）
动作服务端通过 Context Editing API 清理旧 tool_result客户端替换为哨兵
破坏缓存否是
触发50 次调用，每 25 次空闲约 90 分钟
可恢复否否
依赖Anthropic Context Editing；其他 provider 没有等价能力无
每个输出变成0 token约 20 token：[content no longer available]

已在缓存的内容由服务端清理，不在缓存的由客户端替换。哨兵用字节稳定的规范形式，重复执行不改变已缓存内容。例：清理 10 个平均 500 token 的结果，释放约 4800。

Context Editing API

公开 beta（context-management-2025-06-27），不是 Claude Code 专有；并入普通调用。客户端发送未修改的历史和 cache_edits；服务端替换缓存内的旧块，前缀保持有效，客户端不必知道清了哪些。第 2–5 层直接改客户端消息列表。

策略效果
clear_tool_uses清理旧 tool_result，保留最近 N 个（N 未确认）
clear_thinking清理旧 thinking 块
clear_at_least至少清理的 token 数
第 2 层 Snip
  • 触发：第 1 层后仍超（据报告有约 13K token 缓冲，随版本变化）。
  • 从最老开始删除整轮（用户、助手和全部工具调用），每删一轮重算，直到低于阈值。
  • 无摘要、无落盘、无标记；模型不知道之前讨论过什么。
  • 信息全失且缓存前缀失效，但免费且快。
第 3 层 Context Collapse
  • 触发：第 2 层后仍超，约 90% 非阻塞，95% 强制阻塞。
  • 每段 5–10 轮（未确认），各自独立摘要约 100–300 token（估计）。LLM 调用数等于段数。最近 N 轮完整保留（N 未确认）。
  • 原文留在 collapse store：读时投影，类似数据库视图，理论上可回滚。
  • 保留段边界和时间线；第 4 层不保留。

第 4 层 Auto-Compact
  • 一次 LLM 调用把全部历史摘要成约 2000–5000 token 的块，替换旧消息，不可回滚。最近 1–2 轮完整保留。上下文从 70–90% 降到约 15–25%。
  • 阈值覆盖：CLAUDE_AUTOCOMPACT_PCT_OVERRIDE。
  • /compact 或 /compact 保留关于数据库迁移的讨论：给提示词摘要更好。官方建议在 60% 时使用。
  • 丢失：早期指令、设计讨论、推理过程、50 轮以前的代码、风格偏好。保留：当前任务、最近修改的文件名、最近的错误和解决办法、CLAUDE.md。
  • 链式：每次在上次摘要上压缩，信息逐层衰减。长会话可能压缩 3–5 次。
  1. 运行 PreCompact hook。
  2. 用 getCompactPrompt() 构造提示词。
  3. 把全部历史发给 LLM。
  4. 用 buildPostCompactMessages() 构造消息。
  5. 从 CLAUDE.md 重新加载系统提示。

第 5 层 Reactive

先尝试 context-collapse 溢出恢复，再紧急压缩，每轮最多一次。都失败则结束会话。

一次长会话，200K 上下文
上下文运行
0–30%只有 Budget Reduction
30–50%超过 50 次工具调用，Microcompact 清理前 30 个输出，约 15K token，之后每 25 次
超过阈值Microcompact 不够，Snip 删除最老 5 轮，约 25K token
再次超过Microcompact 和 Snip 重复
极端且罕见旧轮次所剩无几，走 Context Collapse，再 Auto-Compact

Storage failures degrade persistence, not event delivery. No new execution runtime, remote service, account integration or history deletion belongs to this design.

Streaming

  • Text and thinking frames coalesce into one animation-frame store update and are placed by offset into every view holding their row. A numbered update or a read flushes pending text first.
  • Tools, steps, citations, status and terminal rows arrive as numbered transcript_update changes, the same rows a read draws.
  • A text frame whose offset lies past the text the row holds shows a lost frame, and an update that does not follow the view's revision shows a missed one; either way the view reads once at its anchor.
  • Connection close flushes received text before clearing which session each turn belongs to.
  • Rendering primitives: bounded history windows, measured row recycling, lazy full tool output, independent follow locks.

Recovery reads

Recovery reads request snapshot-only mode: the execution record and event cursor come from one SQLite transaction with no event bodies, since persisted streams can exceed 200 MB and the Web replay handler consumes only the snapshot. Explicit event-history clients keep full replay.

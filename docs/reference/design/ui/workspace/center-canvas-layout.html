Center canvas layout

Each layout occupies one top-level tab. Any tab content fits a pane: chat, web page, terminal, file preview, program view. The real limit on panes is their minimum size. Floating windows belong to picture-in-picture; a pane is never shared across windows.

Pane grip

No persistent toolbar and no title bar. A ••• grip sits top centre, with an 88×22px hit area. Pressing it never selects text and only prepares a drag: no store commit, focus or route change. A click focuses.

Tiling menu

Mirrors the macOS green-button menu with small layout glyphs. A hint line names the glyph under the pointer, otherwise says to hold Option for quarters. On macOS it also names the shortcut; on Windows and Linux the tiling keys do not exist, the line names none, and Option reads Alt.

The split in the strip

A split window is one tab, as wide as any other, like Chrome's and Arc's split views: the focused pane's icon and title, a miniature of the split with that pane filled, and the pane count. Its close acts on the whole window.

A pane closed from a split that stays is removed in the same tick as the click and the canvas plays the close. When focus changes or a merge just formed the split, icon and name rise in over 200ms.

Window overview

Modelled on Mission Control and the iPad app switcher. The center area recedes to the page colour and every window in the strip becomes a card on a grid, as large as fits, never wider than half the area.

A card keeps its window's split, drawn from the same tree and geometry. Panes have no drop zones: on a visible canvas the bottom half and corners were hard to tell apart.

Landing a merge

One zoom, begun at the release. The commit waits on the desktop shell's transfer cancel (about 50ms) and a render of the split (about 40ms), so waiting would show a gone window and an unchanged card for some 90ms.

  1. The release holds the overview, notes the drop and tabs, and sets landing. The target card grows from its grid place over the center area in 340ms, one uniform-scale transform that plays through the wait. Its window activates underneath, so panes are loaded by the time they make room.
  2. commitCanvasDrop hands the merge to landOverview, which holds it and marks landed.
  3. Landed and under way (about a tenth of a second in), the overview reads each pane's rect in the zooming card, converts to the canvas's unscaled frame, and passes rects plus zoom start, curve and progress to captureCanvasLanding.
  4. It closes, applying the merge in the same tick. A fallback timer applies it too, unanimated.
  5. The shell plays the capture: panes animate real geometry into the split; the docked tab enters from the drop side at final size, translated out and clipped at the canvas edge (clip-path), same 300ms, so the seam moves as one and content never re-wraps.
  6. Measured unscaled first, the canvas root takes over the zoom with the same keyframes and the card animation's own startTime, one clock, on live content rather than blurry JPEGs.

Drag lifecycle

The canvas will host many small app windows, so every drag ends cleanly and leaves other panes alone.

Rendering and native views

  • Recursive geometry feeds stable content hosts: tree edits and zoom do not reparent file editors, terminals or sessions.
  • A pane under 150×110px shows its title and type with a zoom action.
  • Each web pane reports its own bounds (registerVisibleWebTabBounds). While dragging, undersized, or beyond eight visible native views, a pane shows its captured image. Selecting a paused view gives it priority. Hidden views stay alive; no process ends.

Persistence

The window's tab payload stores each group's tree, focus and zoom, with tab references only. Missing references become empty panes. Cross-window payload validation bounds tree depth, node count and serialized size independently of the layout editor. Resources attachment uses its existing backend ownership operation.

Interaction feedback

A click that starts anything slower than about 100ms changes something visible at once.

The three layers

LayerBehaviour
0ms optimisticBefore any network I/O the client shows a transitional state: spinner card, highlighted target, stopping, pending bubble. It is written into the session store as a typed local row, an overlay on a server row, or a flag; never as a change to a server row.
Fast server confirmThe 0ms row is a typed local row carrying the send's clientRequestId. The server stores the same id on the user node or on the function run's pre-created node, so the first read or turn_upsert naming it replaces the local row in place, whichever arrives first, without flicker. An ack to a socket holding no view of the chat carries that read as first_read.
Streaming backfillNumbered transcript_update changes fill the row (tree, steps, status) and text frames add text by offset; the terminal row_upsert finishes it. A field shown ahead of the server is an overlay that ends on a stated event: the terminal status, the next read, the server's matching value, the row leaving, or the request failing.
Failure rollback (required)Backfill supersedes the state, or a timeout reverts it and shows an error toast: 10s for control actions, OPTIMISTIC_TIMEOUT_MS.

Shared helper

optimisticAction({apply, settled, revert, onTimeoutMessage}) in apps/web/lib/runtime-bridge/optimistic-action.ts.

ArgumentRole
applySets the 0ms state
settled()True once real data supersedes it: message gone from the store, tree repopulated, branch.active flipped
revertRuns with the toast on timeout while settled() is false

Used where the confirm path is a load_session reload (retry, version switcher). A purely local transient (stop, fn-form placeholder, branch checkout) inlines the pattern.

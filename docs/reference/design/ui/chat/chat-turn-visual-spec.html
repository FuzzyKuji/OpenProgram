Lifecycle and ownership

  • Streaming, completed and restored messages use the same ExecutionStrip, ThinkingStep and FunctionStep; completion never switches to a boxed table.
  • Without ordered blocks, stored thinking and tool records are shown in stored order. Missing interleaving is not reconstructed and no tool record is invented. Results, errors, identifiers and full-output references stay.
  • Functions started by an Agent reply belong only to that reply's timeline. Only user-invoked functions are independent runtime messages.

Chat math

  • Complete $$, $, \[ and \( blocks are stashed before marked and restored as escaped text after sanitizing. MarkdownText typesets after paint; the chat-area pin path calls typesetMath on the observed column.
  • Unclosed streaming math waits for the next paint with a closer. Prose without math and incomplete openers do not typeset. Invalid math does not throw.

Waiting for a reply

An empty reply shows one static “Thinking…” row with the summary row's shimmer, no › (a green raining label in the code rain style). The spinning activity mark lives on the sidebar row. Approval and terminal states suppress it; timeline, footers and pane titles add no mark.

Failed replies

  • The partial answer and ordered trace stay. One terminal notice follows them, before message actions: a localized headline, technical details on request as plain text. No automatic retry is added.
  • Partial blocks and failure detail are separate fields. Node output keeps the error text for model context and non-Web consumers; the Web mapper restores the answer from ordered text blocks.
  • The node persists detail, reason, retryability and retry delay before the final failure event, so history restores the same notice. Older error output is recognized without rewriting history and does not repeat the answer.
  • Cancellation, approval, nested details, retry and branch semantics and Goal reports are unchanged. Provider taxonomy stays authoritative; no second error store.
Acceptance
  • A public turn emits text and tools, then fails: live and cold history show answer, trace and one notice.
  • Empty and older failed replies stay visible. Successful and cancelled replies gain no notice. Details work narrow and dark.
  • Regression also covers browser permission inheritance and high-level delegation. Bound-page tests supply an explicit binding and expect the stop after three failed attempts on one observation, with the concrete reason.

Transcript update ownership

  • The server owns every row. A read draws a window, numbered transcript_update changes keep it current, and text frames add text to a block by offset. One reducer, apply-transcript-update.ts, applies all three, so a row drawn live is the row a reload draws.
  • The browser adds only what the server has not named yet. A pending send, a function placeholder or a notice is a typed local row, and goes when a read or update names its clientRequestId.
  • A field shown ahead of the server (Stop, a version switch, a chapter pin, a file undo, a goal result) is an overlay that ends on a stated event and never changes the row under it.
  • Execution trees supplement the owning reply: a model-issued function's tree is an item of the reply's callRoots, a function run's tree a field of its row. A tree or frame for a row the view does not hold creates nothing.
  • A missed update or a lost text frame makes the view read once at its anchor. A read during a stream neither loops nor shortens the reply, because the server parks that view's frames until the read's reply has gone. A branch move or structural change reads again.
  • Each execution root keeps its persisted path. Repeated calls stay distinct; a root is consumed once across text-separated groups. A completed function stays in its summary; direct runs stay standalone.

Acceptance replays recorded chats through production reducers and components and requires live to equal cold at every checkpoint: stream, partial history, completion, late trees, steers, errors, cancellation, reconnect and reload.

Sensitive text in previews

  • Known token formats and complete private-key blocks are masked in passive display; pasted previews mask before truncating.
  • Reveal is scoped to the source message, conversation and rendered prose, and never moves to another value. Explicit edit, copy and model payloads keep the original.
  • Display masking only: not password recognition or data removal.

Acceptance uses the real UserBubble with synthetic secrets: long key preview, paste expansion after reveal, content and session changes, show and hide, unchanged source.

Interaction contract
  • The bottom of an intermediate window is not the latest position. Main and split panes share following, adaptive rendering and jump.
  • Jump stays available while newer history exists and after a failed request; repeated clicks share one pending intent.
  • Wheel, pointer and keyboard cancel a pending jump or restoration before the window changes. Ordinary paging still compensates for inserted rows.
  • Pane teardown saves the final anchor. Reconnecting resumes loading without an old retry delay.

Acceptance
  • A synthetic source of 300,000 one-row turns: repeated bidirectional paging keeps pages, rows and measurements bounded; rapid reversals under latency keep a visible message; stale replies, reconnect, branch changes and live updates cannot corrupt the window.
  • Backend page reads do not scan or parse the whole branch once the view is built.
  • Browser tests cover an intermediate-window bottom, failed and repeated jumps, interrupted restoration, independent split panes, unmount and remount, and the saved anchor across queued animation frames.
  • Regression asserts skipped work, semantic equivalence, cache eviction and bounded retention, not timing. Timing and heap figures are synthetic and do not establish latency for large real attachments or tool output.

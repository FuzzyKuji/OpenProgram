Queued messages

Messages typed during a run sit in one raised card above the composer, outside the scrolling transcript. Each message keeps its own identity, order, attachments and settings.

AspectRule
RowOne line: tag (“Next turn”, or why it was not sent), text, hover actions (add to this turn, retry, edit, remove). Clicking the text expands the message and attachments
CardBounded height. The heading collapses it; Clear all removes rows not being edited. Drag or Alt+↑/↓ changes the send order
CapturedText, expanded paste content, attachment bytes or original paths, send settings. Attachments can be queued without starting another execution
EditText, file picking, file drop, previews, removing one attachment. Holds that row until Save (keeps position and original settings) or Cancel (keeps the previous payload), and blocks its drain
Added to this turnAttachments travel too: saved to the session and named by path, images kept for the model at the next safe point. Editing or removing a row with unconfirmed delivery first takes the message back; one the turn already has stays
DrainOrdinary chat sender and attachment envelope, in order, with the exact edited payload. Failure or rejection keeps the whole message; acceptance releases it
SurvivesReload, closed window, App restart. Rows live in localStorage, bytes in IndexedDB; a window adopts unlocked rows under one exclusive lock. A drain removes its row before the socket write: a crash can lose that send, never repeat it
Previews and limits of queued attachments
  • Unsent previews use captured local content, including native paths outside the session workdir: images and text render directly, bounded PDFs use a local Blob URL.
  • Native documents remain path references when sent; preview bytes do not widen backend file access.
  • Persisted attachments keep the read-only DocumentWindow. Missing or unsupported previews report the limitation and keep the attachment.
  • User messages in the transcript keep their own controls and bubbles with reduced vertical spacing. History editing keeps its fork-and-resend semantics.
  • The queue does not delete history, change model behaviour, combine instructions or modify approval decisions.
  • Layout reference: the user's description of Codex, retained messages near the input with a small footprint. No undocumented Codex storage or editing behaviour is assumed.

Implementation status

The five behaviours, the strip and queued messages are implemented. Installed-App checks confirm mixed ordering, format and size labels, full-image preview, draft recovery, folder listing, original-image retention and direct model image recognition. End-to-end document reading is unverified because live executions wait after requesting a read.

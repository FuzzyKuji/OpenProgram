Chat transcript follow

Author: engineering Status: implemented on the web renderer Scope: web renderer (App and browser)

Sending a message does not reliably take the reader to the latest turn. Four overlapping scroll writers disagree about what “bottom” is and who may move the viewport (legacy scrollToBottom, unused useStickToBottom, live useChatAreaStick, and loadSessionHistoryWindow). This page collapses them into one React-owned follow policy: one attach/detach state, one at-bottom predicate, one follow-trigger table, and one padding-edge definition of latest. Chat handlers and the history loader do not pin latest onto an arbitrary viewport.

Current implementation and verified gaps

useChatAreaStick owns main and peer transcript placement, send following and Jump. chat-scroll.ts provides geometry and generation-stamped notes. useHistoryWindow and the history loader own bounded pagination and per-viewport anchor restoration. Legacy follow writers are absent.

Send identity and admission

Accepted normal, direct-function and running queue/steer submissions publish a note for their captured session and scroller. Loading or failed attachments reject admission before queue creation, draft clearing or note publication. Completed notes remain readable by design; a rejected later submit must preserve the existing note and its generation.

First activation and delayed layout

Without saved pixels, first activation creates its own generation and follows latest through delayed layout. Recent returns restore detached reading positions; latest-following and expired views open at latest. A user gesture cancels pending following. A pending accepted welcome send survives activation until its view is ready.

Bottom-aware conversation restoration

Each viewport stores both its scroll offset and whether it was following the latest message. Returning to a viewport that followed latest follows the new bottom through delayed loading and layout. A viewport explicitly scrolled into history restores its saved offset and history anchor. Legacy entries without freshness evidence open at latest. User interaction cancels pending following; main and peer keys remain separate. The asynchronous conversation loader must not overwrite latest placement with stale saved pixels. Reload persistence retains an unchanged position's follow state.

Latest intent also survives an initially empty transcript. When asynchronous rows commit before ResizeObserver delivery, layout preserves the existing follow state and places the new bottom. Height growth is not a reading gesture; the 600 ms growth suppression starts only after actual pointer, wheel or scroll-key input.

Restoration follows one lifecycle policy. A new App or Web document always opens at latest; saved state from another runtime is ignored. Within the same runtime, a conversation revisited less than one hour after leaving restores its reading state. At one hour or later it opens at latest. Returning after the application has lost focus for an hour also follows latest. There is no timer that moves an actively viewed transcript. Leaving, hiding, or unmounting records the departure time even if the reader has not scrolled recently. Latest restoration clears the obsolete history anchor and uses the existing cancellable latest-window loader. Storage records contain offset, bottom intent, timestamp and runtime identity; legacy entries lacking freshness evidence open at latest. The one-hour threshold is defined once.

Older history and first activation

First activation of an older loaded window requests latest and stays detached until a verified latest response is published. It does not snap the stale window while waiting. A browser fixture exercising this activation must provide that response before expecting latest placement. A fixture exercising manual reading of an older window must instead establish an explicit saved viewport; otherwise it unintentionally starts an unrelated activation request.

History restoration ownership

The loader restores each registered viewport using its own captured anchor and key. It does not perform latest placement. The hook preserves manual reading and cancellation while history pages change. Session reloads do not schedule a second pixel restore: a saved offset from the cached window may exceed the shorter latest page and incorrectly clamp reading to its bottom.

Welcome first send

Main retries the current accepted send after the welcome overflow lock clears. Peer sends do not use this path.

Separate peer viewports

Main and peer operations use separate scroller keys. Accepted queue/steer follows only the submitting pane; attachment rejection leaves both viewports unchanged.

Verified browser fixture gaps

Two historical-window browser fixtures wait for a nonzero initial position while withholding the automatic first-activation latest response. Four queue/steer browser cases assume no note exists after rejecting a loading attachment, although initial activation has already created a completed note. These expectations conflict with the activation and note-lifetime contracts. Fix the specific fixtures by establishing saved historical reading positions and comparing the exact note before and after rejected admission. Keep first-activation latest requests, delayed-growth placement, manual cancellation and send semantics unchanged. Existing Node activation regressions retain their acceptance meaning.

Controlled browser tests exercise production hooks with isolated backend responses. They do not establish installed-App or live-provider acceptance. Fixture repair and independent review evidence are recorded separately.

Adopted, modified, and rejected choices

Adopted

One policy module in apps/web/lib/chat/history/chat-scroll.ts. One attached boolean per scroller. Send / queue-drain / first welcome send = take-latest, instant snap. Stream pins only while attached and on the latest history window. Jump to latest remains the explicit smooth re-attach. First activation follows latest; subsequent activation restores the saved position without creating a message. Desktop App uses this same web renderer.

Modified

Take-latest is a generation-stamped note keyed by session id plus the submitting scroller’s chatKey, not a consume-once boolean and not lastRole alone. lastRole === "user" remains a fallback until the send-path note lands in the same merge train. Pointer 600ms suppression applies only to in-transcript clicks that resize content, never to take-latest or Jump. Peer overlay and pad are separate inputs; do not treat --peer-composer-h as --main-composer-height. resolveChatScrollTop keeps the whether-to-move decision; callers then assign latestScrollTop (the named clamped padding edge Jump already uses). Send while history.after is pending until latest loads; attached stays false on the stale page. The history loader never places latest; window anchor restoration remains in history-viewport helpers as specified below.

Rejected

A fourth stick file. Last-message + 16px as the follow target. Send as a second smooth animation. WS handlers calling a scroller. Global window / module stickToBottom. Persisting stickiness to disk. A virtual-list library. Auto-follow of every DAG expand. Rewriting the send/ack protocol. CLI ScrollBox in the web bundle. Turn-anchor-previous-reply-at-top as a parallel mode.

What “bottom” means

Latest is the padding edge of the scroller. latestScrollTop = max(0, scrollHeight - clientHeight) is the named form of the clamp Jump already uses and that assigning scrollTop = scrollHeight already produces when clientHeight > 0. Combined with pad max(25vh, overlay + 24) on main (peer pad is the published --peer-composer-h = overlay + 24), the last relevant content (user bubble, pending-reply indicator, streaming assistant, visible queued rows) sits in the visible band above the composer. Remaining slack is chatAtBottomSlack(pad, overlay) = max(0, pad - overlay) + 8. Overlay is the floating composer box, not the pad CSS variable.

Last-message + 16px is rejected because it measures against the scroller’s visible bottom, which is under the overlay, and because it ignores the pad that Jump already uses. Pinning to the padding edge without slack would hide Jump until the reader scrolled an extra ~25vh; that bug is already fixed in isChatAtBottom and is kept.

Send latch sequence

  1. sendChatMessage (or slash submit) calls appendLocalUserTurn when applicable, then noteTakeLatest({ sessionId, scrollerKey, turnSeed }). Default inside sendChatMessage: scrollerKey = background ? "peer:" + sessionId : sessionId. Interactive submit may pass scrollerKey explicitly. Do not read live activeChatKey at drain (that is the focused session, which may not be the draining session). Queue drain inherits because it already calls sendChatMessage with sessionId and background; send-queue.ts stays unchanged.
  2. The matching hook’s layout effect sees a note whose generation is newer than lastAppliedGeneration and whose scrollerKey equals this instance’s chatKey. Other panes do not latch. The note is not deleted on read (Strict Mode and two hook instances).
  3. If history.after is set, do not set attached, do not snap, keep Jump. Start the same async isCurrent await Jump uses. Layout effect must not await.
  4. When on the latest window (or after a successful latest load): set stuckRef = true regardless of the 600ms pointer window and regardless of current isChatAtBottom. Assign snapToLatest now.
  5. The next column ResizeObserver callback in this turn also snaps (late row height). That pin ignores 600ms because the take-latest generation is still current. Unrelated in-transcript growth still honors 600ms.
  6. Main shell only: subscribe to welcomeVisible or observe #welcome-mount children. When the overflow lock lifts, one retry snap if the same take-latest generation is still current. Peer sends use background: true and skip welcome.
  7. Ack that appends the assistant placeholder does not detach: attached is already latched, not derived from lastRole.

Gesture lifetime and cancellation

A note identifies a send, not permanent permission to scroll. Store notes independently by (sessionId, scrollerKey); peekTakeLatest(sessionId, scrollerKey) reads that pair. A main send and a peer send in the same session must not overwrite each other. Publishing a note must notify the matching view even when no transcript row changes (slash submit); reading a mutable map only during unrelated renders is insufficient. turnSeed identifies the accepted optimistic turn, not the current last row after ack.

  1. Each active follow operation captures session id, scroller key, generation, and a view interaction epoch. Every async completion, next-resize snap, welcome retry, and animation callback verifies all four before writing. A newer send replaces the older operation for that scroller. Jump replaces a pending send operation; send replaces Jump and stops its native animation before instant placement.
  2. Wheel, touch/pointer scroll intent, and scrolling keys in the transcript invalidate pending work before subsequent resize or network callbacks. They clear the forced next-resize/welcome retry. Geometry then determines attached after actual scrolling; clicking an execution control retains the existing temporary growth suppression. Programmatic scroll events alone are not cancellation. After send then user scroll-up, delayed growth never forces reattachment.
  3. Changing key or truly unmounting invalidates the outgoing operation. A recent return restores reading state; an expired return creates a new latest-placement operation without replaying a completed or cancelled send note. Keep note data readable; do not delete it on read. Maintain explicit operation completion/cancellation and per-view applied-generation bookkeeping. Strict Mode effect cleanup cancels that effect's resources; setup must resume a still-valid pending operation, without a second logical send, lost retry, or an orphaned request. Do not mark a generation completed when merely starting a latest request. Session delete and draft drop forget that session’s notes. Idle completed notes without an active viewport are capped; waiting send notes are kept. Releasing a viewport schedules that cap after the current turn so a same-tick remount can retain again.
  4. A first welcome send may publish before the transcript becomes visible. Preserve only that still-pending handoff until its matching view is ready; an initial subscription baseline must not discard it. Retry after visibility/layout readiness once, and cancel on a later user gesture or session departure. Existing provisional-to-real session binding must preserve the pending operation's identity without generating another send or replaying a completed one. Binding is the adopted session identity of that draft, not “any local_* key to any non-draft key”. Ack message-id replacement does not require turnSeed to remain the transcript's last id.
  5. While an older/around request is in flight, a send waits for a verified latest window even if the currently displayed page has no after yet. Use history.after || history.loading to enter asynchronous coordination, then verify the resulting latest page and operation identity. A cancelled/failed request leaves no forced retry and cannot hide Jump. A newer valid gesture may still succeed; an older completion must not detach or clear it.

One next-resize retry belongs to the operation, not to the entire assistant turn. After that retry, ordinary growth uses attached plus the normal interaction rules. Do not infer unlimited bypass from an unchanged generation. Each hook owns its resources and cleanup; no polling timer or persistent attached state is added.

Jump completion with changing content

On latest-load success, Jump starts smooth scrolling directly from the preserved position; no pre-animation snap is allowed. While Jump is active, resize records the changed target but does not instant-pin. At native settle, recompute latestScrollTop. If the target moved, stop the completed animation and perform one instant correction to the current padding edge, then verify placement. Hide Jump only after this verification and only if the same operation is still current. Reduced motion uses the same final verification with instant placement from the start.

The fallback timeout is a watchdog, not proof of arrival. At the timeout, a still-current operation stops native motion, corrects to the current target, verifies, and only then completes. Cancelling must stop browser motion as well as callbacks; removing a scrollend listener alone is not cancellation. No cancelled operation performs a correction. Subsequent growth resumes ordinary attached pinning. Accept a small geometry tolerance (2px); do not substitute the larger reattachment slack for exact Jump placement.

History restoration ownership

loadSessionHistoryWindow coordinates requests and publishes rows/window metadata. It never performs latest placement or examines send/jump notes. useChatAreaStick alone chooses and applies send snap or Jump smooth after a successful latest load. For older/newer/around replacement, existing history-viewport helpers own anchor restoration: capture a separate anchor, old top, and old height for each registered area before the update; restore after flushSync only when that area is still registered for the same session and captured chatKey. A previously registered area that lost registration is not restored. The unregistered #chatArea fallback applies only when nothing was registered at capture and the node is still the live main scroller. A still-connected node is not enough if it has been reused. Use each area's own chat key for height-cache maintenance. Do not reuse the first area's anchor or fallback delta.

History restoration is the explicitly retained scroll writer for window replacement, not another follow policy. It does not run a latest snap, and it must not overwrite an active, newer follow operation. Shared session data can replace rows in both main and peer panes; preserve each non-requesting pane's visible anchor when it remains available. If eviction removes that anchor, the bounded fallback keeps the reader's distance from the end that stayed; a negative result means the window no longer holds the rows the reader was on (an expired snapshot renewed it at the newest page), and the end of the new window is shown rather than the browser's clamp to 0, which read as the transcript jumping to the top. A newest page that no Jump or send asked for (a renewal, a retry) is handed to the stick hook as a take-latest note for each viewport that holds no follow lock; the loader still pins nothing. Scroller isolation does not promise independent history datasets.

Geometry-aware history prefetch

History prefetch estimates reading velocity only while the transcript content height is unchanged. A change in scrollHeight resets that estimate to zero before selecting a request; layout-driven scroll-position adjustment, including virtualized content shrinking at the latest edge, is not evidence that the reader moved toward older history. This conservative reset may reduce advance loading during reflow but retains the fixed edge threshold.

Calculate advance distance independently for each edge. The fixed minimum is max(1600px, 2 × viewport height); the total threshold is capped at 12000px. Only negative velocity extends the older threshold, and only positive velocity extends the newer threshold, using the existing latency estimate and factor of 1.5. Zero velocity retains the fixed minimum, so short content can still request available history without a gesture. If both edges qualify, preserve the existing direction selection.

Keep request serialization, cursor and generation validation, retry backoff, snapshot-renewal handling, hidden-view suppression, connection recovery and disposal unchanged. This policy selects when to request data; it never writes scrollTop, restores an anchor or creates a follow operation. Existing history-viewport helpers retain anchor ownership, and useChatAreaStick retains follow and latest placement.

Acceptance: test opposite-direction motion, virtualized height shrink at latest, both forward-looking thresholds and short-content fill through the real prefetch controller. The unchanged automatic-history browser test must prove no initial older request, scroll-triggered loading, an in-flight reader movement preserved within 3px after prepend, row recycling and no duplicate request. Run the existing history/follow browser cases with the browser marker explicitly enabled.

Trust boundaries, data flow, failures

  • Follow is a view concern. Transcript identity, attached, and the last user gesture are enough. Frame type is not a scroll signal.
  • sessionStorage key chatScrollByKey remains pixel positions only. Do not persist attached. Hardened contexts already swallow write failures.
  • data-self-update-verification continues to skip persistence.
  • Failed latest-window load, or !isCurrent: remain detached, keep Jump visible, do not snap to a stale page, do not leave attached true from a pending take-latest. Jump already returns if loadSessionHistoryWindow is false.
  • Take-latest during an in-flight Jump: cancel the smooth ride and snap (only once latest is on screen). Send wins on 0ms feedback when already on the latest window.
  • Reduced motion: Jump snaps. Send already snaps.
  • Virtualization: recycle keeps measured placeholders so scrollHeight stays honest. Pin after recycle. Do not add react-virtuoso / react-window / @tanstack/react-virtual.
  • Width changes: a new column width keeps the measured heights as estimates instead of dropping them, so a resize never re-renders the whole list. A row re-measures when it renders; one rendering above the viewport moves scrollTop by its estimate's error, since the scroller has no native anchoring. While the width is changing the chat area carries data-width-settling and off-screen rows use content-visibility: auto at their remembered size, so each frame re-wraps only visible rows; when the width holds still for 120 ms the attribute goes and the first visible row keeps its position (unless the view is at the bottom, which the pin keeps).
  • KaTeX: typesetMath on the observed message column stays a growth side effect inside the single pin path, not a second scroller and not a document-wide scan.
  • No backend protocol change.

Compatibility and exclusions

  • App and browser share this web contract.
  • CLI TUI ScrollBox is out of scope.
  • Do not auto-follow DAG strip expand, compaction fold easeScrollBy / pinWhile, parent-return scrollIntoView, message-rail seek, or branch-checkout pivot (_postCheckoutScrollTo). Those remain explicit locators.
  • Do not rewrite occupancy, send-queue admission, or ack pairing except for a take-latest note at the existing appendLocalUserTurn call (and slash submit).
  • Do not keep send as a special-case policy beside stream pinning. Send latches attached (or pending-latest) and chooses instant motion.
  • Peer Jump keeps the existing header button: same attach policy, no #chatView portal, no live bars, no composer-offset positioning in this slice.

Conversation switching and file summaries

Opening a conversation without a saved viewport places it at the latest message, including after asynchronous file-card growth. Recent returns restore reading state; expired or restarted views show latest. A saved pixel offset is not a latest-message anchor. First opening from an older history window requests the latest window through the existing cancellable follow operation. Manual wheel or keyboard scrolling cancels pending following; historical pagination keeps its anchor contract. Main and peer viewports retain separate keys.

Legacy file-change summaries are loaded only near the viewport, then retained in the existing session message store. Re-mounted cards render the successful summary immediately, including confirmed empty results. Errors remain retryable and aborted or stale responses never update another session. History preflight remains fresh and mutation authorization remains server-side; summaries are historical descriptions, not permission to undo.

Acceptance uses actual React components and the scroll hook: remount a legacy card with no second summary request; first open with delayed content growth and reach latest; return to an opened conversation and restore its position; cancel growth following on manual input; first open older history without a saved position and ignore stale completion. No backend protocol, message ordering, persisted history, or model behavior changes.

The hook follows latest for new, expired or previously attached viewports; recent detached views restore saved positions. Actual React regressions cover initial delayed growth, return restoration, manual cancellation, stale completion and summary retention. Review, full frontend gates and installed App evidence are recorded separately in the task report.

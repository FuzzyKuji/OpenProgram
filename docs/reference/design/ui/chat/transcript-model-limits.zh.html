会话记录的限制与约束

属于会话记录模型工程记录。目前已完成的内容：实现状态。

旧数据

已存内容不改写、不重放、不迁移。每种形状都是 legacy.py 中带测试夹具的具名情况。

  • 仅由 predecessor 或由两条边连接的 attach 行；锚定在 user 行上（sub_agent_step）；手动或跨会话（external_reference，仍是 AttachCard）。
  • 没有块（从 tool_calls 回填）、没有状态、错误存在 content 中、没有 id（由时间戳和角色生成的稳定 key 代替 hist_<i>）、extra 为对象或 JSON 字符串、readSpeaker、readNotice、粘贴元素、章节固定、gui_agent 名称的行。
  • 没有 tool_call_id 的 attach 行：把 attach.prompt 与 agent 或 task 工具输入匹配，然后按该回复中 agent 和 task 块的顺序。send_message 只有在有证据时才消耗卡片。仍未匹配的：blockId 为 null，画成未配对卡片。
  • 没有 tool_call_id 的代码节点：同样的规则，经 caller 边。
  • 没有 origin 的行上的回执：沿用现有的头部模式，且被点名的发送方会话必须存在于存储中，所以旧的已送达消息保持原样，而一行没有点名真实会话的手打文字仍是 user 行。
  • 旧插话行、重启提示和兜底块照现在的方式折叠；已在块中的插话不会重复。
  • 带 covers_ids 的摘要仍是压缩行，不再算作版本。
  • 通过 provider id 到达的旧工具行由 tool_output.py 的第二次匹配提供。
  • 被聚合折叠掉的 head（_resolve_head）和断裂的 predecessor 链（predecessor 遍历兜底，记录日志）。
  • 越过 attach 行或其他旁路行继续下去的分支，由曾经停在这种行上的版本箭头留下：走向某版本末端的遍历会穿过它。
  • 没有作业 id 的运行中 attach 行。

轮次分组在读取时计算，所以无需写入即可用于每个旧对话。保存的锚点保持有效，因为行 id 不变，且任何行 id 都能解析。新元数据（attach 上的 tool_call_id、origin、client_request_id）会被旧读取方忽略。

约束手段

类型。 schema.py 生成 wire-types.generated.ts，两者不一致时新鲜度测试失败。TranscriptChange 是带穷尽 never 检查的封闭联合。Row.rowKind 是联合类型，所以分发没有默认分支。存储写入函数不在公开的 store 类型上。

契约测试。 tests/unit/webui/test_transcript_contracts.py 和 apps/web/tests/chat/transcript/transcript-contract.test.mjs。没有任何扫描带允许列表。扫描只读源码，从不读构建产物（openprogram/interfaces/server/_frontend/、docs/_site/）。

  • 只有 apply-transcript-update.ts 写行。
  • 客户端代码不构建 _reply，也不从一个 id 推导另一个 id。
  • openprogram 或 apps 中没有 session_reload 字符串。
  • apps/web 中没有代码读取 display、function 或 content 来决定行的类型。
  • 会话记录包之外没有文件折叠 attach、插话或重启行。一个具名例外：restart-continuation.ts 中的 joinedReply，它拼接的正是 row.continues 指明的行，且都属于自己的轮次。
  • components/chat/messages 中没有基于移位的配对。
  • status.py 和 row-status.ts 之外没有会话记录行状态字面量列表。扫描覆盖 interfaces/server/transcript/、ws_actions/session/、apps/web/components/chat/、apps/web/lib/chat/、apps/web/lib/session-store/ 和 apps/web/lib/runtime-bridge/session/。执行生命周期列表是另一套词表，不在范围内：use-ws.ts、event_effects.py、execution/dag.py。
  • legacy.py 是唯一读取旧记录形状的模块。两个具名例外：tool_output.py 的第二次匹配，按 provider id 提供旧工具行（旧数据）；stripLegacySpeakerLabel，从显示文本中去掉旧频道标签，不决定行类型（仍然存在的限制）。
  • runtime 或 state 中没有来自 interfaces/server 的导入。tests/contracts/repository/test_runtime_layering.py 不扫描这个方向，所以由会话记录契约扫描。
  • 观察者不做投影或 I/O。

行为测试。

  • 页边界扫描：每种切分都等于不分页的读取。
  • 实时等于冷读，经生产 reducer 和组件，覆盖流式、部分历史、页边界、完成、迟到的树更新、错误、取消、重新加载、重连和全新对话。
  • 帧来自真实的服务端发送路径，绝不手写，也绝不注入 id。
  • 重复交付不改变任何内容。
  • 交错属性测试：写入、外部写入、读取、页读取、视图淘汰、丢帧和重连的任何顺序，最终都等于一次全新读取。
  • 真实发布器上交错的文本、工具、文本和插话保持已存块顺序。
  • 未知行和未知条目不创建任何内容。
  • 后台更新下读取器的窗口不变。
  • 终态状态表。
  • 标志清除后没有写入的 Stop 仍能落定该行。
  • 展开时发给运行中代理的第二条消息能到达该视图。
  • 四个缓存对话：第五个在服务端关闭一个视图。
  • 300,000 节点真实服务端基准：首次打开、页读取、被淘汰的会话、外部写入重建、每视图内存。

流程。 每一步在自己的 worktree 中构建，rebase 后合入一次。提交只带自己的路径。只跑受影响的测试和这些契约测试。每次读取或实时切换都曾用比较工具在 dev 实例的真实形状上核对，不匹配项在切换落地前清除。

方面仍然存在的部分

接受的行为

情况接受的结果
占位写入失败不显示实时文本；轮次结束时终态行出现。
最后的文本帧丢失由终态行修复，不运行读取。
两个同类型块之间的空 provider 块段编号可能在最终写入时移动；只有一个打开的步骤关闭。
安静路径上断电进行中回复的末尾可能丢失。
cron 子进程的写入在下一次读取该会话时出现。
对话正在一个 socket 上被读取它的文本在该 socket 上保持，直到读取结束。
页在视图锁下投影该会话的非文本更新等待。
折叠的子代理行显示运行状态，没有文本预览。

已测量但未消除的风险

  • 长时间的自主轮次不可分割，可能有许多兆字节。工具正文保持 32 KiB 内联上限。步骤 0 和 5 测量它，步骤 5 在切换前证明没有退化。
  • 300,000 节点时归属表的内存是每视图几十 MB，靠共享字符串和 LRU。在步骤 0 测量。
  • 黄金夹具覆盖具名的旧形状，比较工具当时只覆盖 dev profile，所以只存在于 stable 数据中的形状可能之后才暴露。未知形状画成普通行。
  • 偏移在 Python 和 JS 之间用 UTF-16 单位。计算错误会变成一次修复读取，而不是损坏；代理对夹具覆盖这一点。
  • 在其他会话持续提交的情况下，在最高流量的聊天文件中工作约六到七周。

未采用的方案

为本设计考察过的提议，以及每项未被采纳的原因
提议未被采纳的原因
为同步作业启用进度预览_poll_progress 原先在仓库中没有调用方，所以没有作业有预览；同步卡片获得作业 id 和实时视图，无用的轮询器已删除。
对同步作业避开 _update_attach_card 的 notices.queue 路径job.wait 为 true 时 notices.queue 已返回 False，同步作业的 wait=True。
job_progress 是步骤 7 交付的原因它唯一的发送者原先在未被调用的轮询器内；实际的作业原因是 job_attach。
在文本帧上放 turn_id运行时 tap 无法知道起始行（重启和插话行加入别的行的轮次），所以文本未命中时丢弃且不读取，由带编号的流找到缺失的行。
暂存该会话的每一帧运行级帧（running_task、execution.updated）按 run_seq 排序，现在就跟在读取之后，所以只暂存写行帧。旧 reducer 运行期间终态 chat_response 会写行，只在这段时间暂存。
让 client_request_id 穿过 TurnRequestWeb 聊天动作自己写 user 节点（_build_user_msg，带 user_already_persisted=True），所以运行时在 prep.py:130 的 user 写入对它不运行，这个 id 不需要进入运行时。
把聊天动作的加入和 first_read 移到步骤 7first_read 按 clientRequestId 替换待发送的行，而本地行从步骤 8 起才带它，所以步骤 7 为无视图的 socket 保留 attach 重新加载。
把 settleDeliveredSteer 留在 handleUserMessage 中落定由插话行的 clientRequestId 触发，这也覆盖没有帧的读取。
Stop 时从令牌退役处唤醒发布器终态行绝不被扣留，所以没有东西在等标志清除。
HTTP 路由取整条分支CommandReply 拒绝超过 4 MiB，所以该路由保持有界，而 CLI、worker_turn 和 rehearsal 取整条分支。
checkout 使用 is_checkout_target/api/chat/checkout 已经应用它（chat_branches.py:595）；attach 行符合该规则，所以 F23 靠箭头不再指向它们来关闭。
linear_history 兜底让 F42 仍未关闭断裂的旧链仍必须显示，而这个遍历喂给同一投影，形状不会不同；session_persistence.py:108 和 routes/chat.py:81 只填服务端镜像，版本 3 的会话记录从不读取它。
基于一个客户端会话记录折叠构建它保留客户端合并决策，正是本设计要消除的缺陷类别；它提供的交付顺序由服务端优先的步骤满足。

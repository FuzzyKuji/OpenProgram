远程 Web 访问

每个 HTTP、SSE 和 WebSocket 请求都要带本次启动的实例令牌，回环地址也不例外。令牌有效即当前 profile 的唯一所有者。没有中继，没有账号。

不变量

  • 认证之前：受保护状态、会话数据、文件字节、密钥元数据、SSE 事件、WebSocket 帧都不外发，也不执行任何动作。
  • 缺少 Origin 绝不建立信任。只在 Bearer 认证通过后，或安全方法的 cookie 请求上允许。
  • 令牌是 Host 和 Origin 校验的补充；cookie 保留 CSRF 控制。
  • origin 配置不完整的非回环监听，在开始监听前就失败。
  • 没有路由返回已存密钥；首次进入之后也没有路由返回令牌。

令牌与凭据

方面规则
取值secrets.token_bytes(32)，外部形式是 43 个字符的无填充 base64url；每次 Web 进程启动都换新
单进程独占且仅所有者可用的锁 <state-dir>/web.lock；第二个进程失败，不碰第一个进程的令牌
文件web/token 在监听就绪前原子写入；web/access.json 只含 version、bind_host、port、effective_origins、token_fingerprint；两者都仅所有者可读，并经 restrict_to_user() 加固
绝不来自配置、命令行参数、环境变量
绝不出现在服务器日志、异常信息、访问日志、遥测、Web 响应。日志只写 sha256:<sha256(原始字节) 前 12 位十六进制>
比较解码为恰好 32 字节，再用 hmac.compare_digest
启动失败与清理
  • 写入沿用 openprogram/extensions/mcp/token_storage.py 的临时文件、os.replace 和权限做法。
  • 拿不到锁，或无法安全创建并读回令牌文件，启动失败。
  • read_active_web_access() 只在快照有效且指纹与实时令牌文件一致时返回 ActiveWebAccess。
  • 绑定失败或关闭时，进程只在持锁且文件里是自己的令牌时删除令牌，只在指纹是自己的时删除 access.json。
  • 未加锁的陈旧文件由下一个进程原子替换。

浏览器登录

fragment 不会出现在 HTTP 请求、代理日志、Referer 或路由中。apps/web/lib/net/auth/owner-auth-bootstrap.ts 在交换完成后才挂载应用，且不用 Web Storage。

POST /api/auth/bootstrap 约定
  • 只接受 POST，需要有效的精确 Origin 和有效 Host。
  • Content-Type: application/json，请求体不超过 256 字节，恰好是 {"token":"<43 字符 base64url>"}。未知键、重复键、非法 base64url、其他长度都拒绝。
  • 带任何 Authorization 头、缺令牌、令牌错误：同一个 401。
  • 成功：204 加 cookie。始终 Cache-Control: no-store；响应里绝无令牌。

给其他设备的登录链接

openprogram web auth-url --base-url https://agent.example.com
  1. 核对 worker 的 PID 和端口文件、access.json 与监听进程：向 GET /api/auth/challenge 发新鲜 nonce，在本地校验 HMAC 证明。令牌绝不发往被探测的端口。
  2. 读取实时令牌文件，把一条 fragment URL 打印到终端，绝不写入应用日志。

--base-url 必须是 access.json 中冻结的有效 origin，不含路径、查询、fragment 或用户信息。HTTP 只放行回环监听上的 localhost，或明文 HTTP 列出的网段内的 IP。

同一个 ASGI 中间件 OwnerAuthMiddleware 在路由分发前处理 HTTP 和 WebSocket。应用路由不自行解释认证。

各请求形式的 Origin

请求凭据Origin

Bearer 的放宽是因为 Node TUI 用 IP 连回环，却出示规范 origin。安全方法是 GET、HEAD、OPTIONS，不改变状态。Sec-Fetch-Site: cross-site 一律拒绝。CORS 头只控制响应能否被读取，不是认证。

origin 如何计算
  • web.host 和 web.allowed_origins 来自当前 profile 的 <state-dir>/config.json。web.host 默认 127.0.0.1，只有局域网或 VPN 直连才需要。
  • 条目只能是 scheme://host[:port]，http 或 https。无效：通配符、路径、查询、fragment、用户信息、不透明 origin、非法 IPv6、未指定和组播地址（所以 0.0.0.0、:: 都不行）。
  • DNS 名做 IDNA 和大小写规范化，IPv6 加方括号，默认端口去掉。
  • effective_origins = 配置的 origin，回环监听再加 http://localhost:<port> 和实际绑定的字面量。非回环监听没有隐式 origin。请求的 Host 永远不会加入集合。
  • Host 必须是一个合法 authority：重复、逗号拼接、带用户信息、未指定和组播形式都拒绝。
  • request_origin = scheme + 解析后的 Host，ws 视同 http，wss 视同 https。这一次比较同时覆盖精确 origin 和 DNS 重绑定。

验收行为
  1. 回环上无凭据的 HTTP、SSE、WebSocket 都失败。
  2. 正确的 Bearer 不带 Origin 也成功；错误的得到同样的 401，不执行任何动作。
  3. 引导在其他 fetch 前清除 fragment，只接受受限 JSON，URL、查询、Referer 中没有令牌，派生指定 cookie，拒绝同时带 Authorization 的请求体令牌，之后能打开 HTTP、SSE、WebSocket。
  4. cookie 的不安全 HTTP 和 WebSocket 在动作或 accept 前拒绝缺失、不透明、跨站和未列出的 origin。
  5. 回环、直连和代理都拒绝外来、重复、逗号拼接、未指定和组播 Host；HTTP/WS 与 HTTPS/WSS 得到相同的 origin 配对。
  6. 默认回环只接受隐式 origin；其他 SSH 本地端口在配置前被拒绝。
  7. 无有效 origin 的非回环监听拒绝启动；列出的 HTTP 网段放行并告警；未指定、组播、文档、基准测试、保留和全局地址的 HTTP 被拒绝。
  8. Uvicorn 代理改写关闭；转发 scheme 只认原始回环对端；伪造的 X-Forwarded-For 不改变信任；公网无 HTTPS 的引导失败；直连 WS 和 Caddy WSS 得到预期 origin。
  9. 同一状态目录的第二个进程改不了实时令牌或快照；绑定失败只删除失败进程自己的文件。
  10. 重启轮换令牌，旧 Bearer 和 cookie 失效。
  11. 格式错误的 Authorization 不回退到 cookie。
  12. 静态资源和 /healthz 不含令牌、会话、文件系统、凭据数据或诊断。
  13. 响应头拒绝嵌入；受保护响应 no-store；401 声明 Bearer realm。
  14. 文档无需认证即可从源码检出和安装包的预构建文件读取，不扫描不构建；Host 校验仍生效；不安全方法和私有 API 除外。
  15. 查看明文返回 410 和 404；替换、保留、删除遵循精确模式；8–11 字符用固定掩码；掩码永不被接受；前端类型没有查看或完整密钥字段。
  16. nginx 和 Caddy 经 HTTPS 承载已认证的 HTTP、SSE、WebSocket，后端留在回环。
  17. 渠道消息保持 paired，不获得所有者权限。
  18. 同一主机名、不同端口的两个 profile 服务器 cookie 不同，各自认证。
  19. 所有权探测检查 PID、端口和快照，只发新鲜 nonce，校验带版本的证明，可选绑定 revision，禁用环境 HTTP 代理，绝不发送或记录令牌。外来监听者以及快照、端口、证明、revision 陈旧或不符的，都不算所有者服务器。

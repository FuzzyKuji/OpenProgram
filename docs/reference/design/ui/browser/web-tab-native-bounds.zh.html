内置浏览器的原生页面边界

Electron 外壳的 DOM 和每个原生 WebContentsView 在任意外壳缩放下保持相同的页面边界。setBounds 用 DIP，渲染进程量的是 CSS px。

单位换算

部分行为
渲染进程发送 getBoundingClientRect() 量得的带小数 CSS px
IPC 边界主进程每次调用都读 event.sender.getZoomFactor()，换算成 DIP，再取整并保证尺寸非负。无效或非正的缩放按 1 处理。
入口webtab:sync-visible 和兼容入口 webtab:set-bounds 同样换算。内部的显示、隐藏、转移路径本来就用 DIP，不再缩放。
缩放变化渲染进程的 resize 监听重新测量并发送当前边界
例子，缩放约 1.095x=812.63, width=518.64 CSS px 变为约 x=890, width=568 DIP。不换算时，网页盖住聊天窗格，右侧留白。
不动用户缩放、分屏比例、DOM 布局、preload API、站点缩放、Browser Agent、依赖、配置

浮层

DOM 浮层的可见矩形与网页 body 相交时才隐藏该原生网页。每个 WebTabPane 用自己的 body 对比当前浮层，没有全局可见标记。

浮层识别方式原生网页
Popover、下拉、listbox、标签和分屏菜单role=dialog/menu/listbox只隐藏相交的窗格。聊天窗格内的工作目录、项目、权限菜单不影响相邻网页。
全屏模态、确认背板、附件预览data-native-view-occluder=true 或合并背板隐藏所有被盖住的窗格
Tooltip、toast、拖拽提示、普通 portal 内容不在选择器内保持可见
桌面主菜单、右键、书签原生菜单主进程单独的浮层持有者走原生菜单生命周期，不经渲染进程 DOM

零面积或仅边缘接触不隐藏。MutationObserver、ResizeObserver 和滚动、缩放监听在浮层关闭、移动或改变大小后重新发布边界；全局 flush 在同一 tick 内合并微任务。

悬浮预览

Agent 的画中画预览走同一条 registerVisibleWebTabBounds / syncVisible 路径，只发布小窗 body，工具栏按钮和右下角缩放把手留在原生视图之外。预览有两层：下面是静态画面，上面是实时原生网页。没有 hold 时才显示网页（PipHoldReason，apps/web/components/center-tabs/pip/web-tab-pip-surface.tsx）。

Hold何时
gesture拖动或缩放
clip滚动的停靠栏遮住一部分
cover菜单、对话框或 popover 与它重叠；网页立即落到最后一张画面之下
motion折叠进或展开出输入框的网页标签
时序与布局
方面行为
第一个 hold截一帧并显示。截图超过 150 ms（PIP_PICTURE_WAIT_MS）时先显示缓存的上一张，到了再替换。无论哪种情况，原生边界都在这 150 ms 内撤走。
最后一个释放发布最终边界；网页在那里绘制后画面才消失
布局setPipZoom 让网页按 1920 宽、高度随预览形状排版，缩放后铺满预览
首次显示或尺寸变化先在不可见处按该尺寸排版，等一次绘制，再等 250 ms（PIP_RELAYOUT_MS）和一次绘制，照顾靠脚本排版的页面。不会先露出标准尺寸或半成品布局。
折叠时保持该布局，展开时原样回来。显示该网页的窗格把缩放恢复为用户值。
画面按标签缓存，下次展开从它开始
动画从标签或 ✕ 关闭时折叠 240 ms，再显示时展开 280 ms（apps/web/lib/browser/web-tab/web-tab-pip-motion.ts）。减少动态效果时直接出现和消失。
后台网页不受影响：原生视图一直存活，只是不给边界

残留：分屏网页跑在框架前面

原生网页和 App 的 DOM 是两个合成器客户端，窗格移动时分屏网页可能偏离框架。悬浮预览用 hold 遮住了这一点，分屏窗格没有 hold。

实测
开发版 App，负载 4.6 到 6.2 下 24 次分屏侧栏移动：979 次绘制中 112 次偏离，最多 13 px
为什么逐帧上报修不了

渲染进程在排版一帧时测量，并在微任务里发送边界；主进程立刻移动视图，其帧约 1 ms 后到达显示合成器。App 自己的帧还要走完主帧、提交和光栅化。

只有 App 的帧赶上截止时间时两者才同帧：120 Hz 下好的轮次毫无余量，坏的轮次晚 0.3 到 0.7 ms。

一次移动的每帧开销相近，所以一旦晚一帧，整次移动网页都在前面（16 到 18 次绘制，最多 14 px）；负载 4 到 8 时，每十二次到每四次移动发生一次。

尝试为何不行
渲染进程无法预知自己的帧会晚
主进程按自己的节奏播放移动同样赶不上晚到的 DOM 帧
beginFrameSubscription在绘制之后才到，网页每次都落后一帧

只有一个合成帧嵌入另一个时，显示合成器才让各表面同步，<webview> guest 和跨进程 iframe 就是这样绘制的。

为什么网页不作为 App 帧的 guest

<webview> guest 随 DOM 移动、裁剪、折叠，不需要边界。在开发版 App 和 Electron 45 上，负载 6 到 12 下 48 次分屏面板移动没有一次绘制偏离框架，移动帧也略省（中位数 3.2 到 3.4 ms，对比 3.7 到 3.9）。决定因素是 Agent 的输入：

Agent 输入Guest原生视图
CDP 发送的文字和按键进入 App 窗口的焦点帧，也就是输入框，Enter 可能发出用户的消息到达网页，不碰 App 焦点
webContents.insertText到达焦点元素，不碰 App 焦点不需要
sendInputEvent 按键widget 获得过一次焦点后才到达；没有编辑命令，Command+A 无效快捷键命令可经 CDP 执行
点击每次都把 App 的键盘焦点移进 guest。交还焦点要走渲染线程；线程忙 150 ms 时，用户紧接着的按键落进了网页。不碰 App 焦点

用户在输入框打字时，Agent 的网页正显示在悬浮预览里，所以 guest 在那里同样不安全。网页在原生和 guest 之间切换还要重新加载：历史、滚动位置和表单值可恢复（navigationHistory.restore），脚本状态、连接、sessionStorage 和表单外的编辑器不能。

输入框与用户决策输出

输入框编辑普通消息和用户打开的函数表单。待处理的决策是输入框上方独立的会话面板，回执显示在对话里。待处理决策不会替换输入框、清空草稿、关闭函数表单、改变发送动作或抢走焦点。

输入框输入

情况行为
模式idle、fn-form
函数表单选择已注册函数打开 FunctionForm。字段、校验、过渡、关闭和发出动画都留在其中。
name(parameter=literal, ...)完整的已注册表达式与表单共用派发器和 schema 校验。说明文字、不完整表达式和代码块仍是聊天文本。
运行中Enter 和发送把消息加入当前轮次（steer）。Cmd/Ctrl+Enter 排到下一轮。空输入保留停止。

名称负责

新问题不自动聚焦。多个问题按稳定顺序独立作答。布局见输入框交互布局。

送达

状态卡片显示
提交中立即显示实际答案和发送中状态
匹配的已应用命令已送达。唯一的确认；事件到达本身不是回执。
结果未知保留原命令 id 和载荷用于重试，显示可用的错误码，不暗示成功
明确拒绝先核对当前请求，再允许作答
已关闭的请求不显示为已接受的答案
已确认的答案或拒绝作为会话 UI 回执保留

提交后的回执保留问答布局，用字段标题，显示可读的值而不是 JSON。表单提交字段对象。审批卡保留可用范围、操作详情和明确的允许或拒绝；提问不授权任何操作。

回执是内存中的展示状态，不是 Workflow 检查点：刷新后重新加载规范的待处理问题。切换标签时，请求仍绑定原 session、execution、generation 和 version。后端 Workflow 问题在原进程继续，预声明的 Agent 等待保持其续接约定。

讨论与事件

讨论操作有自己的反馈输入，把文字作为 reason 放在确切的规范 decline 命令上。模型在同一轮收到，不排队聊天消息。只有匹配的已应用回执才算送达；未确认的拒绝绝不授权执行。普通输入框消息既不拒绝问题，也不作为答案。

验收

输入框有内容时出现待处理问题：问题在输入框外，草稿和焦点保留，发送仍是普通消息。点卡片提交：立即反馈、匹配确认、保留回执、草稿不变、会话隔离、重试身份不变、原生 App 行为正常。

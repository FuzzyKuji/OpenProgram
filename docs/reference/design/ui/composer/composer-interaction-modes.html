Composer and user decision output

The composer edits ordinary messages and user-opened function forms. Pending decisions are separate session panels above it, and receipts appear in the conversation. A pending decision never replaces the composer, clears its draft, closes its function form, changes its send action or takes its focus.

Submitted receipts keep the question-and-answer layout, use field titles and show readable values, not JSON. Forms submit field objects. Approval cards keep their scopes, operation details and explicit allow or deny; asking a question does not authorize an operation.

Receipts are in-memory presentation state, not Workflow checkpoints: a refresh reloads canonical pending questions. Requests stay bound to their session, execution, generation and version across tabs. Backend Workflow questions continue in the original process, and predeclared Agent waits keep their continuation contract.

Discussion and events

A discussion action keeps its own feedback input and sends the text as the reason on the exact canonical decline command. The model receives it in the same turn and no chat message is queued. Only a matching applied receipt confirms delivery; an unconfirmed decline never authorizes execution. An ordinary composer message neither declines a question nor answers it.

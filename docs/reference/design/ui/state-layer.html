Scope and global stay in step

DirectionHow
Scope to globalA setter updates its instance first, so the pane repaints on the same tick, then writes through to the global keyed setter. Hooks come from installScopeWriteThrough at the global store's init, keeping the import one-directional.
Global to scopesetComposerInputFor, setComposerSettings, setRunningTaskFor call pushToSessionStore, so a WS frame, legacy bridge or tab transfer reaches the live instance.
SeedingAn instance seeds from the global maps on first render, so a remount after reload shows the persisted draft.

No mirrors: the global store has no composerInput, composerSettings, runningTask or contextPanelFor. The focused draft is composerDrafts[activeChatKey], computed where needed. Anything that must outlive the tab (localStorage, tab-transfer wire format, cross-session sidebar views) stays in the global keyed maps.

Why instances rather than a keyed global slice
ApproachExampleTrade-off
Store per instance (chosen)VS Code editor groups; Zustand supports itStrongest isolation. Shared data needs a separate layer.
One global store, keyed, with a scope tagRedux normalization, TanStack Query, Slack-style multi-channel UIsEasy debugging and cross-session features, but discipline by convention: one read of the global pointer regresses it.
Physical isolationChrome renderer processesJustified by running untrusted code; process memory and IPC cost for no gain in an app's own split view.

With a keyed slice every read and write supplies the key; a wrong one, or an omitted one meaning the focused session, stays type-correct. With an instance the provider supplies the key once. A keystroke also notifies only that session's subscribers. Parallel Record<sid, T> maps stay, with transcript rows keyed by view: instances persist through them.

The failure a global singleton produces

A component rendered twice reads state that exists once. Both copies show the same value or the last write wins. The type system allows it, and it shows only in split view after a specific interaction.

/context badge: a global boolean opens both popovers. A contextPanelFor: sid pointer fixes that, but each consumer must still compare the right id. In the scope it is a plain contextPanelOpen.

A mirror, a global copy of the focused session's keyed entry, is worse: every write updates both, every switch swaps it, components branch on whether they are bound, and the window-to-window transfer has to rebuild it.

Legacy runtime state

runtimeState (lib/runtime-bridge/state.ts) is a module-level singleton predating the React store. WebSocket frames reach the runtime bridge, which updates it and writes through to the store; conv-store-mirror.ts keeps store.conversations authoritative. It is transitional.

FieldMeaning
currentSessionIdThe legacy active session. Frames gated on session_id === runtimeState.currentSessionId in chat-handlers.ts and conversations.ts are dropped or misrouted for a non-focused session.
conversationsHeavy per-session map with full messages, distinct from the store's summaries
isRunningOne global flag

It is still the default for message rendering outside split view, session switching, branch badge refresh and most frame routing. The split pane bypasses it: #chatView is a singleton addressed by hardcoded ids in about ten bridge modules, so AppShell hides it while split, each pane renders React off the store and sends its own load_session.

What removing it requires
  1. Every currentSessionId gate in chat-handlers.ts and conversations.ts is a store write keyed on data.session_id, so background frames land. Needs the focus pointers first.
  2. runtimeState.conversations has no readers the keyed maps do not cover, making conv-store-mirror.ts unnecessary.
  3. isRunning has no readers; runningTasks covers it.
  4. The #chatView shell is gone, replaced by the React path PeerSessionPane proves. The heaviest condition.

A wrong gate removal silently drops frames, so each pairs with a check that the frame still reaches its session.

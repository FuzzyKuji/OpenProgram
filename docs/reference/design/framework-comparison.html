Strongest: evidence
  • No second implementation among the twelve was confirmed to record the function call tree in conversation history.
  • Model tool results and successfully persisted Agent method calls (session DAG recording on, expose not hidden) are code nodes. They share caller and predecessor edges with user and llm nodes, in the session's append-only log. Multiple heads reference different history branches.
  • OpenClaw Control UI has fork, rewind and branch; pi-mono JSONL carries parentId and /tree switches branches. OpenProgram adds one DAG across user, llm and code nodes, where code nodes hold both tool results and nested calls.
  • Transcript branches and worktrees are independent. Agent branches share the working directory; only jobs bound to worktree_id isolate file changes.

OpenProgram

A general-purpose Python agent harness for one local user: the openprogram command and a persistent worker on port 18100.

Surfaces
TUI (Ink and React), Web (Next.js), Electron desktop, four channels: Telegram, Discord, Slack, WeChat
Turn processing
Surfaces share ChatAgent().run_turn; the Python library enters through Agent or Runtime straight into agent_loop. Context assembly L0, L1, L2; compact when over budget; tool.before gate can deny; finalize writes ContextCommit output and Git commits
Threads
Web and TUI: daemon thread per turn. JobRunner: bounded pool. Dispatcher: asyncio loop per turn. Scheduler: threads and processes
Session storage
One append-only log per session is the source of truth, three roles (user, llm, code), caller and predecessor edges, branch heads. context/commits/ holds per-turn context records
Other storage
usage.db: SQLite usage ledger. Memory: Markdown with rebuildable in-memory BM25 and embedding indexes, background writes, three memory_* tools
Tools
Dynamic registry in four domains (todo, task, agent, message); deferred catalog plus tool_search
Extensions
MCP client and server, ACP, skills, plugins, 34 events, agent.json; bundled, dynamic and custom providers
Authentication
Web and WebSocket: owner_auth with a per-start token and profile-specific cookie. Channels: pairing and allowlists (interfaces/channels/_access.py), a separate source-identity boundary. Not multitenant

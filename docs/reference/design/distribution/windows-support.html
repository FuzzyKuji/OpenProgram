Engineering rules

  • Platform behaviour lives in openprogram/host/_platform/ (filesystem, locking, processes, process ownership, command shell, terminal, environment) or an adapter it selects.
  • Prefer capability detection. Unsupported features fail at their entry point, not with a late NotImplementedError.
  • A weaker replacement for a POSIX safety property is an explicit, documented decision.
  • A fix is incomplete until a Windows CI contract covers it.
  • POSIX 0600, 0700 are not Windows requirements: the profile's inherited ACL stays, and no step removes inheritance or rewrites entries. Atomic replace and process-safe locks are still required.

Self-update and CI

Journal reads are portable, but the in-conversation controller exists only on macOS. Native candidate tests and activation remain unimplemented.

W2: release installer

A native runner builds OpenProgram-<version>-runtime-windows-x86_64.zip with its SHA-256 file; arm64 is built when OPENPROGRAM_RELEASE_WINDOWS_ARM64 is on. One runtime/ root. tui.ink is recorded only after an Ink startup probe succeeds.

  1. install.ps1 (or install.cmd, which fetches it) resolves a stable release, stops and names the platform when the release manifest has no package for it, and hands off to the installer from that immutable tag. On Windows 11 on Arm a release without an Arm package installs the x64 one, which runs under emulation, and says so.
  2. For that fallback, check that the tagged installer can pick the x64 package; refuse the release by name otherwise, before any download.
  3. Check free space, download with resume, validate the checksum and every ZIP entry; reject links and reparse points.
  4. Verify capabilities and cold-start a worker in isolated staging state, under an exclusive per-runtime lock.
  5. Move the verified candidate into its version directory.
  6. Atomically replace the .cmd launcher, keeping openprogram.previous.cmd.

Managed upgrades select the Windows ZIP and tagged PowerShell installer through the compatibility seam. A failure while piped into iex sets the exit code and throws, so the window stays open.

Activation and extraction details
  • Versions stay in directories and the previous launcher is retained. Cached versions are revalidated.
  • The launcher is prepared and snapshotted first. A failed replacement restores it; a failed restore keeps the original at a reported path.
  • ZIP names are validated before writing; files stream through extended-length paths, checking expanded bytes and lengths. Inspection and cleanup use the same APIs. The long-path registry value is untouched.
  • PowerShell passes NullString for the .NET replace, because PowerShell 5 otherwise binds $null as an invalid empty path.
  • Build helpers restore workspace, toolchain, download and browser-cache environment, including on failure.
  • doctor reports long-path and Defender state as read-only advice.

Local refresh publication

windows-refresh-transaction.ps1 publishes ordered, already-verified sibling source and destination pairs for the App, CLI runtime and launchers. Loading it has no side effects.

Transaction contract
  • Paths must not overlap; drive-relative paths and redirected ancestors are rejected. Extended paths, no ACL or machine changes.
  • One exclusive OS lock in the first destination's parent. Payload inspection happens under it.
  • Four callbacks: quiesce old, verify published, quiesce failed, restore old service. Each must return exactly Boolean true.
  • A flushed JSON journal records every source, destination and backup. Publish in order, compensate in reverse.
  • Success keeps originals and a receipt; no runtime tree is deleted. A failed shutdown or rollback keeps the journal and refuses later attempts.
  • Compensating, not crash-atomic: recovery must inspect recorded paths, not trust the last flags.
  • Still to build: freeze the checkout, one wheel for App and CLI, verify before stopping the worker, validate on the default profile and port, coordinate with CLI and Desktop install locks.

W4: command sandbox

The seam finds a real WSL2 distribution, verifies Bash and bubblewrap, probes a namespace, and translates paths with wslpath. Bubblewrap gives the Linux boundaries: read-only root, writable workspace roots, deny paths, PID/IPC/UTS namespaces, private temp, and a network namespace unless policy allows network.

sandbox.modeBehaviour
off (default)Sandboxed only in a conversation with Sandbox on
autoEvery conversation, once the probe succeeds; otherwise native and unsandboxed
workspace-writeReports the missing WSL2 or bubblewrap at the entry point; refuses the command only with sandbox.unavailable_policy=refuse, otherwise runs it in the host shell

No probe changes ACLs, ownership, modes, Defender or WSL settings. AppContainer needs per-application capability and ACL work. Job Objects give CPU and process limits but no filesystem or network boundary.

Without WSL2 the Sandbox switch is disabled and its hint says Sandbox unavailable: needs WSL2, what is missing and wsl --install; doctor says the same. sandbox.unavailable_policy defaults to warn on Windows and refuse elsewhere, so commands run in the host shell instead of all failing.

Why this design

Claude Code (srt-win with a WFP sublayer) and Codex (windows-sandbox-rs, RestrictedToken and Elevated) sandbox natively; MiniMax Code vendors srt-win. A native sandbox is a Rust or C subsystem of ACLs, tokens and filters, so WSL2 stays for now and a native one follows Codex's RestrictedToken level later.

Most Windows machines have no WSL2, and a refuse default made the switch mean "every command fails". The reason sits on the switch, the one control it concerns.

The background worker in the tray

The Assistant and the Butler keep the worker running after every window closes, so the App shows it in the menu bar (macOS) or the notification area (Windows, Linux), with the system's own menu:

  • A status line from the health probe, refreshed every 10 seconds.
  • Open OpenProgram.
  • Stop background: stops the worker as switching versions does, then quits, since the App's windows would start it again.

Closing a window and Quit do what they did and ask nothing. The icon is a single-colour App icon, apps/desktop/main/worker/tray/trayTemplate.png; without that file no tray is created.

Why this design

Claude Code and Codex have no resident process, and OpenCode's server follows its CLI. Alma, a resident desktop assistant, stays in the menu bar or tray, as OpenProgram's always-on agents need to. Asking at every quit would add a prompt to an everyday action. A native menu is not a new panel; its one hint sits on the Stop item.

Uninstalling and the version store

<state>\runtime\users.json lists the installs using the version store (versions/users.py): {install_id, kind: app|cli, path}. Every worker start adds its install, so an older install registers on its first start.

The App's installer adds itself only to a store that already holds a version: a first launch unpacks the seed into an empty <state>\runtime and refuses a folder with anything else in it. Writers take a lock and publish with replace_file.

An uninstall takes its entry off the list; when none is left, it asks whether to delete the downloaded runtime versions too, naming their size; the default answer is No and a silent uninstall keeps them. Conversations, settings and credentials are never deleted.

Why this design
ComparedOn uninstall
Claude CodeKeeps versions apart from user data and leaves the data
CodexIts script removes only its binary

Offering deletion only to the last user is ours: the CLI, the App and a dev profile can share one store. Its gigabytes can be downloaded again, so deletion may be offered; it is destructive, so it defaults to No.

Release decisions

TopicDecision
A failed Windows packageOnly that package is missing from the release, and Check every planned package names it, as for macOS and Linux. Codex releases all or nothing on "built and signed"; one platform's failure here does not hold back another's fix

SigningAzure Trusted Signing, as Codex signs: no hardware certificate to keep, a monthly fee, and SmartScreen stops blocking the first install
Windows on ArmThe x64 package, run under emulation, until the five locked packages have arm64 wheels; then a native package, as Codex's installer picks one
Update from a conversationThe version store's controller: build the new version, move the pointer, keep the previous one for rollback, on Windows as everywhere. A version being retired whose files a process holds stays where it is and is moved to trash on a later pass
Why this design

Claude Code renames a running executable to .old.<timestamp> and removes it on the next start, because it replaces its binary in place.

The version store never does: each version has its own folder and only the pointer moves. A folder holding an open file can be neither moved nor renamed on Windows, so retention leaves it and tries again on the next pass, which is the effect the rename gives Claude Code.

Windows command shell

host/_platform/command_shell.resolve_shell decides which shell a command runs in, for an execution environment and the sandbox in force. The command tool, hooks, the environment block, permission rules, doctor and /api/system/features read its profile; nothing else probes for a shell.

A command runs sandboxed exactly when the profile says so, also for a caller that passes its own sandbox policy. The host part is cached per named bash path, so changing the setting takes effect on the next command; the sandbox is read on every call.

The promises are recoverable delete, UTF-8 file output, the command's own exit code, stopping the whole process tree, and permission rules that can read the command. Each profile states all five as supported, partial or unsupported.

doctor prints the profile and runs echo 你好; exit 3 through the command backend, sandbox included. The row is advice: OK when both come back, INFO with the reason when not, and it gates neither openprogram upgrade nor a self-update. It also names a sandbox that is on but cannot run, and a named bash that is not a file.

Finding bash

  1. The path the owner named: OPENPROGRAM_GIT_BASH_PATH, then the setting shell.windows_bash_path. A path that is not a file is passed over, never an error.
  2. Git for Windows in Program Files or the user's programs.
  3. The bash inside the Git the runtime ships, when the base's base.json names it as gitBash.
  4. bin\bash.exe, then usr\bin\bash.exe, beside each git.exe on PATH: scoop, portable and custom installs.
  5. A bash in an absolute PATH folder that is not the WSL launcher.
  6. Otherwise PowerShell: pwsh 7, then Windows PowerShell 5.1.

The current directory and relative PATH entries are never searched, so a repository's own bash.exe never becomes the shell, and the answer does not depend on where the process started.

The Windows base build checks the unpacked dugite Git for bin\bash.exe and usr\bin\bash.exe and writes the one it finds, relative to <base>\git, or null. No extra Git or coreutils is downloaded.

Why this design

Peers split in two. Codex, OpenCode and Grok Build prefer PowerShell. Claude Code 2.1.321, Kimi Code, Pi and ZCode prefer bash. Oh My Pi embeds a bash engine written in Rust, which a Python runtime cannot reuse.

  • Bash first, PowerShell second, as Claude Code does: only the bash shells keep all five promises. Codex prefers PowerShell because its rules and sandbox were written for it; ours were not.
  • The bundled Git's bash costs no bytes when the archive has one. Downloading coreutils to make one would, and no peer does.
  • Bash beside git.exe follows Kimi Code's order and its usr\bin candidate; Claude Code and OpenCode derive it the same way. The variable name follows Claude Code's CLAUDE_CODE_GIT_BASH_PATH.
  • The PATH lookup stays: it reads only absolute folders and skips the WSL launcher, so removing it would only cost MSYS2 users a setting.
  • A bad named path falls through instead of failing as in Pi, because a missing shell degrades and never halts.

What runs in PowerShell

PowerShell source carries its own UTF-8 setup inside try and ends with exit, so in ConstrainedLanguage the setup fails quietly and the exit code still arrives. For 5.1 the setup also sets $PSDefaultParameterValues['Out-File:Encoding']='utf8': > writes UTF-8 with a byte order mark, which read and grep decode.

Why this design
  • One command tool with the rules in the environment block follows Codex, which appends its guidance by platform. Claude Code splits Bash and PowerShell into two tools; here that would change the tool list whenever the shell changes and break the cached prompt prefix.
  • The 5.1 rules are what 5.1 rejects with a ParserError, which needs no measurement.
  • The Out-File default follows Claude Code's prelude. UTF-16 makes read and grep see NUL bytes; the byte order mark is the one fix that needs nothing from the model. Codex sets only the console encoding, so its > still writes UTF-16. Set-Content keeps its default, so one file never mixes two encodings.

Delete shims under MSYS

The bash puts the delete shims first on PATH again after MSYS prepends /usr/bin. cygpath spells their folder for the bash it sits beside (/c/x for Git Bash and MSYS2, /cygdrive/c/x for Cygwin); a bash without it gets the MSYS spelling made in Python.

Deny and ask rules for PowerShell

Where commands run in PowerShell, deny and ask rules also read the command lowered to POSIX words (runtime/permissions/powershell_words.py). Each pipeline element becomes an argv. Allow rules never read the lowered form: they match the command as written, and "Always allow" saves that exact text.

Reads asPowerShell
rmRemove-Item, ri, rm, del, erase, rd, rmdir
mvMove-Item, mi, mv, move
cpCopy-Item, cp, cpi, copy
-r, -f-Recurse, -Force, or any prefix PowerShell accepts
OperandsPositional words and the values of -Path, -LiteralPath, -Destination

So bash(rm -rf *) stops Remove-Item -Recurse -Force .. A command the lowering cannot read for certain (variables, subexpressions, script blocks, arrays, redirections, &, dot-sourcing, comments, backticks, Unicode quotes and dashes) is asked about, not refused, when it names one of those cmdlets or runs a computed command, and only if a deny rule names rm, mv or cp.

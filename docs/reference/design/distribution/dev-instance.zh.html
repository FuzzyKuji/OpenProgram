稳定版与开发版实例

提交先在开发版跑，只能通过晋升进入稳定版。部署时稳定版不重启，所以稳定版里的对话可以部署，再打开 http://127.0.0.1:18200 或调用它的 API 看结果。

部署到开发版

openprogram dev deploy [ref]（默认 dev）把提交检出到 detached worktree ~/.openprogram-dev/source，在那里运行 scripts/refresh-dev-instance.sh。稳定版不会被停止或写入。

  1. 拒绝未提交或未跟踪的文件。同一时间只跑一次部署，第二次等待。
  2. 同步 Git hooks，报告上次部署以来的文档问题，但不中止。构建 Web 资源和 OpenProgram wheel；违反格式的页面变成可见的错误页。
  3. 在运行时里安装一次完整的 CPython 3.12（uv python install --install-dir），同步到发布版使用的锁定依赖，重装 wheel。
  4. macOS：构建 helper OpenProgram Dev.app（ai.openprogram.runtime.dev），让 runtime-manifest.json 指向它。worker 有自己的身份，屏幕录制、辅助功能等权限与稳定版分开授予。
  5. 设置 dev profile 的端口，绑定 Program 目录。
  6. 只安装或重启 dev worker，作为登录服务（launchd 或 systemd；其他系统直接停止再启动）。最多等 120 秒 /healthz，再把提交记入 runtime/source-revision。
  7. 把 wheel 和 TUI 包留在 ~/.openprogram-dev/artifacts 供晋升使用。
  8. macOS：运行 scripts/install-dev-app.sh。

登录

worker 每次启动都生成新的 owner token，所以一次部署会让浏览器掉登录。开发版 App 自己取新 token。

命令结果
openprogram dev open用默认浏览器打开，已登录；掉登录的提示会写出这条命令
openprogram dev auth-url打印登录链接，给其他浏览器用

从对话里

有 stable 分支时，self_update(action="prepare") 走 dev_stable 后端：开发版是试运行，晋升是切换。调用保存请求并启动脱离的控制器，其余步骤在发起调用的那一轮保存之后才开始。

步骤做什么阶段
1在候选的 worktree 里 rebase 到 dev 上staging
2在主 checkout 里 git merge --ff-only。dev 移动或 index.lock 被占用时退避重试，最多 10 次staging
3openprogram dev deploy <sha>staging
4对端口 18200 和 dev 状态目录做系统探测，再做浏览器探测：打开已登录的 Web 应用，直到消息框出现staging
5等稳定版没有运行中的任务，最多 30 分钟。这期间照常接收对话ready
6stable 已包含该提交时不晋升。否则运行 openprogram dev promote <sha>，始终带明确提交，等待期间不会发出别的会话部署的内容。开发版被别的部署占用时，重新部署并探测一次后再晋升activating
7对端口 18100 做系统探测verifying
8稳定版 worker 恢复后，结果经常规投递和后续轮次回到发起的对话succeeded

每个探测把 doctor 各行与同一实例改动前的结果比较，本来就失败的行（比如开发版没有的登录）不挡更新。

晋升到稳定版

openprogram dev promote [revision] 有意只做成命令，没有设置按钮：它是开发步骤，由 owner 或 owner 要求的 Agent 执行。

要求拒绝信息
提交正是 ~/.openprogram-dev/runtime/source-revision 记录的那个，且不是脏构建serves no clean commit 或 only the commit the development instance serves can be promoted
开发版响应 /healthzthe development instance is not healthy
提交包含当前的 stablepromotion only fast-forwards
10 分钟内稳定版没有运行中的工作，判定规则与自更新控制器相同。从稳定版 worker 内的 shell 调用时只等几秒，因为那一轮在等待期间不会结束。稳定版 worker 没有存活时没有可打断的工作，跳过等待；等待之后会重新核对上面的条件the stable instance is still busy，并列出这些工作
  1. 趁旧 worker 还在服务，备份稳定版 profile（openprogram backup，标签 pre-promote，保留最新 5 份）。
  2. 用 compare-and-swap 移动 refs/heads/stable，两次晋升不会互相覆盖。
  3. 把提交检出到 ~/.openprogram/release-source。
  4. 运行 scripts/refresh-local-app.sh：复用开发版对同一提交的构建，事务式安装 App，重启稳定版 worker。 刷新失败时再运行一次；事务保留原来的 App，所以重试从干净状态开始。

晋升只读取稳定版的数据存储，用来查看正在运行的工作。只有持有 worker.lock 的进程写运行状态，所以由重启后的新代码 worker 接管（见谁拥有运行状态）。

刷新闸门与 Electron 升级

stable 分支存在后，scripts/refresh-local-app.sh 只安装 refs/heads/stable；从其他提交运行会被拒绝，并指向开发版。

稳定版刷新替换 app.asar，保留 App 的 Electron。当 apps/desktop/package.json 锁定了另一个 Electron 或版本更新时，脚本构建同样的外壳，在 App 关闭时搬入 frameworks、可执行文件、Info.plist 和 locales，所以晋升带来的是开发版 App 已经跑过的 Electron。

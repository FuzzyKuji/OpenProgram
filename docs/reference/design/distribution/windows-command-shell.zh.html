Windows 命令 shell

host/_platform/command_shell.resolve_shell 按执行环境和当前生效的沙箱，决定命令在哪个 shell 里运行。命令工具、钩子、环境块、权限规则、doctor 和 /api/system/features 都读它给出的 profile，别处不再探测 shell。

命令是否进沙箱完全按 profile 说的来，调用方自带沙箱策略时也一样。本机部分按指定的 bash 路径缓存，改了设置下一条命令就生效；沙箱每次调用都重新读。

承诺有五项：可恢复删除、文件输出 UTF-8、命令自己的退出码、停止整棵进程树、权限规则能读懂命令。每个 profile 把五项都写成支持、部分或不支持。

doctor 打印 profile，并经命令后端（含沙箱）执行 echo 你好; exit 3。这一行只是建议：两者都回来显示 OK，否则显示 INFO 和原因；它不拦 openprogram upgrade，也不拦自我更新。它还会写明沙箱已打开却运行不了，以及指定的 bash 不是文件。

找 bash 的顺序

  1. 用户指定的路径：OPENPROGRAM_GIT_BASH_PATH，然后是设置 shell.windows_bash_path。路径不是文件时跳过，不报错。
  2. Program Files 或用户程序目录里的 Git for Windows。
  3. 运行时自带的 Git 里的 bash，基座的 base.json 用 gitBash 写明时。
  4. PATH 上每个 git.exe 旁边的 bin\bash.exe，再是 usr\bin\bash.exe：scoop、便携版和自定义目录。
  5. PATH 中绝对路径文件夹里的 bash，但不是 WSL 启动器。
  6. 否则用 PowerShell：先 pwsh 7，再 Windows PowerShell 5.1。

从不搜索当前目录和 PATH 里的相对路径，所以仓库自己的 bash.exe 不会成为 shell，结果也不取决于进程从哪里启动。

Windows 基座构建时，检查解压出的 dugite Git 里有没有 bin\bash.exe 和 usr\bin\bash.exe，把找到的那个（相对 <base>\git）或 null 写进去。不另外下载 Git 或 coreutils。

为什么这样设计

同行分两派。Codex、OpenCode、Grok Build 优先 PowerShell。Claude Code 2.1.321、Kimi Code、Pi、ZCode 优先 bash。Oh My Pi 内嵌了 Rust 写的 bash 引擎，Python 运行时没法直接用。

  • bash 优先、PowerShell 兜底，照 Claude Code：五项承诺只有 bash 系的 shell 全部守得住。Codex 选 PowerShell，是因为它的规则和沙箱按 PowerShell 写，我们的不是。
  • 自带 Git 的压缩包里有 bash，用上它不花一个字节。为此另外下载 coreutils 要付出体积，也没有同行这样做。
  • 从 git.exe 推出 bash 照 Kimi Code 的顺序和它的 usr\bin 候选；Claude Code 和 OpenCode 也这样推。变量名照 Claude Code 的 CLAUDE_CODE_GIT_BASH_PATH。
  • PATH 查找保留：它只查绝对目录、跳过 WSL 启动器，删掉它只会让 MSYS2 用户多配一个设置。
  • 指定的路径无效时继续往下找，不像 Pi 那样报错，因为找不到 shell 时只降级，不停机。

在 PowerShell 里运行时

PowerShell 源码把自己的 UTF-8 设置放在 try 里，最后用 exit 退出，所以在 ConstrainedLanguage 下设置静默失败，退出码照样传回。对 5.1，设置里还有 $PSDefaultParameterValues['Out-File:Encoding']='utf8'：> 写出带 BOM 的 UTF-8，read 和 grep 能解码。

命令工具的描述在所有平台上一样。换了 shell 只改环境块里这一行，在下一条消息旁说一次（组合）。

为什么这样设计
  • 一个命令工具、规则放进环境块，照 Codex：它按平台给出说明。Claude Code 把 Bash 和 PowerShell 拆成两个工具；在这里，换 shell 时工具列表就会变，提示的缓存前缀随之失效。
  • 5.1 的规则写的是 5.1 一定报 ParserError 的写法，不需要测量。
  • Out-File 的默认值照 Claude Code 的前置脚本。UTF-16 让 read 和 grep 读到 NUL 字节；BOM 是唯一不需要模型配合的办法。Codex 只设控制台编码，它的 > 仍写 UTF-16。Set-Content 保持默认，同一个文件就不会混进两种编码。

MSYS 下的删除垫片

MSYS 把 /usr/bin 加到 PATH 前面之后，bash 再把删除垫片放回最前。垫片目录由 cygpath 按它所在的 bash 来写（Git Bash 和 MSYS2 写成 /c/x，Cygwin 写成 /cygdrive/c/x）；没有它的 bash 用 Python 拼好的 MSYS 写法。

PowerShell 命令的拒绝和询问规则

命令在 PowerShell 里运行时，拒绝和询问规则还会读一遍转换成 POSIX 写法的命令（runtime/permissions/powershell_words.py）。管道里每一段成为一个 argv。允许规则从不读转换后的写法：只匹配原文，“始终允许”保存的也是原文。

读作PowerShell
rmRemove-Item, ri, rm, del, erase, rd, rmdir
mvMove-Item, mi, mv, move
cpCopy-Item, cp, cpi, copy
-r、-f-Recurse、-Force，以及 PowerShell 接受的任何前缀
操作数位置参数，以及 -Path、-LiteralPath、-Destination 的值

所以 bash(rm -rf *) 能拦住 Remove-Item -Recurse -Force .。读不准的命令（变量、子表达式、脚本块、数组、重定向、&、点号引入、注释、反引号、Unicode 引号和破折号），如果提到这些 cmdlet 或运行计算出来的命令，只在有拒绝规则指向 rm、mv 或 cp 时转为询问，而不是拒绝。

为什么这样设计
要点原因
Codex，照它做它在进程内用 tree-sitter 转换，普通单词和字面字符串之外一律视为读不懂，删除类别名表也相同
Claude Code解析 PowerShell AST，Bash 规则和 PowerShell 规则互不覆盖，并建议有 Bash 拒绝规则时关掉 PowerShell 工具；我们只有一个命令工具，那等于关掉所有命令
ZCode按方言分别匹配
一条规则管两种 shell用户写 bash(rm -rf *)，本意是“不许递归删除”

询问而不是拒绝审批保持少见：只有自己写了这类拒绝规则的用户，才会多这一次确认

Stable and development instances

Commits run on the development instance first and reach stable only by promotion. Stable does not restart for a deploy, so a stable conversation can deploy, open http://127.0.0.1:18200 or call its API, and look at the result.

Deploying to the development instance

openprogram dev deploy [ref] (default dev) checks the commit out into the detached worktree ~/.openprogram-dev/source and runs scripts/refresh-dev-instance.sh there. Nothing of stable is stopped or written.

  1. Refuse uncommitted or untracked files. One deploy runs at a time; a second waits.
  2. Sync the Git hooks and report docs findings since the last deploy, without stopping. Build the Web assets and the OpenProgram wheel; a page that breaks the format becomes a visible error page.
  3. Install a full CPython 3.12 into the runtime once (uv python install --install-dir), sync the locked dependency set a release installs, reinstall the wheel.
  4. macOS: build the helper OpenProgram Dev.app (ai.openprogram.runtime.dev) and point runtime-manifest.json at it. The worker gets its own identity, so Screen Recording, Accessibility and similar grants are separate from stable.
  5. Set the dev profile's port and bind the Program catalog.
  6. Install or restart only the dev worker as a login service (launchd or systemd; a plain stop and start elsewhere). Wait up to 120 seconds for /healthz, then record the commit in runtime/source-revision.
  7. Keep the wheel and TUI bundle in ~/.openprogram-dev/artifacts for promotion.
  8. macOS: run scripts/install-dev-app.sh.

Signing in

The worker mints a new owner token on every start, so a deploy signs out browsers. The development App fetches its new token itself.

CommandResult

From a conversation

With a stable branch, self_update(action="prepare") uses the dev_stable backend: the development instance is the trial, promotion the switch. The call saves the request and starts a detached controller; the rest runs after the calling turn is saved.

StepWhat happensPhase
1Rebase the candidate onto dev in its worktreestaging
2git merge --ff-only in the primary checkout. A moved dev or a held index.lock retries up to 10 times with backoffstaging
3openprogram dev deploy <sha>staging
4System probe against port 18200 and the dev state directory, then a browser probe: open the signed-in Web app until the message box appearsstaging
5Wait until stable runs no task, up to 30 minutes. Turns stay admittedready
6If stable already contains the commit, nothing is promoted. Otherwise openprogram dev promote <sha>, always with the explicit commit, so the wait cannot ship another session's deploy. If another deploy took development over: redeploy, probe once, promote againactivating
7System probe against port 18100verifying
8The result reaches the origin conversation through the ordinary delivery and follow-up turn, once the stable worker is backsucceeded

Each probe compares the doctor rows with the same instance's before the change, so a row already failing, such as a login development lacks, blocks nothing.

Promoting to stable

openprogram dev promote [revision] is a command on purpose, with no Settings button: a development step run by the owner or an Agent the owner asked.

RequiredRefusal
The commit is the one in ~/.openprogram-dev/runtime/source-revision, not a dirty buildserves no clean commit or only the commit the development instance serves can be promoted
Development answers /healthzthe development instance is not healthy
The commit contains the current stablepromotion only fast-forwards
Stable has no running work within 10 minutes, by the rule the self-update controller waits on. Called from a shell inside the stable worker, a few seconds, since that turn cannot end while it waits. With no live stable worker there is nothing to interrupt, so the wait is skipped; afterwards the conditions above are checked againthe stable instance is still busy, naming the work
  1. Back up the stable profile (openprogram backup, label pre-promote; the newest 5 are kept) while the old worker still serves.
  2. Move refs/heads/stable by compare-and-swap, so two promotions cannot overwrite each other.
  3. Check the commit out into ~/.openprogram/release-source.
  4. Run scripts/refresh-local-app.sh, which reuses the development build of the same commit, installs the App transactionally and restarts the stable worker. A failed refresh runs once more; the transaction leaves the previous App in place, so the retry starts clean.

Promotion only reads the stable stores, to see what is running. Only the process holding worker.lock writes run state, so the restarted worker takes over on the new code (see Who owns run state).

Refresh gate and Electron upgrades

scripts/refresh-local-app.sh installs only refs/heads/stable once that branch exists; from any other commit it refuses and points to the development instance.

A stable refresh replaces app.asar and keeps the App's Electron. When apps/desktop/package.json pins another Electron or carries a newer version, the script builds the same shell and moves its frameworks, executable, Info.plist and locales in while the App is closed, so promotion brings the Electron the development App already ran.

Publishing

Neither instance pushes anything. See Publishing source to GitHub.

Source checkout

Both commands find the repository through OPENPROGRAM_SOURCE_REPO, else ~/.openprogram/source-repo, which both refresh scripts write with the main checkout, not the build worktree.

发布源码到 GitHub

GitHub 只承载 main。它的历史永不和另外两条线合并，也没有东西把 GitHub 的 main 拉回来。

分支

本地只有这三条。worktree 分支合入 dev 后删除，放弃时也删除。想留着的放到 refs/archive/，任何命令都不会把它列为分支，也不会推送。

发布一个版本

scripts/publish-github.sh -m "Sidebar run status, Launchpad, Agent cards" --dry-run
scripts/publish-github.sh -m "Sidebar run status, Launchpad, Agent cards"
scripts/publish-github.sh -m "Windows and Linux Apps" --tag v1.1.0 --dry-run
scripts/publish-github.sh -m "Windows and Linux Apps" --tag v1.1.0
参数作用
-m "summary"版本摘要；新版本必填
--source <ref>改为压缩 dev 上的另一个提交；默认 stable
--dry-run显示提交说明和检查结果，不做改动
--no-push第 5 步后停止
--tag vX.Y.Z第 7 步；不能和 --no-push 同时使用
  1. 把 hook 装进共享的 .git/hooks，每个 worktree 都有。
  2. 拒绝不在 dev 上的来源。main 已是该来源的文件树时没有新版本，直接到第 7 步。
  3. 扫描新增行中看起来真实的凭据（GitHub token、Anthropic API key、AWS access key、私钥块），命中就拒绝。AWS 文档里的示例 key 和测试里的单行 PEM 字符串不算。
  4. 在来源提交的临时检出上跑 scripts.docs_site.check --all，失败就拒绝。
  5. 写提交说明：摘要、距上一版本的本地提交数、Local-Source: trailer。
  6. 用 git commit-tree 创建提交：来源的文件树，上一个 main 提交是唯一父提交（第一个版本没有）。移动 main，把来源记入 refs/publish/last，下个版本从这里开始计数。
  7. 确认 GitHub 的 main 是本地 main 的更早位置后推送，所以只会 fast-forward。
  8. 加 --tag vX.Y.Z 时，给这个 main 提交打标签并推送标签，由此启动 Release 工作流。在移动任何东西之前，它会拒绝已经存在的标签、和 pyproject.toml 或 apps/desktop/package.json 版本不一致的标签，以及缺少 .github/release-notes/vX.Y.Z.md（开头必须是 # OpenProgram X.Y.Z Release Notes）的源提交。--dry-run 会运行这些检查并显示标签。
其他拒绝情况
条件结果
refs/publish/last 不是来源的祖先拒绝，不做改动
没有 origin remote版本留在本地 main
GitHub 的 main 不在本地 main 的历史里拒绝推送

一次发布构建什么

Release 工作流由推送的标签触发。每个平台分支彼此独立。

项目行为
失败的分支只缺自己的文件；发布任务上传成功的部分
release-manifest.json只列实际存在的文件
发布说明多出 “Not in this release” 一节，写明缺什么、为什么缺
拒绝发布只有 wheel 缺失，或者 macOS 和 Linux 的命令行运行时一个都没有时

证书只决定安装包的形式，不决定它有没有。

安装包有凭据没有凭据
macOS AppDeveloper ID 签名并公证，OpenProgram-X.Y.Z-mac-<arch>.dmgad-hoc 签名，文件名带 -unsigned
Windows AppAuthenticode 签名，OpenProgram-X.Y.Z-win-<arch>.exe-unsigned.exe
Linux AppAppImage 和 deb 不需要签名；在 Ubuntu 22.04 上构建，x86_64 和 arm64相同
情况结果
OPENPROGRAM_UPDATE_SIGNING_KEY 缺失或不在 RELEASE_PUBLIC_KEYS 里Windows 和 Linux App 被略过，并在发布说明里写明：没有受信任更新签名密钥的轻量壳 App 永远无法更新
AppImage 构建失败deb 照常发布
不带版本号的副本每个稳定版 App 还会以 OpenProgram-linux-x86_64.AppImage 这样的名字上传一份，供 releases/latest/download/ 链接使用；不进清单

仓库变量用来调整各分支。正常发布一个都不需要设置。

变量默认作用
OPENPROGRAM_RELEASE_DESKTOP_MAC、_WINDOWS、_LINUX开；false 关闭对应平台的 App
OPENPROGRAM_RELEASE_WINDOWS_RUNTIME开；false 关闭Windows 命令行运行时
OPENPROGRAM_RELEASE_WINDOWS_ARM64关；true 打开Windows on Arm 的 App 和运行时
OPENPROGRAM_RELEASE_MAC_THIN关；true 打开轻量版 macOS App，需要签名和更新密钥
OPENPROGRAM_RELEASE_CLI_SEEDS关；true 打开给命令行安装器的 -seed- 资产，需要更新密钥

在这两个开关打开之前，macOS 继续发完整 App，命令行继续用完整运行时：v1.0.0 的 App 和命令行依赖现有的 DMG 名字、运行时压缩包和 release-manifest.json，种子安装也需要已发布的网络更新程序。

Hook

Hook拒绝放行
scripts/git-hooks/pre-push没有 OPENPROGRAM_GITHUB_PUBLISH=1（脚本设置）或发送的不是本地 main 的 refs/heads/main 推送；任何其他分支的推送，那会上传工作历史；不是脚本推送或不指向本地 main 的标签，因为推送标签会启动 Release 工作流删除远端分支或标签
scripts/git-hooks/pre-commit检出 main 时的提交；暂存文档未通过 scripts.docs_site.check 的提交其他所有分支

本机全局 hook（core.hooksPath）把两者委托给仓库的 .git/hooks，所以脚本装在那里。

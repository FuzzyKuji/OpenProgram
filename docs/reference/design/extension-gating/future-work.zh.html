门控：未构建项

默认与 Claude Code、opencode、hermes 对齐；只有出现具体的用户痛点才增加机制。下面每项都未通过这一检验。

想法为何被提出为何不做何时重新考虑
按会话的门控开关：为一次对话覆盖配置角色对一次性任务太严，改配置显得繁重Claude Code 的 permissionMode 和 opencode 的规则集都按 Agent；hermes 没有这种出口。编辑 agent.json 下一轮即生效。覆盖带来状态问题：存在哪里、刷新后是否保留、WebSocket 重连时是否泄漏用户为一个任务反复来回改 agent.json
插件子进程沙箱：限制文件系统和网络插件带任意 Python；恶意插件可窃取 API 密钥或删除工作区参考实现都在进程内加载插件。信任等级已门控危险能力：plugin.json 声明 trust，~/.openprogram/plugin-trust.json 存 verified、community 或 untrusted（默认）。系统沙箱分平台：Linux 的 seccomp、macOS 的 App Sandbox。安装是用户明确操作，并有清单审查出现自动安装插件，例如模型在对话中安装
Frontmatter 中的技能 requires 链技能依赖其他技能的上下文；用户手动串联 /skill A /skill B参考实现和 SKILL.md 规范都没有。正确做法是合并技能或在描述中说明。依赖会带来本项目其他地方没有的顺序、冲突和版本问题作者反复写“与 X 一起使用”
Hook 级门控：钩子限定到某个 Agent 配置openprogram/extensions/plugins/hooks.py 的插件钩子订阅进程级总线，无法按 Agent 选择很少有插件注册钩子。Claude Code 的按 Agent 钩子多数通过插件使用。门控回答模型能用什么；钩子回答调用如何通过某插件必须按 Agent 表现不同
单一规则集：一个 permission: [{pattern, action}] 列表单一事实来源，新增类型更容易纯重构，没有新能力。~/.openprogram/agents/ 下每个配置都要迁移。首个匹配生效使顺序变得重要；分块则不会第五、第六个门控类型让 schema 臃肿

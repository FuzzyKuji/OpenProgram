Memory interface

Task typeBehaviour
One-timeTimezone-aware run_at, runs once
RecurringFive-field cron, owner signatures, frozen sandbox policies, non-interactive execution
MonitoringObservation prompts on cron; records logs and state, no cross-channel exactly-once notification

Excluded: the Memory writer inferring tasks, Commitments on Memory pages, the service implicitly changing Memory, cross-store transactions, an external-token permission model, placeholders or forwarding for deleted records, a second executor, project management, dependencies, subtasks.

Lifecycle of a run

  1. Owner Web UI, an Agent tool or an external API creates the task.
  2. The runtime signs prompt or command, cwd, permissions, sandbox and MemoryRef.
  3. The persistent worker checks once and cron schedules every minute.
  4. Each run begins by loading the memory as it stands now, through workspace_id + memory_id.
  5. Execution stays in the frozen non-interactive boundary and writes Scheduler logs and state.
Tick exceptions
  • An Exception in the @reboot tick or an ordinary tick goes to stderr as a warning and full traceback; the daemon continues at the next minute boundary without replay. After an initial failure, later ticks use reboot=False.
  • Persistent worker: stderr goes to the global worker log. Foreground scheduler-worker: the terminal. Neither is a task execution log.
  • run_once, KeyboardInterrupt, SystemExit and other BaseException stay fail-fast.
  • scheduler-worker and its alias cron-worker, with --once and --list, bypass the stdio redirection meant for Ink TUI startup.

Agent protocol

PhaseAgentBoundary
PlanningOnly for a task worth keeping: memory_update.create_record, then attach the returned memory_id as memory_refsSequential, not atomic; either failure is reported. Temporary reminders need no Memory.
ExecutionReads the original record, then update_record with status, results or what the next run needsOther tools follow the conversation's permission mode. Only Memory lifecycle tools are refused to a schedule not set up by the owner.
ClosureMark completed or closed, or delete_record when nothing is worth keeping. An interactive agent may disable or delete the task.The old ID returns NOT_FOUND; a task still referencing it fails next time, so remove the task first.

Deleted content stays recoverable from reachable Git history if it was committed, the repository exists and history was not rewritten. memory_get queries only HEAD, so an old ID is not queryable through the API.

Scheduler page

  • Shared page header and theme tokens; ManagePageHeader, ManageRow. Search and the primary action share one row in the 64px topbar.
  • Four compact filters in a row below the header, no sidebar; they wrap when narrow. Rows keep schedule, status and actions, numbered in visible order.
  • Empty state: introduction and Create task centered; three suggestion cards in a centered grid up to 960px, one column when narrow, each with title, schedule, prompt and Use.
  • Create and Use open the existing form without creating a task; Escape returns.

Acceptance

  • The three Memory tools execute from a Scheduler prompt worker, deny and ask rules still win, and a scripted run updates a Topic with a Memory Git commit.
  • Regressions cover initial and ordinary ticks, waits, oversleep, logging, CLI entry points and both fail-fast boundaries.
  • No horizontal overflow at 360, 768 and 1440 px container widths; all four filters reachable; loading, search and error states unchanged.

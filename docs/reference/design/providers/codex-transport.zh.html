加载延迟工具

后端把 tools 数组渲染在指令和对话之前。数组的任何改动，包括在末尾追加一个工具，都会让它把整个请求当作未缓存重读。所以延迟工具在搜索它的位置加载，与 Responses API 客户端执行的 tool search 放置方式一致。

部分线上形式
tools 里的 tool_search{"type":"tool_search","execution":"client"}，带它自己的参数
模型的搜索一个 tool_search_call 条目，作为 tool_search 工具运行，回传时不带 id
搜索结果一个 tool_search_output 条目，带结果的加载记录 details["loads"] 里的定义：每个工具一项 {name, definition}，由 record_loads 在加载时写入。不读结果文字，所以之后每次请求这个条目的字节都相同；加载后 schema 改了也不影响它。这一轮不再提供的工具仍留在条目里，调用时和这一轮没有的其他工具一样被拒绝
存下的结果工具节点把加载记录存在 metadata 里、放在文字旁边；从历史渲染时放回工具结果上，所以从历史构建的请求和工具运行那一轮构建的相同
哪些请求provider 在 provider.json 的 tool_search 下为请求的 API 声明了 responses 形式，且模型没有退出（Model.tool_search = False）。只有 openai-codex 声明了；其他 provider 和 API，包括 Bedrock Converse 和兼容 Anthropic 的那些，都把搜到的工具放进数组
已加载集合每个 provider 都从本次请求自己的消息读出（loaded_tools）：工具结果上的加载记录，加上其中压缩摘要带着的工具名。没有别处保存它，所以嵌套运行、另一个分支、回到搜索之前的编辑都看不到这次加载
已加载的工具输入里有 tool_search_output 带着它时不进数组
压缩之后摘要节点存 carried_tool_names：被覆盖的轮次加载过的工具，最近加载或调用的在前，定义总量超过窗口 5% 的部分截掉。Codex 上在摘要前放一对 tool_search_call / tool_search_output，call id 由工具名算出，每个定义取对话第一次发出的那份，所以数组不变；其他 provider 把带过去的工具放进数组

整段对话的每次请求 tools 数组、指令和保留 socket 的形状都相同，所以 WebSocket 增量能跨过一次加载继续。提示里的延迟列表列出全部延迟工具，加载与否都在。

另有两种加载方式仍把工具放进数组、排在对话之前：指南送达时激活的工具（self_update 指南激活 worktree_create），加载记录写在送达指南的那条结果上，以及对话里打开的应用，它的工具从下一轮起常驻。

两者都不写 tool_search_output，所以各自带来一次整段重读，与之前的工具搜索一样。稳定版最近 30 天有 77 次工具搜索，没有 self_update 调用。

握手失败该主机避开 SHUN_S，10 分钟；401、429、5xx 除外

连接数上限后端拒绝

经 HTTP 代理时，握手先发 CONNECT：

  • 代理拒绝、超时或断开连接，和其他握手失败一样，这一轮走 HTTP；
  • 隧道内 TLS 握手期间对端重置或关闭隧道，同样是握手失败；
  • 代理回答前放弃拨号（轮次被停止），代理连接立即关闭，别的不变。

websockets 16 本身会让这条连接留着，迟到的回答到达时记录 InvalidStateError；代理不回答就关闭时，它还会把回答流结束两次，所以 _install_proxy_protocol 换掉了它的代理协议。

websockets 还在 WebSocket 连接建立之前就在隧道里开始 TLS，而 asyncio 已把这条连接当作建立；此时隧道断开会对它调用 connection_lost，_Connection 因为什么都没建立而忽略这次调用。

回复开始后 socket 断开，按普通可重试的流中断处理。OPENPROGRAM_CODEX_ZSTD=0 关闭压缩。

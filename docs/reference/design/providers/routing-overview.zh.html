路由概览

设置 → Providers → 概览显示哪个会话的哪条分支在和哪个模型对话，以及模型失败时发生了什么。只有故障切换是为它单独记录的，其余都来自已有记录。

数据来源

GET /api/routing/overview?window=<seconds>（openprogram/interfaces/server/routes/settings/routing.py）合并：

来源提供
会话索引（list_sessions）标题、source / channel、当前轮次的 running 状态
会话节点图（list_branches、SessionNodeWriter.load）每个打开的分支末端、其最后一次回复的模型、末端是否从子 Agent 派生根开始
用量账本 usage_events时间窗内按会话和模型统计的 Provider 调用；parent_session_id 指向另一会话即为子会话
用量账本 route_events每次故障切换一行：调用会话、失败的 provider/model、下一个 provider/model、原因
凭据存储在用 Provider 的每个账号：状态、限流冷却结束时间
列出条件
轮次正在运行、会话在时间窗内更新过，或账本在时间窗内有它的调用
上限
8 个会话，运行中优先，再按最近活动；其余计为空闲。每个会话 4 条分支，活动分支优先

通道

会话的每一行是一条通道，连到一个模型。

通道含义
branch打开的分支末端。最长的链是主干，标为 main；其余用分支名。
sub_agent链从子 Agent 派生根开始的末端
children按所调用模型分组的子会话，带数量
calls有账本调用但没有回复节点的会话（程序直接调用模型）
background任何列出的会话都解释不了的账本调用：有自己 op-… id 的程序运行、起标题、记忆维护。按模型归到一个“后台调用”条目下，所以图上的数能和上方的调用总数对上。

活跃：运行中轮次的活动末端，或最近 90 秒内有账本调用。

如何保持请求够快

打开会话要逐个文件读节点图。每次读都会释放 GIL，其他服务器线程繁忙时要等着拿回来，所以冷打开可能要几秒。

  • 会话及其通道按 (session, index updated_at) 缓存，没变的会话不再打开。
  • 冷会话在一个后台线程上打开，请求最多等 1.5 秒。
  • 到时没准备好的会话用索引行和账本调用显示，响应带 partial: true，客户端两秒后再请求。

故障切换

stream_with_failover 每次换到下一个候选时追加一行 route_events，用用量上下文里的会话打标。当会话最近一次切换落在某通道的模型上时，图上从活动通道画一条虚线到失败模型，标出原因，并在下方列出最近的切换。

只有配置了备用模型才会有切换。直接展示给用户、没有发生切换的失败不记录在这里。

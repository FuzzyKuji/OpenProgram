档位

ThinkingLevel = "minimal" | "low" | "medium" | "high" | "xhigh" | "max"

另有 off。这是框架自己的名字，与任何 API 无关。选择器只显示模型支持的档位。

从选择器到请求

  1. get_thinking_config_for_model（interfaces/server/thinking_effort.py）用模型的 thinking_levels 生成选项。
  2. _normalize_thinking（runtime/conversation/session_config.py）按 VALID_THINKING 校验，按会话分支保存。新分支创建时继承一次，切换时恢复对应分支的选择。
  3. reasoning_from_config 把它作为 SimpleStreamOptions.reasoning 交给本轮，由 normalize_reasoning_level 限制在模型的档位之内（见下）。
  4. 提供商的 stream_simple() 调用 translate_reasoning(provider, model, level)，把结果写进请求字段，例如 {"output_config": {"effort": "high"}}。

模型没有的档位

为别的模型保存的档位，或 --effort 要的档位，可能不在模型的 thinking_levels 里。normalize_reasoning_level（thinking_spec.py）发送它有的最近一档：

  • 先找更强的下一档，没有再找更弱的：在从 low 起步的模型上，minimal 发送 low；
  • 档位表以外的名字：用模型的默认档位。

照 Pi 的 clampThinkingLevel。回落到默认档位可能把最轻的档位变成中间档；translate_reasoning 对 Anthropic 的 minimal 也是这样映射到 low。

Fetch 如何使用探测
  • 每个提供商目录可有 probe_thinking.py，暴露 probe()。
  • 补全阶段，条目缺 reasoning 时，models/listing/fetchers/__init__.py 经 _load_probe 调用它。
  • 没有探测模块或探测失败都不影响 Fetch。
  • 探测只读。model_overrides 手工维护。

请求修复

每条提供商流都经过它：streaming.stream._metered 在调用提供商前调用 request_repair.prepared，并通过 request_repair.repairing 读事件。

钩子时机返回
before_sending(model, context)每次请求前应用了已知教训的上下文
after_refusal(model, context, refusal)一次尝试还没说话就报错修复后的上下文，不认识则 None

REPAIRS：先 prefill，后 body_cap。第一个修好的请求重发，最多 MAX_RESENDS（3）次。

流规则细节
事件不扣留；消费方只看到回复开始一次
重发去掉第一个 start；拒绝本身不传出
已有 start 之外的内容事件直接透传，不再重发
取消RepairingStream.cancel_producer 关闭当前提供商流，等待上限相同
没有修复认识的拒绝继续交给重试和故障转移

两种修复

请求体上限Prefill
拒绝状态 413，或 body、request、payload、entity too large；不是上下文溢出（utils/overflow.py）“does not support assistant message prefill”、“Requests ending with a model turn are not supported”、“last message cannot be from the assistant”
见于Anthropic 的 32 MB request_too_large、中转部分网关后的 Anthropic 模型、火山引擎 Agent Plan、Vertex AI 上的 Gemini
学到比已发送小的最小声明值，否则已发送的 ¾该模型拒绝
记忆键提供商和 base URL提供商、API 和模型
修复调整到上限的 ¾：最早的历史图片逐张换成一条说明加一条用户消息 Continue.
不动最新用户消息的图片、所有文字、工具结果的文字以工具调用结尾的对话
放弃所有更早的图片都去掉仍太大：拒绝继续传出–

说明文字：[An earlier image was left out: the request was over the provider's size limit.] 留 ¾ 的余量，让对话再长几轮才去更多图片，不至于每轮破坏提示缓存。

Error reasons up to the UI

Flattened to a string, a rate limit, a rejected key and an overlong conversation look alike and offer nothing to do. Scope: the main chat-turn streaming error. Retry and compact-failure strings stay plain.

A memory policy error is unknown and not retryable; error_kind: memory_unavailable names it, so the reason stays inside the set.

Where it happens

PlaceDoes
models/providers/utils/errors.pyErrorReason, LLMError, classify_error, taxonomy_fields; stream_retry drives backoff from them. error_kind gives a narrower stable name (stream_idle, stream_total, model_unavailable, auth…) found through wrapped causes

API consumers, logs and other channels read the reason too. No change to auto-retry policy; this only exposes the fields. A wider audit of except Exception sites is separate.

Verifying

A rejected key gives auth, fatal. A 429 gives rate_limit, retryable, with the hint. An oversized context gives context, fatal. Unit tests cover the mapping and that the Agent boundary keeps an LLMError's reason.

End to end needs a repeatable failure on the model the frontend selected, since it sends its own choice: an expired key for auth, or an OpenRouter :free model that returns 503 for provider.

API key 解析

Provider凭据来源
使用 key 的 LLM provider~/.openprogram 下的 AuthStore，由设置页或 openprogram providers login <provider> --api-key 写入
Amazon BedrockAWS 凭据链；返回哨兵值 "<authenticated>"，没有 bearer key
Google VertexGCP ADC 加项目和区域；同样的哨兵值
环境变量、config.jsonLLM key 绝不读取。config.json 的 api_keys 只用于网页搜索和 TTS。

单一来源让运行时、目录和状态检查不会互相矛盾，设置页保存的 key 在 worker 重启后仍然有效。

调用

函数回答
resolve_provider_key(provider)运行时路径：API key 形状的凭据或哨兵值，否则 None。不含 OAuth 令牌，因为这些线路用 x-api-key 或 Bearer，放访问令牌会 401。
is_configured(provider_id)有 key，或云凭据链满足
resolve_api_key_with_auth_store(provider_id)模型列表和探测：经 resolve_api_key_sync 取 AuthStore 能给出的任何 bearer
env_vars_for(provider_id)key 名称，作标签和标识；回退到 models.dev
provider_id_for_env_var(env_var)反查，按表顺序取第一个；非 LLM key 返回 None

位于 openprogram/models/providers/settings/env_api_keys.py，运行时和服务端都能导入，不成环。credentials.provider_id_for_env_var 转出反查表。

resolve_api_key_sync 的顺序
  1. get_credential_override，供测试或中间件
  2. CredentialProvider.acquire_sync：从池中取刷新后的令牌或 key
  3. resolve_provider_key：云哨兵值

返回 None 时，调用方显示登录提示，或对本地端点无 key 继续。AuthCredentialProcessError 总是向上抛：损坏的 helper 要点名显示，不用过期 key 顶替。

两张名称表
表用途
_PROVIDER_ENV_VARS每个 provider 的全部名称：设置页标签和 add_mode 分类。例如 google 有三个；anthropic 把 ANTHROPIC_OAUTH_TOKEN 放第一；github-copilot 有三个令牌名。
PROVIDER_ENV_VARS扁平，每个 provider 一个名称，models/auth/adoption.py 和 openprogram providers 命令用作“有 key 名称的 provider”列表。有意不含 anthropic 和 copilot，从上表派生会改变登录流程。

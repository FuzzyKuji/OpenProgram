Cache routing

The backend caches a prompt prefix on one replica. A new connection reaches that replica only when the request names its conversation in the session_id and conversation_id headers as well as in prompt_cache_key (CONVERSATION_HEADERS). With the body key alone, a fresh socket missed the whole prefix.

Loading a deferred tool

The backend renders the tools array ahead of the instructions and the conversation. Any change to the array, a tool appended at its end included, makes it read the whole request uncached. A deferred tool is therefore loaded where it was searched for, as the Responses API's client-executed tool search places it.

Same tools array, instructions and kept-socket shape on every request of the conversation, so WebSocket deltas carry on through a load. The prompt's deferred list names every deferred tool, loaded or not.

Two other ways a tool becomes loaded still put it into the array, ahead of the conversation: a guide that activates a tool when it is delivered (the self_update guide activates worktree_create), whose load record goes on the result that delivered the guide, and an application opened in the conversation, whose tools become resident at the next turn.

Neither writes a tool_search_output, so each costs one full re-read, as a tool search did before. In the stable instance's last 30 days there were 77 tool searches and no self_update call.

Through an HTTP proxy the handshake first sends CONNECT:

  • a refusal, a timeout or a dropped proxy connection fails the handshake like any other, so the turn goes over HTTP;
  • a tunnel the far end resets or closes during the TLS handshake inside it fails the handshake the same way;
  • a dial given up before the proxy answers (the turn stopped) closes the proxy connection at once and changes nothing else.

websockets 16 itself left that connection open and logged InvalidStateError when the late answer came, and ended the answer's stream twice when the proxy closed before answering, so _install_proxy_protocol replaces its proxy protocol.

websockets also starts TLS in the tunnel before the WebSocket connection is made, while asyncio counts that connection as made; a tunnel lost then calls connection_lost on it, which _Connection ignores because nothing was set up.

A socket cut after the reply starts is an ordinary retryable stream break. OPENPROGRAM_CODEX_ZSTD=0 turns compression off.

Implementation status

  • A summary written before carried_tool_names existed carries what its covered turns loaded, uncut; on Codex its first request after this change sends the new pair instead of the old kept search, so the prefix breaks once.
  • The checkpoint journal still has its loaded_deferred_tools field; nothing reads it for loading any more, and it goes in a later version.
  • The cached share right after a compaction on Codex is not yet measured against the instructions and tools token count.
  • Results stored before load records existed have none, so on Codex their item carries no tools and the model searches again.

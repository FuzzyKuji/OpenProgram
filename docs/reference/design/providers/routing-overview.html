Routing overview

Settings → Providers → Overview shows which session and branch talks to which model, and what happened when a model failed. Only the failover switches are collected for it; the rest is read from existing records.

Sources

GET /api/routing/overview?window=<seconds> (openprogram/interfaces/server/routes/settings/routing.py) joins:

Limits
8 sessions, running first, then latest activity; the rest count as idle. 4 branches per session, active first

Lanes

A session's rows are lanes, each wired to one model.

LaneIs
branchAn open branch tip. The longest chain is the trunk, labelled main; others use their branch name.
sub_agentA tip whose chain starts at a sub-agent spawn root
childrenChild sessions grouped by the model they called, with a count
callsA session with ledger calls but no reply node (a program calling models directly)
backgroundLedger calls no listed session accounts for: program runtimes with their own op-… ids, titling, memory upkeep. Grouped by model under one Background calls entry, so the map adds up to the call count above it.

Live: the active tip of a running turn, or a ledger call in the last 90 seconds.

Keeping the request fast

Opening a session reads its node graph file by file. Every read gives up the GIL and waits to get it back while other server threads are busy, so a cold open can take seconds.

  • A session and its lanes are cached per (session, index updated_at); an unchanged session is never reopened.
  • Cold sessions open on one background thread; the request waits at most 1.5 s.
  • A session not ready by then is shown from its index row and ledger calls. The response carries partial: true and the client asks again two seconds later.

Failover switches

stream_with_failover appends a route_events row, tagged with the session from the usage context, each time it moves to the next candidate. When a session's latest switch landed on a lane's model, the map draws a dashed edge from the active lane to the failed model, marks that model with the reason and lists recent switches below.

Switches exist only with fallback models configured. A failure shown to the user without a switch is not recorded here.

Writes reread the session store through get_branch. Nothing is buffered in the process, so a restart loses nothing and every message keeps a stable ID. Only user messages and assistant replies count: tool calls and results, runtime-scheduled turns (subagent reports, branch-merge notices) and empty messages never enter memory.

Five write steps

One pass, under a cross-process write lock. The threshold decides whether a model is called, not how much one call writes.

  1. Select every branch message without a written marker, minus tool calls and runtime-scheduled turns (runtime.pending()).
  2. Batch from the oldest message up to the token threshold. The rest waits for the next pass.
  3. Edit: the writer gets the batch text and the directory structure, and edits topics/ in staging.
  4. Organize after 5 batches or 40,000 tokens, and again once a day has passed since global organization with new commits. Skipped otherwise.
  5. Commit the transaction, then mark the nodes. The batch stays in chat history; footnotes link its messages, so nothing is copied.

Why this order
  • The baseline is read before copying: read later, an edit would compare with itself and lost block IDs would go unseen. The second attempt after a rejection takes a fresh baseline for the same reason.
  • A second rejection keeps the turns pending and the markers unset. Reporting success would let the caller pass content never installed.
  • Human edits of Topics use the same staging and validation; invalid ones are rejected at once.
  • Every install records each Topic file's hash, its block IDs and its origin in installed.json in the runtime directory: runtime for a file one of our transactions wrote, or one edited elsewhere that kept every ID we installed; outside for a file that appeared without us, or lost IDs we installed.
  • A file never recorded is ours only when every paragraph cites a chat message. ownership.outside_paths reads the record at every stage, so the rules in Files written outside OpenProgram act on it; paths compare case-folded on macOS and Windows.

Written markers: identity, not position

A session is a graph. Re-asking, retrying or spawning a subagent makes a branch. Each branch's messages enter memory; shared prefixes do not enter twice.

AspectRule
WhereNode metadata, key WRITTEN_NODE_MARKER in writing.py. The value names the memory workspace, so exported sessions keep markers without passing for another workspace.
WhenAfter the transaction installs and the pass changed files. A crash between the two leaves no marker and the same batch pending. Marking first would lose turns silently.
PrefixBranches need no ordering: the first writer marks shared messages; the next walk stops there.
AssumptionTraversal treats markers as a prefix, which relies on each batch taking the oldest turns.
Session storeMarkers must not change updated_at, which the idle watcher reads, and do not use the mark-synchronized path.
CostOnly the current batch is marked. Rescanning would make Git growth quadratic, since the session directory runs git add -A per turn and a changed node is a new blob. The session-index rebuild measured 14–50 ms for 289 nodes, 4.2 MB.

The resident block

Core is the block injected at each session's start: the core section of MEMORY.md.

AspectRoleSize
topics/core.mdSource of truth; writers and nightly organization edit only thisNo limit
Rendered core sectionRebuilt after each install2,000-token budget (core_max_tokens)

The budget limits rendering, not writes. A block past the budget is left out of that injection, stays in the source and remains reachable through search and memory_get. To keep a paragraph visible, move it earlier. An 11,883-token source blocks no write and renders 1,983 tokens.

Why a derived view

A write-path gate would stop stable facts and reject unrelated transactions once the file is full. Clipping a writable file could remove unique block IDs and fail validation; rendered IDs are always a subset of source IDs. Clipping also needs no human-versus-automatic split, because the full source survives.

The idle watcher keeps all of its bookkeeping in one file, ingest-state.json in the personal memory's runtime directory, because a conversation can move between projects. A failure is recorded at the scope of its cause:

A stop is written to that memory's writer status as not retryable, announced once per cause. The status keeps its fields: retries.max_identical_failures is the three tries. With a bad sign-in and twenty idle conversations, an hour of polls makes one model call, where it made twenty and gave up on all twenty. Entries read from the replaced files come over unstopped: a sign-in or memory cause is dropped so the conversation is offered once more, any other keeps one try.

Files written outside OpenProgram

Whatever a Topic file holds is memory. Another tool's notes, a person's paragraph without a citation and a file the chat agent wrote with its file tools are all read, indexed and found. What differs is who may change them and how they are labelled.

Why this design
Sources by author, at commit
Compared: the parser requiring a footnote in every file, against the commit checking who wrote what. A format rule on the read side let one file from another tool fail every write, which is how memory stopped growing.
Checked when written
Claude Code, Codex and Grok Build all check the writer at the moment it writes; our exact citations stay required of the automatic writers, where the execution policy depends on them.
Outside files read-only in place
Compared: rewriting them into our format, copying them into an inbox (Codex's ad-hoc notes), and reading them in place. Another tool rewrites its own files at any time, so IDs and links we add break; a copy diverges and duplicates. Reading in place is the only option with neither.
Ours by the set of IDs
Judging "still ours" by the set of IDs, not their order, covers an editor that reorders paragraphs.
No repair agent
A repair could never succeed on another tool's prose, since no chat message stands behind it, and it ran 127 times against 36 writes in the measured period. Once format no longer decides what is memory, nothing needs holding aside.
Origin labels
"No source" says what is missing, not where a paragraph came from; the reader and the model need to know how far to trust it. The origin is derived from installed.json and the footnotes, so nothing new is stored.
Map redrawn at installs
Compared with throttling the memory note (every 10% or every 5 turns), which no peer does. Tying the list to our own installs means the memory section changes at most once per write, the rate the writer already changes the map at, and search finds a new file the moment it lands.
First-seen day, not modification time
Copying, syncing and formatting move a modification time, so the same sentence would change days. The day we record is stable and honest: it says when memory learned it, labelled "recorded", apart from the event dates of cited paragraphs.
File tools left alone
Grok Build routes them into its memory policy because its organizer owns every topic and would overwrite them. Ours leaves outside files alone, so a direct write is already safe, and requiring citations there would give the model a failure Write and Edit cannot avoid.
Unstable derived IDs
A stable ID could only live in the file, which the read-only rule forbids; outside paragraphs are never link targets, so only a one-off reference in a chat is affected, and falling back to the file serves it.

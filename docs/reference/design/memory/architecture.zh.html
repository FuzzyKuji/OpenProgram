记忆机制

从对话到长期记忆

入口触发调用效果
每轮结束runtime/conversation/turn_runtimewrite(session_id=…)一次写入，且累计到 memory.writer.trigger_tokens 才动手（8000、16000 或 32000，默认 16000）
会话空闲state/memory/session_watcher：每 5 分钟扫描，30 分钟算空闲write(…, force=True)一遍遍写到没有剩余。会话结束后不会再有下一批。
每天 03:00state/memory/scheduler；手动 openprogram memory sleepreorganize(model=…)整理磁盘上的 Topic，不增加内容

写入通过 get_branch 重读会话存储，进程里不缓冲，所以重启不丢内容，每条消息的 ID 也稳定。只算用户消息和助手回复：工具调用与结果、运行时调度的轮次（子 Agent 汇报、分支合并通知）和空消息都不进入记忆。

写入五步

一次写入，全程持跨进程写锁。阈值决定要不要调用模型，不决定一次写多少。

  1. 选取分支上没有已写标记的消息，排除工具调用和运行时调度的轮次（runtime.pending()）。
  2. 分批：从最早的消息累计到 token 阈值，其余留给下一次。
  3. 编辑：写入器拿到这批原文和目录结构，在暂存区里改 topics/。
  4. 整理：满 5 批或 40000 token 时整理一次；距上次全局整理满一天且有新提交时再整理一次。都不满足则跳过。
  5. 提交事务，再标记节点。这批内容留在聊天记录里，脚注链接到消息，不复制。
安装前的校验
规则行为
无引用正文Topic 规范化在清理空章节或空 Topic 之前，以 INVALID_TOPIC_FORMAT 拒绝实质性的无引用正文。changes、patch、编辑器和 CLI 的暂存编辑、写入器 shell 提交都走这项检查。带引用的原生和旧记录、真正的空 Topic 规则不变。
被拒绝时已提交的 Topic、Runtime 状态、revision 和 Git 历史不变。
安装前回调实例持有的可信回调在校验和暂存准备之后、文件移动之前记录自动保存或恢复历史。无效编辑不产生检查点；回调失败则不安装。有效编辑记录编辑前的精确快照和现有检查点期限。工具和请求文本无法提供这个回调。

事务：暂存、校验、安装

检查要求
格式Topic 可解析，每段都引用脚注
块 ID原有 ID 全部保留。段落可以改写、合并或移动。其他段落、Timeline 和关系靠这个 ID 定位段落。
链接跨 Topic 链接指向 #^ 块 ID，没有悬空
引用新引用指向可引用的消息
为什么是这个顺序
  • 基线在复制之前读取：之后再读，编辑就是在和自己比较，丢失的块 ID 发现不了。修复时重新取基线，理由相同。
  • 第二次被拒绝时，这些轮次继续待处理，不打标记。报告成功会让调用方越过没有安装的内容。
  • 人工编辑 Topic 走同一套暂存和校验，无效编辑当场拒绝。

已写标记：身份，而不是位置

会话是图。重新提问、重试或派生子 Agent 都会产生分支。每条分支的消息都进入记忆，共享前缀不重复写入。

方面规则
位置节点元数据，键是 writing.py 里的 WRITTEN_NODE_MARKER。值标识记忆工作区，导出的会话保留标记，也不会被当成另一个工作区的。
时机事务安装成功且这次确实改了文件之后。两步之间崩溃时不留标记，同一批继续待处理。先打标记会悄悄丢轮次。
前缀分支之间不需要先后：先写的分支标记共享消息，下一次回溯到那里停下。
假设回溯把标记当作前缀，这依赖每批都取最早的轮次。
会话存储标记不改 updated_at（空闲监视器读取它），也不走“标记已同步”的路径。
代价只标记当前批次。全量重扫会让 Git 增长变成平方级，因为会话目录每轮 git add -A，改动的节点是新 blob。会话索引重建实测：289 个节点、4.2 MB 用 14–50 ms。
为什么不用序号或 ID 集合

序号描述的是链表结构的一次展开，不是消息。

情况对序号的影响
同一消息走两条路径序号不同
同深度的不同消息序号相同
get_branch 过滤 rewind 轮次；压缩插入摘要节点同一路径两次读取也会变
存着位置 9五轮的分支被当成空；十一轮的分支只写最后两轮
方面节点标记记忆里存 ID 集合
待写内容回溯到第一个标记遍历分支，减去集合
存储现有节点上加一个字段每个线程一个文件，存全部已写 ID
增长无；每次读几个节点每条消息一项；读取要加载整张表
缺失一项回溯提前停下，更早的内容继续待处理恰好那一轮重新待处理
耦合记忆往会话存储写字段，来源、显示类型、分支根和 rewind 状态本来也在那里记忆自管文件、迁移和永久保留

九个框架里，三个存分支对话（Claude Code、OpenClaw、pi-mono：带父指针的只追加文件），三个是线性的，一个重试时重写整个会话并毁掉旧分支，两个不存对话。没有一个把轮次标记为已被记忆消费。

框架做法
Codex分叉成新文件；提取用线程级水位和租约
pi-mono记录不可改；标注和游标移动追加引用，分支摘要在切换时从树上算覆盖范围
Claude Code游标放在进程内存里；引用的消息找不到时重新处理整个会话
OpenClaw在派生记录上写 promotedAt；记忆 hook 把最后十五行当扁平列表读

常驻块

Core 是每个会话开始时注入的块，即 MEMORY.md 的 core 部分。

方面角色大小
topics/core.md权威来源；写入器和夜间整理只改它不限
渲染出的 core 部分每次安装后重建2000 token 预算（core_max_tokens）

预算限制渲染，不限制写入。超出预算的块只是这次不注入，仍留在来源里，能通过搜索和 memory_get 找到。想让某段可见，就把它往前移。11883 token 的来源不阻塞任何写入，渲染出 1983 token。

为什么用派生视图

写路径上设门，文件一满就挡住稳定事实并拒绝无关事务。裁剪可写文件可能删掉独有的块 ID，校验失败；渲染出的 ID 永远是来源 ID 的子集。完整来源还在，裁剪也不用区分人写的和自动写的。

Web、Writer 和 Organizer 中的 Core
位置要求
GET /api/memory/core在工作区锁下读完整快照。content、size、mtime 指来源；另外返回渲染内容、考虑 memory.core.inject 后的实际注入、开关、token 数和预算。
记忆页 Core默认显示只读的实际注入内容和 token 预算，关闭注入时显示为空。Source records 可编辑，通过 compare-and-set 事务保存。保存期间输入的草稿不被刷新覆盖。预览共用一个净化器。
Writer 提示词读全部内容，只记之后有用的事实：不记重复的状态检查、没变化的测量、一次性工具过程和能从项目文件找回的细节。项目进展进该项目的 Topic，不进 Core。
Organizer 提示词在 topics/core.md 里把项目相关、过期或重复的内容移到 Topic 或删除，只留多数未来会话需要的规则、偏好和身份事实。删除的内容留在 Git 历史。

九个接口方法

记忆和 Agent 运行时之间唯一的接口，在 state/memory/backend.py。除 name 外都有默认实现。

方法时机运行时调用方
name标识后端作为属性读取
is_available()这个后端能否启用就绪检查和渠道 provider 路由
system_prompt(tier=…)会话开始：把 MEMORY.md 包进 memory-context 注入，与用户输入区分已接入
search(query)每轮之前；默认 BM25，取前 5，时间预算紧已接入
write(…)每轮之后和空闲时，只有 force 不同已接入
reorganize()每天 03:00 和 openprogram memory sleep已接入
initialize(…)会话开始时一次只有策略包装层转发，运行时不调用
extract_before_discard()压缩时询问摘要该保留什么；不存储只有策略包装层转发，运行时不调用
shutdown()最后一轮之后；现在由空闲监视器通过 write(force=True) 收尾只有策略包装层转发，运行时不调用

三个未接入的方法是扩展点，留给需要连接、最终刷写或压缩前保存的第三方系统；内置后端不需要。召回文本在产生处就包好 <memory-context>。没有工具注册方法：带工具的记忆系统就是插件。

失败行为

write() 返回情况空闲监视器
无返回已写完，或低于阈值标记已处理，下次轮询跳过
失败，可重试锁被占；Git 提交失败；向量后端、模型或写入进程不可用不标记，下次轮询重试。数据还在会话存储里。
失败，不可重试两次编辑都被拒（COMMIT_REJECTED）；来源不可用或 patch 无效；没有 session ID标记已处理并发布 memory.ingest_ended（ok: false）。内容相同，结果相同。
规则细节
无返回即成功忘了 return 也是无返回，反过来解读会无限重试
失败封闭的 MemoryWriteFailureCode 集合；未分类的异常不重试
每轮路径在 debug 日志记下待写内容，下一轮重试
锁竞争算失败，不算未达阈值
对话记忆失败不会让对话失败：每个 hook 自己捕获并记录异常

分支处理

情况现状缺口
其他分支强制的边界写入先写 head，再写其他未归档分支端点；标记给前缀去重。一轮之内只写 head。由空闲监视器触发，不由 head 变化触发
互斥分支一条分支用 Flask，另一条用 FastAPI：同一 Topic 里相邻两段Topic 格式表达不了互斥；检索两条都返回，整理还可能合并
跨会话派生两半各自记账，不丢不重。同一会话内的派生分支共用节点标记。没有链接说明一半是另一半的延续
压缩摘要成为 head通常是侧分支，接在第一条被摘要轮次的前驱上head 移上去时，摘要算未写的助手轮次，同样的事实换措辞再写一遍

统一修改接口

两种表达，一条路径：Runtime 暂存、规范化、引用和关系检查、重建 Timeline/Recent/Relations/Core、原子安装、Git。安装后 Git 失败不假装回滚：结果带 memory_committed 和 git_committed。

结构化操作

操作必填Runtime
create_record最终内容、时间（模型 schema 用 undated，owner REST 也接受 null）、非空 sources[{source,label}]、destination（topic_path、headings、position）校验 Topic、位置和每条新引用；原样保留 label；分配块和证据 ID
update_recordmemory_id 加完整的最终内容、时间、来源替换段落和证据定义；块 ID 和位置不变
delete_recordmemory_id删除记录和不再使用的证据；有块链接会悬空时整体拒绝
move_records有序非空 memory_ids，同样的 destination按给定顺序移动，保留 ID、内容、时间、引用、创建顺序
来源和标签
字段规则
source聊天链接 /s/<session>#<message>、它的 ref openprogram/<session>/<message>，或表示本轮用户消息的 current。没有来源的记录引用这条消息。source_refs: [string] 接受同样的链接。调用方不能提交来历或 owner 身份。
label这一条引用的显示文字，在同一次写入调用中生成。提示词和 schema 要求简短、贴合上下文的关键词，不含 Markdown、URL、ID、发言人名字或时间模板。Runtime 只要求非空字符串，不截断不改写。
输出{"content":"…","sources":[{"source":"/s/session#message","label":"研究范围"}]} 变成 [研究范围](/s/session#message)。解析器读链接目标，不读显示文字。
旧工作区带旧 sources/ 副本的工作区由 store.cite_chats_directly 转换一次。
位置、组合和冲突
主题规则
位置start、end、before、after。锚点需要 anchor_memory_id，在目标 Topic 和标题链内，不在移动集合里。每个 ID 最多一次内容操作和一次移动；删除和移动不能针对同一 ID。
组合合并：一次更新、若干删除、按需移动。拆分：一次更新、若干创建、按需移动。没有 merge_records、split_record、place_records、reorder_records。
清理Runtime 删除没有记录的标题链和 Topic 文件。
旧记录mem_* 保留 ID。共用一个物理段落的所有 ID 按段落顺序连续地一起移动。
证据冲突跨 Topic 同一证据标签但时间或引用语义不同：整体以 INVALID_ARGUMENT 拒绝。只是相对路径不同不算冲突。
旧输入早期 create、update、delete 输入会被转换；schema 只暴露四个名字。
Scheduler本地 owner 的提示任务可调用 memory_search、memory_get、memory_update；服务不双写。已删除的 memory_id 返回 NOT_FOUND，不留占位。
模型范围交互模型、写入器和整理器可以改写、合并、拆分或删除。删除块要在同一事务里修好指向它的链接。已提交的引用不复查。
检索BM25 有带版本的磁盘缓存，按 Topic 文件签名复用进程内索引；embedding 复用解析结果和向量。时间、大小或 inode 变化即失效。

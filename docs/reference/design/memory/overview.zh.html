说话者如何传递
方面规则
来源openprogram/interfaces/channels/base.py 是 dispatch_inbound 的唯一调用方，把 speaker_id 和 speaker_display 经 TurnRequest 与 dispatcher 准备阶段传入用户节点元数据。每个渠道回合都带：scope 在 base.py 之下才解析。
标签display (id)，来自 ChatTurn.speaker_label：名字好读好搜，ID 经得起改名并区分两个 Ada。折叠空白，去控制字符，替换方括号和冒号，每部分 64 字符。
在线 Agent一个 JSON 信封（authority.render_model_input）：speaker_kind、speaker_id、speaker_display、content
写入器每物理行一个紧凑 JSON 对象：ref、speaker、不可信的 content。json.dumps 加 U+2028、U+2029 转义，保证一回合一行，解码可还原原文。
peer_id只是路由目标；群里就是群
Web、CLI、TUI没有说话者
正文绝不清洗，含旧文本开头存有的标签：清洗行首会改写链接、清单、日志和代码里的 [，也没有规则能区分 [2026-08-09] INFO ready 和伪造标签
同类框架openclaw 和 hermes-agent 只在正文前放文本标签，记忆里没有发送者字段，伪造第二个标签同样有效：openclaw 清洗头部但原样传递正文，hermes 两半都直接插值。见说话者身份。

夜间整理

写入只会让文件变长；每个主题一个巨型文件，排序和计数问题就无从回答。

方面规则
覆盖个人工作区、可写的 Agent 空间、本机有记忆的所有已注册项目。openprogram memory sleep：手动运行，不含 Agent 空间。
拆分每个标记超限的文件拆成子文件，段落保留 block ID

顺序每个超限文件从大到小单独运行，再跑全工作区；一次跑完全部会在靠后的大文件之前停下

两个上限，同一提示词实测

校验每次写入

memory.writer.verify（默认关）测试每个提交的批次，因为事实可能落在没人会看的地方。至少三次模型调用，修复再加三次。

步骤做什么
1. 出题模型选一个事实：JSON 问题、预期答案、聊天引用；引用批次外内容被拒绝
2. 检索一次全新运行从不含运行目录的临时副本回答
3. 判定模型比较答案与预期
4. 修复不一致时，一次运行带着问题、答案和失败轨迹，通过普通事务整理真实工作区；第 2、3 步再跑一遍
结果
passed、repaired、unrepaired、error，见 .scriptorium/verification.jsonl（最新 500 条）和 openprogram memory status 的 verification
绝不
让所跟随的写入失败

output_schema 是写入器运行时的约定：OpenProgramAgent 把 schema 加进系统提示，从回复中读取一个 JSON 对象（裸的、围栏的或夹在句子里的），检查必填字段和 JSON 类型。回复缺失或格式错误时共尝试三次。

写入是事务性的

拒绝、锁和自动保存
规则说明
整批被拒的原因引用不存在的消息、定位不存在的记录、链接不存在的块、破坏 Topic 格式

锁.scriptorium/write.lock，跨进程
自动保存与恢复历史准备经实例自有的回调，在校验和暂存准备之后、文件移动之前运行；绝不是工具参数或请求值。被拒的编辑不产生检查点，回调出错不安装任何内容，有效的自动保存保留编辑前快照和检查点期限。

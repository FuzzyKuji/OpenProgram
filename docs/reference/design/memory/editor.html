Reading, editing and history

ActionBehaviour
OpenA topic or Core source record shows rendered Markdown, with its footnotes and links. Controls: Preview, Edit, History.
EditSource text. No Save button.
SaveEach edit goes straight to local draft storage and through a writer serialized per file. A reply never marks newer typing as saved.
Undo, redoIndividual edits, across automatic saves
HistoryNewest first, 50 at a time, with local date and time and commit message. Older entries load on demand.
Select a revisionLines added and removed against its parent
Restore this versionCommits the current state, then a new commit with the chosen document. History is kept.

Git checkpoints

Manual edits are grouped into five-minute checkpoints. The first edit commits memory: before manual editing and records a durable deadline, so the pre-edit state survives even if it was written outside the UI. A server-owned task checks the deadline every 15 seconds and commits memory: manual editing checkpoint, also when the page has closed. Restarts resume pending deadlines.

Data and failure handling

CaseBehaviour
Write pathStaged write: validates references, rebuilds derived views, commits Git history, renders Markdown as before. Source validation is unchanged.
Stale editSubmitted base_content is compared under the write lock; a mismatch is rejected and the draft kept with an error.
NormalizationThe reply returns canonical saved text, because normalization may alter source.
Status shownErrors and Git warnings inline only; no saving or saved indicator.
Navigation, reloadDrafts survive locally.
AccessOwner-authorized endpoints read bounded Git history restricted to topic Markdown. Path and revision inputs cannot escape Memory; a revision must be a full commit id.

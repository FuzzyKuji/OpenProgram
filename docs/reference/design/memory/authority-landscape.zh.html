本地界面和 Telegram、Discord 等渠道共用一个 Agent 和记忆工作区。规则见设计。

未配对的私聊收到 8 位配对码，一小时一次。未配对的群消息被忽略。改名冒充 owner 没有用。

消息到达后的顺序

  1. 渠道入口。发言人 ID 和显示名来自平台元数据，不来自消息文本。
  2. 配对。查稳定 ID，未配对的消息到此为止。批准只来自本地 CLI 或回环 Web 请求。
  3. 归因。speaker_*、owner principal 和 authority_tier 作为独立字段持久化。
  4. 能力。_gated_execute 查固定表，规则和 bypass 跳不过。
  5. 执行或记忆。工作区强制已配对的 memory_update 只能新建或按字节追加。

系统机制采用不同
OpenClawsrc/pairing/pairing-store.ts8 位配对码，不含 0O1I，一小时过期，每渠道账号 3 个待处理。未知私聊不处理。私聊准入、命令 owner 和群授权是分开的状态。配对常量、稳定 ID 授权、进 Agent 前拒绝这里配对还确定工具档位，绝不等于 owner
Codexcodex-rs/memories/README.md提取用租约和退避认领有界 rollout 任务。单一写入者整合并记录结果。线程级水位，同一会话图内没有分支来源。有界批次、单一写入者、失败分类不要任务数据库：已有节点标记、Source 引用和工作区 revision
Hermes Agentagent/memory_manager.pysync_all 在一轮后调用所有 provider；MemoryProvider.on_session_switch 通知切换。没有持久的待处理游标。统一 provider 入口、轮后触发模型写入在 token 阈值或空闲时运行，不是每轮
OpenCode、pi-mono、WeClaw没有对等的长期记忆流程。pi-mono：只追加的 label 和 leaf 记录。OpenCode：线性消息，用 revert 管尾部。WeClaw：下游会话 ID 或有限的进程内历史。pi-mono 用稳定节点 ID 做关联记录都没有同时具备可信 Source、Topic 事务、回填和写入器状态
决定设计
采用稳定 ID 准入、固定能力表、统一写入入口、持久状态、有界回填
改造：OpenClaw 的回填和状态回填只选没有 Topic 引用的可信 Source。状态在本地只读统计，不加载模型，不修复。
拒绝独立任务数据库、每轮同步、回填预览里的外部归档：文件锁和现有记录够用，模型只在阈值或空闲时运行，外部归档不进可信综合

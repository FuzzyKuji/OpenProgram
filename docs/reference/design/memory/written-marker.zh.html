记忆如何知道哪些轮次已写入

会话是 DAG：重问、重试、派生都会分叉。每条分支都要进记忆，共享前缀只进一次。“已写入”记在该轮次自己的节点上。

标记

{"id": "a3f1c2", "role": "user", "predecessor": "9d0e77",
 "metadata": {"memory_written_scriptorium": "w-4f21c8e0"}}
部分原因
键名含 provider记忆接口可插拔，共用布尔值在出现第二个 provider 时就错。这个名字是历史遗留，保持不变：改了会让已标记节点失效。不能和消息字段重名，因为 _node_to_msg 把 metadata 展开到顶层。
值是 workspace会话目录自描述，靠复制迁移。回走只在遇到本 workspace（store.workspace_id()）或 project_layer.written_elsewhere() 里的 id 时停，所以恢复备份保留标记，从别处复制来的会话从头写。一轮只写进一层，切换项目写入开关不会复制对话。
写入方式SessionStore.merge_node_metadata_batch，经 SessionLog.patch_node 每节点一条 node.patch 日志记录

哪些轮次未写入

步骤规则
过滤writing._records：只取可引用发言者的 user、assistant 文本；工具行和运行时调度的轮次根本不进入，自然被跳过。没有稳定 id 的行抛错。
回走online.unwritten_turns：尾部无标记的连续段，旧的在前
分批_first_batch：取开头够阈值的轮次，一天的积压分多次写
每轮conversation/turn_runtime 的 _memory_write：以 head 结尾的分支
会话边界session_watcher（每 5 分钟轮询，空闲 30 分钟）强制 write：head 分支优先，再短也写；其余来自 list_branches 的存活、未归档尖端，未写文本够阈值才写

should_incremental_write 的空闲放行不适用于被放弃的尖端：它们的最后一条消息必然旧，否则每次重试都会被放行。被回退的轮次到不了这里，get_branch 已滤掉。

什么时候标记一批

写入器结果审计判断这一批
改了主题文件_changed_files：有 status == "ok" 的 commit 条目标记
判定没有值得保留的_declined：有收尾的 agent 条目，且 Write、Edit、shell、commit 无失败标记。不标记会永远返回，并显示成 WRITER_NO_PROGRESS。
其他闭包返回 None不标记，重试

没报错不等于有产出。实测：二十轮耗在同一个被拒的编辑上，返回成功，主题文件只有一个字节。

  1. 以事务安装主题文件，要么全装要么不装。脚注直接链接聊天消息，不复制证据。
  2. 标记这一批。两步之间崩溃就是重做；反过来会静默丢轮次。

标记丢失与账本损坏

宁可重做，不可沉默。读不了的 runtime.json 按空状态加载。一路没遇到标记就交出整条分支；写入器能看到已有主题文件，已知事实保持或合并。

旧的 cursors 字段被忽略，也不从它派生标记：它的序号正是被分叉弄坏的值。升级后的会话多一次较大的写入。

标记对会话存储的代价

关注点事实
记忆版本workspace_revision 只哈希记忆 workspace，与 chats 不相交，标记不会被当成并发记忆写入
索引缓存其他进程重建一次索引：289 节点、4.2 MB 用 14–50 毫秒（实测）。mark_synced 避免重复
日志增长每个被标记节点一条记录。只标记这一批，不扫全会话，否则随会话长度平方增长
不能动 updated_at空闲监视器比较这个精确值；动了会强制写入并调用模型。所以不走 append_message 和 SessionNodeWriter.append
不能把别人的写入算成已同步_open 先重建过期索引；_mark_own_write 只吸收本进程自己的追加

为什么用标记

为什么不用位置游标

每会话一个序号，和分支展平后的行位置比较。序号描述的是展平结果，不是消息：同一消息在两条线上有两个号，同深度的不同消息共用一个号，rewind 或压缩还会让后面的行全部移位。它也数记忆跳过的行，所以下表是实测。

从 m3 分叉，存储序号 9行数（共享 + 自有）游标交出标记交出
短5（3 + 2）0自有 2 轮全部
长11（3 + 8）最后 2 轮，并把全部记为已写自有 8 轮全部

长分支更糟：写入一段从对话中间开始的碎片，还报成功。单调计数器退不回分叉点，它和分叉对话本来就是两种形状。

为什么不在记忆旁存 id 集合
节点上的标记id 集合
找未写入从尖端走到第一个标记走完整条分支再减集合
分叉时共享前缀已标记，回走停止前缀 id 被跳过
存储现有节点上一个字段每线程一个文件，存所有写过的 id
增长无每条消息一项，保留到会话结束
一次读取从尖端走几步该线程的整张表
迁移无：整段重交一次无：集合从空开始
丢一项回走提前停，更早的轮次被搁浅该轮次重新交出
耦合记忆往会话存储写一个字段记忆自己记账
  • 集合更精确：回走假设标记构成前缀，批次从旧到新使其成立，但没有校验。
  • 决定选择的是集合的代价：会话本来就按节点记录轮次来源和是否被 rewind 退役。
  • 指向轮次的标记节点（pi-mono 的形状）则会每批往图里加一个节点，所有读者都得跳过。
其他 agent 框架的做法

references/ 下七个框架有答案；claude-code/ 只有一个工具，没有会话代码。

框架形状记忆记录分叉时
codex-cli每 rollout 一条线；分叉即新线程按 rollout 抽取，再整合memories_1.sqlite 按 thread_id 存 jobs.input_watermark、last_success_watermark 和租约新线程无记录：前缀抽取两次
openclawDAG，id/parentId，一份 JSONLdreaming-phases、short-term-promotionsession-ingestion.json 的 lastContentLine 和 seenMessages；派生候选上的 promotedAt新文件从第 0 行：前缀摄入两次。重试改哈希并重扫
hermes-agent每会话一条线，存 SQLite；/branch 复制行MEMORY.md/USER.md，八个 provider记忆没有：每轮 sync_all。SQLite 用 _last_flushed_db_idx各分叉点手工重置基线；八个 provider 有七个没实现 on_session_switch
pi-monoDAG，只追加；label、leaf 条目无分支摘要在导航时走树没有可过期的东西
opencode线，SQLite seq无—revert 后下一次提问删除之后的消息
pi-ai无状态客户端无—无分支
weclaw缓存下游 id；HTTP 保留 20 轮无—无分叉
  • 没有人把记录放在轮次上。openclaw 的 promotedAt 最接近，但在派生记录上。
  • 实际只有两种形状：把单位放粗到分叉无所谓（codex-cli、openclaw、hermes-agent），或从树上算增量（pi-mono）。放粗就放弃了从活会话写入。
  • 它们分叉时的故障是重复，夜间整理能合并。位置游标的故障是遗漏，没有东西能补回。
  • 借鉴：宁可重做，不可沉默。位置丢失时全部重数，因为数出零会让后续抽取永久停止。

Tool guides

Every schema ships in every request, and long schemas are read less carefully. A tool keeps a short schema; the agent loop delivers its other instructions into tool results. Single-entry tools use this: one tool, a few parameters, the instructions for each target or action on first use. Codex computer use and Claude Code skills are the same progressive disclosure.

Declaring

guides.register("self_update", [
    Guide("self_update", overview, mode="open", activates=("worktree_create",)),
    Guide("self_update.prepare", prepare_text, summary="parameters, iteration policy and verification plan",
          required_for=lambda args: args.get("action") == "prepare"),
])

open and included guides end with the index of the tool's applicable lookup guides.

Delivery

  1. _run_loop opens a view (guides.begin_loop). Outside a loop guides do nothing: direct Python calls and tests see plain results.
  2. Before each model request, _stream_assistant_response records the text being sent (guides.observe_request).
  3. Before a call is decided, prechecks.call_problem returns GUIDE_REQUIRED if a required_for guide is unknown: an ordinary tool error, no approval card. The model reads the attached guide and calls again.
  4. When a call ends, _rewrite_tool_result (guides.attach) puts due guides in front of the result, each wrapped in <guide name="…">.

A guide is known while its marker is in the last request's text, or it was delivered since. No ledger: compaction, microcompaction, a worker restart or a fresh agent removes the marker, and the next call that needs the guide receives it. An agent whose prompt already holds a marked guide is not sent it again.

help

help(name) is a resident tool that returns a guide, or a tool's opening guide for a tool name, marked like any delivered guide. No approval; runtime.control authority. An unknown name lists the guides. Inside computer_use_agent code, Python's help and dir work on the cu objects: each docstring is its action's line from the target guide.

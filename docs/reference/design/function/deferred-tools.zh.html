延迟工具

延迟工具已经注册，但它的 schema 要等 tool_search 加载后才送到模型。加载只有搜索这一条路。加载集合从请求自己的消息里读出；一个纪元之内，工具数组只在末尾增长。

Anthropic 上的加载

provider 在 provider.json 的 tool_search 下声明原生形式。Anthropic 为 anthropic-messages 声明 anthropic-reference，并带 models_off: ["haiku"]。

部分有这个形式没有
搜索结果只发 tool_reference 块；旁边没有文字块时补一个兄弟文字块 Tool loaded.；结果文字仍存在节点上供界面显示结果文字
数组已加载工具带 defer_loading: true，按第一次加载的顺序追加，定义取加载记录保存的那份已加载工具作为普通项追加；请求记一次预期断点 tool_loaded
beta 头advanced-tool-use-2025-11-20；Vertex 上 tool-search-tool-2025-10-19无
缓存指纹跳过延迟项；断点打在最后一个普通工具上不变
没有匹配、出错、摘要携带的工具普通文字结果；携带的工具是普通项相同
为什么这样设计
对比对象做法
Claude Code结果里放引用，数组里放 defer_loading 项；排除 haiku
Anthropic tool_addition在历史里公告工具；支持的模型和平台很少
Codex定义放在历史项 tool_search_output 里
Pi追加到数组；一次已知的重读
Hermes桥接工具；延迟工具永远不进数组

defer_loading 项只在被某个结果点名后才参与校验，追加它是允许的；追加普通工具或改写已有工具会被拒绝。Claude Code 在生产上用的就是这种写法；加载只剩搜索一条路，引用就能覆盖所有情况。

目录

可加载工具的列表是 turn_context 的 deferred_catalog 节，放在用户消息旁边。对话的系统提示里没有目录，所以对话中途连上 server 不会改动任何前缀字节。

规则取值
内建延迟工具只列名字
MCP server 或应用一行 namespace：N tools: a, b, …，截到 250 字符；已打开的应用会注明
全量列表没有基线时：第一轮，以及摘要后的第一轮
之后各轮Added deferred tools / Removed deferred tools；没有变化就不发
大小最多 4 KiB，先列名字，再数出省略了几个
基线渲染出的历史里最后一份目录
自带系统提示（Agent 方法、runtime.exec）目录仍内联在那份提示里
为什么这样设计
对比对象做法
Claude Code在 user 侧 reminder 里只追加名字；压缩后重新公告全部名字
Codexdeveloper 消息里按 namespace 发差量，每行 250 字符，上限 4 KiB
Pi系统提示里按 server 列一节，上限相同
Hermes嵌在搜索工具的描述里，按预算降级

只有放进历史，才不会改动已经发出的内容。turn_context 本来就只重发有变化的节。Anthropic 上不用 role: system 消息：Claude Code 在那里用 user 侧，而且有的模型不接受它。

Codex 没有匹配

情况发出的内容
没有匹配、名字不存在、出错tool_search_output 带 tools: []
对已加载工具做 select:再次返回它的定义，并记一次加载
为什么这样设计

Codex 自己的客户端对所有失败都发空列表，这是后端确定接受的唯一形状。Claude Code 和 Pi 返回文字，但那是在它们自己的线路上。模型可以对照目录核对名字。

guide 和应用

教授延迟工具的 guide，以及刚打开的应用，都以 activation_note 结尾：Tools for this: `a`, `b`. Load them with `tool_search select:a,b`. 两者都不加载任何东西；已打开应用的工具仍然是延迟的。

为什么这样设计
对比对象做法
Codex被明确提到的 app 的工具仍然延迟
Claude Code、Pi只通过搜索加载
Hermes只能调用搜得到的工具

只有一条加载路径，数组在每个 provider 上就只以一种方式变化，打开应用也不再重读前缀。代价是一次很便宜、会被记录的 select: 调用。

来源消失

事件给出的原因
应用关闭its application '<id>' was closed
owner 卸载'<owner>' was unloaded
MCP server 断开MCP server '<name>' is disconnected

这些工具离开注册表，目录发一条 Removed。已加载的工具保留数组项；调用它会返回错误 Tool <name> is unavailable: <reason>.。不发 tool_removal。

为什么这样设计

Codex 保留历史并回答 unsupported call；Anthropic 建议保留定义、返回普通错误。Claude Code 改写旧引用，这是一次历史编辑。数组从不缩小，就不会校验失败，也不会重读前缀。

加载前就调用

调用结果
参数合法执行
校验失败，未加载错误末尾加上 This tool's schema was not sent. Load it with `tool_search select:<name>`, then retry.
校验失败，已加载只有错误本身
为什么这样设计

这是 Claude Code 的 buildSchemaNotSentHint。拒绝所有未加载的调用，会让本来正确的调用白白多一轮。

模式和 deny 规则变化

纪元按 provider、模型和第一条消息确定（tool_epoch.epoch_key），所以摘要或换模型会开始新纪元。纪元的第一个请求把被扣下的集合随工具快照一起存下。

变化数组派发
进入或退出计划模式不变permission_decision 拒绝
计划模式之外的 exit_plan_mode不变拒绝，PLAN_MODE_NOT_ACTIVE
整工具 deny 规则、缺能力从下一个纪元起去掉期间拒绝
出现结构化输出 submit 工具带上它开一条新纪元记录—
为什么这样设计

Codex 在计划模式下派发时拒绝；Claude Code 拒绝计划模式下的调用，但把被 deny 的工具滤掉；Anthropic 建议不要原地替换工具列表。对话中途改数组，在会校验工具集的模型上会失败，而派发本来就检查权限。

排序

规则取值
排序器tool_rank，Pi 的 BM25：k1 1.2，b 0.75，名字权重 3，namespace 权重 0.5
索引内容名字、namespace（MCP server 或应用）、描述、hint、schema 属性的名字和描述
分词按 camelCase 和 __ 切分；去掉停用词；词干化；CJK 逐字切分
顺序精确名，其次命中的查询词个数，再次分数
保留select:、逗号列表、先应用的 +term 过滤、Agent 的允许范围；已加载工具也在内
默认个数5
为什么这样设计

Pi 和 Codex 用 BM25；Claude Code 用固定的关键词分值。Pi 的排序器把每条规则写清楚，能不加依赖地移植。每个命中都会被永久加载，所以默认个数用 Claude Code 的 5，而不是 8。

旧的搜索结果

在任何 provider 上，tool_search 的结果都不会缩成存根；工具输出完全不做老化（工具输出）。

为什么这样设计

Claude Code 的 microcompact 跳过 ToolSearch，Codex 从不老化。定义存在加载记录里，存根省不了多少，反而是一次历史编辑。

分支和嵌套运行

运行发给它的工具
两个分支同时运行各自消息里加载过的
嵌套的 runtime.exec它自己的加载；外层聊天看不到
被停止或失败的搜索不加载任何东西
为什么这样设计

Pi 把加载写进每个分支自己的状态。分支是并行运行的，所以加载不能是对话级的状态。

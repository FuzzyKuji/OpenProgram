Harbor 评测适配器

FrontierHarness Eval 这类 Harbor 数据集在每个任务的容器里给编码 agent 打分。scripts/benchmarks/harbor_agent/agent.py 让 OpenProgram 成为这样的 agent：在容器里装好 CLI，用 openprogram --print 执行任务指令，再把这次运行的 token 和费用交给 Harbor。openprogram 包从不导入它，Harbor 也不是 OpenProgram 的依赖。

方面规则
被测代码从一个提交构建并上传的 wheel，或一个已发布的 Git ref；二者必须且只能给一个。Git ref 必须以字符串到达：Harbor 把 --ak 的值当 JSON 读，读成数字的提交号会被拒绝，而不是被改写
安装以 root 用固定版本的 uv 安装，跑在 uv 管理的 Python 3.12 上，与任务自带的 Python 分开；任何 agent 用户都可读。必填的约束文件把每个依赖固定在该提交 uv.lock 的版本上，每次试验跑的都是同一份代码；装上的版本写进试验日志。镜像缺 curl 时才装 curl。同一份安装按提交打一次包，x86_64 glibc 镜像改为直接解包：几秒钟，不联网
密钥Harbor 按 -m（或 --api-key-name）从主机取得；只交给运行命令，用服务商自己的变量名（OPENAI_API_KEY；--ak key_env= 指定别的名字）。不登录，也不存。没有密钥时任务在任何试验开始前就停下。运行结束时状态里发现的凭据会删掉
模型-m 就是 OpenProgram 的 provider/id；Harbor 和 OpenProgram 的服务商名不同时用 --ak provider= 改名
运行以任务的 agent 用户、在镜像的工作目录运行。指令经 stdin 交给 --print=-，不会被当成参数；stdout（事件）和 stderr 写进不同的文件。工具轮数不设上限；需要批准的操作直接拒绝；关闭 core 文件，进程中止时不会在评分目录里留下东西
运行说明每次请求在指令旁告诉模型没有人在看、要把任务做到底；这段话只出现一次，每轮字节相同，服务商的缓存因此一直命中。在 Linux 上 shell 命令读 /proc，镜像里没有 ps 也能运行
请求和产品里一样：系统提示词带工作目录和 shell，工具列表见下一行。第一条用户消息在指令前带上日期和运行说明；容器里的新主目录没有记忆，所以不发记忆地图。不同日子的运行之间只有日期不同
工具产品默认的 27 个已加载：文件和 shell（bash、read、write、edit、apply_patch、glob、grep），后台任务，子 agent 和 goal，todo 和提醒，四个 MCP 工具，tool_search，在 macOS 主机上还有 computer_use_agent。另外 31 个（包括 web_fetch、web_search）放在 tool_search 后面。子 agent、goal 和提醒都计入成绩和花费。--no-web 去掉所有网页工具和服务商端搜索。这是在 macOS 主机上抓到的，Linux 容器里的列表还没核实
工作区--no-project-binding：评分的工作目录里什么都不写，也就没有要清理的标记
失败退出码非零、没有用量摘要，或摘要不是 completed 且至少一次模型请求，试验都算失败。错误类型只看用量摘要，从不看运行的输出，因为输出里是模型的文字。被服务商终止的运行，不论在本轮开始前，还是本轮中 OpenProgram 自己的重试用完之后，都按原因上报（鉴权、限流、服务端、网络、未知模型），因流空闲上限结束的回合报为响应停滞，不论服务商的读取方用什么字眼说。先查 --print 在捕获异常处记下的分类（error_kind、error_reason）；没记的构建，或原因分不出是断连还是停滞的，才读错误的字眼。其余失败都是普通的非零退出，算 agent 的
超时Harbor 的 agent 超时结束运行时，OpenProgram 收到 SIGTERM：取消本轮，最多等 30 秒让它停下（再来一次信号就从取消起只等 2 秒），写出用量摘要和记录，以 143 退出，不论后来的信号何时到
收尾每次运行之后，不论怎样结束（成功、失败、Harbor 超时停止之后）：把 agent 主目录里 OpenProgram 的状态拷到试验的 agent/openprogram-state/，不含 auth/ 和 cache/，然后删除凭据；命名 profile 的状态同样拷到 openprogram-state-<profile>/。只要还留有凭据，这一步就失败。以 agent 用户执行，因为状态在它的主目录；失败只记日志，不会顶替运行本身的结果
重建接着，运行没留下转录时（被直接杀掉或内存耗尽），openprogram transcript 用 --transcript-file 的同一段代码从运行留下的状态生成它。已有的转录保留不动。顺序固定：停止，拷出状态并删掉凭据，重建
退出除这一轮外不发模型请求（标题、分支名、话题归类），也不交给记忆，因为超过阈值后那就是一次模型运行；对话由下一个 worker 的空闲扫描写入记忆。
停止后离开命令等的是回合结束时设置的事件，而不是它的线程：在 Python 3.12 上，信号打断 Thread.join 会把仍在运行的线程标成已结束。等待结束时仍未停下的回合，它在等的命令先被停掉，因为每个命令都在比进程活得久的监管进程下运行；然后进程不走解释器的退出流程直接离开
后续信号只有第一个信号会被抛出，它的处理函数把之后的接住。停止期间记下的信号在文件写好后让进程离开，解释器等线程时来的立即离开，从退出回调起一律忽略，所以退出码保持第一个信号的值（SIGTERM 为 143）
证据--transcript-file 按存储的样子写出这一轮，每条记录一行 JSON：每次模型请求的时间和 token，推理、回复文字、带完整参数的工具调用，以及每个工具结果和时间；不脱敏。它在主机上转成 Harbor 的 trajectory.json（ATIF），每次请求一步，供 harbor view 查看
被直接杀掉进程被直接杀掉时两个文件都不会写出；它的转录从状态重建（见“重建”），状态副本里有带本轮日志记录的会话日志，和记着每次请求 token 的用量账本
工具结果每个结果取自会话日志里本轮的日志记录；日志记录里没有的才退回存储里 4,000 字符的预览，complete 为 false
结果大小输出就是模型读到的结果：最多为模型的工具输出权重（默认 10,000，CJK 字符算 1，其他字符算 0.25）或其窗口的 30%，全文存进文件，模型用 read 翻页读取；shell 工具对很长的输出只留结尾，并说明丢掉了多少字节
网络上报 Harbor 登记的服务商公共 API 主机，白名单任务据此放行

全量运行

scripts/benchmarks/frontier_eval.py 运行一个评测目标：scripts/benchmarks/targets/ 里的一个文件，写着一次评测的全部方法，每一项都注明出处。可比性来自同一个任务里的对照 harness，而不是别的条件下发表的数字。

目标任务 × 尝试模型、强度对照
fh-v1-tb21（默认）FrontierHarness v1 的 21 个 Terminal-Bench 任务（terminal-bench@2.0）× 3；重试 2 次；公布的是每个任务第一次有效尝试的通过率gpt-5.6-terra，mediumCodex 0.148.0
fh-v1.1FrontierHarness v1.1 固定的 62 个任务 × 4；重试 2 次gpt-5.6-sol，mediumCodex 0.148.0
tb2Terminal-Bench 2.0 的 89 个任务 × 5；不重试；不接受任何超时或资源覆盖gpt-5.6-terra，mediumCodex 0.148.0
  • 任务：OpenProgram 和对照 harness（Harbor 自带的适配器，固定版本，给定目标的推理强度）用同样的任务、模型和网络。Harbor 0.25.0、目标的重试策略（由启动器执行）、它公布哪个通过率、它认为可比的环境（Runta）和价目表都写在文件里。
  • 时间上限：沿用每个任务自己的 agent 超时，这 21 个任务是 600 到 1,800 秒，和 FrontierHarness 一样。它的脚本还把一个任务的整次 harbor run -r 2（含重试）限制在 5,400 秒。Harbor 没有这种上限，所以汇总数出保留下来的试验里超过它的；被删掉的重试，其时间不在其中。
  • 偏离：换模型、减少尝试、只跑部分任务、设超时上限、设 agent 环境变量、不带对照、不可比的环境或别的 Harbor 版本，每一项都写进运行记录，并标 methodology_comparable: false。
  • 强度：两个 agent 都按目标的推理强度运行，OpenProgram 经 --print --effort 拿到；启动器的 --effort 给两边换一个强度，算偏离。--print 不接受 --effort 的构建按 Agent 的默认值运行，也算偏离。
  • 网页：目标的 disable_web_search（所有目标都是 false，和已发表的运行一样）为 true 时同样交给两个 agent，并写进运行记录。
  • 试点：run --pilot 只跑目标的 8 个试点任务，记为偏离。名单按 FrontierHarness v1 每题的通过比例分三层固定：难（0.2 及以下）kv-store-grpc、dna-insert、extract-elf；中（0.3 到 0.5）chess-best-move、gcode-to-text；易（0.8 及以上）regex-log、sanitize-git-repo、build-cython-ext。
  • 检查：Docker、实际找到的 Harbor 版本、密钥、剩余磁盘。
  • 构建：用 git archive 从一个提交构建 wheel 和约束文件，所以未发布的提交也能用；为本地 Docker 打好安装包。uv build 之前把提交和构建时间写进源码的 openprogram/_build_info.py，装好的 --version 和每个运行头因此自己就能说出提交，不靠旁边启动器的记录。
  • 重试：Harbor 不重试（max_retries: 0）。它退出后，启动器最多跑目标 max_retries 轮。每轮把 Harbor 的 RetryConfig 会重试的试验和验证器准备失败的试验，连同账本行移到 jobs/<job>.retried/<trial>/<n>/，再运行 harbor job resume。
  • 重试目录：放在任务目录旁边，因为续跑会删掉任务目录里没有 result.json 的文件夹。预算用尽或任务被停下后不再开新一轮。
  • 预算：所有尝试的花费到达预算就停下。OpenProgram 的每次尝试都把花费追加到任务旁边的账本里；两边被移开的每次尝试，账本里也都有一行，写着原因。
  • 丢弃的尝试：--rerun-infra 把每一次连同原因写进账本，按试验名和开始时间区分，所以对照试验以同一个名字重跑后，两次的费用都在。
  • 续跑：wheel、安装包或目标变了就拒绝。--rerun-infra 把算作基础设施或取消的试验移开，再跑一遍；重试轮次从停下的地方接着跑。
  • 汇总：每次试验分为通过、agent 失败、基础设施或取消。
    • 按 agent：按通过和 agent 失败计算的通过率；FrontierHarness 的口径，每个任务取第一次有效尝试；目标公布的是其中哪一个。
    • 首次尝试通过率：之前有一次尝试因 agent 自己的原因结束的试验不算通过；因服务商、网络或容器而重试的不算在内。启动器重试过的任务两边都有；旧任务里由 Harbor 重试并删掉了对照的尝试，只有 OpenProgram 有。
    • 同样按 agent：重试次数和类别；上报的每次尝试的费用，及其中重试尝试的部分；按目标价目表重算的费用；每次通过的费用，按保留下来的试验和同样的价目计算，两边用同一批尝试；容器时长；超过墙钟上限的试验。
    • 和对照配对：同一任务上两边第 n 次计分的尝试配成一对；对只有一边通过的对做 McNemar 精确检验；给出这么多对在 5% 显著性、80% 检验力下能看出的最小差距。同一任务的几次尝试并不独立，任务少时两者都偏乐观。
  • 算基础设施要有证据：基础设施类错误、用量摘要里服务商或网络的原因（注明在本轮开始前还是本轮中）、验证器自己的准备在任何测试运行前就失败，或验证器根本没启动。测试跑过之后验证器超时，算 agent 的。

不做的事

  • agent 内不设费用上限（--max-budget-usd）：一道题因为钱花完而失败，是这个上限造成的结果，不是 harness 的。Codex 没有，FrontierHarness 只限墙钟时间；Harbor 对 Claude Code 和 mini-SWE-agent 的上限默认也不设。花费在 agent 外面由启动器的账本和 SIGINT 控制。
  • 不另写一份实时转录：日志记录和账本本来就逐条写入；转录从它们派生，只生成一次，在退出时或事后。

oracle 冒烟、单任务和全量在本地 Docker 与 Runta 上的命令：scripts/benchmarks/harbor_agent/README.md.

全量运行之前

需要要准备的
Harbor0.25.0，在 PATH 里或由 $HARBOR 指定：uv tool install "harbor[runta]==0.25.0"。
可比的运行环境Runta 账号（runta login，--env runta）。Apple 芯片上的本地 Docker 只能检查流程：镜像靠模拟运行，Docker 只有 4 个 CPU 和 7.7 GB，batched-eval-parity 还需要 docker buildx。
API 密钥模型所属服务商的密钥（openai/... 用 OPENAI_API_KEY，或用 --key-profile），留出下面预算的余量，限流要够同时跑 4 到 16 个试验。openai-codex 这类订阅登录没有可以传进任务容器的密钥。
模型由目标指定，推理强度也是（gpt-5.6-terra、medium）；两个 agent 都用这个强度。换别的要清楚后果：运行就和目标不可比了。check 不会去问服务商是否列出该模型。
带 --effort 的构建--ref 指向的提交，其 --print 要接受 --effort；run 会读 wheel，不接受时会说明。
花钱前的检查先用最便宜的模型跑一个 OpenProgram 试验：转录的 run 记录写着 Linux 容器里加载了哪些工具、首个请求发了什么（模型、强度、include、store），用量摘要里有强度。然后在 Runta 上用 oracle 跑一遍 21 题，再跑 8 题试点（run --pilot）。
构建默认 --ref stable；wheel 和 209 MB 的安装包每个提交构建一次。
费用fh-v1-tb21：21 个任务 × 3 次 × 2 个 agent = 126 次试验。按每次 $2 到 $4（FrontierHarness v1 发表的 Codex 约 $2.3 一次），模型费 $250 到 $500，另加沙箱的容器时长，汇总会统计。8 个任务 × 1 次 × 2 个 agent 的试点 $30 到 $65。fh-v1.1：62 × 4 × 2 = 496 次试验。
时间每次试验约 10 分钟墙钟时间，长尾到一小时；一个验证器镜像可能要拉 16 分钟。fh-v1-tb21 并发 8 要 3 到 5 小时。
结果能说明什么21 个任务 × 3 次配对，能看出约 15 到 20 个百分点的差距；更小的只能报“无明显差别”。要看更小的差距得跑 tb2（89 个任务 × 5 次）。
提交成绩全量运行前先问维护者；新结果不排名（methodology_comparable: false）。

为什么这样设计

主题跟随原因
始终要回加密推理Codex（OpenCode 效果相同）store: false 时服务端不保留推理：请求不要回来，推理模型照样推理、照样计费，下一轮工具调用却接不上。Codex 每次都要；Pi 只在有强度时要。include 是顶层参数，此前的前缀字节和缓存都不变
关闭即 effort: "none"Pi（字节和 Codex 相同）不发推理字段，服务端就按默认强度推理，和“关掉思考”的意思不符。Pi 发它映射表里的关闭值，模型把关闭映射成空时就不发；这里比 none 早的模型（o 系列、gpt-5 到 gpt-5-pro）就是这样
密钥只在运行的环境里Harbor 的 Codex 和 Claude Code 适配器两者都把密钥作为一个进程的服务商变量传入；登录一步会写下凭据，之后还得找出来删掉
启动器负责重试FrontierHarness它在重试前归档尝试，从不替换有效的尝试。Harbor 自己重试前会删掉试验目录，对照组之前的尝试丢了，首次尝试通过率也就算不出来。用 Harbor 的试验钩子则要换掉 harbor run，自己写 Python 入口
转录从状态派生Codex 和 Claude Code 适配器两者都逐条写会话，事后派生轨迹。只有一条路径，被杀的运行和正常结束的运行得到的转录就一样；另写一份实时的可能和它对不上
提交写进构建Claude Code它在构建时注入版本和构建时间。单独拿出来看的试验目录旁边没有启动器的记录；源码检出不受影响
--no-webHarbor（它的 Codex 和 Claude Code 适配器）两者都声明原生网页工具，并在 disable_web_search 时关掉。两边用同一个开关，才能做关掉网页的对照；默认仍开着，和已发表的一样
试点选题FrontierHarness 自己的每题数据原来 8 题里有 5 题在 v1 全部通过，看不出成本长尾和差距；难题最能暴露超时和长尾，所以三层都要有。它的冒烟题 regex-log 也在其中
agent 内不设费用上限Codex、FrontierHarness见不做的事

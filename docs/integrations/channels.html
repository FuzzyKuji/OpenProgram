Chat channels

A message to your bot runs an agent turn and the reply comes back in the same chat. Channels run inside the background service, so the conversation is live in Web and the TUI too.

Quick start

You need an agent (openprogram agents add main) and a working model provider. The wizard picks a platform, logs in, binds an agent and starts the worker.

  1. openprogram channels setup
  2. Message your bot. The first reply is a pairing code.
  3. openprogram channels access approve <channel> <code>

The conversation then appears in the session list.

Commands

Each --id is one bot login with its own credentials and bindings.

openprogram channels list                              # status of every account
openprogram channels accounts add telegram --id work   # create an account slot
openprogram channels accounts login telegram --id work # enter credentials (QR for wechat)
openprogram channels accounts rm telegram work         # delete account + its bindings

openprogram channels bindings add main --channel telegram            # catch-all → agent "main"
openprogram channels bindings add main --channel telegram \
    --account work --peer 123456 --peer-kind direct                  # one peer only
openprogram channels bindings list
openprogram channels bindings rm <binding_id>

Who can talk to your bot

Direct messages use pairing. An unlisted sender's message is dropped before any agent and the sender receives an eight-character code. Approval exists only as a local CLI or API call, so nothing typed in chat can approve anyone. There is no setting that turns the gate off.

openprogram channels access list                       # policy + allowlist + pending codes
openprogram channels access approve telegram K7XQ2MVR  # approve by pairing code
openprogram channels access allow telegram 123456789   # allowlist a user id directly
openprogram channels access revoke telegram 123456789  # remove a sender
  • Codes expire after one hour; a blocked sender gets the same code again, at most once a minute.
  • access allow adds a known platform ID without a code.
  • Everyone on the allowlist reaches the same agent and acts as you, and memory is one workspace for the instance. Keep it to people you would hand this machine to.

What approved senders may do

A direct-message turn has the same tools as the Web UI under that chat session's mode and rules, so in default Bypass permissions it can run commands here without a prompt. Approvals arrive as chat questions, answered with /answer.

openprogram channels accounts set wechat sender_access paired    # or: owner, the default (all channels)

paired limits everyone on the account to replies and memory, in direct messages and groups. For separate memory, someone runs their own instance:

openprogram --profile alice

Anyone else gets no reply, pairing code or error, and no conversation is created. A new group lists nobody.

openprogram channels accounts group-users add telegram 123456789 --access chat   # replies and memory only
openprogram channels accounts group-users add discord 80351110224678912 --access full  # runs as you
openprogram channels accounts group-users remove telegram 123456789
openprogram channels accounts group-users list telegram
openprogram channels accounts group-users add telegram 123456789 --access full --group -1001234567890
openprogram channels accounts group-users remove telegram 123456789 --group -1001234567890   # the group keeps its lists, even when empty
openprogram channels accounts group-users reset telegram --group -1001234567890              # use the account's lists again
  • First block: account-wide lists. Second: one group's lists, which replace the account's for that group; remove keeps the group's lists even when empty, and reset returns to the account's. Bound contacts keep full access. A Discord thread uses its parent's lists unless it has its own.
  • IDs are stable platform user IDs: numeric on Telegram and Discord (Developer Mode, Copy User ID), U… on Slack. The worker log names every ignored sender. Changes apply to the next message.
  • Settings > Channels holds the account-level lists; per-group lists are command-line only.
  • require_mention still applies: an unmentioned message from a listed person waits as context.
  • chat users cannot use /new, /reset, /activation, /memory, /stop or /help. What they write is context for later turns that run as you.
  • access revoke only touches the allowlist; use group-users remove for these lists. A bound contact cannot be chat: revoke first, which also ends their direct messages. Binding someone listed as chat takes them off the lists.
  • Nothing a sender types can change these lists.
Upgrading from a version with group_access

That setting is gone and a stored value is ignored. Teammates approved by pairing code from a group had replies and memory only; on the allowlist they now run as you in groups. Before upgrading, run openprogram channels access list, then for each teammate access revoke and group-users add <channel> <user id> --access chat.

Who said it

Every channel message carries its sender, direct messages included (main puts peers together). Web, CLI and TUI turns have none.

{"speaker_kind":"human","speaker_id":"7391","speaker_display":"Ada","content":"the budget is 50k"}
{"speaker_kind":"human","speaker_id":"8022","speaker_display":"Bo","content":"make it 80k"}
  • The ID stays when someone renames and separates people with the same name; memory records each fact under who said it.
  • A display name is put on one line, capped at 64 characters, square brackets made round. Message text is kept exactly; typing a name in brackets does not impersonate.
  • The web transcript shows a small line above the bubble, such as WeChat · Ada; a WeChat sender has no nickname, so the ID is shortened to its first and last four characters.

Group behaviour

ModeBehaviour
alwaysEvery message starts a turn
mentionOnly an @mention or reply to the bot; the mention is stripped. The next turn gets the latest 50 other messages with senders, behind an "earlier messages in the chat" toggle in the web transcript.
ambientEvery message starts a turn and the agent decides whether to speak with chat_send. Replies to unaddressed messages stay in the web transcript as "overheard". No typing or ack reaction. Addressed messages are answered normally. Costs a model call per message.
openprogram channels accounts set telegram require_mention on       # or: off (also discord, slack)
openprogram channels accounts set telegram group_sessions per-user  # or: shared (telegram only)
  • require_mention sets the default: on is mention, off (default) is always.
  • Someone with full access uses /activation mention|always|ambient; alone it shows the mode. Direct messages are never gated.
  • group_sessions (Telegram; restart the worker): shared (default) or per-user.
  • Group members reach the agent's memory. /memory read stops writes, /memory off removes it, /memory on (default) follows the agent's setting. Direct messages always follow the agent.
  • Other bots' messages are ignored and duplicate deliveries start one turn. At most 10 turns a minute per group; the rest wait as earlier messages.

Delivery details
  • A long reply fills the placeholder then continues in new messages. A placeholder that cannot be edited falls back to a new message.
  • Slack threads and Telegram forum topics keep placeholder, reply, files and the agent's own notes and questions in place; a Telegram topic also shows typing there. A Slack thread reply also sent to the channel counts as a message.
  • Editing a Telegram message sent before the service started does nothing.
  • ack_reaction on (not WeChat) adds 👀 on pickup; Slack needs reactions:write.
  • A long code block stays closed in each message and reopens in the next. Discord replies never ping anyone, @everyone included. A photo Telegram refuses is sent as a file instead.
  • Rate-limited sends retry with Retry-After when given, up to three attempts, then log a structured error. A connection that could not be opened is retried up to four attempts; nothing reached the platform, so nothing arrives twice.
  • Crashed connection loops reconnect with backoff, 5 s doubling to 5 min. Invalid credentials stay down until you log in again; a Telegram token the API rejects counts. WeChat server errors wait and retry, 3 s doubling to 48 s.
  • The service checks accounts every few seconds: linking, logging in, enabling or disabling needs no restart.

A conversation runs one turn at a time, App turns included. While another turn runs or waits for an answer:

  • A chat message waits up to 30 seconds, then the bot says it is busy. Send it again later.
  • An unaddressed group message in ambient mode gets no reply and joins the group's next turn.
  • Typing in the App is refused, as during any other turn.
  • /new and /reset wait up to 30 seconds for a chat app turn, then the bot says it is busy.

Messages from one chat start turns in the order they arrived, even when an earlier one has a slow attachment. Commands do not queue.

Update from chat

self_update installs a committed change from chat. Status and cancellation work on every installation; published versions keep the release updaters above.

Installationself_update(action="prepare")
Source repository with a stable branchLands the commit on dev, deploys and checks it on the development instance, promotes it to the stable App. Development checkout
Packaged App on macOSBuilds and installs into the App, below
Packaged App or release install on Windows or LinuxSays this host has no source-update controller, before creating a request
Plain developer checkoutSays it activates nothing; restart the worker from the checkout

Status: every activation level is verified end to end in the default App. Open: real-App acceptance of other tasks across a restart, and of session and tab restoration.

What repair does and refuses
AspectRule
RunsLocal terminal, no Agent. Needs an interactive terminal and the exact confirmation shown with the action, revision and plan digest. No --yes or force-clear
AuthorityAn approved attempt resumes only within its original ten minutes; a failed or expired one needs fresh confirmation
ControllerSaved before the update. Restores the previous App when rollback is possible, or finishes an already started irreversible commit only with the original accepted evidence
RefusesAn aborted, unactivated transaction keeps the old App. Missing or changed evidence leaves maintenance on
FinishesRestarts the default worker, checks App identity and the live service, clears maintenance. No verifier Job; the verdict stands. A separate result records the recovered version, which does not prove the failed feature works
recover.shSaved runtime outside the App; status is the default. repair still needs interactive confirmation and cannot bypass failed evidence or expired authorization. resume approves nothing new and recreates no verifier Job
Recovery at login
  • Before activation the update publishes ~/Library/LaunchAgents/ai.openprogram.self-update.recovery.UPDATE_ID.plist. It runs once per later login, independently of the App. There is no resident process or periodic retry, and writing it starts nothing.
  • It does not run before login or disk unlock. If App and controller both stop in the current login session, run the saved script.
  • New jobs use launchd's Standard process class. Saved Background entries keep their bindings and policy.
  • Progress goes to bootstrap.log before runtime validation and controller resumption.
  • A completed update validates the saved runtime and removes only its unchanged login file, within the same state lock and without rehashing the whole runtime. The saved runtime, script and evidence stay.
  • Missing or damaged trusted recovery files need manual intervention; nothing is rebuilt from an unverified App.

Undo a change

Target of self_update(action="undo", target=…)Effect
Version idReturns to exactly that version; everything after it stops running. Commits left behind stay under refs/openprogram/undone/. A version no longer on disk is rebuilt from its commit.
CommitReverts that one commit and keeps later ones. If later commits changed the same lines, it stops and names the files.
On a machine with stableThe target is a commit: the revert lands on dev and is promoted, because stable only moves forward.

From a terminal, even when the running version is broken:

openprogram versions list
openprogram versions use VERSION_ID
  • use stops the worker, giving it up to 60 seconds to pause running work, and switches with no checks.
  • A version that keeps failing to start returns to the last good one by itself, and your most recent conversation says so.
  • Either way, at the next healthy start that version is the code new changes are made from. Conversations, settings and files do not change.

Files edited inside a running version

Allowed, but without effect. At the next start they are saved under ~/.openprogram/runtime/unapplied/<time>/ with a changes.patch, the version is restored, and your most recent conversation says so once. openprogram versions list shows them. To use them, git apply the patch in a self_update worktree and run a normal update.

How it runs

The chat tool
  • action is status (default), prepare, retry, cancel or undo.
  • The first result explains the workflow and lists the guides. The first prepare, retry or undo in a conversation is refused once, with that action's instructions (help("self_update.prepare"), help("self_update.retry"), help("self_update.undo")). help("self_update") shows the workflow again.
  • prepare, retry and undo follow the conversation's permission mode; status needs no approval.
  • Conversations show ordinary messages and tool results only: no update history, controls, evidence viewer or recovery notice, and no polling of update-history APIs.
Installation, Jobs and continuation
AspectRule
InstallNew bundle beside the installed one, swapped by rename, verified, then committed or rolled back. Rollback restores the previous bundle at the same restart level.
No restart neededSkips maintenance; conversations and Jobs continue.
Queued JobsKeep their identities and wait through maintenance.
Running workExecutions with durable pause stop at their next checkpoint. The App is replaced only after active attempts and resource claims end. A task without a safe pause must finish before the update deadline, or activation is aborted.
After commit or rollbackOnly executions this update paused resume. Tasks paused by the user or waiting for input stay paused.
Changed tool contractCheckpoint validation still rejects it. An update-owned continuation then keeps the old checkpoint and gets one planning Job from the original task and history, with its tool selection and permission rules. Unresolved side effects or a user cancellation prevent replanning.
Original taskNew updates save an original-session follow-up with a stable Job identity. After maintenance and any repair sequence it keeps checking the requested behavior as a new background turn, with no approval for another installation. Older records get none. Installation success and task continuation are separate outcomes.
Finite resultsPersisted in the original session even if the window is closed or no verification Job was created. Reconciliation reuses the same update, attempt and result-type identity, starts no model turn and does not move HEAD. Interrupted writes retry.
Session or node goneDelivery stays pending and goes nowhere else. A persisted result neither reopens the App nor proves installation.

Status and history APIs
EndpointReturns
GET /api/self-updates?session_id=…History with completed attempts; bounded limit and cursor
GET /api/self-updates/{update_id}?session_id=…Detail
GET /api/self-updates/{update_id}/evidence?session_id=…&evidence_id=…Observations cited by the validated signed result; use the verifier's evidence_id or an assertion's evidence_refs
  • All need owner authentication; evidence also needs the original session. The chat tool shares the same read-only projection. self_update() and self-update status --json expose source_repair_result.
  • candidate_revision and target_app describe the requested installation. last_verified_runtime holds the last matching verification's SHA, PID, timestamp and source, or null; it does not prove the worker is online. state_revision is a counter, not a Git revision.
  • Queries do not initialize or repair state. Invalid state returns an error, not an empty history; changed or invalid evidence too. Running reports self_update_error if its snapshot is unavailable.
  • The projection excludes credentials, raw logs and configuration; repair summaries hold status and any new candidate SHA. It does not replace the CLI recovery output. Stored HTTP or HTML text is not proof of a rendered window.
Reopening the conversation
  • The controller persists the recovery intent before activation and binds the opaque update ID to the installer transaction. If the App was open, activation and rollback reopen it with that ID; a closed App stays closed. Ordinary launches do not consume these requests.
  • Desktop resolves only the original session through owner authentication and acknowledges once the transcript loads in the main window. An expired request, deleted session or authentication failure leaves normal startup, with no notice. Changing pages stops relocation. Neither step starts a verification Job or proves success.

App 更新器做了什么
  • macOS：选择架构匹配的完整 DMG，下载到你指定的位置，验证字节数和 SHA-256 后打开。应用外壳和完整 product runtime 一起替换。未签名安装包：仍要打开。
  • Windows、Linux：在版本库里运行 openprogram upgrade，只有发行版需要更新的外壳时才取 App 文件。
  • Windows App 文件：验证 release metadata、文件长度和 SHA-256。已签名的 App 还要求同一发布者的有效 Authenticode 签名；只有未签名构建的 App 才接受未签名的安装程序。
  • 下载走系统代理，断线后接着下。GitHub API 拒绝或不响应时，App 通过 GitHub 网页找到发行版。
管理版本的 App 启动不了时

薄壳 App 把代码按编号版本放在 ~/.openprogram/runtime （Windows 上是 %USERPROFILE%\.openprogram\runtime）。第一次启动在进度页后解包自带代码，约一分钟。

目标命令

安装或回退到某一版本指定版本的安装命令

macOS 和 Linux 串行化升级。版本目录会保留，所以回滚用同一条命令。运行中的 worker 不会重启。

Windows launcher 替换
  • 激活前准备好一个 openprogram.cmd launcher，再原子替换。上一份保留为 openprogram.previous.cmd。旧的 openprogram.ps1 launcher 会被删除，因为默认脚本策略会拒绝运行它。
  • 即使 launcher 激活失败，已验证的 runtime 也保留，供重试。
带 seed 的发行版
  • 发行版带有 OpenProgram-<version>-seed-<platform>-<arch>.tar.gz 时，install.sh 和 install.ps1 把它装进薄壳 App 使用的版本库 <state>/runtime；openprogram 运行 current 指向的版本。
  • openprogram versions list 列出保留的版本。
  • 没有这个资产时，安装上述普通运行时。
  • 安装中断后，下次运行从头开始。在已有版本库上运行时，通过 openprogram upgrade 更新，并如实报告结果。

版本库安装的正式更新

把 release 当作一组签名文件接收，并带上你自己的提交。v1.1.0 起，Windows 和 Linux App 这样更新。macOS App 和普通终端安装走上面的路径。

openprogram upgrade --check
openprogram upgrade
openprogram upgrade --from <directory>     # files already on this computer
Release 文件内容
version-<platform>.tar.zst某平台的封存版本，例如 macos-arm64
repo.bundle到这次 release 为止的官方源码线
base-<platform>.tar.zstPython 和第三方包。只有这台电脑没有这个 base 时才下载
toolchain-<platform>.tar.zstWeb 构建的 node_modules。只有你有自己的提交要构建时才下载
SHA256SUMS上面每个文件的哈希
update-manifest.json update-manifest.json.sigRelease 内容及其 Ed25519 签名

先检查签名、校验和及本平台需要的每个文件。未签名或被改动的 release 不造成任何变化。

情况结果
没有自己的提交解包预构建版本并试运行
有自己的提交按从旧到新应用到 release 上，再构建并试运行
提交冲突保存它，其余继续
release 已包含跳过
构建或试运行失败保存最新的提交，用其余的重试，最后退到未修改的 release。重试 5 次后，剩余提交一起保存，试未修改的 release。
未修改的 release 失败什么都不变：仍是当前版本，提交还在
需要更新的签名外壳，或 Python 小版本与启动器不同等外壳更新：不解包，官方源码线不动

结果列出带过去和保存的提交。保存的提交是 <state>/runtime/unreplayable/<release>/<commit>.patch，git format-patch 格式，可作为新改动应用。

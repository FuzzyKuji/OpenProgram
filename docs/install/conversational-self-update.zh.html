repair 做什么、拒绝什么
方面规则
运行本地终端，不启动 Agent。需要交互式终端，并准确输入与操作、版本和计划摘要一起显示的确认内容。没有 --yes 或强制解除
授权已授权的操作只能在原来的十分钟内继续；失败或过期后需要重新确认
控制程序更新前保存。能回退时恢复旧 App；已开始不可逆提交时，只有原始验收证据完整才完成提交
拒绝已中止且未激活的事务保持旧 App。证据缺失或变化时继续维护状态
收尾重启默认 worker，检查 App 身份和实际服务，解除维护。不新建验收 Job，结论不变。独立结果记录恢复了哪个版本，服务恢复不代表失败的功能已经正常
recover.sh使用 App 外保存的 runtime，默认 status。repair 仍要交互确认，不绕过失败证据或过期授权。resume 不批准新更新，也不重建验收 Job
登录时恢复
  • 激活前发布 ~/Library/LaunchAgents/ai.openprogram.self-update.recovery.UPDATE_ID.plist。之后每次登录运行一次，不依赖 App；没有常驻进程或周期重试，写入文件也不启动任何东西。
  • 不在登录或磁盘解锁前运行。当前登录会话中 App 和控制进程都停止时，运行保存的脚本。
  • 新任务使用 launchd 的 Standard 进程类型。已保存的 Background 项保留绑定和调度策略。
  • 运行环境验证和恢复 controller 前，进度写入 bootstrap.log。
  • 已结束的更新在同一状态锁内验证保存的 runtime，只移除内容未变的登录文件，不重新哈希整个 runtime。保存的 runtime、脚本和证据保留。
  • 可信恢复文件缺失或损坏时需人工处理，不从未验证的 App 重建。

撤销修改

self_update(action="undo", target=…) 的目标结果
版本号回到正好那个版本，之后的内容不再运行。被丢下的提交留在 refs/openprogram/undone/。不在磁盘上的版本从其提交重新构建。
提交revert 这一个提交，后面的保留。后面的提交改过同样的行时，停下并列出文件。
有 stable 的机器目标是提交：revert 落到 dev 并晋升，因为 stable 只向前移动。

在终端里，当前版本坏了也能用：

openprogram versions list
openprogram versions use VERSION_ID
  • use 停止 worker，最多给 60 秒暂停运行中的任务，然后不做检查直接切换。
  • 版本反复起不来时自动回到上一个可用版本，并在你最近的对话里说明。
  • 两种情况下，下一次正常启动后，该版本都成为之后修改的起点。对话、设置和文件不变。

运行中版本里被改动的文件

可以改，但不生效。下一次启动时存到 ~/.openprogram/runtime/unapplied/<时间>/ 并附 changes.patch，版本恢复原样，并在你最近的对话里说明一次。openprogram versions list 列出它们。要使用时，在 self_update 的 worktree 里 git apply，再走一次正常更新。

如何运行

聊天工具
  • action 取 status（默认）、prepare、retry、cancel 或 undo。
  • 第一次结果说明流程并列出指南。对话中第一次 prepare、retry 或 undo 会被拒绝一次，并附上该动作的说明（help("self_update.prepare")、help("self_update.retry")、help("self_update.undo")）。help("self_update") 可再看流程。
  • prepare、retry 和 undo 按会话的权限模式处理；status 不需要审批。
  • 会话只显示普通消息和工具结果：没有更新历史、操作按钮、证据查看器或恢复提示，也不轮询更新历史接口。
安装、Job 和后续任务
方面规则
安装新 bundle 暂存在已安装 App 旁，重命名换入，验证后提交或回退。回退以同一重启级别恢复上一版 bundle。
无需重启跳过维护，对话和 Job 照常继续。
排队 Job维护期间保持身份并等待。
运行中的任务支持持久暂停的执行在下一个检查点停止。活动 attempt 和资源占用结束后才替换 App。无法安全暂停的任务必须在更新期限内结束，否则中止激活。
提交或回退后只恢复由本次更新暂停的执行。用户暂停或等待输入的任务保持暂停。
工具合同变化检查点继续拒绝。更新触发的恢复被拒绝时，保留旧检查点，依据原任务和历史创建一个规划 Job，保留工具选择和权限规则。存在未解决的副作用或用户已取消时，不重新规划。
原任务新更新保存带固定 Job 身份的原会话后续任务。维护和修正序列结束后，它以新的后台轮次继续检查目标行为，不授予再次安装的权限。旧记录没有这项。安装成功与任务继续分别记录。
有限结果持久化到原会话，即使窗口已关或未创建验证 Job。重复检查使用相同的 update、attempt 和结果类型标识，不启动模型轮次，不移动 HEAD。写入中断会重试。
原会话或节点不存在保持待投递，不改投别处。持久化不会重新打开 App，也不证明安装成功。
离线打包和激活前检查
方面规则
依赖基线必须与候选的 uv.lock 和 scripts/release/product-runtime.json 完全一致。不一致或缓存缺失时，在激活前停止更新，绝不因此允许下载或沿用不匹配的依赖。
构建工具保存 runtime 中固定版本的工具，以及既有 npm、uv、Electron-builder、node-gyp 缓存的私有副本。
Electron 归档匹配控制器固定的版本、架构和发布 SHA-256，候选只读获得 electronDist。
打包内容完整构建：候选的 Web、文档、wheel 和 Desktop archive。部分构建：从已安装 App 的副本出发。
worker 冒烟测试只用控制器选择的私有 loopback 端口，从不用 18100。
浏览器和图标检查由重新校验过的保存 controller runtime 执行，位于所有候选可写路径之外，资源树 hash 必须匹配。控制器从不执行可写的构建 runtime 副本。全部完成才激活。
恢复协议候选和已安装 App 都带匹配的声明，由打包和刷新脚本根据实际 Desktop archive、安装器、runtime manifest、后端和编译后的 Web 文件生成。等待后和恢复时重新检查。
停止激活声明缺失、不兼容或变化，事务 ID 不匹配，或冻结的 owner 配置无效，都在替换旧 App 前停止。没有声明的旧 App 需要先做一次显式完整更新。
状态和历史接口
接口返回
GET /api/self-updates?session_id=…历史，含已结束的 attempt；有上限的 limit 和 cursor
GET /api/self-updates/{update_id}?session_id=…详情
GET /api/self-updates/{update_id}/evidence?session_id=…&evidence_id=…已校验签名结果引用的观察记录；用 verifier 的 evidence_id 或 assertion 的 evidence_refs
  • 都需要 owner 认证；证据还需要原会话。聊天工具使用同一只读投影。self_update() 和 self-update status --json 提供 source_repair_result。
  • candidate_revision 和 target_app 描述请求的安装。last_verified_runtime 包含最近一次匹配验证的 SHA、PID、时间和来源，或为 null；不证明 worker 在线。state_revision 是计数器，不是 Git revision。
  • 查询不初始化或修复状态。无效状态返回错误，不显示空历史；证据被改或无效也返回错误。Running 读不到快照时报告 self_update_error。
  • 投影不含凭据、原始日志和配置；修正摘要含状态和新 candidate SHA。不替代 CLI 恢复输出。保存的 HTTP 或 HTML 文本不证明窗口已渲染。
重新打开会话
  • 控制器在激活前持久化恢复意图，并把不透明更新 ID 绑定到安装事务。App 原本打开时，激活和回退都用该 ID 重新打开；原本关闭则保持关闭。普通启动不消费这些请求。
  • Desktop 通过 owner 认证只解析原会话，在主窗口加载会话记录后确认。请求过期、会话删除或认证失败时正常启动，无提示。切换页面后停止定位。这些步骤不启动验证 Job，也不证明成功。
